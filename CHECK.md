# CHECK

Pending design decisions — deliberately kept out of the README until they are settled.

- Mixin mechanism: **settled (2026-10-06) — not added.** An `include`-style mixin is inheritance renamed: a single include is single inheritance, multiple includes are multiple inheritance, and both drag in method-resolution order, diamond ambiguity, implicit method provenance, `self` / field coupling, and the fragile-base problem — exactly what the no-inheritance decision rejected. Interfaces with default method bodies are the same trap and are also excluded. Reuse stays with duck-typed functions, composition, and structural interfaces. Delegation is not a separate mechanism either: forwarding to a contained object is ordinary composition code — `def draw() { return self.inner.draw() }` — and gets no construct, keyword, or auto-forwarding, because it expresses nothing the ordinary methods cannot and would only hide method provenance. Struct embedding is the same space under another name: Go's anonymous embedding promotes an inner type's methods and fields into the outer one, which is inheritance in effect — promotion, shadowing, and a depth-based resolution rule together are a hidden method-resolution order — and it leaves the outer type's method set invisible at its declaration. It also amplifies *accidental interface satisfaction*: because Emo's interfaces are structural (satisfaction by shape, no `implements`), a promoted method can make a type satisfy an interface its author never intended, and a later change to the embedded type silently flips that satisfaction. Go's embedding of `sync.Mutex` — which exposes `Lock`/`Unlock` and satisfies `sync.Locker` without the author asking — is the canonical example. Emo's safeguard is that a class's method set is exactly its own `def`s, so satisfaction changes only when its own body changes; the residual coincidental-name hazard is inherent to structural typing and is mitigated by small, clearly named interfaces. The whole inheritance-shaped space — mixin, include, default methods, delegation, embedding — is therefore closed: reuse is duck-typed functions, composition, and structural interfaces, plus plain code.
- Error handling: **settled (2026-10-11) — no catch construct; expected failures are values, violations raise.** Supersedes the 2026-10-06 `begin`/`catch`/`ensure` settle. The deciding evidence is the backends: `interp`/`ocaml`/`ts`/`beam` get host exceptions for free, but `c` needs `setjmp`/`longjmp` plus a drain of the refcount/autorelease state along every unwound frame, wasm's raise is a host `abort` no in-wasm handler can resume from, and `riscv64` refuses `raise` outright — six targets, six stack disciplines, a permanent two-tier language for one construct. The Erlang split takes its place, and Emo already runs its other half (an uncaught exception kills only the offending process, the per-process arena reclaims its memory, supervision is library-level): an **expected failure** — parse errors, IO, network, not-found, anything the data can trigger — is an ordinary value, the call returning `(R.ok, value)` or `(R.error, reason)`, the reason a String carrying the message convention (package prefix: `json: expected array element at byte 3`); a **violation** — a broken contract, a bug — raises and ends the process. `Exception` stays the language's one exception class — no subclasses (Emo has no inheritance), the name reserved against user shadowing — carrying `message` and an optional `data` Map whose role is machine-readable context for crash reports and supervision, never type identity: nothing dispatches on exceptions when nothing catches them, so the `e.is(Timeout)` narrowing idea dies with the catch design. The `raise` operand must be an `Exception` instance (anything else gets its own E-code), and the uncaught report prints non-empty `data` alongside the message. `R { ok, error }` is a built-in enum (root-env binding, the `Exception` precedent) so matching a returned tuple never costs an import; the tag is spelled `R.ok`/`R.error` — a bare lowercase `ok` in a pattern is a binding and would match everything, and atoms (`:ok`) were rejected as a new value type across all targets for what the enum already expresses. The name's one shadow — the R language of statistical computing — is cosmetic: the two never share an artifact (that R lives as the `/usr/bin/R` command, `.R` files, and CRAN; Emo's `R` is a type name always spelled in qualified form — `R.ok`, `(R, String)` — and no Emo command, file extension, or package carries the bare letter), a single-letter identifier inside another language raises no trademark question, and the fingerprint test passes — enum-dot tags over tuples are the Erlang shape, and R has no such syntax (its counterpart concept is the factor). Migration is the follow-up: the eight raising packages (~220 raise sites) and the runtime-backed packages (`os`/`file`/`net`) split per call into tuple returns and keep-raising violations.
- Binding patterns: **settled (2026-10-11)** — `const` and `var` take a full pattern, not just a name: `const (R.ok, body) = file.read(path)`. A pattern that does not match is a runtime error — the same rule as a `case` scrutinee matching no branch — making the assert-match binding (Erlang's `{ok, B} = f(X)`) the expect-success fast path of the tuple convention. No `match` keyword: the construct is a binding, and `case` already owns the pattern vocabulary. Lowered at IR level by desugaring to a one-arm `case` wrapping the rest of the block, so the six backends see only existing nodes; the parser's `const (` form is a hard error today, so the extension breaks no grammar.
- Type layering: **settled (2026-10-11) — three tiers, two promotion criteria, the freestanding target as the accretion stop.** **"Built-in" names what belongs to the language itself** — the spec core's value model, the capability types, `R`, and `Exception` — the mechanisms and types a program uses without importing anything. Two axes are independent of that ownership and must not be read as defining it: **name availability**, because the checker's root environment also carries the runtime implementations the standard library's Emo source calls (`os_read`, `file_write`, `net_connect`) — those are the runtime's implementation of a package, reachable without `require` but never the API, and no document presents them as a surface; and **per-target capability** (the target-capability table — the split already exists: `riscv64` refuses `raise` and refuses `Map` at emit time while the names stay import-free). **Spec core**: the value model the language's own semantics depend on — `Bool`/`Char`/`Int64`/`Byte`/`Float64`/`String`/`Array`/`Tuple`/enum/class/interface, plus `R` (it is an enum); a target that cannot implement the tier is not an Emo target. **Capability builtins**: `Map`/`List`/`Box`/`Bytes`/`Pid`/the connection types/`Exception` — import-free names, gated per target, the tier **frozen** (its status is the checker's inherited type vocabulary, not a precedent; refusing where unimplementable is the tier's normal shape). **Stdlib**: every future type lands there by default. Promotion needs (a) *syntax dependence* — a syntactic construct's own operand type (`Exception` qualifies through `raise`; nothing else does), or (b) *universal dependence plus trivial implementability on every target including freestanding* (`R` qualifies: every failing call returns it, and it lowers to a tagged word). The freestanding target is the standing reason the capability tier stays frozen: each type promoted above the spec core must either be re-implemented in assembly for `riscv64` or publicly refused, fragmenting the language. (The lineage analogue is C's freestanding profile; the wording is Emo's own.) **Revised 2026-10-15 (T49.3): `ArrayBuilder` joins the tier** — recorded as a revision, not a promotion, because it meets neither criterion: no syntactic construct has an `ArrayBuilder` operand, and `riscv64` refuses it by name at emit time (exit 65, the `Map` precedent) rather than implementing it. What it does have is the `List` precedent beside it: a mutable collection belonging to the same closed set the mutability rule names, import-free, gated per target, refused where unimplementable — the tier's normal shape. What made the addition necessary is that the language had no sub-quadratic way to build an array whose length is not known up front (`Array.append` copies the whole array per element), so the choice was a named builtin or a capability the language simply lacked. The freeze stands as policy; this is one recorded exception, paying the same freestanding-refusal cost every tier member already pays.
- Raw strings: **settled (2026-10-06)** — not needed now. There is no regex and no multi-line string requirement, and a raw string hides the escaping that "everything is visibly what it is" wants visible; the escape set stays `\n \r \t \\ \' \"`. Revisit only if regex or text templating lands, and then with a form of Emo's own (not Go backticks or Python triple quotes).
- Numeric literal formats: **settled (2026-10-06)** — hexadecimal `0x`, binary `0b`, and octal `0o` prefixes, plus `_` as a digit separator (`1_000_000`, `0xFFFF_FFFF`); no C-style leading-zero octal and no width suffixes (bare literals stay `Int64`/`Float64`; `Byte` keeps its `B` suffix). Floats gain exponent forms (`1e10`, `1.5e-3`); no hex floats. The prefixes are a shared C-family convention, not one language's signature.
- Numeric width: **settled** — numeric types are width-explicit: `Int64`/`Int32` and `Float64`/`Float32`; defaults are `Int64` and `Float64`; no width-less `Int`/`Float` spellings; bare literals default to the 64-bit type (decided 2026-10-05 — README, Type System; rationale in `docs/numeric-width.md`). The last open sub-item **settled (2026-10-11): the `ocaml` backend's route is boxed `Int64` — already the shipped route.** The dynamic layer carries `Int64 of int64` and arithmetic emits boxed `Int64.add`-style operations, so 64-bit wrap-around semantics are correct there today; the unboxed two-word hi/lo emulation was never taken (its RV32 motivation is moot — the freestanding target is `riscv64`, with native 64-bit registers), and the `c` target — the default since step 24 — supersedes the performance question, as the step-23 entry above records. The mechanical `Int` → `Int64` / `Float` → `Float64` rename across checker/stdlib/examples/docs has landed.
- Float math and conversion primitives: **settled** — `Float64.sqrt`/`floor`/`ceil`/`trunc`, `Float64.to_int64` (truncating toward zero), and `Int64.to_float64` joined the core surface (decided 2026-10-06); the first consumer is the wasm interpreter (step 22), which needed them for the float families. `nearest` (round-half-to-even) is built in Emo from `floor`. The TS / wasm / BEAM backends emit them now (2026-10-19): `ts_core.ts` dispatches the four math names and both conversions on their receiver kinds, `emo_wasm.ml` lowers them to `f64.sqrt`/`floor`/`ceil`/`trunc` and `i64.trunc_f64_s`/`f64.convert_i64_s`, and `emo_beam.ml` calls `math:sqrt`/`floor`/`ceil`, with `erlang:trunc` behind a `float/1` for `trunc` and for `Float64.to_int64`. `examples/float_methods` prints the same twelve lines on the interpreter and on `ocaml`, `c`, `typescript`, `wasm` and `beam`. A target that cannot honor one still fails loudly, per the `foreign def` rule.
- Int32 / Float32: explicitly-named fixed-width types for FFI (`int32_t` / C `float`), bare-metal MMIO/device registers, and RV32 hot loops. **Surface settled (2026-10-06)**: explicit-only conversions named with the existing pattern (`Int32.from_int64(x)` / `x.to_int32()`, `Float32.from_float64(x)` / `x.to_float32()`); no implicit conversions and no mixed arithmetic; `Int32` wraps modulo 2³², `Float32` rounds per operation to binary32; no width suffixes (bare literals stay `Int64`/`Float64`). See `docs/numeric-width.md`.
- `foreign def` on non-native targets: **settled (2026-10-06)** — every target that cannot honor `foreign def` refuses it loudly at check time with a clear diagnostic, driven by a target-capability table (today only the OCaml-emitting native backend can honor it; the future `c` backend will too; `wasm`, `typescript`, `beam`, and the freestanding `riscv64` until C interop lands all refuse). Per-target availability is also declared through the manifest's `targets` mechanism, so a package is rejected at resolution. This gates any FFI deepening.
- C FFI binding-surface syntax: **settled in step 14** — `foreign def name(params) Ret = "c_symbol"`. The capability table moved with the targets (2026-10-10): the `c` target calls the symbol directly (step 23) and honors `Int64` parameters plus `Void` returns — the shape of a fire-and-forget call, and every externally linkable declaration lands in `.emo-build/emo_defs.h` for shims to compile against; the OCaml-emitting backend wraps `Float64`/`String`/`Bool` through generated C stubs (see `docs/c-backend.md` and `docs/ocaml-backend.md`).
- Self-contained hosted native backend (no OCaml runtime): **scheduled as step 23 (2026-10-06)** — `plan/hosted-native-ffi.md` remains the design record; `plan/step-23-c-target.md` is the execution plan. (a) Settled: the route is emit C (next item). (b) Reclamation **settled 2026-10-06** by the dedicated entry below — reference counting over the identity-bearing objects, value-semantic data arena-allocated (the T23.5 gate). (c) The HPC surface stays out of step 23's scope — it remains the gate beyond the backend. When the `c` backend covers the golden subset it supersedes the open item above on the native backend's route to 64-bit integer arithmetic on OCaml's 63-bit `int`.
- Codegen route for a self-contained native backend: **settled (2026-10-06) — emit C**, the step-23 route, with LLVM ruled out (C++ dependency, unstable API, opaque generated code, against the "emit and delegate" / readable-output line) and hand assembly confined to the freestanding `riscv64` target. Emitting C reuses the existing `cc` dependency, yields GCC/Clang autovectorization and OpenMP pragmas, and makes the C ABI the FFI surface. **Tail-call lowering settled (2026-10-06, step 23): the trampoline / block loop** — every self- or mutually-tail call is a parameter rebind and a jump to the function head, and `return` is a branch to the epilogue, never a raised signal (this is also the fix for the emit-OCaml backend's ~4x loop regression). **Wrap-around `Int64` settled (2026-10-06): unsigned `uint64_t` arithmetic cast back; `-fwrapv` is the documented fallback, not the plan.** The emitter also owns `restrict`-annotated vectorizer-friendly loops and the dynamic layer (tagged unions plus `retain`/`release`; `raise` ends the offending process — the root's death ends the program — by draining its fiber's frame chain, no unwinder and no `longjmp`, per the cross-target-invariants entry). See `plan/hosted-native-ffi.md` and `plan/step-23-c-target.md`.
- Reclamation model for the dynamic world without a tracing GC: **settled (2026-10-06, the T23.5 gate) — reference counting over the identity-bearing objects; implemented on the `c` target 2026-10-11.** Only instances, closures, and Box carry identity in Emo; tuples, arrays, and strings are value-semantic (assignment copies), so they cannot participate in cycles and stay in the bump arena until process exit — no per-object bookkeeping for them. The identity objects get malloc'd cells with a header refcount; the emitter owns the discipline (increment on capture/assignment into a longer-lived slot, decrement at binding scope exit and on overwrite; write barriers on the two mutation points — `Set_field` and `Box.replace`); cycles among instances and closures leak, documented (the Swift model). No language-surface addition is required: refcounts live in the cell header. Rationale: the settled codegen route already names `retain`/`release` as what this emitter owns; reference counting needs no stop-the-world, fits Emo's value semantics (the Swift / Objective-C lineage CHECK.md already cites), and frees memory before the scheduler and IO tasks (T23.9/T23.10) make long-running programs real. **The landed shape adds one runtime mechanism the settle's wording predates: a frame-scoped autorelease pool (the ObjC shape) — every generated body opens a pool at entry and closes it at every return, and statement boundaries drain the current frame — so expression-internal temporaries need no ownership analysis at any call site.** The emitter's discipline in full: a dynamic binding retains at init and releases at its block's end (bindings in a re-entered tail body hoist their zero-initialized slots and release-on-reassign, so a tail-recursive loop reclaims per pass); a parameter slot of a re-entered body retains at entry and releases at exit; tail-call rebinds swap through a write barrier and unwind the current pass's bindings while keeping the slots the next pass loads; `Set_field`/`Box.replace` barriers live inside the runtime entry points; closure creation and the arena aggregates retain what they capture (arena-held identities live to process exit, the documented shape); `send` copies the message into the mailbox and the mailbox owns the copy (`spawn` retains the closure into the fiber; a taken message transfers). The same-day verification: the whole golden tier byte-identical, plus a live-count probe (`emo_identity_live_count`) asserting a 10 000-iteration churn loop returns the identity count to its baseline while a List-held instance stays live. A future precise collector remains possible on the same layout (an immediate is never a valid pointer).
- C runtime string layout: **settled (2026-10-06, T23.3)** — a String in the `c` backend's runtime is `emo_str {int64 len; const char *bytes}`, length-prefixed and passed by value; no NUL terminator internally, one is appended only when a string crosses the FFI boundary (T23.8). Literals are C compound literals; the builders (concat, the scalar renderings) allocate in the bump arena and live until process exit — the reclamation decision landed as T23.5 (arena for value-semantic data), and reclaiming the value families is step 49. T23.4's heap String cell keeps this layout inside the tagged word's cell.
- The `c` backend's runtime language: **settled (2026-10-06, T23.3) — C, not Emo's specialized subset** (the hosted-native-FFI assessment leaned C: interop is a bridge, not a foundation). The runtime stays readable, reviewable C in `src/emo_codegen/c/`, compiled by the same `cc` invocation as the emitted program; self-hosting the runtime is not a goal (the reference implementation is OCaml by design).
- HPC criteria for the self-contained backend: **settled (2026-10-11) as the standing gate, in this priority order**: (1) vectorization/SIMD — the codegen route must deliver it (emit C, not LLVM or hand assembly); (2) a data-parallel construct (OpenMP-style parallel loop with reductions); (3) zero-copy FFI buffer passing — a mutable, address-stable, typed buffer (`Buffer[Float64]` or equivalent) borrowed for the call, per the `cgo` model, since `Array` is immutable and `Bytes` is byte-addressed; (4) ecosystem. GC is a latency and predictability concern (headroom, jitter), not the gate. Reference sample: Go — GC + custom backend + `cgo`, still not an HPC language because it does not autovectorize and has no parallel-loop primitive.
- Loop forms: **direction settled (2026-10-06)** — keep guaranteed tail calls *and* add `for`/`while`. Rationale: tail calls are a semantic (constant-stack iteration), not just an optimization, and they are nearly free on BEAM (native), wasm, and asm (a single `tail`); only the emit-C route needs a trampoline, which is not worth sacrificing the guarantee for. They also carry the actor `receive` idiom (README, Concurrency), and the current native backend's tail-call defect is an implementation bug (the `try … with Native_return` return convention), fixed by a branch to the epilogue, not a reason to change the language. Advantages of the loops: they are the native shape for vectorization/SIMD and `#pragma omp parallel for` (the HPC criteria), they remove the need for tail-position proof in loop code, and they are the least-surprise form for imperative and numeric iteration, pairing with `var`. The Go pre-1.22 loop-capture trap is already prevented — a `var` cannot escape its block, and capturing one in a closure that outlives the block is a compile error (README, Syntax) — so the earlier fresh-binding caution in `plan/README` is subsumed.
- Loop surface: **`for` settled (2026-10-06)** — the form is `for var i = 0; i < 100; i = i + 50 { ... }`: no parentheses (matching the paren-less `if`), a `var` declaration in the header scoped to the header and body, three `;`-separated clauses (init / condition / post), and the post written as an assignment (`i = i + 50`). This makes `;` a token, legal only inside a `for` header — the one place Emo uses it. The parser's existing `suppress_block_sugar` flag (already set for an `if` condition) applies to all three clauses, so a trailing `{` opens the body rather than attaching as a trailing block; the Go loop-capture trap is already prevented by the `var`-escape rule. Worked example: `for var i = 0; i < 100; i = i + 50 { println("i = ${i}") }` prints `i = 0` then `i = 50`. **`while` settled (2026-10-06): `while cond { }`** — paren-less and condition-only; the loop variable is declared before the loop and advanced in the body, e.g. `var i = 0` then `while i < 100 { println("i = ${i}"); i = i + 1 }`. `for` keeps all three clauses (no omissions), since `while` covers the condition-only case. The post / increment stays explicit (`i = i + 1`); `+=`/`++` are not added. **`break` settled (2026-10-06): a bare statement** — `break` takes no arguments and no parentheses, is used inside a loop, and binds to the nearest enclosing loop; `continue` is its pair, skipping to the next iteration and running a `for`'s post clause first. Both are rejected outside a loop. `do`/`while` is not added. With this the loop surface is settled; README and `plan/README` carry it; **implemented 2026-10-11 (step 26)** — lexer, parser, checker, and interpreter (`examples/loops` golden through `emo run`, ten million iterations flat), with the six backends refusing the loop statements until step 27 lowers them. **Lowered on all six targets (2026-10-11, step 27)**: the IR carries While/For/Break/Continue; c emits its own `while` and a `while(1)` form whose continue label runs the post; ocaml uses the ref discipline plus a pair of local exceptions per loop; typescript uses the native `for` with a labeled driver loop for tail calls; wasm lowers to block/loop/br_if with a post block; beam threads every free variable through a hidden recursive function with a done flag; riscv64 uses labels and jumps, and gained `/` and `%` (`div`/`rem` with a zero-division abort) so `examples/loops` boots — golden on all six targets plus the interpreter.
- Backend naming: **settled (2026-10-06)** — drop `native`; name backends by emission mechanism: `ocaml` (emits OCaml, links the OCaml runtime; today's `native`), `c` (emits C, own runtime; the step-23 backend), `riscv64` (emits RISC-V assembly; freestanding), plus `wasm`, `typescript`, `beam`. Rationale: `native` names a category, not a mechanism, and is itself ambiguous (C? riscv64?); the mechanism is what differs between backends and what scales once two hosted machine-code backends exist. `native` ceases to be a `--target` value; "native executable" is prose for what `ocaml`/`c`/`riscv64` produce. `c` is reserved and must not enter `known_targets` until its backend works. The rename is a mechanical whole-repo change, **implemented 2026-10-06** as its own step after step 23 (as allowed): every literal site below now carries `ocaml` — `known_targets`, the CLI default/help/error text, `emo init`'s manifest, `emo_project`'s defaults, the stdlib/example/benchmark `package.emo` files (lockfiles regenerated), the tests including `emo_lsp`'s fixtures, and the docs quoting the target; historical plan files keep the original value with a "today `ocaml`" note. Literal target-string sites (2026-10-06 grep): `src/emo_pkg/emo_pkg.ml` (`known_targets` plus two manifest samples), `src/emo_cli/emo_cli.ml` (the `match target` arm, the default value, `~target:"native"`, the `emo init` manifest), `src/emo_project/emo_project.ml` (two `~target:"native"`), the eleven `package.emo` files under `stdlib/registry/` and `examples/`, `test/emo_pkg/emo_pkg_test.ml`, `test/emo_project/emo_project_test.ml`, and the docs that quote the target (`README.md`, `docs/zh-CN/README.zh-CN.md`, `docs/stdlib/{net,http}.md`, `docs/zh-CN/stdlib/{net,http}.md`, `docs/TASKS.md`, `docs/zh-CN/TASKS.md`, `plan/step-13-networking.md`, `plan/step-17-typescript.md`, `plan/step-20-wasm-runtime.md`); prose `native` meaning native code (`docs/c-backend.md`, `docs/ocaml-backend.md`, `docs/industrial-software.md`) is unaffected.
- Binary / CLI tool distribution mechanism: **direction settled (2026-10-06) — defer to the `c` backend, then ship self-contained `emo` tool binaries per platform.** The `c` backend drops the OCaml-toolchain dependency from the tool, so a per-platform `emo` binary becomes usable; it does **not** drop `cc` — `emo build` still invokes the system C compiler for the emitted C, a far lower bar than OCaml (only a direct machine-code backend would remove it). Channels: prebuilt binaries per platform (GitHub Releases) as the primary route, with `opam` and a Homebrew formula as the source-building alternatives. macOS notarization is **solved, not a blocker**: with an Apple Developer account, sign (`codesign`, hardened runtime), notarize (`notarytool`), and staple the distributed zip (a bare Mach-O cannot be stapled); the certificate and credentials live in CI secrets. Windows ships prebuilt; signing uses **Microsoft Trusted Signing** — a managed cloud service (subscription, CI-friendly, short-lived certificates, builds SmartScreen reputation) — since the project has a registered company to pass organizational identity validation, or an OV/EV Authenticode certificate (post-2023 CAs require the key on hardware/HSM). SmartScreen reputation accrues with download volume rather than switching on with a certificate, and distributing through winget/scoop/chocolatey avoids the browser's Mark-of-the-Web; EV's historic instant reputation is no longer reliable. Lower the barrier with a check-and-guide command (`emo doctor`) that detects `ocamlfind`/`ocamlopt`, checks the version against the shipped `emo_runtime.cmxa`, and prints — or, with consent, delegates to the system package manager for — the platform install command; provision through `opam` and Homebrew (`opam install emo` brings a matching toolchain). A self-service `emo toolchain download` was rejected: it would make Emo a compiler redistributor and lock in a subsystem the `c` backend obsoletes. Rationale: `docs/toolchain-distribution.md`.
- Toolchain defaults for the v1.0.0 distribution (M7, step 24): **settled (2026-10-07) — four decisions.** (a) **The default build target flips `ocaml` → `c`**, and the whole default pipeline agrees: `emo build` without `--target`, the project loader's dependency resolution (`emo run`/`emo check`), `emo deps resolve`, and the checker's default capability target all mean `c`. A distributed binary carries no OCaml toolchain, so out of the box the tool must work on the download; the `ocaml` target remains for source installs (opam brings its runtime) and refuses with source-install guidance on a prebuilt installation that lacks it — never raw ocamlfind output. (b) **The stdlib embeds into the compiler as generated data** — the C runtime's own mechanism ("installed files beside the binary" is the rejected shape: it breaks single-file channels and every wrongly-unpacked archive); `EMO_REGISTRY` keeps overriding with a filesystem registry. (c) **`emo install` is the project-dependencies frontend** — read manifest, resolve against the registry, fetch into the cache, write `package.lock`, ready to run; global executable installation (the cargo-install shape) is out of scope for 1.0. **Amended 2026-10-17: the `emo install` command is removed** — the build path already resolves, fetches and materializes on its own, and `emo deps resolve` writes the lockfile, so the command duplicated both at ~90% overlap under a name that reads as the (never-built) install-binaries-into-PATH shape; the name sits free for a real global-binary design should one ever be settled. (d) **The dependency cache leaves the temp directory** for a durable user location (`~/.cache/emo` honoring `XDG_CACHE_HOME`) — the OS wipes `$TMPDIR`, and a product cannot re-fetch on every build. - The runtime-independence principle: **settled (2026-10-07, before T25.1)** — a target's runtime is written in the target's language, carried as generated data inside the compiler, and compiled by the target's own toolchain on the user's machine; the host contributes only the emitter. No target's runtime may be looked up beside the binary or in the host build tree: `c`, `ocaml`, and `typescript` runtimes ride inside the compiler as generated data (the `emo_codegen/{c,ts}` dune-rule pattern), while `wasm` and `beam` runtimes ride inside the emitted module itself (the wasm engine imports and OTP are the *target* ecosystem's ABI and standard library, as libc is to `c` — a different axis from the compiler's host language). Consequence: target generation stays the host's job, so a future host rewrite touches only the emitters; a target works wherever the target's own toolchain exists, on any installation shape — `emo build --target ocaml` needs the OCaml toolchain on PATH, never an `emo_runtime.cmxa` in the host build tree. The host/target distinction this completes is recorded in `docs/toolchain.md`.
- The ocaml runtime's dependency policy: **settled (2026-10-07, T25.4)** — the standalone runtime's core (values, strings, the scheduler) stands on the OCaml standard library plus `unix`, which ships with the compiler; TLS keeps `ssl` as the one opam-package dependency; the runtime's build invocation declares both (ocamlfind `-package unix,ssl`) and refuses with a clear message when `ssl` is absent. **eio drops out entirely**: the standalone scheduler is the deterministic poll loop the compiled path already ran on, so the provisional plan to keep `eio_main` on the target side is superseded — a target-ecosystem dependency nobody's program needs is not declared.
- Cross-module type names: **settled (2026-10-14) — module-qualified type names, superseding the 2026-10-10 program-wide bare-name rule.** A type reference is a path, exactly like a value reference: `ui.VNode` and `sync.WaitGroup` name another module's type, a bare `Order` names the current module's own, and package-relative forms (`internal.svg.Renderer` inside a package) work as they do for values. `Emo_check.resolve_type_ref` splits a written reference at its last dot-segment (the type name; every earlier segment a lower_snake module), normalizes that module path relative-to-package-then-absolute, checks the internal boundary, and returns the qualified display name (`sync.WaitGroup`); the pre-registration tables (`Emo_check.preregister_types`, now taking `~packages`/`~package_deps` so package-relative references resolve) are keyed by it, `ClassType`/`InterfaceType`/`EnumType` carry it, and the IR and every backend key class/interface/enum tables, `is()` vtables, and enum tags by it. Two modules may therefore declare the same short name — they are two distinct types, each addressed by its module — and E4021 (the bare-name collision) is gone. Construction, `is()` narrowing, enum member access (`ui.Color.red`), and enum patterns all accept the qualified spelling; the built-in `R` enum and `Exception` class stay bare. Consequences: the earlier 2026-10-10 machinery (two-phase program-wide pre-registration, the program's value-signature tables, `is()` narrowing across modules, construction loading the declaring module on first use) is unchanged except that its keys and surface are qualified; the internal rule is a path rule on the declaring module (a reference from outside its subtree reports E5001 at the use site, naming both modules); registry-package types resolve for their consumers and an interface signature may name its own interface inside a checked program, while a lone-file view (the LSP's single-file check) still resolves only that file's own declarations, keyed bare. `docs/emo-ui-check.md`'s evidence holds with the surface spelled `ui.VNode`.
- Cross-module value signatures: **settled (2026-10-11, the feat/checker pass) — the program's def/const/group tables pre-register beside the type tables**. The 2026-10-10 pre-registration made cross-module *types* check; values stayed blind — `lib.make(x)`'s arguments went unchecked, `lib.answer` read as Unknown, another module's group member never resolved, and every divergence the interpreter raises at run time (E5004 unknown member, E4004 wrong argument) surfaced only there. The fix rides the same two-phase pass: `preregister_types` now also collects every unit's defs and foreigns as declared `FuncType`s, every top-level const/var as its initializer's type (typed in the unit's own order, diagnostics dropped — the module's own check reports them), and every `emo` group's defs and consts into a program-wide registry mirroring the runtime's (groups are global at runtime, so the checker's per-module table gains a program-level fallback). A qualified call checks through `check_apply` like any call; a bare `lib.make` reads as the closure's `FuncType`; a member that resolves nowhere reports E5004 statically — the runtime's own message. Shadowing stays runtime-faithful: a dotted path is a module reference only when its head is not a local binding (the runtime looks the head up in the environment first — the `list` example's local `const list = List.new(...)` under a module named `list` is what pinned this). Group member reads type directly (consts carried nothing before — a bare `Math.tau` read as Unknown even same-module). Two pre-existing checker bugs fell out: `longest_module_prefix` generated the path's *suffixes*, never its prefixes (harmless while it only under-recorded refs, fatal once member resolution keyed on it), and the Member arm treated the empty dotted path as a module prefix, swallowing bare member access on non-simple receivers (`foo(1).field` read as Unknown forever). Registry packages join automatically — the same `p.files` walk feeds the pre-registration, so `json.decode(text)` now checks its argument and returns the interface. The packages' interfaces moved their `get` onto the interface (json gained the four raising scalar variants, matching the classes it already had; the "an interface signature cannot name its own interface" comments predated self-referencing signatures and were stale). Unblinding receivers also surfaced two latent c-side deviations, both pre-existing and both fixed to the interpreter's answer: `emo_box_replace` returned the box while every other target returns the new value, and the emitter's `to_string` dispatch arm captured statically-typed instance receivers, printing the debug repr instead of the class's own method — instances now dispatch by class first, the conversion answering only when no method carries the name. A capitalized name that resolves to no type, group, or module reports E4003 at its write site in a program check — the runtime's value-carrying builtins (`Int64`, `Byte`, `Float64`, `Box`, `Bytes`, `List`, `ArrayBuilder`, `Map`, `Exception`) stay legal — while the lone-file view (the LSP's single-file check) keeps the old silence, exactly like every other cross-file gap it cannot see through.
- A Zig-emitting backend: **settled (2026-10-11) — shelved; not a seventh target** (`docs/zig-backend.md`). Emitting Zig is mechanically a mirror of the `c` target, and its one unique gain — safe-mode bounds and overflow checking on generated code — is a mid-sized development-time benefit set against a full backend's cost and a permanent churn tax: Zig breaks language and std APIs in every release, 1.0 has no date, and incremental compilation covers only x86_64-linux. Without its std library the emitter produces curly-braced C with worse tooling — a strictly worse `c` target; with it, every compiled program rides a pre-1.0 std — the churn the runtime-independence principle refuses. The shelving carries written re-evaluation triggers, set now so the bar is explicit: Zig 1.0 or completed language stabilization, incremental compilation beyond x86_64-linux, or a concrete requirement the `c` target cannot meet through `zig cc`. What survives is not a backend: `zig cc` as an optional compiler driver for the existing `c` target — cross-compilation from any host, static musl Linux binaries, Windows without MSVC — is its own small step, taken if Windows or static Linux distribution enters the plan, and only after the driver's version joins the `c` cache key (today it hashes source, runtime, cclib, and the emo binary, so a swappable driver would serve stale binaries after an upgrade). `riscv64` stays direct assembly text; nothing passes through Zig.
- FFI compound data — struct shapes: **settled and implemented (2026-10-11) — a tuple or a carrier class is the shape declaration; the carriers are Emo's own**. A `foreign def` parameter whose type is a tuple crosses the C ABI as a C struct by value: the element types in order are the layout, and a nested tuple element nests a struct within the struct. A class instance carries the same by its init-assigned fields — the carrier-class contract is that the class's shape *is* its init signature: every field assigns a same-named parameter, in order, and every field type stays in the tier (a marshaling scalar or a nested tuple); a computed or extra field, a stateless class, and a class-typed field all refuse. A compound foreign **return** crosses back as a tuple — a class-typed return refuses ("name the tuple"), because a return would have to fabricate an object identity a C value cannot carry. The `c` target declares the same `typedef struct` the C side sees — into `main.c` and `emo_defs.h`, so a shim compiles against the real layouts — and per shape emits two static converters (one flattening the argument word into the struct, per carrier kind, so the argument expression stays a single textual occurrence; one rebuilding the tuple word from a returned struct); the by-value calling convention (register vs. memory class, the SysV classification) is cc's job, which is the emit-C route paying for itself. Identical layouts share one typedef, keyed by the serialized member tree. No language-level struct type exists — records are class instances and anonymous compound values are tuples, and the FFI surface declares shapes *through* them, so nothing new enters the value model. Rejected along the way: making the carrier rule lenient (strictness first — a divergent field list marshals the wrong bytes silently). Open for later: struct fields that are themselves carrier classes, pointer OUT-parameters (`&x` shapes), and the other honoring target (`ocaml`) gaining shapes — each refuses loudly today, per the `foreign` rule.
- The C→Emo callback contract: **settled (2026-10-11) — a single-method structural interface is the callback type; implemented on the `c` target the same day** (spike evidence in `spike/macos-gui`). A `foreign def` parameter may name an interface; the `c` target emits a trampoline plus an opaque userdata handle, and the C side calls through them into the object's one method — registration is explicit ordinary code, with no invisible plumbing. The convention: one interface-typed Emo parameter expands to two adjacent C parameters, the function pointer and the `void *`, and the callback's C signature is the method's marshaled parameters followed by the trailing `void *userdata` — the idiom every C callback API already expects, and the pair lands in `emo_defs.h` so a shim's signature drift breaks at cc time. The callback method stays in the marshaling tier (`Float64`/`String`/`Bool`/`Int64` parameters, plus `Void` returns); the trampoline boxes the arguments and dispatches by method name through `emo_send`, so identical signatures share one static trampoline and distinct receivers ride the userdata. Rejected: `&def` function references — an address-of-def reads as first-class functions seeping through the FFI seam, and there is no representation to back it (the `c` target's call discipline is plain symbol calls; callbacks are deliberately not first-class); a C-style struct-of-function-pointers registration — the struct-shaped Go borrow already refused. What the spike proved meanwhile: C already calls Emo defs as plain extern symbols (module-qualified, `main__`-prefixed), with callback state traveling through the signature because Emo gives cross-callback state no global home; the interface contract generalizes exactly that shape. The interpreter still refuses every foreign def at run time (E3009), and the other honoring target (`ocaml`) refuses the interface parameter at check time until its marshaling path grows one.
- Package-carried native code and the manifest `link` field: **settled and implemented (2026-10-12), with the `sqlite3` package as the first consumer.** A package may carry `.c`/`.h` sources in its tree — collected, checksummed, embedded, and published beside its `.emo` modules (the tree is the package, so the sources are auto-collected exactly like the modules; no manifest field names files) — which the `c` target compiles in the program's single cc invocation, and the manifest gains an optional `link = [...]` field naming the system libraries to link (bare names only: a `-`- or `/`-shaped entry is refused with E5103 — the manifest stays data, never a flag fragment; `--cclib` keeps the verbatim-flag role). Both ride the existing cclib mechanism into the build's cache key — sources by content, libraries by name. A native-carrying package is honored by the `c` target alone: resolution's `targets` gate stays the first line, and a package declaring the current target while carrying native inputs makes the build refuse outright (E5007, naming the packages) rather than silently dropping the link. The `sqlite3` package itself: `targets = ["c"]`, `link = ["sqlite3"]`, its `foreign def`s in a subtree-private `internal/ffi.emo` against a package-carried shim whose every signature is exact-ABI (`int64_t`/`double`/`bool`/`const char *`) so SQLite's `int` returns never meet the FFI undeclared; the shim includes the generated `emo_defs.h`, so drift breaks at cc time in both directions. Handles ride pointer-sized Int64s; bind indices are 1-based (they name the SQL text's `?NNN`), column indices 0-based (SQLite's convention); a NULL column reads as `""` with `column_is_null` telling the two apart; embedded NULs truncate at the boundary until Bytes can cross the FFI; blobs are out of scope until then. Errors follow the package's base-branch convention — raise, per `os` — and join the error-handling migration to `(R.ok, …)` / `(R.error, …)` tuples when that branch lands. Rejected along the way: baking SQLite into the always-linked C runtime (every binary would link `-lsqlite3`, and the interpreter would need its own binding) and vendoring the amalgamation (a quarter-million lines of third-party C for what every host already ships).
- EmoUI native packaging: **settled and implemented (2026-10-14, landed 2026-10-18 as T48.7) — the manifest grows per-package native fields; a native backend does not ship an app-level build script.** A native UI backend has to be an ordinary package a program reaches with a `require`, so what AppKit and GTK 4 need must be declarable in the manifest rather than restated in each consumer's build script. The need is concrete: a macOS backend is an Objective-C translation unit built with `-fobjc-arc -framework AppKit`, and a GTK 4 backend needs `pkg-config gtk4`'s cflags and libs; the spikes work around both with an app-level script passing `--cclib="$PWD/shim.o"` and `--cclib="-framework AppKit"`, which makes every EmoUI app carry a build script instead of a `require` — friction on the requirement's "just download and use", and the one thing a consumer cannot discover from the package it depends on. This extends the `link` field above rather than replacing it: the manifest stays data (bare names, no flag fragments), the native sources stay auto-collected from the package tree, and the new fields are per-package, so the resolution gate and the build's cache key keep working unchanged. The field surface itself — `pkg_config` versus explicit compile/link flag lists, and whether `.m` joins `.c`/`.h` in the collected set — was T48.7's own work, as was its implementation; T48.8 and T48.9 were gated on it. Rejected: documenting the app-level build-script path as the supported one — it is what the spikes needed, not what a user of a UI package should need. **Landed surface (T48.7):** `pkg_config` names bare pkg-config modules — their `--cflags` join the one compile and their `--libs` join the link — and `frameworks` names bare macOS frameworks, linked as `-framework NAME`; the collected set adds `.m` to `.c`/`.h`, and the `c` target compiles `.m` under `-fobjc-arc` as its fixed policy. Both fields refuse `-`-shaped, path-shaped, and empty entries, so the manifest stays data.
- Standard-library requires: **settled (2026-10-14), superseded 2026-10-17 by the standard-library pin entry below — an unscoped `require` resolves the standard library implicitly; only a scoped package pairs with the manifest.** The official standard library owns the top-level short names (`json.decode()`, `http.get(url)`) and ships inside the compiler, so `require "json"` needs no `deps` entry: the loader takes the highest version the registry publishes for each unscoped require (the bundled registry by default, `EMO_REGISTRY` when set), resolves that package's own stdlib closure with the manifest's pins in one MVS solve, and registers the modules for checking and the visibility rule. Implicit pins never enter `package.lock` — the manifest stays the recorded resolution — and an implicit pin may not silently move a manifest pin: a stdlib closure demanding a different exact version than the manifest states is an E5007 conflict the manifest must settle. A scoped `require` (`acme/tools`) keeps the strict pairing (missing from `deps` is E5006), and an unscoped name the registry does not publish is E5009 at the require. The LSP mirrors both and folds the modules of unpinned stdlib requires into its index.
- Cross-target invariants the targets do not all honor: **settled (2026-10-15, step 50).** Found 2026-10-14 during a target-feasibility survey, which recorded three rules whose implementations disagreed; two of the three were never open questions — they were conformance gaps against promises already made, and neither moved a language surface. (1) **The `c` target's `raise` ended the program, not the process — fixed.** `emo_raise` rendered the value and called `exit(1)`, while the process model promises the opposite — "an unhandled error ... kills only the offending process" (`docs/intro/concurrency.md:11`) — and the settled error split above rests on that promise. `emo_raise` (`src/emo_codegen/c/emo_c_runtime.c:2086`) now branches three ways: outside the scheduler, or in the root, it keeps the old behaviour (render `uncaught exception: …` and `exit(1)` — T23.6's E3010 rendering, and the root's death is the program's end, `docs/intro/concurrency.md:12`); in a spawned process it drains its own frame chain and ends only itself. **This entry's own cost estimate was wrong, and the correction is the reason the fix was small.** It said closing the gap "means the per-fiber unwind the `catch` design was refused for" — `setjmp`/`longjmp` plus a drain at every C frame. None of that is needed, because the runtime already had the whole mechanism: the autorelease pool is a heap-allocated frame chain hung off the fiber (`emo_process.top_frame` → `emo_frame.parent`), so a fiber's frames are reachable without touching the C stack; `emo_process_halt_current()` (`:2071`) already ends a fiber by swapping to the scheduler and never returning — that is how every `makecontext`'d fiber ends today; and the scheduler already reaps a finished fiber's stack and already treats only the root's finish as program end. The fix is the drain helper `emo_fiber_release_frames` (`:1956`) — the same walk `emo_pool_exit` did, releasing each pooled item and returning the frame nodes to the free list — called by `emo_raise` and by `halt()`, which had the identical leak. No emitter change: `emo_c.ml` already emitted a plain `emo_raise(v)`. Observable result matches the interpreter (`emo_sched_det.ml`): the root's raise prints and exits 1, a child's raise kills only the child and prints nothing. (2) **The `c` target's `send` shared the message; it did not snapshot — fixed.** The snapshot was already promised for each of Map, Box, List and ArrayBuilder (`docs/intro/syntax.md`), the interpreter deep-copies across that boundary (`emo_eval.ml`'s `snapshot`), the standalone OCaml runtime already did, and `stdlib/registry/sync/0.1.0/sync.emo` states it outright for a handle; the `c` backend emitted a bare `emo_process_send(pid, msg)` (`emo_c.ml:1926`) and the runtime only `emo_retain`ed the cell into the mailbox, so a Box sent between `c`-target processes was shared. `emo_deep_copy` (`emo_c_runtime.c:2106`) now sits beside the mailbox and `emo_process_send` (`:2206`) stores `emo_deep_copy(message)`, following the interpreter's rule over the kinds this runtime has — `Box`, `Bytes`, `Tuple`, `Array`, `List`, `ArrayBuilder`, `Map`, `Instance` are rebuilt (instances copy their fields and keep the class; a map copy preserves insertion order), while `Int64`, `Float64`, `String`, `Enum`, `Closure` and `Pid` pass through as immutable data or as the identity the boundary deliberately shares. The emitter needed one line (`emo_c.ml`): the mailbox take releases its only claim on the snapshot before the branch binds, so the scan now holds its own (`emo_autorelease(emo_retain(...))`) — without it the value was freed between take and bind. Copied arena aggregates leak exactly as every arena aggregate does, this file's step-49 limit rather than a new one. (3) **`foreign def` had no emitter-level refusal on `wasm` and `beam` — fixed.** The capability table is the intended sole gate, but it admits `Float64`/`String`/`Bool` on *every* target — the `c`-only rows are `Int64` and `Void` — and neither `emo_wasm.ml` nor `emo_beam.ml` mentioned `fforeign` anywhere; only `emo_ts.ml`, `emo_c.ml`, `emo_codegen.ml`, and `emo_riscv.ml` handled it. The survey's guess is now answered: the IR carries the symbol in `fforeign` on an otherwise ordinary `func` record with `fbody = []` (`emo_ir.ml:1354`), so both emitters were emitting an **ordinary function for a declaration that has no Emo body** — a silently absent symbol, not a downstream refusal. Each emitter now refuses per function, beside the code that would have lowered it, with the shape the riscv target already uses: `raise (Emo_ir.Lower_error "the <target> target does not support \`foreign def\` yet")`, which the CLI renders as `emo build: …` and exit 65 — the code the `Map` and `ArrayBuilder` refusals carry. **The `typescript` half, the item's only remainder, is fixed (2026-10-17).** `ts_runtime.ts:2378-2389` stored the reference, verified by running the T12.4 program under `node` — interp/ocaml/c printed `1\n99\n`, typescript printed `99\n99\n`. `send` now deep-copies its message with the runtime's `deepCopy`, so typescript prints `1\n99\n` too, and `test/emo_cli`'s `cross_target` group pins it. **The `wasm` half — the entry's last remainder — is fixed (2026-10-19, T52.3).** `rt_send` (`emo_wasm.ml`) deep-copies the message through a new `deep_copy` runtime before it joins the mailbox — `Box`, `Map`, `List`, `ArrayBuilder`, `Tuple`, `Array`, `Bytes`, and a class instance's fields rebuilt (a map copy inserts in index order, which is the insertion order; an instance goes through `struct.new_default` and re-stores its real fields over the null pad), while the immutable kinds and `Pid` fall through as the same reference, the `c` runtime's `emo_deep_copy` rule — and the `cross_target` group pins it on `wasm` with this program's twin (`receive` parks the whole body on this target, so the entry trails and the sender's side prints first: `99`, then `1`) plus a message carrying a `Map`, `List`, `ArrayBuilder`, and `Bytes` at once, whose echoed copy shows the sender's post-send writes gone and the insertion order kept. Three `wasm` gaps met while pinning, none of them the send's: the runtime dispatch for `.get` on a receiver the checker could not type knows `Bytes` and `ArrayBuilder` but not `Map`, so a map read straight out of the mailbox traps; a field read still demands a known class (`wasm: field read without a known class`); and `to_str` has no `Box` or tuple arm, so `println` of either aborts. They stay recorded, not fixed here — the first two are the unknown-receiver surface the Map lowering (T52.2) has yet to cover, the third predates this milestone entirely.
- `c` target long-running memory: **settled (2026-10-14, the arena-scope spike) and landed 2026-10-17 (T49.1–T49.5) — region reclamation is not viable as a standalone mechanism; the value families need refcounting, and that is its own milestone (`plan/step-49-value-reclamation.md`).** A region reclaims 100% of the arena's bytes and 0% of the leak that actually grows the process, because identities are `malloc`'d outside the arena while the arena's aggregates retain them across the region's boundary — so the references a reset drops without releasing are unrecoverable, and the raw reset strands those refcounts permanently. The obvious repair, logging the retains the arena performed and replaying them in reverse at the reset, is O(k²) per render, because `emo_array_append` copies and re-retains every element on every append. The same probes found the second cost this workload pays: there is no O(1) array append and no conversion back from `List` to an indexable `Array`, so a dynamically grown children array is quadratic either way. **The array-growth half is answered (2026-10-15, T49.3):** `ArrayBuilder` is an amortized-O(1) append that copies out into an `Array`, so growing the children array no longer goes through `Array.append`'s per-element copy — and it needed no representation change, so nothing here waits on the reclamation milestone. Its growth follows the `Map` doubling in the same runtime, and its retired buffers stay arena-resident and leak exactly as `Map`'s do, which is this entry's already-recorded limit rather than a new one. The `List` → `Array` conversion half stays open, deliberately: nothing in the language reads a deque by index, and adding a conversion to `List` would give the deque a second job it does not need. Evidence: `spike/arena-scope/` (three probes with checked-in outputs; at 400 nodes a render allocates ~1 MB and leaks ~820 identities, both unbounded at 60 fps). Two mechanisms were weighed and rejected rather than left implicit: **per-fiber arenas**, which would let a finished fiber's arena be freed whole, but `send` and `spawn` pass arena pointers across and retain them, so they demand copy-on-send for every value family — the escape analysis relocated onto the concurrency hot path; and **making identities arena-resident again** so a region contains everything it holds, which would remove the refcounting T23.5 landed and leave the region as the only mechanism, straight back into the boundary probe 3 shows cannot always be named. Consequence for step 48: **T48.8 and T48.9 proceed at demo scale with the limit documented**, rather than waiting on reclamation or shipping a region that would make half the leak harder to fix later. (The note retired 2026-10-17: the milestone landed, and the demo-scale caveat no longer holds.) **The runtime half is landed (2026-10-17, T49.1):** every dynamic cell is now `malloc`'d with a refcount header — the T23.5 identity discipline extended to the value families — so a value cell reaches zero and frees, and an aggregate's release frees its holdings (tuple and array elements, list nodes, map entries and buckets, builder buffers). The emitter's ownership vocabulary widened with it: `may_own` covers every dynamic type, every construction or boxed crossing pools its birth at the statement boundary, the tail-rebind and hoisted-binding barriers take the new claim before dropping the old (a self-passing slot was the last owner — release-first freed it mid-jump), `Map.remove` hands back the claim its siblings hand, and the dynamic→native String crossing copies (`emo_str_owned_of`, like the to_string copies) because a native view outlives the cell's statement-pooled claim. The probe (`emo_identity_live_count`, now counting every cell) returns to baseline across a 3 000-iteration churn that builds and drops instance trees, style maps, arrays, builders, and interpolated strings. The cycle audit the step owes: the immutable families (String, Bytes, Tuple, Array, Enum, boxed scalars) are **structurally acyclic** — an element word is evaluated before its container's cell exists, and `Array.append`'s fresh cell cannot appear among its own elements — while the mutable identities (Box, List, Map, ArrayBuilder, instances, closures) can cycle exactly as instances always could (`l.push_back(l)` typechecks through an `Unknown` element), which stays the documented leak class, not a new one. What remained for T49.2 was the pool's own contract and the native transient class. **It is landed (2026-10-17, T49.2): String joined the dynamic world.** The three candidates the step's open item put on the table were weighed in writing before the code: **a wider pool** (statement-scoped native transients) is unsound, because a `String`-typed binding holds a native view across statements (`const s = a ++ x` reads `s` three statements later) — a reset would strand every such binding, and making the escapes copy means deciding who owns the copy, which is the ownership analysis the pool exists to erase; **a smarter emitter** (release at last use for native bytes) is that same analysis spelled differently; so **the representation moved instead** — typed `String` positions are `EMO_STRING` cells like every other dynamic value, the string builders (`emo_cell_concat`, `emo_cell_from_*`, `emo_cell_substring`/`lower`/`trim`/`split`, `emo_to_string_cell`) allocate the result cell directly with no bump-arena intermediate, and the native `emo_str` shrinks to three forms that cannot leak: static compound literals, borrows of a cell's bytes inside one statement (POSIX paths, the FFI's `emo_str_cstr` at call duration), and copies at the C boundary. The leaf builders answer **self-pooled births** — they open no pool frame, so the claim lands in the calling statement's frame and dies at its boundary, and a result that crosses a frame re-claims through the return's `__ret` — which is why `to_str`'s scalar cases wrap nothing while the general constructors (`emo_box_str` and friends, callable from runtime internals that cannot tolerate a hidden pool entry) still pool at the emitter. The runtime's own transients got call-scoped ownership: the printf render buffer, the file/net read buffers, `execv`'s argv and `list_dir`'s names are malloc'd and freed within the call. The same churn that T49.1 left at ~690 native bytes per iteration now holds **RSS flat across 3 000, 30 000 and 120 000 iterations (10.3 MB at each)** with the live-cell count at zero, and every c golden stays byte-identical. The pool's contract, stated once: the pool owns every dynamic claim at statement granularity — births from the leaf builders and from the emitter's wrapped constructions alike — and nothing native survives a statement.

- A Lua-emitting backend: **settled (2026-10-14) — shelved; not an eighth target** (`docs/lua-backend.md`). On three axes it would fit Emo better than any target that exists: Lua 5.3's integer subtype satisfies the Int64 wrap-around invariant natively, Lua's coroutines are the stackful cooperative process model the `c` target builds out of `ucontext` fibers, and Lua guarantees the proper tail calls `c` and `typescript` only approximate. What a Lua target uniquely offers — the artifact a host `require`s into its own process, which no shipped target provides, since the wasm target still needs the host to have a wasm engine — dies exactly where it would be worth something; compiling standalone Lua instead competes with the `c` and `typescript` targets rather than reaching a new host, while paying the explanation cost of a crowded and partly abandoned dialect space (MoonScript, YueScript, Teal, Fennel, TypeScriptToLua, Haxe's Lua target, Amulet ML, Urn). What survives is not a backend: if the goal is an Emo artifact inside a process someone else owns, the cheaper direction is an embedding surface — a documented C embed ABI on the `c` target, or a documented import/export surface on the wasm target — evaluated as its own small step, with no version wall and runtimes that already exist. - Operand evaluation order on the compiled targets: **found 2026-10-15 (T48.3) — fixed 2026-10-17.** `ocaml` evaluates a call's arguments right to left; the interpreter, `c`, `typescript` and `beam` evaluate them left to right (`wasm` lowers them in source order, read from its emitted WAT). - Package name characters and the archive filename: **settled (2026-10-17) — each part of an `owner/name` package name is a lowercase identifier: 1–64 characters, a letter first, then letters, digits, or `_`; `-` is excluded.** The short name is what `require` binds, so a dash in it could never survive contact with code — `require "david/foo-bar"` names a module `foo-bar`, which no identifier can spell — and since publishing runs through one central registry, the registry simply refuses such names instead of defining a transliteration (the crates.io `-`→`_` mapping is the rejected shape: one package, two spellings). Underscore stays, after a same-day reversal of an over-tight first cut: `_` is in the identifier alphabet and never collides with the filename's dash joins, and the one place a `_` can visually vanish — underlined links and italic prose — is a rendering problem, met by the discipline that identifiers always render as code (monospace, never underlined) on the registry site and in docs; banning `_` in the language would have bought nothing for it while making every call site read against Emo's snake_case grain. The same rule covers registry usernames and org names: they become the owner part of published names, so a looser identity rule would mint accounts that could never publish under their own name. The payoff lands in the wire format: with dash-free parts, the published archive's name and the download URL join with single dashes — `<owner>-<name>-<version>.emoji`, `GET /downloads/<owner>-<name>-<version>.emoji` — replacing the `--` joins that existed only to stay parseable against dash-bearing names; the server's parse is unchanged apart from the separator, since versions are strict major.minor.patch and owner/name parts never contain a dash, the filename is always exactly three dash-separated segments. - TLS on the `c` target: **settled (2026-10-17) — the three `net` TLS builtins land in the C runtime against the system OpenSSL/LibreSSL, behind hand-declared prototypes and IR-keyed conditional linkage; no FFI-based binding and no new package.** The premise the settle corrects: TLS was never missing from the standard library — `net_tls_connect` / `net_tls_connect_insecure` / `net_listen_tls` exist as builtins, the interpreter's scheduler and the standalone OCaml runtime implement them through the opam `ssl` library and `typescript` through `node:tls`, and `http`'s `https://` already routes through them — the gap is that the `c` target, the default, sends the three names to `emo_unsupported`, so `https` is dead precisely on the default target. The work is therefore conformance with the other targets, not new surface: the Emo source of `net` and `http` does not move. The user-level-FFI route was evaluated and refused: `foreign` dies under `emo run` (E3009) and on `typescript`/`wasm`/`beam`/`riscv64`, the `ocaml` target's marshaling tier cannot carry an `Int64` handle, and OpenSSL's setter surface is macro-shaped (`SSL_CTX_set_min_proto_version` is `SSL_CTX_ctrl` underneath), so an FFI binding means hand-computed ctrl codes at the seam while demoting a working three-target capability to a `c`-only one — and `http` could not switch implementations per target anyway, because Emo has no conditional compilation. **Linkage keys on use, not on presence:** the runtime's TLS section compiles only under `EMO_HAS_TLS`, which the CLI defines — together with `-lssl -lcrypto` — only when the program's IR genuinely reaches one of the three builtins, detected by the `c` emitter's own walk over the entry-reachable call graph (the flag flips where reachable code calls one of the three — static calls, spawns, function values, and conservatively every body carrying a reached method's name — never a scan of emitted text; a package function that is only emitted, never reached, neither flips it nor costs the program its linkage). A program that never touches TLS neither links nor requires OpenSSL; without the macro the three names still exist as `emo_unsupported` bodies, today's honest refusal — the mirror image of the `sqlite3` settle, which refused baking SQLite into the always-linked runtime, and for the same reason. **The prototypes are hand-written** — roughly fifteen declarations plus the frozen constants of the stable 1.1-era client/server API (the `SSL_CTX_ctrl` codes and wire-version constants verified once against a real OpenSSL 3.x header and pinned with that provenance in a comment) — because no platform should need TLS headers: the subset is declared once in the runtime, and the libraries are the machine's own (Linux links the distro OpenSSL through the dev package's `-lssl`/`-lcrypto` symlinks; macOS has shipped no OpenSSL headers since Xcode 10 and current releases no longer ship the `/usr/lib` TLS dylibs at all, so its OpenSSL comes from Homebrew or similar via `--cclib -L<dir>` — the implementation's probe caught the settled text's stale no-`-L` premise and this clause records the correction); the signature risk this takes on is held by the TLS goldens on every CI platform. Semantics are the ocaml scheduler's, with a `fd → SSL*` side table standing where its conn's `ltls : Ssl.socket option` stands so `TcpConn`'s existing read/write/close methods route through it: verification on with the system trust store (`SSL_CERT_FILE`/`SSL_CERT_DIR` honored), SNI from the connect hostname, the TLS 1.2–1.3 window, the insecure variant as the same handshake with verification off, server-side PEM certificates, and nonblocking parking on `WANT_READ`/`WANT_WRITE` where the interpreter parks on ocaml-ssl's `want_read`/`want_write`. - Standard-library pins: **settled (2026-10-17) — every `require` pairs with a manifest pin, the standard library included; the 2026-10-14 implicit resolution is withdrawn.** The implicit rule treated the standard library as part of the compiler, but its packages are versioned like any other — `json 0.1.0` pins `float 0.1.0`, `http` pins `net`, `bufio` pins `os` — and run through the same MVS solve, so an unpinned `require "json"` resolved to whichever version the installed compiler bundled: a compiler upgrade silently moved a program's dependencies, the one thing the lockfile exists to prevent, and the manifest no longer stated the whole resolution. The loader now reports an unscoped require the manifest does not pin as E5006 — the strict pairing's own code — with the hint naming the exact line to add (``add `"json" = "0.1.0"` to the manifest's deps block``), the version read from the bundled registry (or the filesystem registry `EMO_REGISTRY` names); an unscoped name no registry publishes stays E5009 at the require. Three shapes were weighed: the lockfile alone carrying stdlib versions the manifest omits (refused — Emo chose exact manifest pins precisely so the manifest determines the roots, and a lost lockfile would reintroduce the drift), the tool writing pins into `package.emo` (refused — a manifest edited by a build is the implicit addition the design philosophy forbids, and needs a format-preserving editor besides), and the explicit pin, which is one rule for stdlib and third-party packages alike and a revert rather than a third mechanism. The pin is only worth something if the version it names stays resolvable, so **the bundled registry only gains versions**: a standard-library bump adds `stdlib/registry/<name>/<new>/` beside the versions already there and never removes one, and every bundled version must keep building under the current compiler (an old stdlib version that no longer compiles is a language compatibility break, which user code would hit just the same). Dropping the implicit path removed `stdlib_pins` and `resolution_with_stdlib` from the loader — the E5007 implicit-versus-manifest conflict goes with them, there being nothing implicit left to conflict — and the LSP mirrors the rule: an unpinned stdlib require is a quick-fixable E5006 whose hint carries the version, and the index follows the manifest's pins alone. Every example in the tree already pinned its standard-library dependencies, so none moved.

- The lockfile's first appearance: **settled (2026-10-17) — a run with no `package.lock` records the resolution it establishes; an existing one is never rewritten.** The prior behavior resolved in memory and wrote nothing, so a project could work indefinitely without its record — every run a fresh resolution, a yank or a registry change shifting the closure under a program that ran fine yesterday, and the fix (`emo deps resolve`) one command nobody was prompted to run. Creating the missing file is a different act from rewriting one: nothing the developer chose moves (the manifest's pins are the developer's, the lockfile is their derived record), the work is already done — the run resolved and fetched everything — and discarding the result only loses reproducibility. So `resolution_for_run`, on a missing lockfile, resolves, writes, and says so on stderr (`wrote package.lock — commit it beside the manifest`); a tree it cannot write to still runs, the lockfile being a record, not a prerequisite. All three behaviors that would silently *change* a recorded resolution stay errors: a stale lockfile still fails pointing at `emo deps resolve`, and the split that made this safe is `Lockfile.read` now answering `Missing` versus `Malformed` — a damaged lockfile used to be conflated with an absent one and silently ignored (a fresh in-memory resolution answered instead, violating "never silently re-resolved"); it is now refused with the same pointer to regeneration and never overwritten. `emo deps list` names the missing file instead of printing the raw syscall error. The rejected alternative — auto-regenerating a stale lockfile — remains rejected: the lockfile is in version control, and a run that rewrites it commits a resolution nobody chose. The CI companion is `--locked` on `run`/`build`/`check`/`test`: a guard at the command layer refuses a project with dependencies and no lockfile (exit 66) instead of letting the run establish one — stale and damaged lockfiles already error on every path, so missing was the single hole; a project with no dependencies owes no lockfile and passes untouched.

- `emo deps add`: **settled (2026-10-17) — `emo deps add <package> <version>` pins a package in the manifest and locks the resolution.** With every require needing a manifest pin, the workflow owed a command that writes the pin: `emo deps add json 0.1.0` inserts `"json" = "0.1.0"` into package.emo and writes package.lock, so the very next run — or `--locked` in CI — uses it. - Language protocols (metaprogramming): **settled (2026-10-21) — an explicit, closed registry; the `emo` module is the registry.** Metaprogramming in Emo is language protocols: named methods the language dispatches on, plain snake_case spelling, no marker affixes — the explicit-protocols school with the marker's job moved into the checker (definition-site contract) and the `emo.` prefix (call-site dispatch marker). The registry is `emo`, the language's own function group, ambient in every program like `R`/`Exception` (no `require`); its surface is the complete protocol list. The keyword does double duty — `emo Name { ... }` declares a group, expression-position `emo.` accesses the language's own — and no package may bind under the short name `emo`. v1 entries: `emo.to_string(x)` ⇒ `x.to_string()` (contract `def to_string() String`) and `emo.length(x)` ⇒ `x.length()` (contract `def length() Int64`); the general call shape is receiver-first with the rest passing through in order, named arguments and trailing blocks included. Contract enforcement follows the `init` precedent (E2011): a protocol name as a `def` inside a class or interface body must match the contract exactly — any other signature is a hard error stating the contract; a same-named non-conforming method silently falling to the default rendering is the near-miss trap structural hook lookup is known for, and Emo refuses it. Outside class/interface bodies the names stay ordinary (the `foreign`/`init` positional style), so a top-level `def to_string` is fine. Dispatch sites: `println` writes `emo.to_string(value)` plus a newline; interpolation renders each `${...}` part with the same entry; containers render their elements recursively through it. A class without `to_string` keeps its structure dump (`#Point(x: 1, y: 2)`, strings quoted inside) as a defined default — never an error — and the rule "byte-identical on every target" is what unifies today's drift (the `c` target prints `#main.Point(...)`, the interpreter `#Point(...)`). `printf("%s", ...)` stays `String`-only and `+` never concatenates a non-`String`: rendering joins are interpolation's job. `==` is not a protocol (equality is structural by language rule, nothing to override), and the registry dispatches methods, never operators — no `emo.equals`, no arithmetic hooks (a domain type spells `v.plus(w)`), no truthiness conversion, no missing-method hooks, no second rendering entry beside `to_string`, no custom `case` matchers; Comparable-style ordering interfaces and iterator protocols (`each`/`iter`-family) are rejected outright. Entry governance is two questions, both required: the method is load-bearing in the language surface (a construct dispatches on it — `to_string` ← `println`/interpolation/containers — or the builtins carry it as the canonical shared name — `length` ← the six builtin collections), and the contract is closed (checkable exactly at the definition and the call; `emo.map(x, fn)` fails this — the `fn`↔elements relation is unstatable without generics, and every use would be an explicit call where `x.map(fn)` is already the direct form; collection operations, if they come, are the collection types' own methods). The registry is the language's reserved set, grown by design decision only — generic programming over shapes is what interfaces are for. Implementation note the registry makes load-bearing: the builtin-name traps recorded above (`to_bytes`, T45.3; `Pack.length` → `count`, T45.5) are exactly protocol-shaped collisions — a class method named like a builtin must reach the class's vtable whatever the name — and the fix landed first (2026-10-21): `method_call` on `wasm` and `beam` dispatches instance-first for every builtin-named arm, golden in `examples/builtin_names`. **Implemented 2026-10-21, the whole registry:** `emo.f(x, rest...)` lowers in the parser into the method call `x.f(rest...)` (E2028 on the keyword's other uses; E4025/E5105 refuse a package binding as `emo`); rendering answers a class's own `to_string` before the structure dump on the interpreter and every hosted target — the dump itself unified to the interpreter's form, entry module bare (`examples/to_string_render`); the typescript target keeps its scheduler turn order by rendering synchronously unless a protocol value is on the path; and the contracts are enforced where the names are defined — `def to_string`/`def length` with another signature in a class or interface body is E4026, with a near-miss hint on E4001 (`did you mean \`lenght\`?`). Design doc: `docs/protocols.md` (zh-CN mirror alongside).
- A receive branch could not read a module-level const on `wasm`: **found and fixed 2026-10-25 (T1.5).** A module const lowers to a memoized zero-arg thunk, and a read inside a receive branch lowers as a `Var` the receive handler could not resolve — the handler is a hidden function with a fresh local map, and `captured_bindings` captures only enclosing locals, which a module const never becomes; every other target answered the same program correctly, and `wasm` died at lowering with an internal `failwith`. **Fixed in the `Var` arm's resolution**: after the binders and the locals, a read of a name whose const thunk exists (the mangled name in `env.consts`) emits the thunk's call — the handler reads the same memoized value the binding holds, with no capture machinery and no park-payload change. The receive-branch shape the atomic goldens use (a branch reading an entry const) now builds and runs on `wasm` byte-for-byte with the other five targets.
- The atomic memory model: **settled (2026-10-25) — `Atomic` in `core` as Box's synchronized sibling, sequential consistency only; `peek`/`poke` volatile by definition; `fence()` the one barrier.** Design note: `docs/atomics.md` (zh-CN mirror alongside); the demand comes from EmoOS S1 — an interrupt body and the thread code it interrupts share one address space on metal, and a read-modify-write built from `peek` and `poke` cannot survive an interrupt firing between them. **The atomic semantics.** `Atomic[Int64]` and `Atomic[Bool]` are the two payload spellings that check; everything else refuses by name at check time (`Float64` has no honest lock-free read-modify-write across targets, and non-scalars — strings, containers, boxes, a nested `Atomic` — are not cells). The ops are `load`/`store`/`exchange`/`compare_exchange`/the `fetch_*` family, plus `fence()` as a free function; every read-modify-write returns the value the cell held **before** the operation, `compare_exchange` returns the pair `(Bool, previous)` — `(Bool, Int64)` on an `Int64` cell, `(Bool, Bool)` on a `Bool` cell — with a mismatch a value and not an error, and `fetch_add`/`fetch_sub` refuse on `Bool` (arithmetic is not Bool's vocabulary). Arithmetic wraps by the `Int64` rule; `==` compares the cells' current values, each operand read as an atomic load. **Copying an `Atomic` copies the handle and shares the cell** — the `Pid` precedent, and the one declared exception to "mutability never crosses a process boundary": on the BEAM a shared cell cannot be un-shared (the runtime's atomic array is reached through a reference; a reference copied is a cell shared), so a snapshot rule would be one target silently breaking the rule, while handle-sharing is uniform and synchronized by construction. **The lowering is per-target honest** — the matrix lives in the design note: interp/`ts`/`wasm` exact no-ops (cooperative single contexts, sequential consistency holds vacuously, refusals still check); `c` the `__atomic` builtins at sequential consistency; `ocaml` its `Atomic` module, the bitwise family as compare-and-set loops; `beam` the runtime's `atomics` array, **superseding the one-line `counters` choice recorded in the EmoOS README the same day** — `counters`' read-modify-write reports only `ok` and returns no previous value, while `atomics` is documented sequentially consistent, signed 64-bit wrapping at 2⁶⁴ (the `Int64` rule), serves the pair contract natively, and recovers the previous value exactly under the wrap rule (`add_get`/`sub_get`, `previous = new − v`); `riscv64` is the real one — `amoswap.d.aqrl` for `store`/`exchange`, the fence-bracketed `ld` for `load`, LR/SC (`lr.d.aqrl`/`sc.d.rl`) for `compare_exchange` and, while the cell's word is a boxed value, for the `fetch_*` family too (the AMO arithmetic is Stage B's direct form), `fence rw, rw` for `fence()` — as runtime helpers in the generated image (landed 2026-10-25, T1.6; see the riscv64 value-model entry below). **`peek`/`poke` are volatile by definition** — never elided, never reordered against each other; the UART status loop is the classic victim of an optimizer without the rule — and **`fence()` is a free function in `core`**, a full sequential-consistency barrier over ordinary and volatile accesses alike; it cannot make a `peek`-then-`poke` pair atomic — nothing does, and raw-memory read-modify-write is not a construct. **Unsynchronized cross-context sharing of a `Box` field is undefined**: an interrupt body against the thread it interrupted on metal today, SMP harts when unparked, any future simultaneous context — named, not hidden; ordinary field access never pays a hidden synchronization toll, and the fixes are the ones the note provides (an `Atomic` cell, `peek`/`poke` with `fence()` and the single-writer ring discipline). The surface lands with T1.3, the lowerings with T1.4–T1.6, the goldens with T1.7 of the EmoOS tracker.
- The `riscv64` value model's tag width: **settled (2026-10-25, T1.6) — five-bit tags over 32-byte-aligned blocks; numeric literals are static `.rodata` cells.** The four-bit tag (16-byte blocks) had all eight pointer kinds taken — Int64, Float64, String, Tuple, Array, Box, Closure, Instance — so `Atomic` was the first kind with no seat, and `Bytes`, `List`, `Map`, and `Pid` are queued behind it for the kernel steps. The rejected alternative was a kind carried in the header word for the overflow kinds (an `Atomic` as a Box whose header says "synchronized"): two sources of truth for one question, and every Box path growing a header test to stay honest. The tag widened instead — `Atomic` is kind 8 (tag 16), seven seats remain — at the price of 32-byte blocks, which halves the heap's density for the one-word cells and surfaced at once: `examples/fib`'s `count_down(1000000)` boxed three Int64 per iteration (two literals and the result) and exhausted the 64 MiB heap at the new size. The literals were the waste, not the width: an Int64 or Float64 cell is immutable, so a literal is now one static read-only cell in `.rodata` (`[header][bits]`, 32-byte aligned, one per distinct value) and an evaluation is its address — the heap holds computed values only, the loop allocates one cell per iteration, and every existing riscv64 golden is byte-identical. Stage B (S2) is the real cure for per-operation boxing; this is the honest floor until it lands.
- The atomic goldens (EmoOS T1.7): **four findings, two fixed (2026-10-25).** The cross-target corpus `examples/atomic_cell` (every target, QEMU included) and the refusal goldens (`test/emo_cli`'s `atomic_refusal`: fifteen payloads in the type position, fourteen at the constructor, the op-level refusals, on all six compiled targets) met these on the way to green. (1) **`beam`'s Int64 wrap did not wrap below the minimum — fixed.** `emo_mask` was `((v + 2⁶³) rem 2⁶⁴) − 2⁶³`, and Erlang's `rem` keeps the dividend's sign, so an overflow above the maximum wrapped while an underflow stayed a bignum: `min - 1` answered `-9223372036854775809` — an integer outside Int64 — on `beam` alone, through every `+`, `-`, bitwise, and shift on the target (all share the mask), and the atomic `fetch_sub` at the minimum then fed that bignum to `atomics:compare_exchange` and died with `badarg`. The mask is now the low 64 bits (`band`, two's complement at any width) read back as signed. (2) **`typescript`'s `EAtomic` had no `to_string` arm and no wrap — fixed.** `println(cell)` rendered `<atomic>` while `cell.to_string()` on an open receiver (a class field) threw `NoMethodError`, and `fetch_add`/`fetch_sub` were raw bigint arithmetic; both now follow the Int64 rule in `ts_core.ts`. (3) **A program whose artifact stem is an OTP module name cannot run on `beam` — dodged by naming.** The corpus was first named `atomics`: the `-o` stem is the module atom, OTP's own `atomics` module is preloaded, and `atomics:main()` is `undef`. The same holds for `lists`, `maps`, `string`, and every other OTP module; the beam build could refuse such stems loudly, which is recorded here and not done. (4) **`Atomic.new(Bytes.new(4))` checks clean — found, not fixed.** `Bytes.new` has no constructor rule (List, Box, Map, Exception, and Atomic have one), so its result is `Unknown`, and the payload scope admits Unknown by design. Typing it `Bytes` is one rule, but the Bytes method rules accept exactly `Int64` arguments — an `Unknown` index is E4004 — so every `Bytes.new` receiver in the registry indexing by a field or a dynamic value would start failing; the Unknown-tolerant pass over those rules comes first. The type-position refusal (`Atomic[Bytes]`) is pinned; the constructor form stays out of the golden until the rule lands.
- Raw memory access: **settled (2026-10-25) — `peek8`/`poke8`/`peek64`/`poke64` in `core` as free functions, freestanding-only; the byte lane rides `Byte`.** Design note: `docs/raw-memory.md` (zh-CN mirror alongside). The surface: `peek8(addr : Int64) : Byte` (a volatile byte load, read unsigned 0–255 — the MMIO-natural reading), `poke8(addr, b : Byte) : Void`, `peek64(addr) : Int64`, `poke64(addr, v : Int64) : Void`. **The width rides the payload type** — `Byte` is the language's existing unsigned 8-bit primitive (mod-256 wrap arithmetic, `Byte.from_int64` range-checked loud / `Int64.to_byte` low-eight-bits / `Byte.to_int64` widening, all pre-existing on every hosted target), so the zero-extension and silent-truncation questions the design discussion opened with have no room to exist: the value that crosses is the value that fits, and no new type was added — a proposal to add `Int8`/`Int16` was weighed and declined the same day (an `Int8` would stand beside `Byte` as a second, signed 8-bit vocabulary, and no roadmap consumer names either). The width set is deliberately `{8, 64}`: the 32-bit lane waits for `Int32` (surface already settled in `docs/numeric-width.md` — `peek32 : Int32` / `poke32(addr, v : Int32)` is its honest shape, first consumer virtio MMIO, EmoOS T7.1), and a 16-bit lane has no consumer. **`poke` answers `Void`** — a raw-memory read-modify-write is not a construct (the atomics entry's rule), and answering the previous value would invite the non-atomic pattern; the synchronized form is an `Atomic` cell. **The admission principle: a target admits `peek`/`poke` iff the program owns the address space** — `riscv64` admits (the volatile helpers `lbu`/`ld`/`sb`/`sd` in the generated image, emitted in program order), the six hosted targets refuse by name at check time (E4028, at the reference site): the atomics no-op precedent does not carry (an atomic no-op is exact because nothing runs concurrently; a peek no-op must invent a value — a silent fallback), a hosted program owns no address (the runtime's heap belongs to the host, and there is no in-language way to obtain one), the rare hosted case that needs raw C has `foreign def`, and the dual-run harness's interface seam is *enforced* by the refusal rather than trusted to discipline. **Address semantics**: exactly what the hardware sees, `Int64`, nothing validated — a bad address **traps** (the firmware's reset before the kernel installs `stvec`, the kernel's trap path after EmoOS M2), named as the machine's defined behavior rather than waved off as undefined; natural alignment and little-endian are the caller's discipline, no checks and no byteswap construct. **The riscv64 value model gains the `Byte` immediate** (immediate kind 3 in bits 3:1, the byte in bits 11:4) — literals, in-type arithmetic wrapping mod 256, comparisons, `to_string`, and the three conversions, the semantics every hosted target already runs; two named gaps stay: a `Byte` inside an `Unknown`-typed arithmetic operand fails loudly on riscv64 (the dynamic-operand helpers refuse it), and `Bytes` buffers remain refused on the target. The scheduled cost, not a gap: each `peek` allocates a boxed cell until Stage B (EmoOS T2.3 unboxes the lanes) — polling loops stay out of the goldens until then. **Landed 2026-10-26 (EmoOS T1.8)**; the QEMU golden (`examples/peek_poke`: RAM roundtrips on both widths, the little-endian byte picture, the full Byte arithmetic family, and the 16550's line-status register read byte-wide — 0x60, the reset value) and the per-hosted-target refusal goldens (`test/emo_cli`'s `peek_refusal`, five targets E4028 by name plus riscv64 checking clean) pin it. **Two divergences found on the way, recorded and not fixed.** (1) The `c` target's `Byte.from_int64` silently masks to the low eight bits (`(uint8_t)(x & 255)`) where the interpreter — and now riscv64 — range-check 0–255 loudly (E3004): the strictness-first answer is the checked one, and the `c` emitter should take it when the Byte surface next gets a pass. (2) The IR loses the static type of two receiver shapes — a builtin type-level method's *result* (`Byte.from_int64(7).to_int64()`) and a *module-level `const`* read (`const b = ...; b.to_int64()`) — so on riscv64 both fall to the dynamic dispatch, which answers only `to_string` on a Byte immediate and fails loudly ("no such method on this value"); parameters, locals, and ordinary expressions carry their types, so binding before calling is the shape that works, and the same type loss is why Atomic's cell keeps a dynamic method table (`emo_atomic_mtbl`).
- The riscv64 typed calling convention (EmoOS T2.1, Stage B's first half): **settled and landed (2026-10-26) — a fully typed top-level `def` takes raw-register params and results; the boxing adapters stand at every typed↔dynamic boundary.** The convention: `Int64` crosses as the raw payload in the integer bank (`a0..a7`), `Float64` as the raw bits in the float bank (`fa0..fa7`) — the psABI's two independent banks, each counting from zero — every other statically known type crosses as the tagged word both conventions already share (Bool/Char/Byte/enum immediates and String/container/instance pointers are representation-identical, so their "adapter" is the identity), `Void` answers nothing, and a result crosses raw in `a0` (`Int64`) or `fa0` (`Float64`); an `Unknown` param or result keeps the whole def on the dynamic convention. **The scope is top-level defs** — methods, constructors, and closures stay dynamic: the runtime's by-name dispatch (`emo_dyn_method`, the interface tables) passes tagged words and cannot know a signature, so a typed method would corrupt through every dynamic path; extending the convention there wants trampolines and is its own later task, while a def on riscv64 is only ever reached by a direct call (first-class function references refuse on the target), so its convention is closed under its call sites. **The adapters, while bodies still emit dynamic (T2.2 unboxes them):** the callee's entry spills every raw param to its slot and then boxes each `Int64`/`Float64` param in place for the dynamic body (after the closure-record spill — the boxing calls clobber the argument registers), its exit unboxes the tagged result at the return label, and a call site unboxes its raw args into their bank registers and boxes a raw result back — a pessimisation by design, the scaffolding T2.2 melts. **The tail-call rule:** a return-position call lowers to `tail` only when the callee's result representation equals this function's own (tagged↔tagged, raw↔same raw; `Void` and the tagged word agree because nobody reads the register) — the tail path bypasses the return label, so no adapter could convert a mismatch; a disagreeing pair takes the plain call and lets this function's own exit adapter do the work, which also covers a method tail-calling a typed def and a typed body returning a dynamic call's result. **A const thunk adopts its signature's convention with the memo slot holding the raw result** (store-side unbox, hit-side load — `fmv.d.x` for a Float64), every reader being a call site keyed on the thunk's signature. **The value heap grew 64 → 96 MiB for the T2.1→T2.2 window**: the boundary adapters allocate (an entry box per numeric param, a box per consumed result), and `examples/fib`'s `count_down(1000000)` rides ~61 MiB of them on top of fib's own ~3 MiB — past the old end and exactly the kind of silent-death the bump avoids; the heap is .bss NOBITS so the image does not grow, QEMU virt's default 128 MiB still holds it with 20 MiB to spare, and the `peek_poke` playground at `0x87000000` stays above the new end. **Goldens:** the new `examples/typed_calls` (bank-interleaved int/float params, the 100k-deep typed tail chain, Int64 wrap at both bounds, Bool/Byte/String tagged params, a Void result, the const memo's store and hit, method and closure calls living beside the convention) answers byte-for-byte on the interpreter, `c`, `wasm`, `beam`, and `riscv64` under QEMU, and all nine prior riscv64 QEMU goldens stay byte-identical. One corpus accommodation, not a fix: `${tag}` of a `Byte` widens through `.to_int64()` because the `c` target has no Byte-in-string form yet (the same output on every target either way).
- The riscv64 native body (EmoOS T2.2, Stage B's escape-point half): **settled and landed (2026-10-26) — a fully typed def computes unboxed; a value boxes only where it escapes.** The representation rule is per-expression, keyed on the checker's static type: an `Int64` expression yields the raw payload in `a0`, a `Float64` expression the raw bits in `fa0`, every other type the tagged word both conventions already pass — and the rule is universal inside a native body, so consumers may trust it. The producers: integer and float literals (`li`, the read-only cell's bits through `fmv.d.x`), raw locals, the arithmetic/comparison/conversion paths with their final boxes stripped (`emit_binary`/`emit_unary`/the int and float pairs take a `~boxed` flag; the pairs become plain moves), typed-def calls (spill and fill are raw moves — the T2.1 boundary disappears), and `Var` reads — which unbox on read when the local holds a tagged word, keeping the rule honest for the one binding kind that stores tagged (below). **The escape points, and only these, box**: container elements (`Tuple`/`Array` literals), `Set_field` values, closure captures (the record holds tagged words), interpolation parts and `println`'s argument, every dynamic callee's arguments — method calls (the runtime's by-name dispatch, the interface tables, and the direct class-method call all keep the dynamic convention per T2.1), calls to dynamic-signature defs, first-class block calls — plus `Box`/`Atomic` payloads and a `case` scrutinee (the pattern tests read the tagged word). The reverse crossing: a dynamic producer's result unboxes keyed on the expression's static type (method results, dynamic-def results, `peek64`'s helper cell until T2.3 inlines the load). **The case-binding discipline** — the one real bug the stress corpus caught: a pattern binding copies the boxed scrutinee word into its slot, so the name must leave the raw set (`frame.raw`, the typed params and numeric `var`/`let` bindings) and its reads unbox; the first cut read the binding raw and interpolated a pointer. **Scope**: only fully typed top-level defs go native (`conv_of`, the T2.1 gate); methods, constructors, closures, and dynamic-signature defs emit exactly as before — the dynamic world's code is unchanged byte for byte. **Found on the way, recorded and not fixed**: the IR's `decl_type` maps `Byte` and every applied annotation (`Array[Int64]`, `Box[Int64]`, class and interface names) to `Unknown`, so defs with such signatures stay on the dynamic convention — correct (the dynamic fallback decodes what arrives), just not native; enriching `decl_type` changes what all six backends read from `fparams`/`fresult` (the ocaml wrapper's `unbox_<type>` family, the c FFI stubs' marshaling) and is its own task with its own goldens. **The value heap stays at 96 MiB**: the T2.1→T2.2 window closed — `examples/fib`'s `count_down(1000000)` now recurses allocation-free, and `add`'s body fell from 24 instructions with 3 heap calls to 15 with none — but dynamic bodies still box per operation, the bump's exhaustion is loud, and QEMU virt's 128 MiB holds the headroom. Every prior riscv64 QEMU golden stayed byte-identical; the native-body stress corpus (while/for loops, array indexing, string building, case with bindings, float loops) runs interpreter-identical under QEMU.
- The riscv64 unboxed raw-memory lanes (EmoOS T2.3): **settled and landed (2026-10-26) — in a typed body each `peek`/`poke` is its one inline volatile instruction; an MMIO read allocates nothing.** In a native body the address is already the raw `Int64` (the representation rule), so the four builtins lower to exactly `lbu`/`ld`/`sb`/`sd` at `0(a0)` — a `peek64` answers the raw payload, a `peek8` re-encodes the byte as the immediate, a `poke` decodes its Byte operand with the shift or moves its raw `Int64` — no helper call, nothing on the heap, and volatile ordering kept by construction: one instruction per access, emitted in program order, in a backend with no optimizer. Dynamic bodies keep the runtime helpers — their tagged world must box every answer regardless, so nothing changes for the dynamic corpus. The pin is load-bearing: `examples/peek_poke`'s typed `burn` def reads one byte four million times — at 32 bytes a read that is 128 MiB, past the 96 MiB heap and its loud exhaustion — and prints the checksum, with a native `peek64` roundtrip beside it. This closes the scheduled cost the raw-memory note named at T1.8 ("a polling loop is a heap burner until Stage B"): the kernel's polling loops burn registers now, not heap.
- Step 2 close-out (EmoOS T2.4): **re-verified and recorded (2026-10-26) — every riscv64 QEMU golden byte-identical through T2.1–T2.3, and the hot-loop count is in the step trail.** The full `dune runtest` suite ran green after each of the three tasks; the count comes from real images, the same `count_down(n Int64) Int64` program built by the T1.8 compiler and by this one: 43 → 33 instructions in the function, and per call level one `emo_box_i64` heap call and one 32-byte cell → zero of both. The honest caveat the trail records: a tail-call-heavy function's dynamic form was already lean, so the instruction ratio (1.3×) is smaller than `add`'s (24 → 15 with 3 heap calls → 0, with T2.2) — allocation elimination, not a uniform speedup number, is what Stage B's first step delivers, and there it is total. With T2.1–T2.4 checked, S2 is complete: typed bodies keep `Int64` in registers, boxing happens only at escape points, and an MMIO read allocates nothing.
- Package-carried native sources for `riscv64` (EmoOS T3.1): **settled and implemented (2026-10-26) — a package's `.S` sources assemble into the image, and its `runtime.S` and `link.ld` own the image's boot stub and linker script; the default runtime stays for ordinary programs.** The shape follows the c target's package-carried native code (2026-10-12) — the tree is the package, sources auto-collected, no manifest field names files, and the manifest stays data. A file named `runtime.S` is the package's boot stub and a file named `link.ld` its linker script, by base name alone wherever the tree puts them; every other `.S` in the tree is an image source, and `.S`/`.ld` join the published-and-checksummed file set beside the modules. The two components are independent and each optional — a package keeps whichever defaults it does not provide — and **at most one package provides each**: two providers cannot both own the image, so the merge refuses with E5013 naming both (two candidates inside one tree are the same refusal at the source). The root package's own tree participates — the kernel package is a root, and its `.S` sources, stub, and script live beside its modules — while the hosted commands (check, run, test) load dependencies without the native gate and stay indifferent to the tree's native files. **The honesty gate now has two shapes**: the C sources, `link`, `frameworks`, and `pkg_config` modules are honored by the c target alone; the `.S` sources and the image components by the riscv64 target alone — any other target refuses the build outright (E5007, naming the packages) rather than dropping the inputs silently, in both directions (a C-carrying package on riscv64 refuses too). **What the package's stub replaces is exactly the entry discipline**: the compiler's `runtime_asm` splits into the boot stub (`emo_start` … `emo_park`, arch attribute always emitted first) and the runtime body — allocator, boxing, atomics, dispatch, formatting — which stays; the generated code and the package's stub both call into it, and `emo_program` is global now so a stub in its own object reaches it. The build assembles the package sources as one unit — stub first, then plain sources — and links the package's object before the program's, because OpenSBI enters at the image's load address, not the ELF entry: the boot stub must open `.text`. Goldens: `examples/native_image` boots the package-owned image under QEMU — the stub's magic, the plain source's data word read through a pointer the stub parked, and an absolute symbol only the package's linker script defines, all three values in the expected output; the unit suite pins per-tree collection (root and dependency), the two-directional target refusals, and the two-provider conflict; every prior riscv64 QEMU golden stays byte-identical on the default path.
- The kernel's `core` layering, enforced (EmoOS T3.2): **settled and implemented (2026-10-26) — on the riscv64 target a standard-library require refuses at check time; the kernel builds on `core` alone.** The rule was decided with the freestanding target (step 19: "`core` is the only library layer kernel code may use"); T3.2 makes it loud instead of latent. The gate sits at the front of the build's resolution — before the pin gate and the fetch — so a stdlib require on a kernel program answers the layering error (E5014, at the require's own site: "`json` reaches the standard library: the riscv64 target is the kernel's, and its only library layer is `core`") whether or not the manifest pins it, preempting E5006 and the target gate with the earlier, honest answer. The name is a stdlib package by the bundled registry's own judgment, so a typo'd unscoped require keeps its E5009 — the layering message never claims a name the standard library does not publish. Scoped requires stay legal: a kernel service is an ordinary package that declares the riscv64 target, resolved and checked like any dependency. The rename rode along: the kernel package's manifest is `emo_os` (the flat name both READMEs already carried) — a manifest name is plain data and parses as-is, while the registry's owner/name rule lives only in the publish path, which is exactly right for a package that never publishes; `emo build` and `emo emoji build` both verified against the renamed manifest.
- Processes on metal (EmoOS T3.3): **implemented (2026-10-26) — `spawn`/`send`/`receive` unblocked on `riscv64`: green threads on the boot hart, the context switch as the callee-saved swap plus `sp` in the emitted `.S`, per-process stacks from `.bss`, copy-on-send mailboxes, Pid as pointer kind 9 (tag 18).** The scheduling discipline matches the hosted reference: spawn does not yield; send snapshots the message (the copy-on-send boundary — `emo_copy_deep`: Box/tuple/array/instance fresh, Atomic shares the cell, Int64/Float64/String/closure/Pid as-is), wakes a parked receiver, and yields the sender; receive scans the mailbox oldest-first, dequeues the first message its patterns accept (guards included; a non-matching message stays queued), and parks on no match; the root exiting ends the program; a switch with nobody runnable is the loud deadlock ("all processes are blocked"). The spawn delivers its evaluated arguments on the child's fresh stack through a per-site entry thunk (the psABI registers for a typed def, the dynamic words for a first-class block), and a returning body lands on `emo_process_done`. Slots (64) never return to free — pids are unique for the whole run — so a send to a dead pid is dropped, never redirected; the process-table ceiling (64) and the per-process mailbox (32 words, full = loud) are the documented bounds. The receive's scan index rides `s0` (every helper is ABI-clean; the switch saves the callee-saved set). `Pid ==` is identity, `to_string` renders `<pid N>`, `self_pid()` is a runtime helper. The deep copy's element loop walks block words `2..header` (the elements sit after the length word), one past the payload-word count the header carries — `copy_deep` now bounds at `header + 1`, so the last element is copied and the fresh block wears the original's tag; the first cut stopped one word short, and a tuple message across the wake-and-rescan path failed the post-wake pattern match (int/Box/string messages through the identical path passed because their copies ride the as-is or Box paths). The golden (`examples/processes`) pins the working surface: int messages, a Box message, a tuple message with both elements bound, a guarded fan-in with a non-matching message left queued, a send to a dead pid dropped, `self_pid`, and pid printing — byte-identical under QEMU.
- The scheduler's policy fields and the send-time donation (EmoOS T3.4): **implemented (2026-10-26) — dispatch stays round-robin; every slot holds the process's own priority, its effective priority, and its CPU quota; a message carries its sender's effective priority, and a process's effective priority is the maximum of its own and what its queued messages carry.** The decisions, in order. **Round-robin dispatch is kept** — the run queue is the FIFO ring and `emo_schedule` pops its head; priority-ordered dispatch lands together with the first setter of a priority, because either one alone is unobservable (a pick that consults all-zero priorities is the FIFO pick, and a setter nobody dispatches on is a number in a table). **The effective priority is derived, never stored as a residue**: the mailbox is two rings — the message word and the priority it carries, the sender's *effective* priority at the send (so a relay passes a donation on) — and the effective priority is raised at enqueue (the donation, in `emo_send`: the target rises to the sender when the sender outranks it) and re-formed at dequeue (`emo_mb_remove` shifts both rings together and recomputes own ⊔ the carried priorities that remain); a parked receiver keeps the donation its unmatched messages carry, because the work is still owed. This is the asynchronous form of the README's "the maximum of its own and the priorities of the processes waiting on it" — in Emo's model a send never blocks and a receive waits on no one in particular, so the only edges the graph has today are the queued messages, and the slot table (state words and rings) *is* the wait graph the scheduler holds; the synchronous edge — a process blocked on one specific process — arrives with the synchronous kernel call (T4.2), which adds the waiting-on word and the transitive propagation along it (no word is laid down now: no primitive would write it). **Inheritance at spawn**: a child takes its spawner's own priority and quota; its effective starts at its own (an empty mailbox). **Priorities compare signed**, a larger number ranking higher. **The quota is the CPU slice budget in ticks**, 0 the unassigned value; the tick (T3.6) consumes it and fixes its meaning. **The hosted reference (`emo_sched_det`) has no priorities** — this is kernel-side structure the hosted scheduler never needs, and the dual-run harness (T3.8) compares program output, which dormant fields never touch. Everything is dormant by construction: no surface sets a priority, so every one is 0 and the dispatch reads none of them — all twelve riscv64 QEMU goldens stay byte-identical. The pins: `examples/processes` grew six carriers into one mailbox pulled out in a scrambled order, so every dequeue lands on a different ring position and shifts both rings; a 60-process scratch corpus (30 scrambled ints, 15 tuples, 15 boxes — 61 of the 64 slots) ran interpreter-identical under QEMU; and the dormant chain was exercised live under gdb against the golden's image with priorities injected into the slots — inheritance (own 3, quota 11 onto the first child), the carry and the donation (a child's effective 7 in the root's ring, the root 3 → 7), and the re-forming at dequeue (back to 3) — with the serial output unchanged.

- The console leaves the firmware (EmoOS T3.5): **implemented (2026-10-26) — the 16550A at `0x10000000` is driven by ordinary Emo over the raw `peek`/`poke` lanes, and the runtime's print path routes through a one-word console hook that the kernel's boot stub parks the driver's entry in; SBI keeps poweroff and nothing else.** The decisions, in order. **The driver is Emo, not assembly** — the kernel's device code is exactly the code the language is for, and the driver reads like it: `uart_init` (interrupts off until the tick of T3.6, divisor, 8N1, FIFOs enabled and cleared), `console_put_byte` polling the line-status register's transmitter-empty bit and writing the transmit holding register byte-wide, `console_read_byte` polling data-ready and reading the receive buffer. Both polling loops are fully typed defs, so their bodies are native (T2.2/T2.3): one inline volatile load per poll step, one store per byte, **zero allocation on the console path** — a printed string boxes once at the `println` boundary and not per byte. **The indirection is one word, not a driver interface**: `emo_console_hook` in `.bss`, zero until a stub writes it; `emo_console_emit` tail-calls the hook with the raw byte in `a0` — the psABI discipline, the hook being the raw entry of a fully typed def — and answers the legacy SBI putchar ecall when the hook is zero. **The default stays SBI**: the compiler's boot stub never touches the hook, so ordinary programs and every existing golden are untouched; a kernel package opts in by owning its boot stub (T3.1) and parking the entry after the `.bss` clear (the hook word lives in `.bss`, so the order is clear-then-park). **Top-level defs are `.globl` now** — the stub reaches `console_put_byte` by its module-prefixed label across object files, and T3.6's trap shim will reach its handler the same way; the labels are module-prefixed, so the global binding collides with nothing. **The newline and the failure path ride the hook too** — `emo_println`'s newline byte and `emo_fail`'s announce go through `emo_console_emit`, so a kernel panic prints through the same UART. **SBI keeps exactly one duty**: the legacy shutdown ecall in the stub and in `emo_fail`. The pins: the kernel's `run.sh` counts exactly one `supervisor_ecall` for the whole boot under `-d int` (the poweroff — `println` made zero, against twelve on the SBI path for the same greeting), the kernel echoes a line fed after boot (the read lane; OpenSBI's boot takes the UART first, so input written before the payload polls never arrives — the harness writes only after the greeting is on the wire), and QEMU exits on its own — the SBI poweroff still ends the machine. All twelve riscv64 QEMU goldens stay byte-identical on the default path.

- Traps and the tick (EmoOS T3.6): **implemented (2026-10-27) — the kernel package owns its trap machinery (`trap.S` beside the stub, plus its own `link.ld`), the timer transport is probed by attempting the capability, and the tick runs the ISR discipline: no allocation by construction, a preallocated ring, ack + enqueue + the scheduler's wake.** The decisions, in order. **The frame makes preemption a context switch**: the shim lays 544 bytes on the interrupted process's own stack, the top 208 shaped exactly like the scheduler's context frame (ra, s0–s11, fs0–fs11, the spare word), the rest below it — so `emo_sched_preempt` points the victim's slot at the frame's switch section, swaps its ra slot for the resume stub (parked by the boot stub into the runtime's `emo_trap_resume_hook`, the T3.5 hook pattern), re-queues the victim, and jumps into the scheduler's pick; the resume reads the rest of the frame through negative offsets once the scheduler's pop has brought sp back to the interrupted value — the arithmetic closes exactly (the landing sp is `X + 208`). Everything round-trips: all general and floating registers, `sstatus`, `sepc`, and `scause`. **The timer transport is probed by attempting it**: Sstc is an ISA delegation, not an SBI extension, so nothing can be asked — the first `stimecmp` write either works or traps as an illegal instruction, and the shim answers its own probe (the state word to 2, `sepc` + 4, sret; the probing window is the three instructions around the write), with the legacy SBI `set_timer` ecall (a7 = 0) as the fallback transport — chosen per boot, both pinned in `run.sh` (`sstc=false`: one ecall per re-arm; `sstc=true`: exactly one ecall for the whole boot, the poweroff). **The tick's scheduler role is the quota**: the dispatch loads the incoming slot's quota into the runtime's slice countdown, the tick consumes one, a spent slice preempts, and the next dispatch reloads — so the quota is a slice budget per turn, 0 the unassigned value that never preempts, and the dormant field of T3.4 becomes live the moment a quota is set. **The interrupt-safety rule is masking, and the mask is per-region**: every scheduler-state mutation opens with `csrci sstatus, 2` and unmasks on every exit the resumed process flows through — including the park path, whose resume bypasses the parking function and therefore unmasks there — and the switch records the mask in the context frame's spare word, so a process preempted or parked mid-region resumes still masked and unmasks when its own region ends; a timer interrupt can therefore never land inside a scheduler region, and the ISR's helpers (the quota step, the preemption) assume the mask a trap entry already provides. Helpers called only from masked contexts (the run-queue push, the mailbox reads) toggle nothing. **The ring is kernel-owned raw memory at a fixed address** — the package's `link.ld` places the section at 0x87000000, in the free RAM above the heap — and the protocol is single-producer single-consumer: the ISR writes the entry (the tick's sequence number), fences store-store, then advances the producer cursor; a full ring counts a drop and moves on; the kernel's own Emo drains it with `peek`/`poke` like any device. **No allocation in an ISR body holds by construction**: the shim and everything reachable from a trap are assembly over fixed words — `emo_alloc` is not reachable. **The dispatch is `scause`'s and honest about the rest**: the supervisor timer interrupt runs the discipline, and any other trap is the loud failure (the message through the console hook, then SBI poweroff). The pins: the two-boot `run.sh` above, plus the tick proof — a 100M-iteration typed sweep whose exact checksum is the register-file pin under dozens of interleaved traps, the tick-count verdicts, the echo, the self-exit; and the dormant quota chain driven live under gdb against a scratch image — quota 2 injected, the preempt path hit within two ticks, the victim's frame verified in its slot (ra slot = the resume stub, `scause` = 0x8000…005, the spare word carrying the pre-trap SIE, the resume landing at `X + 208`), the preempted sweep finishing with the exact checksum. All twelve riscv64 QEMU goldens stay byte-identical — the compiler's runtime changes (the masked regions, the slice load at dispatch, the two new helpers) alter code, never output, and the trap machinery is armed only by a boot stub that opts in.

- The interrupt-driven console (EmoOS T3.7): **implemented (2026-10-27) — the UART's receive line rides the PLIC into the trap shim, the shim fills a preallocated input ring and wakes the device-waiter, and readers block on ordinary mailboxes; the console process is ordinary Emo.** The decisions, in order. **The wake is a new park state, not a new channel**: `device_wait` — a raw builtin beside the peek/poke lanes, checker-registered on `riscv64` alone and refused by name everywhere else (E4028, the raw-memory admission rule) — parks the caller in state 4, a state only the device world wakes; the ISR's `emo_sched_wake_console` flips the first state-4 slot to alive and re-queues it, and the resume is exactly the call's return. A send does not wake a 4 — a request arriving while the driver sleeps queues in its mailbox for the next pass — so the mailbox stays the only request queue and the ring stays the only byte channel. **The console process is ordinary Emo** — sleep while the ring is empty, then hand each byte to the oldest unread request — and readers block on an ordinary `receive`; no bare-memory rendezvous crosses into Emo. **The input ring is kernel-owned raw memory at a fixed address** (the package's `link.ld` places the 8+8+128-byte section a page above the tick ring), SPSC with the same protocol as the tick ring: the entry, a store fence, then the producer cursor; a full ring leaves the bytes in the UART's FIFO and the line re-raises after the complete — the device's own backpressure, no drops counted. **The ISR discipline is the tick's**: claim through the PLIC, drain, wake, complete — all assembly over fixed words, `emo_alloc` unreachable, run inside the trap's hardware mask. **The PLIC wiring is the kernel's, and OpenSBI's leftover is part of the contract**: priority 1 for IRQ 10, the enable bit in S-mode context 1, and threshold zero for that context — because OpenSBI leaves S-mode contexts' thresholds at 7 (masked) when it hands over; the claim/complete registers are context 1's (`0x0c201004`). **The deadlock detector learned the idle loop**: a switch with nobody runnable now waits in `wfi` when a state-4 waiter exists — the timer and the devices can land, and the pick retries after each — and is still the loud deadlock otherwise; the idle loop zeroes the slice countdown so the tick's quota step sleeps with the hart. **Two latent bugs surfaced and were fixed**: the trap shim had no `.align 2`, so link-time compression could leave `stvec` holding a 2-byte-aligned address — the low bits are the vector mode, and every trap landed in the weeds (the symptom was an illegal-instruction loop inside OpenSBI's own probing, mercifully loud); and the spawn's initial context frame never wrote the spare word that records the mask state, so **every spawned process was born with interrupts masked and never unmasks** — invisible to T3.6 (dormant quotas, nothing observed ticks) and fatal the moment a child needed the timer or the devices; the frame now records SIE-on, the state of a process born outside any scheduler region. **Found, not fixed: `do builtin()` lowers as a spawn** whose "closure" word is the builtin's return value — the spawn thunk then jumps through it, and the wild jump was this task's longest debugging detour (a `jalr` through a parked call's junk result, wearing the disguise of scheduler corruption); the honest form for a statement park is the plain call, which is what the kernel writes, and the `do`-on-a-builtin lowering deserves its own loud refusal. The pins: the two-boot `run.sh` (both timer transports, since the console depends on the trap machinery end to end), the tick proof under interleaved traps, five console deliveries in request order, a feed timed after the reader's request was pending (the console demonstrably slept in `device_wait` before a byte existed), the echo, the self-exit; all twelve riscv64 QEMU goldens byte-identical.
