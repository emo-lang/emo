# CHECK

Pending design decisions — deliberately kept out of the README until they are settled.

- Mixin mechanism: **settled (2026-10-06) — not added.** An `include`-style mixin is inheritance renamed: a single include is single inheritance, multiple includes are multiple inheritance, and both drag in method-resolution order, diamond ambiguity, implicit method provenance, `self` / field coupling, and the fragile-base problem — exactly what the no-inheritance decision rejected. Interfaces with default method bodies are the same trap and are also excluded. Reuse stays with duck-typed functions, composition, and structural interfaces. Delegation is not a separate mechanism either: forwarding to a contained object is ordinary composition code — `def draw() { return self.inner.draw() }` — and gets no construct, keyword, or auto-forwarding, because it expresses nothing the ordinary methods cannot and would only hide method provenance. Struct embedding is the same space under another name: Go's anonymous embedding promotes an inner type's methods and fields into the outer one, which is inheritance in effect — promotion, shadowing, and a depth-based resolution rule together are a hidden method-resolution order — and it leaves the outer type's method set invisible at its declaration. It also amplifies *accidental interface satisfaction*: because Emo's interfaces are structural (satisfaction by shape, no `implements`), a promoted method can make a type satisfy an interface its author never intended, and a later change to the embedded type silently flips that satisfaction. Go's embedding of `sync.Mutex` — which exposes `Lock`/`Unlock` and satisfies `sync.Locker` without the author asking — is the canonical example. Emo's safeguard is that a class's method set is exactly its own `def`s, so satisfaction changes only when its own body changes; the residual coincidental-name hazard is inherent to structural typing and is mitigated by small, clearly named interfaces. The whole inheritance-shaped space — mixin, include, default methods, delegation, embedding — is therefore closed: reuse is duck-typed functions, composition, and structural interfaces, plus plain code.
- Error handling: **settled (2026-10-11) — no catch construct; expected failures are values, violations raise.** Supersedes the 2026-10-06 `begin`/`catch`/`ensure` settle. The deciding evidence is the backends: `interp`/`ocaml`/`ts`/`beam` get host exceptions for free, but `c` needs `setjmp`/`longjmp` plus a drain of the refcount/autorelease state along every unwound frame, wasm's raise is a host `abort` no in-wasm handler can resume from, and `riscv64` refuses `raise` outright — six targets, six stack disciplines, a permanent two-tier language for one construct. The Erlang split takes its place, and Emo already runs its other half (an uncaught exception kills only the offending process, the per-process arena reclaims its memory, supervision is library-level): an **expected failure** — parse errors, IO, network, not-found, anything the data can trigger — is an ordinary value, the call returning `(R.ok, value)` or `(R.error, reason)`, the reason a String carrying the message convention (package prefix: `json: expected array element at byte 3`); a **violation** — a broken contract, a bug — raises and ends the process. `Exception` stays the language's one exception class — no subclasses (Emo has no inheritance), the name reserved against user shadowing — carrying `message` and an optional `data` Map whose role is machine-readable context for crash reports and supervision, never type identity: nothing dispatches on exceptions when nothing catches them, so the `e.is(Timeout)` narrowing idea dies with the catch design. The `raise` operand must be an `Exception` instance (anything else gets its own E-code), and the uncaught report prints non-empty `data` alongside the message. `R { ok, error }` is a built-in enum (root-env binding, the `Exception` precedent) so matching a returned tuple never costs an import; the tag is spelled `R.ok`/`R.error` — a bare lowercase `ok` in a pattern is a binding and would match everything, and atoms (`:ok`) were rejected as a new value type across all targets for what the enum already expresses. The name's one shadow — the R language of statistical computing — is cosmetic: the two never share an artifact (that R lives as the `/usr/bin/R` command, `.R` files, and CRAN; Emo's `R` is a type name always spelled in qualified form — `R.ok`, `(R, String)` — and no Emo command, file extension, or package carries the bare letter), a single-letter identifier inside another language raises no trademark question, and the fingerprint test passes — enum-dot tags over tuples are the Erlang shape, and R has no such syntax (its counterpart concept is the factor). Migration is the follow-up: the eight raising packages (~220 raise sites) and the runtime-backed packages (`os`/`file`/`net`) split per call into tuple returns and keep-raising violations.
- Binding patterns: **settled (2026-10-11)** — `const` and `var` take a full pattern, not just a name: `const (R.ok, body) = file.read(path)`. A pattern that does not match is a runtime error — the same rule as a `case` scrutinee matching no branch — making the assert-match binding (Erlang's `{ok, B} = f(X)`) the expect-success fast path of the tuple convention. No `match` keyword: the construct is a binding, and `case` already owns the pattern vocabulary. Lowered at IR level by desugaring to a one-arm `case` wrapping the rest of the block, so the six backends see only existing nodes; the parser's `const (` form is a hard error today, so the extension breaks no grammar.
- Type layering: **settled (2026-10-11) — three tiers, two promotion criteria, the freestanding target as the accretion stop.** **"Built-in" names what belongs to the language itself** — the spec core's value model, the capability types, `R`, and `Exception` — the mechanisms and types a program uses without importing anything. Two axes are independent of that ownership and must not be read as defining it: **name availability**, because the checker's root environment also carries the runtime implementations the standard library's Emo source calls (`os_read`, `file_write`, `net_connect`) — those are the runtime's implementation of a package, reachable without `require` but never the API, and no document presents them as a surface; and **per-target capability** (the target-capability table — the split already exists: `riscv64` refuses `raise` and refuses `Map` at emit time while the names stay import-free). **Spec core**: the value model the language's own semantics depend on — `Bool`/`Char`/`Int64`/`Byte`/`Float64`/`String`/`Array`/`Tuple`/enum/class/interface, plus `R` (it is an enum); a target that cannot implement the tier is not an Emo target. **Capability builtins**: `Map`/`List`/`Box`/`Bytes`/`Pid`/the connection types/`Exception` — import-free names, gated per target, the tier **frozen** (its status is the checker's inherited type vocabulary, not a precedent; refusing where unimplementable is the tier's normal shape). **Stdlib**: every future type lands there by default. Promotion needs (a) *syntax dependence* — a syntactic construct's own operand type (`Exception` qualifies through `raise`; nothing else does), or (b) *universal dependence plus trivial implementability on every target including freestanding* (`R` qualifies: every failing call returns it, and it lowers to a tagged word). The freestanding target is the standing reason the capability tier stays frozen: each type promoted above the spec core must either be re-implemented in assembly for `riscv64` or publicly refused, fragmenting the language. (The lineage analogue is C's freestanding profile; the wording is Emo's own.) **Revised 2026-10-15 (T49.3): `ArrayBuilder` joins the tier** — recorded as a revision, not a promotion, because it meets neither criterion: no syntactic construct has an `ArrayBuilder` operand, and `riscv64` refuses it by name at emit time (exit 65, the `Map` precedent) rather than implementing it. What it does have is the `List` precedent beside it: a mutable collection belonging to the same closed set the mutability rule names, import-free, gated per target, refused where unimplementable — the tier's normal shape. What made the addition necessary is that the language had no sub-quadratic way to build an array whose length is not known up front (`Array.append` copies the whole array per element), so the choice was a named builtin or a capability the language simply lacked. The freeze stands as policy; this is one recorded exception, paying the same freestanding-refusal cost every tier member already pays.
- Raw strings: **settled (2026-10-06)** — not needed now. There is no regex and no multi-line string requirement, and a raw string hides the escaping that "everything is visibly what it is" wants visible; the escape set stays `\n \r \t \\ \' \"`. Revisit only if regex or text templating lands, and then with a form of Emo's own (not Go backticks or Python triple quotes).
- Numeric literal formats: **settled (2026-10-06)** — hexadecimal `0x`, binary `0b`, and octal `0o` prefixes, plus `_` as a digit separator (`1_000_000`, `0xFFFF_FFFF`); no C-style leading-zero octal and no width suffixes (bare literals stay `Int64`/`Float64`; `Byte` keeps its `B` suffix). Floats gain exponent forms (`1e10`, `1.5e-3`); no hex floats. The prefixes are a shared C-family convention, not one language's signature.
- Numeric width: **settled** — numeric types are width-explicit: `Int64`/`Int32` and `Float64`/`Float32`; defaults are `Int64` and `Float64`; no width-less `Int`/`Float` spellings; bare literals default to the 64-bit type (decided 2026-10-05 — README, Type System; rationale in `docs/numeric-width.md`). The last open sub-item **settled (2026-10-11): the `ocaml` backend's route is boxed `Int64` — already the shipped route.** The dynamic layer carries `Int64 of int64` and arithmetic emits boxed `Int64.add`-style operations, so 64-bit wrap-around semantics are correct there today; the unboxed two-word hi/lo emulation was never taken (its RV32 motivation is moot — the freestanding target is `riscv64`, with native 64-bit registers), and the `c` target — the default since step 24 — supersedes the performance question, as the step-23 entry above records. The mechanical `Int` → `Int64` / `Float` → `Float64` rename across checker/stdlib/examples/docs has landed.
- Float math and conversion primitives: **settled** — `Float64.sqrt`/`floor`/`ceil`/`trunc`, `Float64.to_int64` (truncating toward zero), and `Int64.to_float64` joined the core surface (decided 2026-10-06); the first consumer is the wasm interpreter (step 22), which needed them for the float families. `nearest` (round-half-to-even) is built in Emo from `floor`. The TS / wasm / BEAM backends do not yet emit these; a target that cannot honor one fails loudly, per the `foreign def` rule.
- Int32 / Float32: explicitly-named fixed-width types for FFI (`int32_t` / C `float`), bare-metal MMIO/device registers, and RV32 hot loops. **Surface settled (2026-10-06)**: explicit-only conversions named with the existing pattern (`Int32.from_int64(x)` / `x.to_int32()`, `Float32.from_float64(x)` / `x.to_float32()`); no implicit conversions and no mixed arithmetic; `Int32` wraps modulo 2³², `Float32` rounds per operation to binary32; no width suffixes (bare literals stay `Int64`/`Float64`). See `docs/numeric-width.md`.
- `foreign def` on non-native targets: **settled (2026-10-06)** — every target that cannot honor `foreign def` refuses it loudly at check time with a clear diagnostic, driven by a target-capability table (today only the OCaml-emitting native backend can honor it; the future `c` backend will too; `wasm`, `typescript`, `beam`, and the freestanding `riscv64` until C interop lands all refuse). Per-target availability is also declared through the manifest's `targets` mechanism, so a package is rejected at resolution. This gates any FFI deepening.
- C FFI binding-surface syntax: **settled in step 14** — `foreign def name(params) Ret = "c_symbol"`. The capability table moved with the targets (2026-10-10): the `c` target calls the symbol directly (step 23) and honors `Int64` parameters plus `Void` returns — the shape of a fire-and-forget call, and every externally linkable declaration lands in `.emo-build/emo_defs.h` for shims to compile against; the OCaml-emitting backend wraps `Float64`/`String`/`Bool` through generated C stubs (see `docs/c-backend.md` and `docs/ocaml-backend.md`).
- Self-contained hosted native backend (no OCaml runtime): **scheduled as step 23 (2026-10-06)** — `plan/hosted-native-ffi.md` remains the design record; `plan/step-23-c-target.md` is the execution plan. (a) Settled: the route is emit C (next item). (b) Reclamation **settled 2026-10-06** by the dedicated entry below — reference counting over the identity-bearing objects, value-semantic data arena-allocated (the T23.5 gate). (c) The HPC surface stays out of step 23's scope — it remains the gate beyond the backend. When the `c` backend covers the golden subset it supersedes the open item above on the native backend's route to 64-bit integer arithmetic on OCaml's 63-bit `int`.
- Codegen route for a self-contained native backend: **settled (2026-10-06) — emit C**, the step-23 route, with LLVM ruled out (C++ dependency, unstable API, opaque generated code, against the "emit and delegate" / readable-output line) and hand assembly confined to the freestanding `riscv64` target. Emitting C reuses the existing `cc` dependency, yields GCC/Clang autovectorization and OpenMP pragmas, and makes the C ABI the FFI surface. **Tail-call lowering settled (2026-10-06, step 23): the trampoline / block loop** — every self- or mutually-tail call is a parameter rebind and a jump to the function head, and `return` is a branch to the epilogue, never a raised signal (this is also the fix for the emit-OCaml backend's ~4x loop regression). **Wrap-around `Int64` settled (2026-10-06): unsigned `uint64_t` arithmetic cast back; `-fwrapv` is the documented fallback, not the plan.** The emitter also owns `restrict`-annotated vectorizer-friendly loops and the dynamic layer (tagged unions plus `retain`/`release`; `raise` ends the offending process — the root's death ends the program — by draining its fiber's frame chain, no unwinder and no `longjmp`, per the cross-target-invariants entry). See `plan/hosted-native-ffi.md` and `plan/step-23-c-target.md`.
- Reclamation model for the dynamic world without a tracing GC: **settled (2026-10-06, the T23.5 gate) — reference counting over the identity-bearing objects; implemented on the `c` target 2026-10-11.** Only instances, closures, and Box carry identity in Emo; tuples, arrays, and strings are value-semantic (assignment copies), so they cannot participate in cycles and stay in the bump arena until process exit — no per-object bookkeeping for them. The identity objects get malloc'd cells with a header refcount; the emitter owns the discipline (increment on capture/assignment into a longer-lived slot, decrement at binding scope exit and on overwrite; write barriers on the two mutation points — `Set_field` and `Box.replace`); cycles among instances and closures leak, documented (the Swift model). No language-surface addition is required: refcounts live in the cell header. Rationale: the settled codegen route already names `retain`/`release` as what this emitter owns; reference counting needs no stop-the-world, fits Emo's value semantics (the Swift / Objective-C lineage CHECK.md already cites), and frees memory before the scheduler and IO tasks (T23.9/T23.10) make long-running programs real. **The landed shape adds one runtime mechanism the settle's wording predates: a frame-scoped autorelease pool (the ObjC shape) — every generated body opens a pool at entry and closes it at every return, and statement boundaries drain the current frame — so expression-internal temporaries need no ownership analysis at any call site.** The emitter's discipline in full: a dynamic binding retains at init and releases at its block's end (bindings in a re-entered tail body hoist their zero-initialized slots and release-on-reassign, so a tail-recursive loop reclaims per pass); a parameter slot of a re-entered body retains at entry and releases at exit; tail-call rebinds swap through a write barrier and unwind the current pass's bindings while keeping the slots the next pass loads; `Set_field`/`Box.replace` barriers live inside the runtime entry points; closure creation and the arena aggregates retain what they capture (arena-held identities live to process exit, the documented shape); `send` copies the message into the mailbox and the mailbox owns the copy (`spawn` retains the closure into the fiber; a taken message transfers). The same-day verification: the whole golden tier byte-identical, plus a live-count probe (`emo_identity_live_count`) asserting a 10 000-iteration churn loop returns the identity count to its baseline while a List-held instance stays live. A future precise collector remains possible on the same layout (an immediate is never a valid pointer).
- C runtime string layout: **settled (2026-10-06, T23.3)** — a String in the `c` backend's runtime is `emo_str {int64 len; const char *bytes}`, length-prefixed and passed by value; no NUL terminator internally, one is appended only when a string crosses the FFI boundary (T23.8). Literals are C compound literals; the builders (concat, the scalar renderings) allocate in the bump arena and live until process exit — the reclamation decision landed as T23.5 (arena for value-semantic data), and reclaiming the value families is step 49. T23.4's heap String cell keeps this layout inside the tagged word's cell.
- The `c` backend's runtime language: **settled (2026-10-06, T23.3) — C, not Emo's specialized subset** (the hosted-native-FFI assessment leaned C: interop is a bridge, not a foundation). The runtime stays readable, reviewable C in `src/emo_codegen/c/`, compiled by the same `cc` invocation as the emitted program; self-hosting the runtime is not a goal (the reference implementation is OCaml by design).
- HPC criteria for the self-contained backend: **settled (2026-10-11) as the standing gate, in this priority order**: (1) vectorization/SIMD — the codegen route must deliver it (emit C, not LLVM or hand assembly); (2) a data-parallel construct (OpenMP-style parallel loop with reductions); (3) zero-copy FFI buffer passing — a mutable, address-stable, typed buffer (`Buffer[Float64]` or equivalent) borrowed for the call, per the `cgo` model, since `Array` is immutable and `Bytes` is byte-addressed; (4) ecosystem. GC is a latency and predictability concern (headroom, jitter), not the gate. Reference sample: Go — GC + custom backend + `cgo`, still not an HPC language because it does not autovectorize and has no parallel-loop primitive.
- Loop forms: **direction settled (2026-10-06)** — keep guaranteed tail calls *and* add `for`/`while`. Rationale: tail calls are a semantic (constant-stack iteration), not just an optimization, and they are nearly free on BEAM (native), wasm, and asm (a single `tail`); only the emit-C route needs a trampoline, which is not worth sacrificing the guarantee for. They also carry the actor `receive` idiom (README, Concurrency), and the current native backend's tail-call defect is an implementation bug (the `try … with Native_return` return convention), fixed by a branch to the epilogue, not a reason to change the language. Advantages of the loops: they are the native shape for vectorization/SIMD and `#pragma omp parallel for` (the HPC criteria), they remove the need for tail-position proof in loop code, and they are the least-surprise form for imperative and numeric iteration, pairing with `var`. The Go pre-1.22 loop-capture trap is already prevented — a `var` cannot escape its block, and capturing one in a closure that outlives the block is a compile error (README, Syntax) — so the earlier fresh-binding caution in `plan/README` is subsumed.
- Loop surface: **`for` settled (2026-10-06)** — the form is `for var i = 0; i < 100; i = i + 50 { ... }`: no parentheses (matching the paren-less `if`), a `var` declaration in the header scoped to the header and body, three `;`-separated clauses (init / condition / post), and the post written as an assignment (`i = i + 50`). This makes `;` a token, legal only inside a `for` header — the one place Emo uses it. The parser's existing `suppress_block_sugar` flag (already set for an `if` condition) applies to all three clauses, so a trailing `{` opens the body rather than attaching as a trailing block; the Go loop-capture trap is already prevented by the `var`-escape rule. Worked example: `for var i = 0; i < 100; i = i + 50 { println("i = ${i}") }` prints `i = 0` then `i = 50`. **`while` settled (2026-10-06): `while cond { }`** — paren-less and condition-only; the loop variable is declared before the loop and advanced in the body, e.g. `var i = 0` then `while i < 100 { println("i = ${i}"); i = i + 1 }`. `for` keeps all three clauses (no omissions), since `while` covers the condition-only case. The post / increment stays explicit (`i = i + 1`); `+=`/`++` are not added. **`break` settled (2026-10-06): a bare statement** — `break` takes no arguments and no parentheses, is used inside a loop, and binds to the nearest enclosing loop; `continue` is its pair, skipping to the next iteration and running a `for`'s post clause first. Both are rejected outside a loop. `do`/`while` is not added. With this the loop surface is settled; README and `plan/README` carry it; **implemented 2026-10-11 (step 26)** — lexer, parser, checker, and interpreter (`examples/loops` golden through `emo run`, ten million iterations flat), with the six backends refusing the loop statements until step 27 lowers them. **Lowered on all six targets (2026-10-11, step 27)**: the IR carries While/For/Break/Continue; c emits its own `while` and a `while(1)` form whose continue label runs the post; ocaml uses the ref discipline plus a pair of local exceptions per loop; typescript uses the native `for` with a labeled driver loop for tail calls; wasm lowers to block/loop/br_if with a post block; beam threads every free variable through a hidden recursive function with a done flag; riscv64 uses labels and jumps, and gained `/` and `%` (`div`/`rem` with a zero-division abort) so `examples/loops` boots — golden on all six targets plus the interpreter.
- Backend naming: **settled (2026-10-06)** — drop `native`; name backends by emission mechanism: `ocaml` (emits OCaml, links the OCaml runtime; today's `native`), `c` (emits C, own runtime; the step-23 backend), `riscv64` (emits RISC-V assembly; freestanding), plus `wasm`, `typescript`, `beam`. Rationale: `native` names a category, not a mechanism, and is itself ambiguous (C? riscv64?); the mechanism is what differs between backends and what scales once two hosted machine-code backends exist. `native` ceases to be a `--target` value; "native executable" is prose for what `ocaml`/`c`/`riscv64` produce. `c` is reserved and must not enter `known_targets` until its backend works. The rename is a mechanical whole-repo change, **implemented 2026-10-06** as its own step after step 23 (as allowed): every literal site below now carries `ocaml` — `known_targets`, the CLI default/help/error text, `emo init`'s manifest, `emo_project`'s defaults, the stdlib/example/benchmark `package.emo` files (lockfiles regenerated), the tests including `emo_lsp`'s fixtures, and the docs quoting the target; historical plan files keep the original value with a "today `ocaml`" note. Literal target-string sites (2026-10-06 grep): `src/emo_pkg/emo_pkg.ml` (`known_targets` plus two manifest samples), `src/emo_cli/emo_cli.ml` (the `match target` arm, the default value, `~target:"native"`, the `emo init` manifest), `src/emo_project/emo_project.ml` (two `~target:"native"`), the eleven `package.emo` files under `stdlib/registry/` and `examples/`, `test/emo_pkg/emo_pkg_test.ml`, `test/emo_project/emo_project_test.ml`, and the docs that quote the target (`README.md`, `docs/zh-CN/README.zh-CN.md`, `docs/stdlib/{net,http}.md`, `docs/zh-CN/stdlib/{net,http}.md`, `docs/TASKS.md`, `docs/zh-CN/TASKS.md`, `plan/step-13-networking.md`, `plan/step-17-typescript.md`, `plan/step-20-wasm-runtime.md`); prose `native` meaning native code (`docs/c-backend.md`, `docs/ocaml-backend.md`, `docs/industrial-software.md`) is unaffected.

Channels: prebuilt binaries per platform (GitHub Releases) as the primary route, with `opam` and a Homebrew formula as the source-building alternatives. macOS notarization is **solved, not a blocker**: with an Apple Developer account, sign (`codesign`, hardened runtime), notarize (`notarytool`), and staple the distributed zip (a bare Mach-O cannot be stapled); the certificate and credentials live in CI secrets. SmartScreen reputation accrues with download volume rather than switching on with a certificate, and distributing through winget/scoop/chocolatey avoids the browser's Mark-of-the-Web; EV's historic instant reputation is no longer reliable. - Toolchain defaults for the v1.0.0 distribution (M7, step 24): **settled (2026-10-07) — four decisions.** (a) **The default build target flips `ocaml` → `c`**, and the whole default pipeline agrees: `emo build` without `--target`, the project loader's dependency resolution (`emo run`/`emo check`), `emo deps resolve`, and the checker's default capability target all mean `c`. (b) **The stdlib embeds into the compiler as generated data** — the C runtime's own mechanism ("installed files beside the binary" is the rejected shape: it breaks single-file channels and every wrongly-unpacked archive); `EMO_REGISTRY` keeps overriding with a filesystem registry. (c) **`emo install` is the project-dependencies frontend** — read manifest, resolve against the registry, fetch into the cache, write `package.lock`, ready to run; global executable installation (the cargo-install shape) is out of scope for 1.0. (d) **The dependency cache leaves the temp directory** for a durable user location (`~/.cache/emo` honoring `XDG_CACHE_HOME`) — the OS wipes `$TMPDIR`, and a product cannot re-fetch on every build. Supersedes the interim `emo doctor` shape above: doctor becomes the target-aware environment check (step 24). Rationale: `plan/step-24-toolchain.md`.
- The runtime-independence principle: **settled (2026-10-07, before T25.1)** — a target's runtime is written in the target's language, carried as generated data inside the compiler, and compiled by the target's own toolchain on the user's machine; the host contributes only the emitter. No target's runtime may be looked up beside the binary or in the host build tree: `c`, `ocaml`, and `typescript` runtimes ride inside the compiler as generated data (the `emo_codegen/{c,ts}` dune-rule pattern), while `wasm` and `beam` runtimes ride inside the emitted module itself (the wasm engine imports and OTP are the *target* ecosystem's ABI and standard library, as libc is to `c` — a different axis from the compiler's host language). Consequence: target generation stays the host's job, so a future host rewrite touches only the emitters; a target works wherever the target's own toolchain exists, on any installation shape — `emo build --target ocaml` needs the OCaml toolchain on PATH, never an `emo_runtime.cmxa` in the host build tree. The host/target distinction this completes is recorded in `docs/toolchain.md`.
- The ocaml runtime's dependency policy: **settled (2026-10-07, T25.4)** — the standalone runtime's core (values, strings, the scheduler) stands on the OCaml standard library plus `unix`, which ships with the compiler; TLS keeps `ssl` as the one opam-package dependency; the runtime's build invocation declares both (ocamlfind `-package unix,ssl`) and refuses with a clear message when `ssl` is absent. **eio drops out entirely**: the standalone scheduler is the deterministic poll loop the compiled path already ran on, so the provisional plan to keep `eio_main` on the target side is superseded — a target-ecosystem dependency nobody's program needs is not declared.
- Cross-module type names: **settled (2026-10-14) — module-qualified type names, superseding the 2026-10-10 program-wide bare-name rule.** A type reference is a path, exactly like a value reference: `ui.VNode` and `sync.WaitGroup` name another module's type, a bare `Order` names the current module's own, and package-relative forms (`internal.svg.Renderer` inside a package) work as they do for values. `Emo_check.resolve_type_ref` splits a written reference at its last dot-segment (the type name; every earlier segment a lower_snake module), normalizes that module path relative-to-package-then-absolute, checks the internal boundary, and returns the qualified display name (`sync.WaitGroup`); the pre-registration tables (`Emo_check.preregister_types`, now taking `~packages`/`~package_deps` so package-relative references resolve) are keyed by it, `ClassType`/`InterfaceType`/`EnumType` carry it, and the IR and every backend key class/interface/enum tables, `is()` vtables, and enum tags by it. Two modules may therefore declare the same short name — they are two distinct types, each addressed by its module — and E4021 (the bare-name collision) is gone. Construction, `is()` narrowing, enum member access (`ui.Color.red`), and enum patterns all accept the qualified spelling; the built-in `R` enum and `Exception` class stay bare. Consequences: the earlier 2026-10-10 machinery (two-phase program-wide pre-registration, the program's value-signature tables, `is()` narrowing across modules, construction loading the declaring module on first use) is unchanged except that its keys and surface are qualified; the internal rule is a path rule on the declaring module (a reference from outside its subtree reports E5001 at the use site, naming both modules); registry-package types resolve for their consumers and an interface signature may name its own interface inside a checked program, while a lone-file view (the LSP's single-file check) still resolves only that file's own declarations, keyed bare. `docs/emo-ui-check.md`'s evidence holds with the surface spelled `ui.VNode`.
- Cross-module value signatures: **settled (2026-10-11, the feat/checker pass) — the program's def/const/group tables pre-register beside the type tables**. The 2026-10-10 pre-registration made cross-module *types* check; values stayed blind — `lib.make(x)`'s arguments went unchecked, `lib.answer` read as Unknown, another module's group member never resolved, and every divergence the interpreter raises at run time (E5004 unknown member, E4004 wrong argument) surfaced only there. The fix rides the same two-phase pass: `preregister_types` now also collects every unit's defs and foreigns as declared `FuncType`s, every top-level const/var as its initializer's type (typed in the unit's own order, diagnostics dropped — the module's own check reports them), and every `emo` group's defs and consts into a program-wide registry mirroring the runtime's (groups are global at runtime, so the checker's per-module table gains a program-level fallback). A qualified call checks through `check_apply` like any call; a bare `lib.make` reads as the closure's `FuncType`; a member that resolves nowhere reports E5004 statically — the runtime's own message. Shadowing stays runtime-faithful: a dotted path is a module reference only when its head is not a local binding (the runtime looks the head up in the environment first — the `list` example's local `const list = List.new(...)` under a module named `list` is what pinned this). Group member reads type directly (consts carried nothing before — a bare `Math.tau` read as Unknown even same-module). Two pre-existing checker bugs fell out: `longest_module_prefix` generated the path's *suffixes*, never its prefixes (harmless while it only under-recorded refs, fatal once member resolution keyed on it), and the Member arm treated the empty dotted path as a module prefix, swallowing bare member access on non-simple receivers (`foo(1).field` read as Unknown forever). Registry packages join automatically — the same `p.files` walk feeds the pre-registration, so `json.decode(text)` now checks its argument and returns the interface. The packages' interfaces moved their `get` onto the interface (json gained the four raising scalar variants, matching the classes it already had; the "an interface signature cannot name its own interface" comments predated self-referencing signatures and were stale). Unblinding receivers also surfaced two latent c-side deviations, both pre-existing and both fixed to the interpreter's answer: `emo_box_replace` returned the box while every other target returns the new value, and the emitter's `to_string` dispatch arm captured statically-typed instance receivers, printing the debug repr instead of the class's own method — instances now dispatch by class first, the conversion answering only when no method carries the name. A capitalized name that resolves to no type, group, or module reports E4003 at its write site in a program check — the runtime's value-carrying builtins (`Int64`, `Byte`, `Float64`, `Box`, `Bytes`, `List`, `ArrayBuilder`, `Map`, `Exception`) stay legal — while the lone-file view (the LSP's single-file check) keeps the old silence, exactly like every other cross-file gap it cannot see through.
- A Zig-emitting backend: **settled (2026-10-11) — shelved; not a seventh target** (`docs/zig-backend.md`). Emitting Zig is mechanically a mirror of the `c` target, and its one unique gain — safe-mode bounds and overflow checking on generated code — is a mid-sized development-time benefit set against a full backend's cost and a permanent churn tax: Zig breaks language and std APIs in every release, 1.0 has no date, and incremental compilation covers only x86_64-linux. Without its std library the emitter produces curly-braced C with worse tooling — a strictly worse `c` target; with it, every compiled program rides a pre-1.0 std — the churn the runtime-independence principle refuses. The shelving carries written re-evaluation triggers, set now so the bar is explicit: Zig 1.0 or completed language stabilization, incremental compilation beyond x86_64-linux, or a concrete requirement the `c` target cannot meet through `zig cc`. What survives is not a backend: `zig cc` as an optional compiler driver for the existing `c` target — cross-compilation from any host, static musl Linux binaries, Windows without MSVC — is its own small step, taken if Windows or static Linux distribution enters the plan, and only after the driver's version joins the `c` cache key (today it hashes source, runtime, cclib, and the emo binary, so a swappable driver would serve stale binaries after an upgrade). `riscv64` stays direct assembly text; nothing passes through Zig.
- FFI compound data — struct shapes: **settled and implemented (2026-10-11) — a tuple or a carrier class is the shape declaration; the carriers are Emo's own**. A `foreign def` parameter whose type is a tuple crosses the C ABI as a C struct by value: the element types in order are the layout, and a nested tuple element nests a struct within the struct. A class instance carries the same by its init-assigned fields — the carrier-class contract is that the class's shape *is* its init signature: every field assigns a same-named parameter, in order, and every field type stays in the tier (a marshaling scalar or a nested tuple); a computed or extra field, a stateless class, and a class-typed field all refuse. A compound foreign **return** crosses back as a tuple — a class-typed return refuses ("name the tuple"), because a return would have to fabricate an object identity a C value cannot carry. The `c` target declares the same `typedef struct` the C side sees — into `main.c` and `emo_defs.h`, so a shim compiles against the real layouts — and per shape emits two static converters (one flattening the argument word into the struct, per carrier kind, so the argument expression stays a single textual occurrence; one rebuilding the tuple word from a returned struct); the by-value calling convention (register vs. memory class, the SysV classification) is cc's job, which is the emit-C route paying for itself. Identical layouts share one typedef, keyed by the serialized member tree. No language-level struct type exists — records are class instances and anonymous compound values are tuples, and the FFI surface declares shapes *through* them, so nothing new enters the value model. Rejected along the way: making the carrier rule lenient (strictness first — a divergent field list marshals the wrong bytes silently). Open for later: struct fields that are themselves carrier classes, pointer OUT-parameters (`&x` shapes), and the other honoring target (`ocaml`) gaining shapes — each refuses loudly today, per the `foreign` rule.
- The C→Emo callback contract: **settled (2026-10-11) — a single-method structural interface is the callback type; implemented on the `c` target the same day** (spike evidence in `spike/macos-gui`). A `foreign def` parameter may name an interface; the `c` target emits a trampoline plus an opaque userdata handle, and the C side calls through them into the object's one method — registration is explicit ordinary code, with no invisible plumbing. The convention: one interface-typed Emo parameter expands to two adjacent C parameters, the function pointer and the `void *`, and the callback's C signature is the method's marshaled parameters followed by the trailing `void *userdata` — the idiom every C callback API already expects, and the pair lands in `emo_defs.h` so a shim's signature drift breaks at cc time. The callback method stays in the marshaling tier (`Float64`/`String`/`Bool`/`Int64` parameters, plus `Void` returns); the trampoline boxes the arguments and dispatches by method name through `emo_send`, so identical signatures share one static trampoline and distinct receivers ride the userdata. Rejected: `&def` function references — an address-of-def reads as first-class functions seeping through the FFI seam, and there is no representation to back it (the `c` target's call discipline is plain symbol calls; callbacks are deliberately not first-class); a C-style struct-of-function-pointers registration — the struct-shaped Go borrow already refused. What the spike proved meanwhile: C already calls Emo defs as plain extern symbols (module-qualified, `main__`-prefixed), with callback state traveling through the signature because Emo gives cross-callback state no global home; the interface contract generalizes exactly that shape. The interpreter still refuses every foreign def at run time (E3009), and the other honoring target (`ocaml`) refuses the interface parameter at check time until its marshaling path grows one.
- Package-carried native code and the manifest `link` field: **settled and implemented (2026-10-12), with the `sqlite3` package as the first consumer.** A package may carry `.c`/`.h` sources in its tree — collected, checksummed, embedded, and published beside its `.emo` modules (the tree is the package, so the sources are auto-collected exactly like the modules; no manifest field names files) — which the `c` target compiles in the program's single cc invocation, and the manifest gains an optional `link = [...]` field naming the system libraries to link (bare names only: a `-`- or `/`-shaped entry is refused with E5103 — the manifest stays data, never a flag fragment; `--cclib` keeps the verbatim-flag role). Both ride the existing cclib mechanism into the build's cache key — sources by content, libraries by name. A native-carrying package is honored by the `c` target alone: resolution's `targets` gate stays the first line, and a package declaring the current target while carrying native inputs makes the build refuse outright (E5007, naming the packages) rather than silently dropping the link. The `sqlite3` package itself: `targets = ["c"]`, `link = ["sqlite3"]`, its `foreign def`s in a subtree-private `internal/ffi.emo` against a package-carried shim whose every signature is exact-ABI (`int64_t`/`double`/`bool`/`const char *`) so SQLite's `int` returns never meet the FFI undeclared; the shim includes the generated `emo_defs.h`, so drift breaks at cc time in both directions. Handles ride pointer-sized Int64s; bind indices are 1-based (they name the SQL text's `?NNN`), column indices 0-based (SQLite's convention); a NULL column reads as `""` with `column_is_null` telling the two apart; embedded NULs truncate at the boundary until Bytes can cross the FFI; blobs are out of scope until then. Errors follow the package's base-branch convention — raise, per `os` — and join the error-handling migration to `(R.ok, …)` / `(R.error, …)` tuples when that branch lands. Rejected along the way: baking SQLite into the always-linked C runtime (every binary would link `-lsqlite3`, and the interpreter would need its own binding) and vendoring the amalgamation (a quarter-million lines of third-party C for what every host already ships).
- EmoUI native packaging: **direction settled (2026-10-14) — the manifest grows per-package native fields; a native backend does not ship an app-level build script.** A native UI backend has to be an ordinary package a program reaches with a `require`, so what AppKit and GTK 4 need must be declarable in the manifest rather than restated in each consumer's build script. The need is concrete: a macOS backend is an Objective-C translation unit built with `-fobjc-arc -framework AppKit`, and a GTK 4 backend needs `pkg-config gtk4`'s cflags and libs; the spikes work around both with an app-level script passing `--cclib="$PWD/shim.o"` and `--cclib="-framework AppKit"`, which makes every EmoUI app carry a build script instead of a `require` — friction on the requirement's "just download and use", and the one thing a consumer cannot discover from the package it depends on. This extends the `link` field above rather than replacing it: the manifest stays data (bare names, no flag fragments), the native sources stay auto-collected from the package tree, and the new fields are per-package, so the resolution gate and the build's cache key keep working unchanged. The field surface itself — `pkg_config` versus explicit compile/link flag lists, and whether `.m` joins `.c`/`.h` in the collected set — is T48.7's own work, as is its implementation; T48.8 and T48.9 stay gated on it. Rejected: documenting the app-level build-script path as the supported one — it is what the spikes needed, not what a user of a UI package should need.
- Standard-library requires: **settled (2026-10-14) — an unscoped `require` resolves the standard library implicitly; only a scoped package pairs with the manifest.** The official standard library owns the top-level short names (`json.decode()`, `http.get(url)`) and ships inside the compiler, so `require "json"` needs no `deps` entry: the loader takes the highest version the registry publishes for each unscoped require (the bundled registry by default, `EMO_REGISTRY` when set), resolves that package's own stdlib closure with the manifest's pins in one MVS solve, and registers the modules for checking and the visibility rule. Implicit pins never enter `package.lock` — the manifest stays the recorded resolution — and an implicit pin may not silently move a manifest pin: a stdlib closure demanding a different exact version than the manifest states is an E5007 conflict the manifest must settle. A scoped `require` (`acme/tools`) keeps the strict pairing (missing from `deps` is E5006), and an unscoped name the registry does not publish is E5009 at the require. The LSP mirrors both and folds the modules of unpinned stdlib requires into its index.
- Cross-target invariants the targets do not all honor: **settled (2026-10-15, step 50).** Found 2026-10-14 during a target-feasibility survey, which recorded three rules whose implementations disagreed; two of the three were never open questions — they were conformance gaps against promises already made, and neither moved a language surface. (1) **The `c` target's `raise` ended the program, not the process — fixed.** `emo_raise` rendered the value and called `exit(1)`, while the process model promises the opposite — "an unhandled error ... kills only the offending process" (`docs/intro/concurrency.md:11`) — and the settled error split above rests on that promise. `emo_raise` (`src/emo_codegen/c/emo_c_runtime.c:2086`) now branches three ways: outside the scheduler, or in the root, it keeps the old behaviour (render `uncaught exception: …` and `exit(1)` — T23.6's E3010 rendering, and the root's death is the program's end, `docs/intro/concurrency.md:12`); in a spawned process it drains its own frame chain and ends only itself. **This entry's own cost estimate was wrong, and the correction is the reason the fix was small.** It said closing the gap "means the per-fiber unwind the `catch` design was refused for" — `setjmp`/`longjmp` plus a drain at every C frame. None of that is needed, because the runtime already had the whole mechanism: the autorelease pool is a heap-allocated frame chain hung off the fiber (`emo_process.top_frame` → `emo_frame.parent`), so a fiber's frames are reachable without touching the C stack; `emo_process_halt_current()` (`:2071`) already ends a fiber by swapping to the scheduler and never returning — that is how every `makecontext`'d fiber ends today; and the scheduler already reaps a finished fiber's stack and already treats only the root's finish as program end. The fix is the drain helper `emo_fiber_release_frames` (`:1956`) — the same walk `emo_pool_exit` did, releasing each pooled item and returning the frame nodes to the free list — called by `emo_raise` and by `halt()`, which had the identical leak. No emitter change: `emo_c.ml` already emitted a plain `emo_raise(v)`. Observable result matches the interpreter (`emo_sched_det.ml`): the root's raise prints and exits 1, a child's raise kills only the child and prints nothing. (2) **The `c` target's `send` shared the message; it did not snapshot — fixed.** The snapshot was already promised for each of Map, Box, List and ArrayBuilder (`docs/intro/syntax.md`), the interpreter deep-copies across that boundary (`emo_eval.ml`'s `snapshot`), the standalone OCaml runtime already did, and `stdlib/registry/sync/0.1.0/sync.emo` states it outright for a handle; the `c` backend emitted a bare `emo_process_send(pid, msg)` (`emo_c.ml:1926`) and the runtime only `emo_retain`ed the cell into the mailbox, so a Box sent between `c`-target processes was shared. `emo_deep_copy` (`emo_c_runtime.c:2106`) now sits beside the mailbox and `emo_process_send` (`:2206`) stores `emo_deep_copy(message)`, following the interpreter's rule over the kinds this runtime has — `Box`, `Bytes`, `Tuple`, `Array`, `List`, `ArrayBuilder`, `Map`, `Instance` are rebuilt (instances copy their fields and keep the class; a map copy preserves insertion order), while `Int64`, `Float64`, `String`, `Enum`, `Closure` and `Pid` pass through as immutable data or as the identity the boundary deliberately shares. The emitter needed one line (`emo_c.ml`): the mailbox take releases its only claim on the snapshot before the branch binds, so the scan now holds its own (`emo_autorelease(emo_retain(...))`) — without it the value was freed between take and bind. Copied arena aggregates leak exactly as every arena aggregate does, this file's step-49 limit rather than a new one. (3) **`foreign def` had no emitter-level refusal on `wasm` and `beam` — fixed.** The capability table is the intended sole gate, but it admits `Float64`/`String`/`Bool` on *every* target — the `c`-only rows are `Int64` and `Void` — and neither `emo_wasm.ml` nor `emo_beam.ml` mentioned `fforeign` anywhere; only `emo_ts.ml`, `emo_c.ml`, `emo_codegen.ml`, and `emo_riscv.ml` handled it. The survey's guess is now answered: the IR carries the symbol in `fforeign` on an otherwise ordinary `func` record with `fbody = []` (`emo_ir.ml:1354`), so both emitters were emitting an **ordinary function for a declaration that has no Emo body** — a silently absent symbol, not a downstream refusal. Each emitter now refuses per function, beside the code that would have lowered it, with the shape the riscv target already uses: `raise (Emo_ir.Lower_error "the <target> target does not support \`foreign def\` yet")`, which the CLI renders as `emo build: …` and exit 65 — the code the `Map` and `ArrayBuilder` refusals carry. **Left open, and the item's only remainder: the `typescript` target still shares on send.** `ts_runtime.ts:2378-2389` stores the reference, verified by running the T12.4 program under `node` — interp/ocaml/c print `1\n99\n`, typescript prints `99\n99\n`; `wasm`'s `rt_send` (`emo_wasm.ml:4180`) does the same, though that target refuses this program's shape for unrelated reasons. The same conformance gap, on the target whose runtime is being split for the browser; it is recorded here rather than fixed because the fix belongs with that work.
- `c` target long-running memory: **settled (2026-10-14, the arena-scope spike) — region reclamation is not viable as a standalone mechanism; the value families need refcounting, and that is its own milestone (`plan/step-49-value-reclamation.md`).** A region reclaims 100% of the arena's bytes and 0% of the leak that actually grows the process, because identities are `malloc`'d outside the arena while the arena's aggregates retain them across the region's boundary — so the references a reset drops without releasing are unrecoverable, and the raw reset strands those refcounts permanently. The obvious repair, logging the retains the arena performed and replaying them in reverse at the reset, is O(k²) per render, because `emo_array_append` copies and re-retains every element on every append. The same probes found the second cost this workload pays: there is no O(1) array append and no conversion back from `List` to an indexable `Array`, so a dynamically grown children array is quadratic either way. **The array-growth half is answered (2026-10-15, T49.3):** `ArrayBuilder` is an amortized-O(1) append that copies out into an `Array`, so growing the children array no longer goes through `Array.append`'s per-element copy — and it needed no representation change, so nothing here waits on the reclamation milestone. Its growth follows the `Map` doubling in the same runtime, and its retired buffers stay arena-resident and leak exactly as `Map`'s do, which is this entry's already-recorded limit rather than a new one. The `List` → `Array` conversion half stays open, deliberately: nothing in the language reads a deque by index, and adding a conversion to `List` would give the deque a second job it does not need. Evidence: `spike/arena-scope/` (three probes with checked-in outputs; at 400 nodes a render allocates ~1 MB and leaks ~820 identities, both unbounded at 60 fps). Two mechanisms were weighed and rejected rather than left implicit: **per-fiber arenas**, which would let a finished fiber's arena be freed whole, but `send` and `spawn` pass arena pointers across and retain them, so they demand copy-on-send for every value family — the escape analysis relocated onto the concurrency hot path; and **making identities arena-resident again** so a region contains everything it holds, which would remove the refcounting T23.5 landed and leave the region as the only mechanism, straight back into the boundary probe 3 shows cannot always be named. Consequence for step 48: **T48.8 and T48.9 proceed at demo scale with the limit documented**, rather than waiting on reclamation or shipping a region that would make half the leak harder to fix later.
- The in-tree project layout: **settled (2026-10-15) — `projects/` at the repository root holds one subdirectory per named Emo project, named after its eventual repository.** So `projects/emo-ui`, `projects/emo-os`, `projects/emo-shell`: software written *in* Emo and shipped as its own thing, beside the compiler's own tree rather than inside it — the three share a brand and a release rhythm and belong under one parent, and none of them is the language, the standard library, or an example. **This supersedes the hosting half of the EmoUI decision above**, and only that half: `github.com/emo-lang/emo-ui` stops being a repository created up front and becomes a `projects/emo-ui` subtree, while the decision's substance stands — EmoUI is still not a standard-library package, which in-tree hosting cannot change because the stdlib embed walks `stdlib/registry` alone, so `projects/emo-ui` never enters the compiler binary. Naming each directory after its eventual repository is the point: `git subtree split -P projects/emo-ui` later yields the standalone repository with its history, so the choice is reversible and the extraction mechanical. What it does cost is the thing the third-party decision was avoiding — UI releases now ride the same repository and CI as the compiler — accepted for now rather than paid for with a second repository to keep in sync. Four properties make the layout free to the compiler build, each verified: the repository root carries no `package.emo`, so each project's own manifest roots it and no project is swept into another's check; `dune`'s default target lists `src`/`bin`/`test` explicitly, so a new top-level directory is not built; `devtools/gen-stdlib-data.sh` walks `stdlib/registry` alone; and `.emo-build/` is already ignored. Rejected: `packages/` — `package` already names a manifest's dependency unit (`package.emo`, `stdlib/registry`), so the directory would collide with a concept the reader already has; `userland/` — EmoOS *is* an operating system and its userland is inside it, so the name misfiles two of the three; `suite/` and `stack/` — both assert a single shipped product or a single vertical layering, which does not hold (EmoUI renders on macOS and in a browser, EmoOS is bare metal); `apps/` (EmoOS is not an application), `platforms/` and `systems/` (EmoUI is a framework), `flagships/` (marketing register); and `cmd/`/`pkg/`, the Go shapes the design philosophy refuses on sight.
- Terminal input's placement (T48.5): **settled (2026-10-15) — raw mode is a standard-library capability, shipped the `sqlite3` way.** Reading a terminal in raw mode is not a UI-framework concern and not a compiler concern: it is a system capability of the same kind `sqlite3` exposes, so it becomes a standard-library package whose package tree carries its own `.c`/`.h`, reached through `foreign def` against an exact-ABI shim, honored by the `c` target alone and gated by `targets` — the package-carried-native-code shape above, unchanged, with no new mechanism. The alternative it displaces is the one the step plan had provisionally written, a termios binding living compiler-side; that placement is refused because a `foreign def` is a package's own business and the compiler owns no terminal, and because a UI-framework-side placement would make a TUI backend the only backend needing it — the same argument that keeps EmoUI itself out of the standard library, pointed the other way. The package therefore belongs in `stdlib/`, requires the runtime (it leaves the freestanding tier alone), and its consumers (`ui-tui`, the package's own tests) reach it with an ordinary `require`. What stays open is its surface — line-buffered reads first with raw mode behind them — and that is T48.5's own work.
- A Lua-emitting backend: **settled (2026-10-14) — shelved; not an eighth target** (`docs/lua-backend.md`). On three axes it would fit Emo better than any target that exists: Lua 5.3's integer subtype satisfies the Int64 wrap-around invariant natively, Lua's coroutines are the stackful cooperative process model the `c` target builds out of `ucontext` fibers, and Lua guarantees the proper tail calls `c` and `typescript` only approximate. Every one of those holds only at Lua 5.3 and later, and the hosts a Lua target exists to reach are all below it — Neovim, OpenResty, and Love2D are LuaJIT 2.1, Redis is 5.1, Roblox is Luau, Wireshark is 5.2, and none of them has an integer subtype, so none can honor the invariant; emulating it on doubles is the two-word hi/lo scheme the numeric-width entry above records as never taken, revived for the one target whose whole value is the host process. The version spread does not close either: 5.5 reserves `global`, makes a `for` control variable read-only, and breaks binary chunk compatibility, so 5.1 through 5.5 plus LuaJIT plus Luau is the Zig churn tax with two extra dialect axes. What a Lua target uniquely offers — the artifact a host `require`s into its own process, which no shipped target provides, since the wasm target still needs the host to have a wasm engine — dies exactly where it would be worth something; compiling standalone Lua instead competes with the `c` and `typescript` targets rather than reaching a new host, while paying the explanation cost of a crowded and partly abandoned dialect space (MoonScript, YueScript, Teal, Fennel, TypeScriptToLua, Haxe's Lua target, Amulet ML, Urn). The shelving carries written re-evaluation triggers, set now so the bar is explicit: a concrete embedding host whose Lua is 5.3 or later, or one that can move there; a language requirement only a Lua target serves; or evidence that Emo's users are in the Lua-dialect ecosystem. What survives is not a backend: if the goal is an Emo artifact inside a process someone else owns, the cheaper direction is an embedding surface — a documented C embed ABI on the `c` target, or a documented import/export surface on the wasm target — evaluated as its own small step, with no version wall and runtimes that already exist. The survey's reusable finding: truncating division, truncated modulo, arithmetic shift, and OCaml's `%g` each need a hand-written helper on any host whose defaults differ, and Lua's operators are the floored, logical, C-formatting branch of the family — all four at once — which is why a Lua backend's long pole would be the golden tier, not the emitter. Nothing here schedules work on the existing targets.
- Module-level bindings on the hosted targets: **found 2026-10-15 (T48.2) — open; recorded, not fixed, and the EmoUI loop is built around it.** EmoUI's event-tag table wants to be a module-level binding and cannot be one, which is why the loop owns it (`ui.Registry`, handed to `view`) instead. Three findings, each with a two-file repro: **(1) a non-entry module's `const` lowers to a zero-arg function, and every read re-runs the initializer** — deliberate lowering (`emo_ir.ml`, pass 2: "A const binding in a non-entry module becomes a zero-arg function other modules can call"), but the interpreter evaluates the initializer once and keeps the value, so `lib.emo`'s `const b = Box.new(0)` with `def bump() Int64 { b.replace(b.read() + 1); return b.read() }` read three times prints `1 2 3` under `emo run` and `0 0 0` on `ocaml`, `c` and `typescript` — the identity is gone and the divergence is silent, so a module-level `const` whose initializer allocates (`Box`, `List`, a class) is a fresh value per read on every compiled target. **(2) a `const` in the *entry* module is no symbol at all** — the pre-registration pass skips it (`when m.mpath <> input.entry`, `emo_ir.ml`) and a def reading it lowers to `Type_ref`: `c` refuses (`the c target does not support this expression form (Type_ref) yet`) and `ocaml` emits the type's *name*, so a program whose whole body is `const greeting = "hi"` / `def say() { println(greeting) }` / `say()` prints `hi` under `emo run` and `greeting` from the `ocaml` binary, while `typescript`/`wasm`/`beam` build it. **(3) a module-level `var` is `ocaml`-only, and three targets crash on it** — `c` refuses with a diagnostic (`the c target does not support module-level variable assignment yet`), and `typescript`, `wasm` and `beam` exit 125 with an escaping OCaml exception (`emo: internal error, uncaught exception: Failure("ts: module-level `var` is not supported")`) rather than a refusal, which is a compiler bug independent of the missing capability. Nothing here needs a language-surface decision; it is a conformance-and-diagnostics debt, and (1) is the one that changes answers rather than refusing them.
- The Elm loop's shape on the hosted targets: **found 2026-10-15 (T48.2) — open; recorded with a minimal pair, not fixed.** `ui.run(view, update, model, backend)` takes the application's `update` and `view` as `Block` values, and a bare def name is the only expression that yields one. `projects/emo-ui/probe/def_shape` is that shape in miniature, and it is what `c` and `wasm` refuse: `c` has no def-as-value at all (`the c target does not support this expression form (Global) yet`; only class methods get a dynamic entry, `emit_thunk`, `emo_c.ml:2834`), and `wasm` refuses a `Call_value`/`Closure` with more than one parameter (`only one-parameter closures are supported yet`, `emo_wasm.ml:549-561`, `630-639`) — which a two-argument `update` reaches immediately. `ocaml`, `typescript` and `beam` build it, and `emo run` runs it. `projects/emo-ui/probe/handler_shape` is the same loop with the application's two functions behind a `Handler` interface — no `Block`-valued function anywhere, the calls ordinary interface dispatch, the application still narrowing its model with `is()` exactly as a backend narrows a node — and all five targets build it, with `c` and `ocaml` printing what `emo run` prints. So the gap is the loop's landed spelling, not the loop: the decision (`projects/emo-ui/README.md`, T48.2) is either to grow the two targets (def-as-value on `c`; n-ary dynamic calls and n-parameter function values on `wasm`) or to move the application's `view`/`update` behind an interface, which is a `docs/emo-ui.md` Layer 5 revision. Until one lands, `projects/emo-ui`'s package gate is green on `ocaml`/`typescript`/`beam` and refuses on `c` and `wasm`, and `./check.sh` pins both refusals and both probes.
- Operand evaluation order on the compiled targets: **found 2026-10-15 (T48.3) — open; recorded, and the golden is written around it.** `ocaml` evaluates a call's arguments right to left; the interpreter, `c`, `typescript` and `beam` evaluate them left to right (`wasm` lowers them in source order, read from its emitted WAT). The reversal covers every operand position — a call's arguments, an array literal's elements, a binary operator's operands, an interpolation's parts, and named arguments — and it moves nothing but the *order* of side effects: every value a program computes is the same, no check catches it after the fact, and a program that hands out ids, counters or event tags from an operand position simply answers differently on one target. That is not hypothetical: `Registry.on` is exactly such a side effect, and the first version of `projects/emo-ui/golden/main.emo` registered its three tags inside the array literal it built the tree from, which read `Save #0 Cancel #1` on the interpreter and `Save #1 Cancel #0` on `ocaml`; the golden now takes its tags in statements of their own, and `ui`'s own test was rewritten the same way. The cause is the emitted source rather than a decision: `emo_codegen.ml:543` writes a call as `func [a1; a2; a3]`, and OCaml itself evaluates a constructor's arguments right to left, so the host language's rule reaches Emo's. That no document states an order is the second half of the finding — four targets and the interpreter agree by accident of emission — so closing it means writing the order down (left to right is what five of the six already do) and having the OCaml emitter bind its arguments in order instead of leaving them in a list literal. `projects/emo-ui/probe/eval_order` is the minimal pair — `emo run` prints `12 = 3`, the `ocaml` binary prints `21 = 3`, the value identical and the trace reversed — and `./check.sh` pins both.
- An enum's display form across the targets: **found 2026-10-15 (T48.3) — open; recorded, and the debug form avoids it by construction.** Interpolating an enum prints its bare tag on the interpreter, `ocaml` and `c` (`red`), the module-qualified name on `typescript` (`main.Color.red`), and raises on `beam`, where `{emo_no_to_str, {emo_enum, 'main.Color', red}}` ends the process — the `beam` runtime has no conversion clause for the kind at all; a tuple carrying an enum rides along with whichever the target does (`(ok, 12.5)` against `(R.ok, 12.5)`, `R` being built-in and so carrying no module to qualify with). It matters out of proportion to its size because a golden is bytes: `projects/emo-ui/debug.emo` interpolates no enum and no tuple anywhere — it destructures (`align_name`, `extent`) and spells the name it prints itself — while a node carrying an enum in a prop would still render per-target bytes, which is a limit of the form to revisit if one ever does. What the display form *should* be is a surface question the language has not answered: the bare tag is the reference today only because the golden follows the interpreter, while the vocabulary is qualified everywhere it is written (`ui.Color.red`). `projects/emo-ui/probe/enum_print` is the minimal case, and `./check.sh` pins the interpreter's line, `typescript`'s line, and `beam`'s raise.
- The manifest's `deps` key: **settled (2026-10-15, T11.9) — a string literal, and the block's one spelling.** The change was forced by this repository's own packages: the EmoUI core pins itself as `emo/ui` and could not, because a deps key was parsed as a scoped identifier — the owner half had to lex as an identifier, and `emo` is a reserved word (`emo { }` group syntax), which a hyphenated owner fails the same way. The deeper fault is that a package name was code in this one place and data everywhere else: `name = "emo/ui"` is a string, `require "emo/ui"` takes a string, `Lockfile.dep` and `Registry.fetch ~name` are strings, the require↔pin pairing is a string compare — and the `a / b` fold that turned a scoped name into an identifier was structure the reader cannot see, which the design rules forbid. So a deps key is now a plain string literal (`deps { "emo/ui" = "0.1.0" }`, `deps { "json" = "2.3.1" }`), the fold and the `E4015` scoped-name check it fed are deleted rather than kept as a legacy path, the manifest parser moves to a profile of its own (`Emo_parser.parse_program_in ~manifest:true`, `Emo_pkg.parse_manifest` its only caller), and the package fields (`name`, `version`, `targets`, `link`) stay identifier bindings — a fixed schema of fields against a name→version map. One spelling only: the identifier key form is `E5102` with a hint naming the string form, a string-keyed package field is `E5102` instead of a field silently dropped, an empty dependency name is `E5102`, and a stray statement inside `deps` is `E5104`; outside a manifest nothing moved (`"json" = "1"` stays `E2015` invalid assignment target). A manifest written by an older compiler no longer parses — accepted pre-1.0, the same precedent the lockfile sets ("delete and re-resolve"): there is no manifest-format version and no compatibility mechanism in the tree. 29 manifests migrated (`examples/**`, `benchmarks/http_echo`, five standard-library packages, the emo-ui golden) and every committed lockfile re-resolved; `docs/intro/package-management.md` carries the decided surface. A `package.emo` is data everywhere it is read, not just in the editor: `emo check <FILE>` reads it as a manifest rather than as a module, so the CLI and the LSP agree on what a manifest says, and `Emo_pkg.is_manifest_file` is the one place that decides (the token-level phase-A manifest helpers T11.7 superseded are gone with it). The commands that need a program go the other way and refuse it — `emo run` and `emo build` exit 66 on a manifest named as the entry, rather than reading its fields as unbound names, and the refusal names the module to run or `emo emoji build`, the command that builds a package from its manifest.
- Where a project roots (T11.10): **settled (2026-10-16) — the working directory, which must hold `package.emo`; no ancestor is ever consulted.** What stood before was "the nearest `package.emo` at or above the entry file, else the working directory", and both halves guessed. A manifest-less tree silently became a project rooted at cwd, so `emo check examples/alias_demo/main.emo` typed at the repository root checked the whole repository and reported other examples' errors; and the same file meant different things depending on where the command was typed, with nothing ever saying "this is not a project". The rule is now two lines: a project is the directory you stand in, and that directory holds `package.emo`. A missing `./package.emo` is **E5010** (``no package.emo in the current directory``; hint ``run `emo new <name>` to scaffold a project here``), and its span is the directory itself rather than `cwd/package.emo` — `Render` falls back to the caller's source when `span.file` is not a readable file, so a nonexistent path would put the `-->` line and the excerpt out of agreement. An entry that is not a module of the package rooted there is **E5011** (``the entry `<entry>` is not a module of the package rooted at `<cwd>` ``, hint `run the command from the package directory that contains the entry`, span: the entry at 1:1, which exists and so reads correctly). Both surface through `Static_errors` → exit **65**, like every other project-shape failure; the four commands already gated on cwd (`deps resolve`/`update`, `install`, `publish`, `emoji build`) keep their own bare message and 66, a pre-existing split left alone. Multi-level layouts lose nothing: a package root holding `src/main.emo` runs as `emo run src/main.emo` from that root, because the entry names a module path of the package, not a file beside the cwd. The cost was paid once, in the sweep — every runnable tree that lacked a manifest got one (16 under `examples/`, 7 under `benchmarks/`, 6 under `spike/`, and the release workflow's smoke project), and the tests were restructured so each fixture stands in the directory it roots at, in a directory of its own, since a rooted tree is parsed and checked whole and one broken fixture would otherwise poison its siblings. The LSP tightened the same way: it indexes a project only when the root it was handed holds `package.emo` (`find_root` returns an option, no upward guess), publishes no diagnostics for a root without one, and says why — one `window/showMessage` warning when `initialize` finds none, and a deduplicated `window/logMessage` per manifest-less directory a buffer arrives in, pointing at the existing `emo.package.init` command. `scan` now skips a child directory carrying its own manifest, matching the compiler's `walk`: the index used to be a superset, so the editor resolved references the compiler refused. Consequence worth naming, because it is the point of the rule: `emo check <FILE>` from the repository root no longer works as a convenience — this repository's root carries no manifest, so the command stops with E5010 and you `cd` into the package first, which is the one behaviour the rule is meant to produce.

- The `beam` target's function values and loop-body rebinding: **found 2026-10-16 (T48.4) — both were silent, and both are fixed.** The terminal backend's scripted run forced two lowering defects the beam goldens had no shape to reach. **(1) A bare def passed as a `Block` was emitted as `fun 'mod':'name'/arity`** (`emo_beam.ml`, the `Global` arm) — a *remote* fun naming a function the emitted module does not export. `erlc` accepts it, so the build was green, but the loader leaves the module unusable: every call, `main/0` included, raises `undef`, and `erlang:function_exported(out, main, 0)` still answers `true`. Nothing that hands an application's `view`/`update` to `ui.run` could run on beam, which is why the T48.2 gate read "beam builds the loop" and never "beam runs it". The fix emits a local closure over the plain function (`fun (_blk1, _blk2) -> apply 'name'/2 (_blk1, _blk2)`); the whole program lowers into one BEAM module, so a local reference is always callable. **(2) A `case` inside a loop body did not thread a rebinding of an outer `var` out of the branch.** `emit_loop_body`'s `case` arm went through the plain `stmt` path, whose branch `let`s shadow only inside the branch, so `var more = true` / `while more { case … 3 -> { more = false } … }` never ended and `var acc` accumulation inside a `case` was dropped — the promise `examples/branch_var` states ("a `var` rebound inside an `if`, a `case`, or a loop body keeps its new value") held at statement level and not inside a loop. The fix routes a rebinding `case` through the same `emit_threaded_control` threading the statement level already used. `test/emo_cli`'s `beam_block` group pins (1) and `beam_var` group pins (2); the `typescript` emitter still shares (2) — `bucket` in `examples/branch_var` prints `30 30 30` there — which is the same pre-existing gap the target's missing example coverage hides, recorded here rather than fixed because the TS runtime is being split for the browser (`CHECK.md`, the cross-target invariants entry above).

- A `for` loop inside a class `init` on `beam`: **found 2026-10-16 (T48.4) — open; the TUI backend works around it.** `beam` lowers the loop's statements into a helper that no longer has `self` in scope, so a class whose `init` builds a value with a loop fails the build with `unbound variable '_selfN' in <module>__<Class>__new/1`. A minimal repro — `def init(n Int64) { self.n = n; const out = ArrayBuilder.new(); for var y = 0; y < n; y = y + 1 { out.push(y) } self.rows = Box.new(out.to_array()) }` — builds and runs on `ocaml`, `c` and `typescript` and refuses on `beam`. `projects/emo-ui/tui/ui_tui.emo`'s `Screen.init` calls the top-level `blank_rows(width, height)` for exactly this reason, and says so at the call site; a fix belongs with the emitter's `init` lowering, beside the two defects above.

- Registry endpoints and the HTTP pull: **settled (2026-10-16).** The manifest gains an optional `registry = "https://…"` field naming the endpoint the *project* pulls dependencies from — read only when the manifest is the project root, ignored in a dependency's own manifest (a package is always fetched from the registry its consumer chose), and naming the publish endpoint too (**amended 2026-10-17**, superseding the same-day cut that kept `emo publish` off the field): `emo publish` resolves its endpoint as `--registry` / `EMO_REGISTRY` / the manifest's `registry` field / the most recent stored login, and `emo emoji login` reads the first three the same way (it has no stored login to fall back to), so the project's manifest is the one place its registry is named; the manifest outranks the machine-local most-recent-login fallback because a committed choice beats an accident of login order, and the token still comes only from the entry minted for the resolved registry. The field takes URLs only: a committed manifest must name an endpoint every machine reaches identically, so filesystem registries remain an `EMO_REGISTRY`-only developer/test affordance — and `EMO_REGISTRY` itself now accepts an `http(s)://` value too (previously a URL there was silently misread as a directory). Pull precedence: `EMO_REGISTRY` > the manifest field > the bundled stdlib. Two consequences fall out of the name-ownership rule: a package is publishable only as `owner/name`, so a registry service can never host the top-level short names — under an HTTP registry, unscoped (stdlib) names route to the bundled registry while scoped names go remote, and one merged index feeds the single MVS solve so a scoped package's stdlib dependency resolves in the same pass; and the frozen pull protocol (`GET /api/v1/packages/:owner/:name/versions`, `GET /api/v1/dependencies?packages=…`, `GET /downloads/<owner>-<name>-<version>.emoji`) is spoken by embedded Emo programs over the bundled `http`/`json` packages — the publish uploader's mechanism — so a lone binary pulls with no HTTP stack of its own. Yanked versions are excluded from fresh resolution but stay downloadable for existing lockfiles. And the gap this closes surfaced a latent one: `package.lock` checksums were recorded but never compared on re-fetch — every fetch path (resolve, install, run/build/check's load) now verifies the content digest against the lockfile or the registry's advertised checksum, E5007 on mismatch, for every endpoint kind. The `.emoji` decoder (`Archive.unpack`) reads both this encoder's stored blocks and general deflate streams (fixed and dynamic Huffman) back — required because the registry service re-packs uploads into its canonical archive (compressed, with an `EMO-METADATA.json` member that never feeds the content digest) — verifying both gzip trailers and every tar header checksum. LSP package-name completion skips HTTP endpoints rather than blocking the editor on the network.

- Package name characters and the archive filename: **settled (2026-10-17) — each part of an `owner/name` package name is a lowercase identifier: 1–64 characters, a letter first, then letters, digits, or `_`; `-` is excluded.** The short name is what `require` binds, so a dash in it could never survive contact with code — `require "david/foo-bar"` names a module `foo-bar`, which no identifier can spell — and since publishing runs through one central registry, the registry simply refuses such names instead of defining a transliteration (the crates.io `-`→`_` mapping is the rejected shape: one package, two spellings). Underscore stays, after a same-day reversal of an over-tight first cut: `_` is in the identifier alphabet and never collides with the filename's dash joins, and the one place a `_` can visually vanish — underlined links and italic prose — is a rendering problem, met by the discipline that identifiers always render as code (monospace, never underlined) on the registry site and in docs; banning `_` in the language would have bought nothing for it while making every call site read against Emo's snake_case grain. The same rule covers registry usernames and org names: they become the owner part of published names, so a looser identity rule would mint accounts that could never publish under their own name. The payoff lands in the wire format: with dash-free parts, the published archive's name and the download URL join with single dashes — `<owner>-<name>-<version>.emoji`, `GET /downloads/<owner>-<name>-<version>.emoji` — replacing the `--` joins that existed only to stay parseable against dash-bearing names; the server's parse is unchanged apart from the separator, since versions are strict major.minor.patch and owner/name parts never contain a dash, the filename is always exactly three dash-separated segments. This supersedes the `--` spelling in the registry-endpoints entry above; the registry service enforces the same name rule and the same parse.
