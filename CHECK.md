# CHECK

Pending design decisions — deliberately kept out of the README until they are settled.

- Mixin mechanism: **settled (2026-10-06) — not added.** An `include`-style mixin is inheritance renamed: a single include is single inheritance, multiple includes are multiple inheritance, and both drag in method-resolution order, diamond ambiguity, implicit method provenance, `self` / field coupling, and the fragile-base problem — exactly what the no-inheritance decision rejected. Interfaces with default method bodies are the same trap and are also excluded. Reuse stays with duck-typed functions, composition, and structural interfaces. Delegation is not a separate mechanism either: forwarding to a contained object is ordinary composition code — `def draw() { return self.inner.draw() }` — and gets no construct, keyword, or auto-forwarding, because it expresses nothing the ordinary methods cannot and would only hide method provenance. Struct embedding is the same space under another name: Go's anonymous embedding promotes an inner type's methods and fields into the outer one, which is inheritance in effect — promotion, shadowing, and a depth-based resolution rule together are a hidden method-resolution order — and it leaves the outer type's method set invisible at its declaration. It also amplifies *accidental interface satisfaction*: because Emo's interfaces are structural (satisfaction by shape, no `implements`), a promoted method can make a type satisfy an interface its author never intended, and a later change to the embedded type silently flips that satisfaction. Go's embedding of `sync.Mutex` — which exposes `Lock`/`Unlock` and satisfies `sync.Locker` without the author asking — is the canonical example. Emo's safeguard is that a class's method set is exactly its own `def`s, so satisfaction changes only when its own body changes; the residual coincidental-name hazard is inherent to structural typing and is mitigated by small, clearly named interfaces. The whole inheritance-shaped space — mixin, include, default methods, delegation, embedding — is therefore closed: reuse is duck-typed functions, composition, and structural interfaces, plus plain code.
- Exception catching syntax: **settled (2026-10-06)** — `begin { body } catch { pattern -> { } } ensure { }`, with `raise` unchanged for throwing. `catch` reuses the `case`/`receive` branch grammar on the caught exception (no scrutinee); the first matching branch wins, and a raise that matches no branch keeps propagating (unlike `case`, which errors on no match). The three clauses share one scope, so `ensure` can release resources acquired in `begin`; `ensure` runs on every exit (normal completion, raise, or `return`). The construct is a statement, not an expression, and there are still no checked exceptions (README). Implementation is unscheduled.
- Raw strings: **settled (2026-10-06)** — not needed now. There is no regex and no multi-line string requirement, and a raw string hides the escaping that "everything is visibly what it is" wants visible; the escape set stays `\n \r \t \\ \' \"`. Revisit only if regex or text templating lands, and then with a form of Emo's own (not Go backticks, Rust `r"..."`, or Python triple quotes).
- Numeric literal formats: **settled (2026-10-06)** — hexadecimal `0x`, binary `0b`, and octal `0o` prefixes, plus `_` as a digit separator (`1_000_000`, `0xFFFF_FFFF`); no C-style leading-zero octal and no width suffixes (bare literals stay `Int64`/`Float64`; `Byte` keeps its `B` suffix). Floats gain exponent forms (`1e10`, `1.5e-3`); no hex floats. The prefixes are a shared C-family convention, not one language's signature.
- Numeric width: **settled** — numeric types are width-explicit: `Int64`/`Int32` and `Float64`/`Float32`; defaults are `Int64` and `Float64`; no width-less `Int`/`Float` spellings; bare literals default to the 64-bit type (decided 2026-10-05 — README, Type System; rationale in `docs/numeric-width.md`). Open: the native backend's route to 64-bit integer arithmetic on OCaml's 63-bit `int` — emit OCaml's boxed `Int64` vs unboxed two-word hi/lo emulation (the technique RV32 codegen will also need). The mechanical `Int` → `Int64` / `Float` → `Float64` rename across checker/stdlib/examples/docs has landed.
- Float math and conversion primitives: **settled** — `Float64.sqrt`/`floor`/`ceil`/`trunc`, `Float64.to_int64` (truncating toward zero), and `Int64.to_float64` joined the core surface (decided 2026-10-06); the first consumer is the wasm interpreter (step 21), which needed them for the float families. `nearest` (round-half-to-even) is built in Emo from `floor`. The TS / wasm / BEAM backends do not yet emit these; a target that cannot honor one fails loudly, per the `foreign def` rule.
- Float math and conversion primitives: the wasm interpreter (step 21) is the first consumer that needs `sqrt`, `floor`, `ceil`, `trunc`, `nearest`, and float ↔ int conversion (`Float64.to_int64` / `Int64.to_float64`). Today the only path is `foreign def` (native-only, and unavailable under `emo run`), so the runtime would otherwise reimplement correctly-rounded `sqrt` and the rounding directions in Emo. Settle whether these join the core surface — with a second consumer named, per the unification gate — or stay out and force the workaround; the pressure is recorded in `plan/step-21-wasm-interpreter.md`.
- Int32 / Float32: explicitly-named fixed-width types for FFI (`int32_t` / C `float`), bare-metal MMIO/device registers, and RV32 hot loops. **Surface settled (2026-10-06)**: explicit-only conversions named with the existing pattern (`Int32.from_int64(x)` / `x.to_int32()`, `Float32.from_float64(x)` / `x.to_float32()`); no implicit conversions and no mixed arithmetic; `Int32` wraps modulo 2³², `Float32` rounds per operation to binary32; no width suffixes (bare literals stay `Int64`/`Float64`). See `docs/numeric-width.md`.
- `foreign def` on non-native targets: **settled (2026-10-06)** — every target that cannot honor `foreign def` refuses it loudly at check time with a clear diagnostic, driven by a target-capability table (today only the OCaml-emitting native backend can honor it; the future `c` backend will too; `wasm`, `typescript`, `beam`, and the freestanding `riscv64` until C interop lands all refuse). Per-target availability is also declared through the manifest's `targets` mechanism, so a package is rejected at resolution. This gates any FFI deepening.
- C FFI binding-surface syntax: **settled in step 13** — `foreign def name(params) Ret = "c_symbol"`, `Float64`/`String`/`Bool` only, compiled through generated C wrappers (see `docs/native-backend.md`).
- Self-contained hosted native backend (no OCaml runtime): **scheduled as step 24 (2026-10-06)** — `plan/step-23-hosted-native-ffi.md` remains the design record; `plan/step-24-c-target.md` is the execution plan. (a) Settled: the route is emit C (next item). (b) Reclamation stays open — bump/arena with documented leakage is the provisional profile; settle reference counting vs bounded arenas in `CHECK.md` before any long-running dynamic program ships (gates T24.5). (c) The HPC surface stays out of step 24's scope — it remains the gate beyond the backend. When the `c` backend covers the golden subset it supersedes the open item above on the native backend's route to 64-bit integer arithmetic on OCaml's 63-bit `int`.
- Codegen route for a self-contained native backend: **settled (2026-10-06) — emit C**, the step-24 route, with LLVM ruled out (C++ dependency, unstable API, opaque generated code, against the "emit and delegate" / readable-output line) and hand assembly confined to the freestanding `riscv64` target. Emitting C reuses the existing `cc` dependency, yields GCC/Clang autovectorization and OpenMP pragmas, and makes the C ABI the FFI surface. **Tail-call lowering settled (2026-10-06, step 24): the trampoline / block loop** — every self- or mutually-tail call is a parameter rebind and a jump to the function head, and `return` is a branch to the epilogue, never a raised signal (this is also the fix for the emit-OCaml backend's ~4x loop regression). **Wrap-around `Int64` settled (2026-10-06): unsigned `uint64_t` arithmetic cast back; `-fwrapv` is the documented fallback, not the plan.** The emitter also owns `restrict`-annotated vectorizer-friendly loops and the dynamic layer (tagged unions plus `retain`/`release`; exceptions via `setjmp`/`longjmp`). See `plan/step-23-hosted-native-ffi.md` and `plan/step-24-c-target.md`.
- Reclamation model for the dynamic world without a tracing GC: **settled (2026-10-06, the T24.5 gate) — reference counting over the identity-bearing objects**, with the value-semantic data arena-allocated. Only instances, closures, and Box carry identity in Emo; tuples, arrays, and strings are value-semantic (assignment copies), so they cannot participate in cycles and stay in the bump arena until process exit — no per-object bookkeeping for them. The identity objects get malloc'd cells with a header refcount; the emitter owns the discipline (increment on capture/assignment into a longer-lived slot, decrement at binding scope exit and on overwrite; write barriers on the two mutation points — `Set_field` and `Box.replace`); cycles among instances and closures leak, documented (the Swift model). No language-surface addition is required: refcounts live in the cell header. Rationale: the settled codegen route already names `retain`/`release` as what this emitter owns; reference counting needs no stop-the-world, fits Emo's value semantics (the Swift / Objective-C lineage CHECK.md already cites), and frees memory before the scheduler and IO tasks (T24.9/T24.10) make long-running programs real. The `c` backend continues to ship the bump/arena profile with documented leakage through the golden tier — every golden program runs to exit — and the retain/release emitter work lands before T24.9 makes processes real; a future precise collector remains possible on the same layout (an immediate is never a valid pointer).
- C runtime string layout: **settled (2026-10-06, T24.3)** — a String in the `c` backend's runtime is `emo_str {int64 len; const char *bytes}`, length-prefixed and passed by value; no NUL terminator internally, one is appended only when a string crosses the FFI boundary (T24.8). Literals are C compound literals; the builders (concat, the scalar renderings) allocate with malloc and leak by design until the reclamation decision lands. T24.4's heap String cell keeps this layout inside the tagged word's cell.
- The `c` backend's runtime language: **settled (2026-10-06, T24.3) — C, not Emo's specialized subset** (step 23 leaned C: interop is a bridge, not a foundation). The runtime stays readable, reviewable C in `src/emo_codegen/c/`, compiled by the same `cc` invocation as the emitted program; self-hosting the runtime is not a goal (the reference implementation is OCaml by design).
- HPC criteria for the self-contained backend, **in priority order**: (1) vectorization/SIMD — the codegen route must deliver it (emit C, not LLVM or hand assembly); (2) a data-parallel construct (OpenMP-style parallel loop with reductions); (3) zero-copy FFI buffer passing — a mutable, address-stable, typed buffer (`Buffer[Float64]` or equivalent) borrowed for the call, per the `cgo` model, since `Array` is immutable and `Bytes` is byte-addressed; (4) ecosystem. GC is a latency and predictability concern (headroom, jitter), not the gate. Reference sample: Go — GC + custom backend + `cgo`, still not an HPC language because it does not autovectorize and has no parallel-loop primitive.
- Loop forms: **direction settled (2026-10-06)** — keep guaranteed tail calls *and* add `for`/`while`. Rationale: tail calls are a semantic (constant-stack iteration), not just an optimization, and they are nearly free on BEAM (native), wasm, and asm (a single `tail`); only the emit-C route needs a trampoline, which is not worth sacrificing the guarantee for. They also carry the actor `receive` idiom (README, Concurrency), and the current native backend's tail-call defect is an implementation bug (the `try … with Native_return` return convention), fixed by a branch to the epilogue, not a reason to change the language. Advantages of the loops: they are the native shape for vectorization/SIMD and `#pragma omp parallel for` (the HPC criteria), they remove the need for tail-position proof in loop code, and they are the least-surprise form for imperative and numeric iteration, pairing with `var`. The Go pre-1.22 loop-capture trap is already prevented — a `var` cannot escape its block, and capturing one in a closure that outlives the block is a compile error (README, Syntax) — so the earlier fresh-binding caution in `plan/README` is subsumed.
- Loop surface: **`for` settled (2026-10-06)** — the form is `for var i = 0; i < 100; i = i + 50 { ... }`: no parentheses (matching the paren-less `if`), a `var` declaration in the header scoped to the header and body, three `;`-separated clauses (init / condition / post), and the post written as an assignment (`i = i + 50`). This makes `;` a token, legal only inside a `for` header — the one place Emo uses it. The parser's existing `suppress_block_sugar` flag (already set for an `if` condition) applies to all three clauses, so a trailing `{` opens the body rather than attaching as a trailing block; the Go loop-capture trap is already prevented by the `var`-escape rule. Worked example: `for var i = 0; i < 100; i = i + 50 { println("i = ${i}") }` prints `i = 0` then `i = 50`. **`while` settled (2026-10-06): `while cond { }`** — paren-less and condition-only; the loop variable is declared before the loop and advanced in the body, e.g. `var i = 0` then `while i < 100 { println("i = ${i}"); i = i + 1 }`. `for` keeps all three clauses (no omissions), since `while` covers the condition-only case. The post / increment stays explicit (`i = i + 1`); `+=`/`++` are not added. **`break` settled (2026-10-06): a bare statement** — `break` takes no arguments and no parentheses, is used inside a loop, and binds to the nearest enclosing loop; `continue` is its pair, skipping to the next iteration and running a `for`'s post clause first. Both are rejected outside a loop. `do`/`while` is not added. With this the loop surface is settled; README and `plan/README` carry it; implementation is unscheduled.
- Backend naming: **settled (2026-10-06)** — drop `native`; name backends by emission mechanism: `ocaml` (emits OCaml, links the OCaml runtime; today's `native`), `c` (emits C, own runtime; the step-23 backend), `riscv64` (emits RISC-V assembly; freestanding), plus `wasm`, `typescript`, `beam`. Rationale: `native` names a category, not a mechanism, and is itself ambiguous (C? riscv64?); the mechanism is what differs between backends and what scales once two hosted machine-code backends exist. `native` ceases to be a `--target` value; "native executable" is prose for what `ocaml`/`c`/`riscv64` produce. `c` is reserved and must not enter `known_targets` until its backend works. The rename is a mechanical whole-repo change, **implemented 2026-10-06** as its own step after step 24 (as allowed): every literal site below now carries `ocaml` — `known_targets`, the CLI default/help/error text, `emo init`'s manifest, `emo_project`'s defaults, the stdlib/example/benchmark `package.emo` files (lockfiles regenerated), the tests including `emo_lsp`'s fixtures, and the docs quoting the target; historical plan files keep the original value with a "today `ocaml`" annotation. Literal target-string sites (2026-10-06 grep): `src/emo_pkg/emo_pkg.ml` (`known_targets` plus two manifest samples), `src/emo_cli/emo_cli.ml` (the `match target` arm, the default value, `~target:"native"`, the `emo init` manifest), `src/emo_project/emo_project.ml` (two `~target:"native"`), the eleven `package.emo` files under `stdlib/registry/` and `examples/`, `test/emo_pkg/emo_pkg_test.ml`, `test/emo_project/emo_project_test.ml`, and the docs that quote the target (`README.md`, `docs/zh-CN/README.zh-CN.md`, `docs/stdlib/{net,http}.md`, `docs/zh-CN/stdlib/{net,http}.md`, `docs/TASKS.md`, `docs/zh-CN/TASKS.md`, `plan/step-12-networking.md`, `plan/step-15-typescript.md`, `plan/step-19-wasm-runtime.md`); prose `native` meaning native code (`docs/native-backend.md`, `docs/industrial-software.md`) is unaffected.
- Binary / CLI tool distribution mechanism: **direction settled (2026-10-06) — defer to the `c` backend, then ship self-contained `emo` tool binaries per platform.** The `c` backend drops the OCaml-toolchain dependency from the tool, so a per-platform `emo` binary becomes usable; it does **not** drop `cc` — `emo build` still invokes the system C compiler for the emitted C, a far lower bar than OCaml (only a direct machine-code backend would remove it). Channels: prebuilt binaries per platform (GitHub Releases) as the primary route, with `opam` and a Homebrew formula as the source-building alternatives. macOS notarization is **solved, not a blocker**: with an Apple Developer account, sign (`codesign`, hardened runtime), notarize (`notarytool`), and staple the distributed zip (a bare Mach-O cannot be stapled); the certificate and credentials live in CI secrets. Windows ships prebuilt; signing uses **Microsoft Trusted Signing** — a managed cloud service (subscription, CI-friendly, short-lived certificates, builds SmartScreen reputation) — since the project has a registered company to pass organizational identity validation, or an OV/EV Authenticode certificate (post-2023 CAs require the key on hardware/HSM). SmartScreen reputation accrues with download volume rather than switching on with a certificate, and distributing through winget/scoop/chocolatey avoids the browser's Mark-of-the-Web; EV's historic instant reputation is no longer reliable. Linux ships prebuilt (no gatekeeper equivalent). Release tooling itself is unscheduled. **Interim settled (2026-10-06):** the `c` backend is now scheduled (step 24); until it ships, the emit-OCaml backend stays and `emo build` (native/`ocaml`) requires the user's OCaml toolchain — documented, not hidden. Lower the barrier with a check-and-guide command (`emo doctor`) that detects `ocamlfind`/`ocamlopt`, checks the version against the shipped `emo_runtime.cmxa`, and prints — or, with consent, delegates to the system package manager for — the platform install command; provision through `opam` and Homebrew (`opam install emo` brings a matching toolchain). A self-service `emo toolchain download` was rejected: it would make Emo a compiler redistributor and lock in a subsystem the `c` backend obsoletes. Rationale: `docs/toolchain-distribution.md`.
