# CHECK

Pending design decisions — deliberately kept out of the README until they are settled.

- Mixin mechanism: **settled (2026-10-06) — not added.** An `include`-style mixin is inheritance renamed: a single include is single inheritance, multiple includes are multiple inheritance, and both drag in method-resolution order, diamond ambiguity, implicit method provenance, `self` / field coupling, and the fragile-base problem — exactly what the no-inheritance decision rejected. Interfaces with default method bodies are the same trap and are also excluded. Reuse stays with duck-typed functions, composition, and structural interfaces. Delegation is not a separate mechanism either: forwarding to a contained object is ordinary composition code — `def draw() { return self.inner.draw() }` — and gets no construct, keyword, or auto-forwarding, because it expresses nothing the ordinary methods cannot and would only hide method provenance. Struct embedding is the same space under another name: Go's anonymous embedding promotes an inner type's methods and fields into the outer one, which is inheritance in effect — promotion, shadowing, and a depth-based resolution rule together are a hidden method-resolution order — and it leaves the outer type's method set invisible at its declaration. It also amplifies *accidental interface satisfaction*: because Emo's interfaces are structural (satisfaction by shape, no `implements`), a promoted method can make a type satisfy an interface its author never intended, and a later change to the embedded type silently flips that satisfaction. Go's embedding of `sync.Mutex` — which exposes `Lock`/`Unlock` and satisfies `sync.Locker` without the author asking — is the canonical example. Emo's safeguard is that a class's method set is exactly its own `def`s, so satisfaction changes only when its own body changes; the residual coincidental-name hazard is inherent to structural typing and is mitigated by small, clearly named interfaces. The whole inheritance-shaped space — mixin, include, default methods, delegation, embedding — is therefore closed: reuse is duck-typed functions, composition, and structural interfaces, plus plain code.
- Error handling: **settled (2026-10-11) — no catch construct; expected failures are values, violations raise.** Supersedes the 2026-10-06 `begin`/`catch`/`ensure` settle. The deciding evidence is the backends: `interp`/`ocaml`/`ts`/`beam` get host exceptions for free, but `c` needs `setjmp`/`longjmp` plus a drain of the refcount/autorelease state along every unwound frame, wasm's raise is a host `abort` no in-wasm handler can resume from, and `riscv64` refuses `raise` outright — six targets, six stack disciplines, a permanent two-tier language for one construct. The Erlang split takes its place, and Emo already runs its other half (an uncaught exception kills only the offending process, the per-process arena reclaims its memory, supervision is library-level): an **expected failure** — parse errors, IO, network, not-found, anything the data can trigger — is an ordinary value, the call returning `(R.ok, value)` or `(R.error, reason)`, the reason a String carrying the message convention (package prefix: `json: expected array element at byte 3`); a **violation** — a broken contract, a bug — raises and ends the process. `Exception` stays the language's one exception class — no subclasses (Emo has no inheritance), the name reserved against user shadowing — carrying `message` and an optional `data` Map whose role is machine-readable context for crash reports and supervision, never type identity: nothing dispatches on exceptions when nothing catches them, so the `e.is(Timeout)` narrowing idea dies with the catch design. The `raise` operand must be an `Exception` instance (anything else gets its own E-code), and the uncaught report prints non-empty `data` alongside the message. `R { ok, error }` is a built-in enum (root-env binding, the `Exception` precedent) so matching a returned tuple never costs an import; the tag is spelled `R.ok`/`R.error` — a bare lowercase `ok` in a pattern is a binding and would match everything, and atoms (`:ok`) were rejected as a new value type across all targets for what the enum already expresses. The name's one shadow — the R language of statistical computing — is cosmetic: the two never share an artifact (that R lives as the `/usr/bin/R` command, `.R` files, and CRAN; Emo's `R` is a type name always spelled in qualified form — `R.ok`, `(R, String)` — and no Emo command, file extension, or package carries the bare letter), a single-letter identifier inside another language raises no trademark question, and the fingerprint test passes — enum-dot tags over tuples are the Erlang shape, and R has no such syntax (its counterpart concept is the factor). Migration is the follow-up: the eight raising packages (~220 raise sites) and the native builtins (`os`/`file`/`net`) split per call into tuple returns and keep-raising violations.
- Binding patterns: **settled (2026-10-11)** — `const` and `var` take a full pattern, not just a name: `const (R.ok, body) = file.read(path)`. A pattern that does not match is a runtime error — the same rule as a `case` scrutinee matching no branch — making the assert-match binding (Erlang's `{ok, B} = f(X)`) the expect-success fast path of the tuple convention. No `match` keyword: the construct is a binding, and `case` already owns the pattern vocabulary. Lowered at IR level by desugaring to a one-arm `case` wrapping the rest of the block, so the six backends see only existing nodes; the parser's `const (` form is a hard error today, so the extension breaks no grammar.
- Type layering: **settled (2026-10-11) — three tiers, two promotion criteria, the freestanding target as the accretion stop.** "Built-in" is two orthogonal axes: name availability (spellable without `require`) and per-target capability (the target-capability table — the split already exists: `riscv64` refuses `raise` and check-refuses `Map` while the names stay import-free). **Spec core**: the value model the language's own semantics depend on — `Bool`/`Char`/`Int64`/`Byte`/`Float64`/`String`/`Array`/`Tuple`/enum/class/interface, plus `R` (it is an enum); a target that cannot implement the tier is not an Emo target. **Capability builtins**: `Map`/`List`/`Box`/`Bytes`/`Pid`/the connection types/`Exception` — import-free names, gated per target, the tier **frozen** (its status is the checker's inherited type vocabulary, not a precedent; refusing where unimplementable is the tier's normal shape). **Stdlib**: every future type lands there by default. Promotion needs (a) *syntax dependence* — a syntactic construct's own operand type (`Exception` qualifies through `raise`; nothing else does), or (b) *universal dependence plus trivial implementability on every target including freestanding* (`R` qualifies: every failing call returns it, and it lowers to a tagged word). The freestanding target is the standing reason the capability tier stays frozen: each type promoted above the spec core must either be re-implemented in assembly for `riscv64` or publicly refused, fragmenting the language. (The lineage analogue is C's freestanding profile; the wording is Emo's own.)
- Raw strings: **settled (2026-10-06)** — not needed now. There is no regex and no multi-line string requirement, and a raw string hides the escaping that "everything is visibly what it is" wants visible; the escape set stays `\n \r \t \\ \' \"`. Revisit only if regex or text templating lands, and then with a form of Emo's own (not Go backticks or Python triple quotes).
- Numeric literal formats: **settled (2026-10-06)** — hexadecimal `0x`, binary `0b`, and octal `0o` prefixes, plus `_` as a digit separator (`1_000_000`, `0xFFFF_FFFF`); no C-style leading-zero octal and no width suffixes (bare literals stay `Int64`/`Float64`; `Byte` keeps its `B` suffix). Floats gain exponent forms (`1e10`, `1.5e-3`); no hex floats. The prefixes are a shared C-family convention, not one language's signature.
- Numeric width: **settled** — numeric types are width-explicit: `Int64`/`Int32` and `Float64`/`Float32`; defaults are `Int64` and `Float64`; no width-less `Int`/`Float` spellings; bare literals default to the 64-bit type (decided 2026-10-05 — README, Type System; rationale in `docs/numeric-width.md`). The last open sub-item **settled (2026-10-11): the `ocaml` backend's route is boxed `Int64` — already the shipped route.** The dynamic layer carries `Int64 of int64` and arithmetic emits boxed `Int64.add`-style operations, so 64-bit wrap-around semantics are correct there today; the unboxed two-word hi/lo emulation was never taken (its RV32 motivation is moot — the freestanding target is `riscv64`, with native 64-bit registers), and the `c` target — the default since step 24 — supersedes the performance question, as the step-23 entry above records. The mechanical `Int` → `Int64` / `Float` → `Float64` rename across checker/stdlib/examples/docs has landed.
- Float math and conversion primitives: **settled** — `Float64.sqrt`/`floor`/`ceil`/`trunc`, `Float64.to_int64` (truncating toward zero), and `Int64.to_float64` joined the core surface (decided 2026-10-06); the first consumer is the wasm interpreter (step 22), which needed them for the float families. `nearest` (round-half-to-even) is built in Emo from `floor`. The TS / wasm / BEAM backends do not yet emit these; a target that cannot honor one fails loudly, per the `foreign def` rule.
- Int32 / Float32: explicitly-named fixed-width types for FFI (`int32_t` / C `float`), bare-metal MMIO/device registers, and RV32 hot loops. **Surface settled (2026-10-06)**: explicit-only conversions named with the existing pattern (`Int32.from_int64(x)` / `x.to_int32()`, `Float32.from_float64(x)` / `x.to_float32()`); no implicit conversions and no mixed arithmetic; `Int32` wraps modulo 2³², `Float32` rounds per operation to binary32; no width suffixes (bare literals stay `Int64`/`Float64`). See `docs/numeric-width.md`.
- `foreign def` on non-native targets: **settled (2026-10-06)** — every target that cannot honor `foreign def` refuses it loudly at check time with a clear diagnostic, driven by a target-capability table (today only the OCaml-emitting native backend can honor it; the future `c` backend will too; `wasm`, `typescript`, `beam`, and the freestanding `riscv64` until C interop lands all refuse). Per-target availability is also declared through the manifest's `targets` mechanism, so a package is rejected at resolution. This gates any FFI deepening.
- C FFI binding-surface syntax: **settled in step 14** — `foreign def name(params) Ret = "c_symbol"`. The capability table moved with the targets (2026-10-10): the `c` target calls the symbol directly (step 23) and honors `Int64` parameters plus `Void` returns — the shape of a fire-and-forget call, and every externally linkable declaration lands in `.emo-build/emo_defs.h` for shims to compile against; the OCaml-emitting backend wraps `Float64`/`String`/`Bool` through generated C stubs (see `docs/native-backend.md`).
- Self-contained hosted native backend (no OCaml runtime): **scheduled as step 23 (2026-10-06)** — `plan/hosted-native-ffi.md` remains the design record; `plan/step-23-c-target.md` is the execution plan. (a) Settled: the route is emit C (next item). (b) Reclamation **settled 2026-10-06** by the dedicated entry below — reference counting over the identity-bearing objects, value-semantic data arena-allocated (the T23.5 gate). (c) The HPC surface stays out of step 23's scope — it remains the gate beyond the backend. When the `c` backend covers the golden subset it supersedes the open item above on the native backend's route to 64-bit integer arithmetic on OCaml's 63-bit `int`.
- Codegen route for a self-contained native backend: **settled (2026-10-06) — emit C**, the step-23 route, with LLVM ruled out (C++ dependency, unstable API, opaque generated code, against the "emit and delegate" / readable-output line) and hand assembly confined to the freestanding `riscv64` target. Emitting C reuses the existing `cc` dependency, yields GCC/Clang autovectorization and OpenMP pragmas, and makes the C ABI the FFI surface. **Tail-call lowering settled (2026-10-06, step 23): the trampoline / block loop** — every self- or mutually-tail call is a parameter rebind and a jump to the function head, and `return` is a branch to the epilogue, never a raised signal (this is also the fix for the emit-OCaml backend's ~4x loop regression). **Wrap-around `Int64` settled (2026-10-06): unsigned `uint64_t` arithmetic cast back; `-fwrapv` is the documented fallback, not the plan.** The emitter also owns `restrict`-annotated vectorizer-friendly loops and the dynamic layer (tagged unions plus `retain`/`release`; `raise` terminates the process — no unwinder exists, per the error-handling entry). See `plan/hosted-native-ffi.md` and `plan/step-23-c-target.md`.
- Reclamation model for the dynamic world without a tracing GC: **settled (2026-10-06, the T23.5 gate) — reference counting over the identity-bearing objects; implemented on the `c` target 2026-10-11.** Only instances, closures, and Box carry identity in Emo; tuples, arrays, and strings are value-semantic (assignment copies), so they cannot participate in cycles and stay in the bump arena until process exit — no per-object bookkeeping for them. The identity objects get malloc'd cells with a header refcount; the emitter owns the discipline (increment on capture/assignment into a longer-lived slot, decrement at binding scope exit and on overwrite; write barriers on the two mutation points — `Set_field` and `Box.replace`); cycles among instances and closures leak, documented (the Swift model). No language-surface addition is required: refcounts live in the cell header. Rationale: the settled codegen route already names `retain`/`release` as what this emitter owns; reference counting needs no stop-the-world, fits Emo's value semantics (the Swift / Objective-C lineage CHECK.md already cites), and frees memory before the scheduler and IO tasks (T23.9/T23.10) make long-running programs real. **The landed shape adds one runtime mechanism the settle's wording predates: a frame-scoped autorelease pool (the ObjC shape) — every generated body opens a pool at entry and closes it at every return, and statement boundaries drain the current frame — so expression-internal temporaries need no ownership analysis at any call site.** The emitter's discipline in full: a dynamic binding retains at init and releases at its block's end (bindings in a re-entered tail body hoist their zero-initialized slots and release-on-reassign, so a tail-recursive loop reclaims per pass); a parameter slot of a re-entered body retains at entry and releases at exit; tail-call rebinds swap through a write barrier and unwind the current pass's bindings while keeping the slots the next pass loads; `Set_field`/`Box.replace` barriers live inside the runtime entry points; closure creation and the arena aggregates retain what they capture (arena-held identities live to process exit, the documented shape); `send`/`spawn` retain into the mailbox/fiber, and a taken message transfers. The same-day verification: the whole golden tier byte-identical, plus a live-count probe (`emo_identity_live_count`) asserting a 10 000-iteration churn loop returns the identity count to its baseline while a List-held instance stays live. A future precise collector remains possible on the same layout (an immediate is never a valid pointer).
- C runtime string layout: **settled (2026-10-06, T23.3)** — a String in the `c` backend's runtime is `emo_str {int64 len; const char *bytes}`, length-prefixed and passed by value; no NUL terminator internally, one is appended only when a string crosses the FFI boundary (T23.8). Literals are C compound literals; the builders (concat, the scalar renderings) allocate with malloc and leak by design until the reclamation decision lands. T23.4's heap String cell keeps this layout inside the tagged word's cell.
- The `c` backend's runtime language: **settled (2026-10-06, T23.3) — C, not Emo's specialized subset** (the hosted-native-FFI assessment leaned C: interop is a bridge, not a foundation). The runtime stays readable, reviewable C in `src/emo_codegen/c/`, compiled by the same `cc` invocation as the emitted program; self-hosting the runtime is not a goal (the reference implementation is OCaml by design).
- HPC criteria for the self-contained backend: **settled (2026-10-11) as the standing gate, in this priority order**: (1) vectorization/SIMD — the codegen route must deliver it (emit C, not LLVM or hand assembly); (2) a data-parallel construct (OpenMP-style parallel loop with reductions); (3) zero-copy FFI buffer passing — a mutable, address-stable, typed buffer (`Buffer[Float64]` or equivalent) borrowed for the call, per the `cgo` model, since `Array` is immutable and `Bytes` is byte-addressed; (4) ecosystem. GC is a latency and predictability concern (headroom, jitter), not the gate. Reference sample: Go — GC + custom backend + `cgo`, still not an HPC language because it does not autovectorize and has no parallel-loop primitive.
- Loop forms: **direction settled (2026-10-06)** — keep guaranteed tail calls *and* add `for`/`while`. Rationale: tail calls are a semantic (constant-stack iteration), not just an optimization, and they are nearly free on BEAM (native), wasm, and asm (a single `tail`); only the emit-C route needs a trampoline, which is not worth sacrificing the guarantee for. They also carry the actor `receive` idiom (README, Concurrency), and the current native backend's tail-call defect is an implementation bug (the `try … with Native_return` return convention), fixed by a branch to the epilogue, not a reason to change the language. Advantages of the loops: they are the native shape for vectorization/SIMD and `#pragma omp parallel for` (the HPC criteria), they remove the need for tail-position proof in loop code, and they are the least-surprise form for imperative and numeric iteration, pairing with `var`. The Go pre-1.22 loop-capture trap is already prevented — a `var` cannot escape its block, and capturing one in a closure that outlives the block is a compile error (README, Syntax) — so the earlier fresh-binding caution in `plan/README` is subsumed.
- Loop surface: **`for` settled (2026-10-06)** — the form is `for var i = 0; i < 100; i = i + 50 { ... }`: no parentheses (matching the paren-less `if`), a `var` declaration in the header scoped to the header and body, three `;`-separated clauses (init / condition / post), and the post written as an assignment (`i = i + 50`). This makes `;` a token, legal only inside a `for` header — the one place Emo uses it. The parser's existing `suppress_block_sugar` flag (already set for an `if` condition) applies to all three clauses, so a trailing `{` opens the body rather than attaching as a trailing block; the Go loop-capture trap is already prevented by the `var`-escape rule. Worked example: `for var i = 0; i < 100; i = i + 50 { println("i = ${i}") }` prints `i = 0` then `i = 50`. **`while` settled (2026-10-06): `while cond { }`** — paren-less and condition-only; the loop variable is declared before the loop and advanced in the body, e.g. `var i = 0` then `while i < 100 { println("i = ${i}"); i = i + 1 }`. `for` keeps all three clauses (no omissions), since `while` covers the condition-only case. The post / increment stays explicit (`i = i + 1`); `+=`/`++` are not added. **`break` settled (2026-10-06): a bare statement** — `break` takes no arguments and no parentheses, is used inside a loop, and binds to the nearest enclosing loop; `continue` is its pair, skipping to the next iteration and running a `for`'s post clause first. Both are rejected outside a loop. `do`/`while` is not added. With this the loop surface is settled; README and `plan/README` carry it; **implemented 2026-10-11 (step 26)** — lexer, parser, checker, and interpreter (`examples/loops` golden through `emo run`, ten million iterations flat), with the six backends refusing the loop statements until step 27 lowers them. **Lowered on all six targets (2026-10-11, step 27)**: the IR carries While/For/Break/Continue; c emits its own `while` and a `while(1)` form whose continue label runs the post; ocaml uses the ref discipline plus a pair of local exceptions per loop; typescript uses the native `for` with a labeled driver loop for tail calls; wasm lowers to block/loop/br_if with a post block; beam threads every free variable through a hidden recursive function with a done flag; riscv64 uses labels and jumps, and gained `/` and `%` (`div`/`rem` with a zero-division abort) so `examples/loops` boots — golden on all six targets plus the interpreter.
- Backend naming: **settled (2026-10-06)** — drop `native`; name backends by emission mechanism: `ocaml` (emits OCaml, links the OCaml runtime; today's `native`), `c` (emits C, own runtime; the step-23 backend), `riscv64` (emits RISC-V assembly; freestanding), plus `wasm`, `typescript`, `beam`. Rationale: `native` names a category, not a mechanism, and is itself ambiguous (C? riscv64?); the mechanism is what differs between backends and what scales once two hosted machine-code backends exist. `native` ceases to be a `--target` value; "native executable" is prose for what `ocaml`/`c`/`riscv64` produce. `c` is reserved and must not enter `known_targets` until its backend works. The rename is a mechanical whole-repo change, **implemented 2026-10-06** as its own step after step 23 (as allowed): every literal site below now carries `ocaml` — `known_targets`, the CLI default/help/error text, `emo init`'s manifest, `emo_project`'s defaults, the stdlib/example/benchmark `package.emo` files (lockfiles regenerated), the tests including `emo_lsp`'s fixtures, and the docs quoting the target; historical plan files keep the original value with a "today `ocaml`" note. Literal target-string sites (2026-10-06 grep): `src/emo_pkg/emo_pkg.ml` (`known_targets` plus two manifest samples), `src/emo_cli/emo_cli.ml` (the `match target` arm, the default value, `~target:"native"`, the `emo init` manifest), `src/emo_project/emo_project.ml` (two `~target:"native"`), the eleven `package.emo` files under `stdlib/registry/` and `examples/`, `test/emo_pkg/emo_pkg_test.ml`, `test/emo_project/emo_project_test.ml`, and the docs that quote the target (`README.md`, `docs/zh-CN/README.zh-CN.md`, `docs/stdlib/{net,http}.md`, `docs/zh-CN/stdlib/{net,http}.md`, `docs/TASKS.md`, `docs/zh-CN/TASKS.md`, `plan/step-13-networking.md`, `plan/step-17-typescript.md`, `plan/step-20-wasm-runtime.md`); prose `native` meaning native code (`docs/native-backend.md`, `docs/industrial-software.md`) is unaffected.
- Binary / CLI tool distribution mechanism: **direction settled (2026-10-06) — defer to the `c` backend, then ship self-contained `emo` tool binaries per platform.** The `c` backend drops the OCaml-toolchain dependency from the tool, so a per-platform `emo` binary becomes usable; it does **not** drop `cc` — `emo build` still invokes the system C compiler for the emitted C, a far lower bar than OCaml (only a direct machine-code backend would remove it). Channels: prebuilt binaries per platform (GitHub Releases) as the primary route, with `opam` and a Homebrew formula as the source-building alternatives. macOS notarization is **solved, not a blocker**: with an Apple Developer account, sign (`codesign`, hardened runtime), notarize (`notarytool`), and staple the distributed zip (a bare Mach-O cannot be stapled); the certificate and credentials live in CI secrets. Windows ships prebuilt; signing uses **Microsoft Trusted Signing** — a managed cloud service (subscription, CI-friendly, short-lived certificates, builds SmartScreen reputation) — since the project has a registered company to pass organizational identity validation, or an OV/EV Authenticode certificate (post-2023 CAs require the key on hardware/HSM). SmartScreen reputation accrues with download volume rather than switching on with a certificate, and distributing through winget/scoop/chocolatey avoids the browser's Mark-of-the-Web; EV's historic instant reputation is no longer reliable. Linux ships prebuilt (no gatekeeper equivalent). Release tooling itself is unscheduled. **Interim settled (2026-10-06):** the `c` backend is now scheduled (step 23); until it ships, the emit-OCaml backend stays and `emo build` (native/`ocaml`) requires the user's OCaml toolchain — documented, not hidden. Lower the barrier with a check-and-guide command (`emo doctor`) that detects `ocamlfind`/`ocamlopt`, checks the version against the shipped `emo_runtime.cmxa`, and prints — or, with consent, delegates to the system package manager for — the platform install command; provision through `opam` and Homebrew (`opam install emo` brings a matching toolchain). A self-service `emo toolchain download` was rejected: it would make Emo a compiler redistributor and lock in a subsystem the `c` backend obsoletes. Rationale: `docs/toolchain-distribution.md`.
- Toolchain defaults for the v1.0.0 distribution (M7, step 24): **settled (2026-10-07) — four decisions.** (a) **The default build target flips `ocaml` → `c`**, and the whole default pipeline agrees: `emo build` without `--target`, the project loader's dependency resolution (`emo run`/`emo check`), `emo deps resolve`, and the checker's default capability target all mean `c`. A distributed binary carries no OCaml toolchain, so out of the box the tool must work on the download; the `ocaml` target remains for source installs (opam brings its runtime) and refuses with source-install guidance on a prebuilt installation that lacks it — never raw ocamlfind output. (b) **The stdlib embeds into the compiler as generated data** — the C runtime's own mechanism ("installed files beside the binary" is the rejected shape: it breaks single-file channels and every wrongly-unpacked archive); `EMO_REGISTRY` keeps overriding with a filesystem registry. (c) **`emo install` is the project-dependencies front end** — read manifest, resolve against the registry, fetch into the cache, write `package.lock`, ready to run; global executable installation (the cargo-install shape) is out of scope for 1.0. (d) **The dependency cache leaves the temp directory** for a durable user location (`~/.cache/emo` honoring `XDG_CACHE_HOME`) — the OS wipes `$TMPDIR`, and a product cannot re-fetch on every build. - The runtime-independence principle: **settled (2026-10-07, before T25.1)** — a target's runtime is written in the target's language, carried as generated data inside the compiler, and compiled by the target's own toolchain on the user's machine; the host contributes only the emitter. No target's runtime may be looked up beside the binary or in the host build tree: `c`, `ocaml`, and `typescript` runtimes ride inside the compiler as generated data (the `emo_codegen/{c,ts}` dune-rule pattern), while `wasm` and `beam` runtimes ride inside the emitted module itself (the wasm engine imports and OTP are the *target* ecosystem's ABI and standard library, as libc is to `c` — a different axis from the compiler's host language). Consequence: target generation stays the host's job, so a future host rewrite touches only the emitters; a target works wherever the target's own toolchain exists, on any installation shape — `emo build --target ocaml` needs the OCaml toolchain on PATH, never an `emo_runtime.cmxa` in the host build tree. The host/target distinction this completes is recorded in `docs/toolchain.md`.
- The ocaml runtime's dependency policy: **settled (2026-10-07, T25.4)** — the standalone runtime's core (values, strings, the scheduler) stands on the OCaml standard library plus `unix`, which ships with the compiler; TLS keeps `ssl` as the one opam-package dependency; the runtime's build invocation declares both (ocamlfind `-package unix,ssl`) and refuses with a clear message when `ssl` is absent. **eio drops out entirely**: the standalone scheduler is the deterministic poll loop the compiled path already ran on, so the provisional plan to keep `eio_main` on the target side is superseded — a target-ecosystem dependency nobody's program needs is not declared.
- Cross-module type names: **settled (2026-10-10, the emo-ui gate) — program-wide type pre-registration** (the GUI spikes' Option A; evidence in `docs/emo-ui-check.md`). Every module's classes, interfaces, and enums register before any module is checked (`Emo_check.preregister_types`, feeding `check_module` / `check_module_typed`); names stay unqualified and are program-unique — a name's second declaration is a loud E4021 naming both modules. The uniqueness rule is not a new restriction but an existing emitter assumption made checkable: the lowered program keys class tables and `is()` vtables by the bare name, so two same-named classes in one discovered tree never lowered correctly anyway. Module-qualified type names (`ui.VNode`) remain a possible later layer if real collisions appear; nothing changes in the surface until one does. Consequences: type declarations and `is()` narrowing resolve across modules (the ui/app split checks and runs identically through the interpreter and the `c` target), and construction joins them — `Point.new(...)` builds another module's class and `Color.green` names another module's enum member, the lowering resolving the bare name through the program's owner table and the interpreter loading the declaring module on first need, like any module reference. The internal rule reaches bare names with them: a type declared under `internal/` resolves only inside its subtree, and a bare use outside — a type declaration, an `is()` target, construction, or a pattern — reports E5001 at the use site, naming both modules (settled 2026-10-10; the checker carries each type's declaring path in the pre-registration). Registry-package types resolve for their consumers so method calls on package values are checked like any other (the `xml` package's element accessors moved onto its interface accordingly), and an interface signature may name its own interface inside a checked program — while a lone-file view (the LSP's single-file check) still resolves only that file's own declarations.
- Cross-module value signatures: **settled (2026-10-11, the feat/checker pass) — the program's def/const/group tables pre-register beside the type tables**. The 2026-10-10 pre-registration made cross-module *types* check; values stayed blind — `lib.make(x)`'s arguments went unchecked, `lib.answer` read as Unknown, another module's group member never resolved, and every divergence the interpreter raises at run time (E5004 unknown member, E4004 wrong argument) surfaced only there. The fix rides the same two-phase pass: `preregister_types` now also collects every unit's defs and foreigns as declared `FuncType`s, every top-level const/var as its initializer's type (typed in the unit's own order, diagnostics dropped — the module's own check reports them), and every `emo` group's defs and consts into a program-wide registry mirroring the runtime's (groups are global at runtime, so the checker's per-module table gains a program-level fallback). A qualified call checks through `check_apply` like any call; a bare `lib.make` reads as the closure's `FuncType`; a member that resolves nowhere reports E5004 statically — the runtime's own message. Shadowing stays runtime-faithful: a dotted path is a module reference only when its head is not a local binding (the runtime looks the head up in the environment first — the `list` example's local `const list = List.new(...)` under a module named `list` is what pinned this). Group member reads type directly (consts carried nothing before — a bare `Math.tau` read as Unknown even same-module). Two pre-existing checker bugs fell out: `longest_module_prefix` generated the path's *suffixes*, never its prefixes (harmless while it only under-recorded refs, fatal once member resolution keyed on it), and the Member arm treated the empty dotted path as a module prefix, swallowing bare member access on non-simple receivers (`foo(1).field` read as Unknown forever). Registry packages join automatically — the same `p.files` walk feeds the pre-registration, so `json.decode(text)` now checks its argument and returns the interface. The packages' interfaces moved their `get` onto the interface (json gained the four raising scalar variants, matching the classes it already had; the "an interface signature cannot name its own interface" comments predated self-referencing signatures and were stale). Unblinding receivers also surfaced two latent c-side deviations, both pre-existing and both fixed to the interpreter's answer: `emo_box_replace` returned the box while every other target returns the new value, and the emitter's builtin `to_string` arm captured statically-typed instance receivers, printing the debug repr instead of the class's own method — instances now dispatch by class first, the conversion answering only when no method carries the name. A capitalized name that resolves to no type, group, or module reports E4003 at its write site in a program check — the runtime's value-carrying builtins (`Int64`, `Byte`, `Float64`, `Box`, `Bytes`, `List`, `Map`, `Exception`) stay legal — while the lone-file view (the LSP's single-file check) keeps the old silence, exactly like every other cross-file gap it cannot see through.
- A Zig-emitting backend: **settled (2026-10-11) — shelved; not a seventh target** (`docs/zig-backend.md`). Emitting Zig is mechanically a mirror of the `c` target, and its one unique gain — safe-mode bounds and overflow checking on generated code — is a mid-sized development-time benefit set against a full backend's cost and a permanent churn tax: Zig breaks language and std APIs in every release, 1.0 has no date, and incremental compilation covers only x86_64-linux. Without its std library the emitter produces curly-braced C with worse tooling — a strictly worse `c` target; with it, every compiled program rides a pre-1.0 std — the churn the runtime-independence principle refuses. The shelving carries written re-evaluation triggers, set now so the bar is explicit: Zig 1.0 or completed language stabilization, incremental compilation beyond x86_64-linux, or a concrete requirement the `c` target cannot meet through `zig cc`. What survives is not a backend: `zig cc` as an optional compiler driver for the existing `c` target — cross-compilation from any host, static musl Linux binaries, Windows without MSVC — is its own small step, taken if Windows or static Linux distribution enters the plan, and only after the driver's version joins the `c` cache key (today it hashes source, runtime, cclib, and the emo binary, so a swappable driver would serve stale binaries after an upgrade). `riscv64` stays direct assembly text; nothing passes through Zig.
- FFI compound data — struct shapes: **settled and implemented (2026-10-11) — a tuple or a carrier class is the shape declaration; the carriers are Emo's own**. A `foreign def` parameter whose type is a tuple crosses the C ABI as a C struct by value: the element types in order are the layout, and a nested tuple element nests a struct within the struct. A class instance carries the same by its init-assigned fields — the carrier-class contract is that the class's shape *is* its init signature: every field assigns a same-named parameter, in order, and every field type stays in the tier (a marshaling scalar or a nested tuple); a computed or extra field, a stateless class, and a class-typed field all refuse. A compound foreign **return** crosses back as a tuple — a class-typed return refuses ("name the tuple"), because a return would have to fabricate an object identity a C value cannot carry. The `c` target declares the same `typedef struct` the C side sees — into `main.c` and `emo_defs.h`, so a shim compiles against the real layouts — and per shape emits two static converters (one flattening the argument word into the struct, per carrier kind, so the argument expression stays a single textual occurrence; one rebuilding the tuple word from a returned struct); the by-value calling convention (register vs. memory class, the SysV classification) is cc's job, which is the emit-C route paying for itself. Identical layouts share one typedef, keyed by the serialized member tree. No language-level struct type exists — records are class instances and anonymous compound values are tuples, and the FFI surface declares shapes *through* them, so nothing new enters the value model. Rejected along the way: making the carrier rule lenient (strictness first — a divergent field list marshals the wrong bytes silently). Open for later: struct fields that are themselves carrier classes, pointer OUT-parameters (`&x` shapes), and the other honoring target (`ocaml`) gaining shapes — each refuses loudly today, per the `foreign` rule.
- The C→Emo callback contract: **settled (2026-10-11) — a single-method structural interface is the callback type; implemented on the `c` target the same day** (spike evidence in `spike/macos-gui`). A `foreign def` parameter may name an interface; the `c` target emits a trampoline plus an opaque userdata handle, and the C side calls through them into the object's one method — registration is explicit ordinary code, with no invisible plumbing. The convention: one interface-typed Emo parameter expands to two adjacent C parameters, the function pointer and the `void *`, and the callback's C signature is the method's marshaled parameters followed by the trailing `void *userdata` — the idiom every C callback API already expects, and the pair lands in `emo_defs.h` so a shim's signature drift breaks at cc time. The callback method stays in the marshaling tier (`Float64`/`String`/`Bool`/`Int64` parameters, plus `Void` returns); the trampoline boxes the arguments and dispatches by method name through `emo_send`, so identical signatures share one static trampoline and distinct receivers ride the userdata. Rejected: `&def` function references — an address-of-def reads as first-class functions seeping through the FFI seam, and there is no representation to back it (the `c` target's call discipline is plain symbol calls; callbacks are deliberately not first-class); a C-style struct-of-function-pointers registration — the struct-shaped Go borrow already refused. What the spike proved meanwhile: C already calls Emo defs as plain extern symbols (module-qualified, `main__`-prefixed), with callback state traveling through the signature because Emo gives cross-callback state no global home; the interface contract generalizes exactly that shape. The interpreter still refuses every foreign def at run time (E3009), and the other honoring target (`ocaml`) refuses the interface parameter at check time until its marshaling path grows one.
- Package-carried native code and the manifest `link` field: **settled and implemented (2026-10-12), with the `sqlite3` package as the first consumer.** A package may carry `.c`/`.h` sources in its tree — collected, checksummed, embedded, and published beside its `.emo` modules (the tree is the package, so the sources are auto-collected exactly like the modules; no manifest field names files) — which the `c` target compiles in the program's single cc invocation, and the manifest gains an optional `link = [...]` field naming the system libraries to link (bare names only: a `-`- or `/`-shaped entry is refused with E5103 — the manifest stays data, never a flag fragment; `--cclib` keeps the verbatim-flag role). Both ride the existing cclib mechanism into the build's cache key — sources by content, libraries by name. A native-carrying package is honored by the `c` target alone: resolution's `targets` gate stays the first line, and a package declaring the current target while carrying native inputs makes the build refuse outright (E5007, naming the packages) rather than silently dropping the link. The `sqlite3` package itself: `targets = ["c"]`, `link = ["sqlite3"]`, its `foreign def`s in a subtree-private `internal/ffi.emo` against a package-carried shim whose every signature is exact-ABI (`int64_t`/`double`/`bool`/`const char *`) so SQLite's `int` returns never meet the FFI undeclared; the shim includes the generated `emo_defs.h`, so drift breaks at cc time in both directions. Handles ride pointer-sized Int64s; bind indices are 1-based (they name the SQL text's `?NNN`), column indices 0-based (SQLite's convention); a NULL column reads as `""` with `column_is_null` telling the two apart; embedded NULs truncate at the boundary until Bytes can cross the FFI; blobs are out of scope until then. Errors follow the package's base-branch convention — raise, per `os` — and join the error-handling migration to `(R.ok, …)` / `(R.error, …)` tuples when that branch lands. Rejected along the way: baking SQLite into the always-linked C runtime (every binary would link `-lsqlite3`, and the interpreter would need its own binding) and vendoring the amalgamation (a quarter-million lines of third-party C for what every host already ships).
