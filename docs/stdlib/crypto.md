# The `crypto` Package

The standard library's primitives layer: hashes, MACs, key
derivation, AEAD ciphers, a signature scheme, and a key agreement —
the pieces every protocol is built from, and nothing above them (no
TLS, no certificates, no key storage). Pure Emo over `Int64` and
`Bytes`, so every target the package declares answers with the same
bytes: the goldens ride the interpreter, `ocaml`, `c`, `typescript`,
`wasm`, and `beam`, and every line of them agrees with the RFC and
NIST vectors and — wherever Go's standard library carries the
primitive — with values generated by Go's own `crypto` packages on
the committing machine.

The package is a root module and eight submodules, called by their
qualified names:

| Module | What it holds |
|---|---|
| `crypto` | the constant-time comparison and the hex codec |
| `crypto.sha2` | SHA-256, SHA-224, SHA-512, SHA-384, SHA-512/224, SHA-512/256 — streaming and one-shot |
| `crypto.sha3` | SHA3-224/256/384/512 and SHAKE128/256 |
| `crypto.hash` | the `Hash` interface and HMAC over the SHA-2 family |
| `crypto.kdf` | HKDF and PBKDF2 over the SHA-2 family |
| `crypto.cipher` | ChaCha20, Poly1305, ChaCha20-Poly1305, AES with CTR, CBC, and GCM |
| `crypto.sign` | Ed25519 |
| `crypto.ecdh` | X25519 |
| `crypto.legacy` | SHA-1 and MD5, for existing data only |

## Using the package

```emo
require "crypto"
```

The standard library ships with the compiler, but its packages are
versioned like any other: `require "crypto"` needs `"crypto" = "0.1.0"`
in the manifest's `deps` block.

```emo
const digest = crypto.sha2.sha256("abc".to_bytes())
println(crypto.hex_encode(digest))
```

## Bytes are the carrier

Keys, nonces, digests, tags, signatures, and every input the
algorithms read come in as `Bytes` and go out as `Bytes`. A String
cannot carry raw bytes on every target — on `typescript` a String is
UTF-8 text, and a digest byte at or past 0x80 would decode to U+FFFD —
so the package does not pretend otherwise. Text stays text at exactly
one place: `hex_encode` answers the ASCII rendering as a String and
`hex_decode` reads one back. A caller hashing text hands over
`text.to_bytes()`, which is exact on every target.

## The error split

The standard library's rule holds throughout, and every function
below spells its own case:

- **A caller's mistake raises.** A key, nonce, seed, or point of the
  wrong length; a counter past its range; a negative output length;
  an iteration count below one; a CBC ciphertext that is not a
  positive multiple of sixteen. These are contract violations — the
  program is wrong, not the data — and the raise's message begins
  `crypto:`.
- **A data reason is a value.** A tag that does not verify, padding
  that does not read back, a signature that is not the key's, a
  shared secret of all zeros, a hex string that is not hex. These
  answer `(R.error, reason)` with the reason beginning `crypto:`, and
  the functions that can fail this way are the ones whose answer is
  `(R, …)`.

A forgery is met with the same answer whatever its shape: a flipped
byte, a wrong AAD, a truncated box, a wrong key — `open` answers
`(R.error, "crypto: authentication failed")` for all of them, and
`ed25519_verify` answers `false` for every bad signature, so the
answer itself does not say which check failed.

## The root: comparison and hex

```emo
def constant_time_compare(a Bytes, b Bytes) Bool
def hex_encode(data Bytes) String
def hex_decode(text String) (R, Bytes)
```

`constant_time_compare` answers whether the two byte strings are
equal, accumulating the XOR of every pair into one word so the
comparison's shape does not depend on where the first difference sits;
the lengths enter the same accumulator, and unequal lengths answer
false. Compare tags and digests through it, never with `==`.

`hex_encode` answers two lowercase characters per byte; `hex_decode`
is its strict inverse — an even number of characters, both cases of
every digit accepted — and anything else is the value
`(R.error, "crypto: hex_decode odd length 3")` or
`(R.error, "crypto: hex_decode expects a hex digit at byte 4")`, the
offset naming the first offending byte.

## `crypto.sha2` — the SHA-2 family

```emo
class Digest {
  def write(data Bytes) Void
  def sum() Bytes
  def reset() Void
  def size() Int64
  def block_size() Int64
}

def new() Digest
def new224() Digest
def sha256(data Bytes) Bytes
def sha224(data Bytes) Bytes

class Wide {
  def write(data Bytes) Void
  def sum() Bytes
  def reset() Void
  def size() Int64
  def block_size() Int64
}

def new512() Wide
def new384() Wide
def new512_224() Wide
def new512_256() Wide
def sha512(data Bytes) Bytes
def sha384(data Bytes) Bytes
def sha512_224(data Bytes) Bytes
def sha512_256(data Bytes) Bytes
```

The one-shots answer the digest of the whole input: 32 bytes for
SHA-256, 28 for SHA-224, 64 for SHA-512, 48 for SHA-384, 28 for
SHA-512/224, 32 for SHA-512/256. The classes are the streaming shape:
`write` absorbs any number of pieces in any sizes, `sum` answers the
digest of everything written so far and **leaves the state standing**
— more writes continue the stream, and a second `sum` without a write
answers the same digest — and `reset` returns the hasher to its
initial state. `size` is the digest length and `block_size` the
compression block (64 bytes for `Digest`, 128 for `Wide`). `Digest`
carries the two 32-bit-word variants and `Wide` the four 64-bit-word
variants; the factory names the variant. Nothing here raises.

## `crypto.sha3` — SHA-3 and SHAKE

```emo
def sha3_224(data Bytes) Bytes
def sha3_256(data Bytes) Bytes
def sha3_384(data Bytes) Bytes
def sha3_512(data Bytes) Bytes
def shake128(data Bytes, length Int64) Bytes
def shake256(data Bytes, length Int64) Bytes
```

FIPS 202 over the Keccak-f[1600] permutation. The four hashes answer
28, 32, 48, and 64 bytes; the two extendable-output functions answer
exactly `length` bytes, any length, the squeeze continuing across the
rate as the standard describes. A negative `length` raises. One-shot
only: the streaming shape waits for a consumer.

## `crypto.hash` — the `Hash` interface and HMAC

```emo
interface Hash {
  def write(data Bytes) Void
  def sum() Bytes
  def reset() Void
  def size() Int64
  def block_size() Int64
}

def hmac_sha256(key Bytes, data Bytes) Bytes
def hmac_sha224(key Bytes, data Bytes) Bytes
def hmac_sha512(key Bytes, data Bytes) Bytes
def hmac_sha384(key Bytes, data Bytes) Bytes
def hmac_sha512_224(key Bytes, data Bytes) Bytes
def hmac_sha512_256(key Bytes, data Bytes) Bytes
```

`Hash` is the structural interface every hasher answers by shape —
`crypto.sha2.Digest` and `crypto.sha2.Wide` satisfy it without naming
it, so a function taking `h crypto.hash.Hash` holds either. The HMAC
functions (RFC 2104) answer the tag of `data` under `key` for the
named hash: the key may be any length — longer than the block, it is
hashed first; shorter, zero-padded — and the tag is the hash's length.
One-shot; compare tags through `crypto.constant_time_compare`. Nothing
here raises.

## `crypto.kdf` — HKDF and PBKDF2

```emo
def hkdf_sha256(ikm Bytes, salt Bytes, info Bytes, length Int64) Bytes
def hkdf_sha256_expand(prk Bytes, info Bytes, length Int64) Bytes
// … and the same pair for sha224, sha512, sha384, sha512_224, sha512_256

def pbkdf2_sha256(password Bytes, salt Bytes, iterations Int64, length Int64) Bytes
// … and the same for sha224, sha512, sha384, sha512_224, sha512_256
```

`hkdf_<alg>` is RFC 5869's extract-then-expand: the pseudorandom key
is `hmac_<alg>(salt, ikm)` — an empty `salt` stands for the
hash-length zero bytes the RFC prescribes — and the output is
`length` bytes expanded over `info`. `hkdf_<alg>_expand` is the second
step alone, for a caller who already holds the pseudorandom key (the
extract step is not re-exported: it *is* the HMAC call). The
construction's own rules raise: a negative `length`, and a `length`
past 255 times the hash length.

`pbkdf2_<alg>` is RFC 8018's PBKDF2 with HMAC-`<alg>` as the
pseudorandom function: `length` bytes from the password and salt over
`iterations` rounds. A negative `length` raises, and so does an
`iterations` below one; the count itself is the caller's number — no
work-factor policy lives in the package, and the classic 4096 is two
seconds compiled and a minute on the interpreter.

## `crypto.cipher` — ChaCha20-Poly1305 and AES

```emo
def chacha20(key Bytes, nonce Bytes, counter Int64, data Bytes) Bytes
def poly1305(key Bytes, message Bytes) Bytes
def chacha20_poly1305_seal(key Bytes, nonce Bytes, plaintext Bytes, aad Bytes) Bytes
def chacha20_poly1305_open(key Bytes, nonce Bytes, sealed Bytes, aad Bytes) (R, Bytes)

def aes_encrypt_block(key Bytes, block Bytes) Bytes
def aes_decrypt_block(key Bytes, block Bytes) Bytes
def aes_ctr(key Bytes, iv Bytes, data Bytes) Bytes
def aes_cbc_encrypt(key Bytes, iv Bytes, plaintext Bytes) Bytes
def aes_cbc_decrypt(key Bytes, iv Bytes, ciphertext Bytes) (R, Bytes)
def aes_gcm_seal(key Bytes, nonce Bytes, plaintext Bytes, aad Bytes) Bytes
def aes_gcm_open(key Bytes, nonce Bytes, sealed Bytes, aad Bytes) (R, Bytes)
```

**ChaCha20** (RFC 8439) answers `data` XORed with the keystream from
the 32-byte key, the 12-byte nonce, and the initial block `counter`
(0 through 2^32 − 1). **Poly1305** answers the 16-byte tag of
`message` under a 32-byte one-time key. **ChaCha20-Poly1305** is the
AEAD: `seal` answers the ciphertext followed by the 16-byte tag, the
`aad` authenticated but not encrypted; `open` takes that box back and
answers `(R.ok, plaintext)` when the tag verifies and
`(R.error, "crypto: authentication failed")` when it does not — the
same value for a flipped byte, a wrong AAD, a box shorter than a tag,
and a wrong key. A key that is not 32 bytes, a nonce that is not 12,
and a counter out of range raise.

**AES** (FIPS 197) takes a key of 16, 24, or 32 bytes — anything else
raises — and `aes_encrypt_block`/`aes_decrypt_block` are the cipher
and its inverse over one 16-byte block (another length raises).
`aes_ctr` (SP 800-38A) answers `data` XORed with the keystream, the
16-byte `iv` the initial counter block and the full 128 bits stepping
big-endian; the caller's `iv` is copied, not advanced. `aes_cbc_encrypt`
pads with PKCS#7 — every pad byte carries the pad's own length, so the
output is always a multiple of sixteen, one block longer than a
plaintext that already was one — and `aes_cbc_decrypt` answers the
plaintext with that padding removed: a ciphertext that is not a
positive multiple of sixteen raises, padding that does not read back
is the value `(R.error, "crypto: invalid padding")`. **GCM**
(SP 800-38D) is the AEAD: a 12-byte nonce (another length raises), the
ciphertext followed by the 16-byte tag, `open` answering the same two
values ChaCha20-Poly1305's does. GHASH is pure bitwise arithmetic with
no table.

Two contracts the construction cannot enforce for the caller:

- **Nonce reuse breaks both AEADs irrecoverably.** A key and nonce
  pair encrypts once. For the stream and counter modes the same holds
  for the key and counter block.
- **CBC decryption answers padding failures without hiding the
  timing**, and a system that lets an attacker observe which
  ciphertexts fail is the padding oracle. Authenticate before
  decrypting — encrypt-then-MAC with `hmac_sha256` and
  `constant_time_compare`, or simply use GCM.

## `crypto.sign` — Ed25519

```emo
def ed25519_public(seed Bytes) Bytes
def ed25519_sign(seed Bytes, message Bytes) Bytes
def ed25519_verify(public Bytes, message Bytes, signature Bytes) Bool
```

RFC 8032's Ed25519. The secret key is the 32-byte seed the RFC calls
the private key — the package derives everything else from it, so the
doors take the seed and nothing else, and a seed is any 32 bytes of
entropy (`rand.bytes(32)`). `ed25519_public` answers the 32-byte
public key; `ed25519_sign` the 64-byte signature of the message, R
then S, deterministic — the same seed and message always answer the
same bytes; `ed25519_verify` whether the signature is the public key's
signature of the message.

The verifier checks the group equation without the cofactor,
[S]B = R + [k]A, the form Go's `crypto/ed25519` checks, and it answers
`false` — the same `false` — for a wrong message, a flipped byte, a
signature that is not 64 bytes, an S at or above the group order (the
malleable twin the RFC refuses, so each signature has exactly one
accepted form), and a public key that does not decode to a point. A
seed or a public key that is not 32 bytes raises.

## `crypto.ecdh` — X25519

```emo
def x25519(scalar Bytes, point Bytes) (R, Bytes)
def x25519_public(scalar Bytes) Bytes
```

RFC 7748's X25519, the Diffie-Hellman function on Curve25519. A
private key is any 32 bytes — the function clamps them on the way in,
so entropy is all a caller needs — and `x25519_public` answers the
32-byte public key, the scalar's multiple of the base point.
`x25519(scalar, point)` answers the shared secret of one's own scalar
and the other side's public key: `(R.ok, secret)`, 32 bytes, or
`(R.error, "crypto: x25519 low-order point")` when the secret came out
all zeros — the other side's point was of small order and the secret
carries no contribution from this side. That is the contributory check
RFC 7748 §6.1 describes and Go's `crypto/ecdh` performs; a caller who
wants the raw function's all-zero answer does not get it here. The
point's top bit is ignored, as the RFC requires. A scalar or point that
is not 32 bytes raises.

Both sides derive the same secret:

```emo
const alice = crypto.ecdh.x25519_public(a)
const bob = crypto.ecdh.x25519_public(b)
// x25519(a, bob) and x25519(b, alice) answer the same 32 bytes
```

Hand the secret to a key-derivation function (`hkdf_sha256` with both
public keys in `info`) before using it as a key.

## `crypto.legacy` — SHA-1 and MD5

```emo
def sha1(data Bytes) Bytes
def md5(data Bytes) Bytes
```

**Both are broken for every security purpose.** SHA-1 has had
constructed collisions since 2017 and MD5 since 2004; neither can
answer a new question — not a signature, not an integrity check an
adversary could influence, not a password hash. They are here because
the world's existing data still needs verifying: a checksum in an old
manifest, a fingerprint in a legacy protocol. The module's name is the
warning. One-shot only — 20 bytes for SHA-1, 16 for MD5 — and nothing
here raises. DES, RC4, and DSA are not in the package and will not be.

## Constant time: what is promised, per target

The discipline is **source-level**: in the implementations of the
primitives that handle secrets, no branch and no memory index depends
on a secret byte. The Poly1305 and Curve25519 field arithmetic is
fixed-shape limb arithmetic with masked selects; the Ed25519 scalar
multiplication is double-and-add-always, 256 steps whatever the scalar,
with a masked select; the X25519 ladder swaps through a mask; the
scalar reduction modulo the group order is a fixed count of masked
trial subtractions; GHASH is branchless; `constant_time_compare`
accumulates every byte. Two places are different and documented as
such:

- **AES's SubBytes is a table lookup indexed by secret bytes.** The
  S-box is one derived 256-byte table (not the five T-tables), and the
  field multiplies around it are branchless, but the lookup itself is
  a memory access whose address is a secret — the classic cache-timing
  channel on a shared machine. An AES-NI shim on `c` is the later
  optional hardening.
- **Public data is compared and branched on freely:** the verifier's
  final equality, point decoding, hex decoding, length checks. Nothing
  secret rides those paths.

What the source discipline becomes on each target is a property of
that target's code generator and runtime, and the honest statement is
per target. **The package guarantees the discipline in the source and
nothing more; none of the targets has been measured for timing
leakage.**

| Target | What `Int64` is | What is added or lost |
|---|---|---|
| interpreter (`emo run`) | a boxed OCaml `int64` inside a tree-walking evaluator | the evaluator allocates on every operation and its own control flow is not shaped by the discipline; no timing property can be claimed |
| `ocaml` | OCaml's `int64`, boxed in many positions | the arithmetic compiles to machine instructions, but allocation and the GC run at data-dependent moments; the masked selects are plain integer operations and the compiler has no reason to turn them into branches, which is not the same as a guarantee |
| `c` | `int64_t` | the straightest path: the masked selects are ordinary integer operations; a C compiler may still legally rewrite a mask-and-xor select into a branch, and the `Bytes` accessors are bounds-checked (branches on indices, which are never secret); unverified at the machine-code level |
| `typescript` | a `BigInt` | arbitrary-precision arithmetic whose cost depends on the magnitude of the values — a timing channel by construction, and no constant-time claim is made for this target |
| `wasm` | a WebAssembly `i64` | the arithmetic is native; the engine's JIT decides what the masked selects become, and no claim is made |
| `beam` | an Erlang integer, masked to 64 bits after every operation | arbitrary-precision underneath — values above the small-integer range become heap bignums — so the cost depends on the magnitude, and no constant-time claim is made |

The practical reading: on `c` and `ocaml` the source discipline is
worth having and is what the package offers; on `typescript`, `wasm`,
and `beam`, and on the interpreter, treat the package as correct but
not as side-channel resistant, and keep long-lived secrets off those
targets or off shared hardware.

## The vectors

Every golden is a diff against the RFC's own vectors and — wherever
Go carries the primitive — against the Go standard library's answer
on the committing machine, frozen into `expected.txt` only after both
agreed:

- `examples/crypto_hash` — the SHA-2 family (RFC 6234's suite, the
  padding edges from 55 to 129 bytes, the 0x00–0xFF sweep, the
  streaming and reset panels), the SHA-3 family and SHAKE at two
  lengths across the rate, HMAC (RFC 4231 with the 131-byte keys), HKDF
  (RFC 5869) and PBKDF2 (RFC 7914 at one and two iterations), the
  legacy pair, and the hex codec's edges — 175 Go-agreed lines, on
  every target.
- `examples/crypto_aead` — ChaCha20's block and stream, Poly1305,
  ChaCha20-Poly1305's box with the three forgeries and nine sizes
  across the block and pad boundaries, against the RFC's own vectors
  and a Python reference written from the RFC (Go keeps that
  construction outside its standard library); AES's three FIPS 197
  known answers and their inverses, GCM's NIST cases and nine sizes,
  CBC and CTR at six lengths and a counter carry — fifty Go-agreed
  lines; on every target.
- `examples/crypto_sign` — RFC 8032's five vectors (public key,
  signature, verification) and the six rejections — 21 lines agreeing
  with Go's `crypto/ed25519`, on every target.
- `examples/crypto_ecdh` — RFC 7748's two vectors, the §6.1 exchange
  both ways, the ladder's first iteration, the two low-order refusals
  with their reason, and a sweep — agreeing with Go's `crypto/ecdh`, on
  every target.
- c-only — eleven to eighty seconds on the interpreter, under a second
  compiled: `examples/crypto_hash_million` (RFC 6234's million `a`),
  `examples/crypto_kdf` (PBKDF2 at 4096 iterations),
  `examples/crypto_sign_sweep` (thirteen message lengths),
  `examples/crypto_ecdh_iterated` (RFC 7748's thousand iterations).

## Targets and performance

Targets: all five — `ocaml`, `c`, `typescript`, `wasm`, `beam` — and
the interpreter, byte-identically. The interpreter is the slow leg:
one Ed25519 signature or verification is about a third of a second,
an X25519 agreement a tenth, a SHA-256 of a megabyte about twenty
seconds, PBKDF2 at 4096 iterations a minute, a thousand X25519
agreements eighty seconds. Compiled, each of those is well under a
second — the thousand agreements take 0.6 s on `c` — so interactive
work runs on `emo run` and anything that loops runs on a build.

Entropy is not in this package: `rand.bytes` is the source, and
`rand.drbg_sha256` the reproducible stream, in the separate `rand`
package ([`docs/stdlib/rand.md`](rand.md)).
