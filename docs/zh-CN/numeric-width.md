# 数值位宽 —— 每个目标同一套位宽显式的类型

## 决定

数值类型的位宽是显式的。**`Int64`** 是默认整数类型：64 位二进制
补码、回绕，在所有目标上如此——算术按模 2⁶⁴ 进行，溢出行为在
原生、Wasm、BEAM、裸机上完全一致。**`Float64`** 是默认浮点类型：
在每个目标上都是 IEEE 754 binary64（2026-10-05 定案）。

不存在不带位宽的 `Int` 或 `Float` 拼写，将来也不会以别名形式加入；
无注解的整数字面量是 `Int64`，无注解的浮点字面量是 `Float64`
（`Int64` 部分取代同日早先"保留 `Int` 拼写、不引入 `Int64` 名字"
的决定）。

实现里目前仍拼写为 `Int` 和 `Float`（检查器、stdlib、examples）；
到 `Int64`/`Float64` 的机械重命名与下文的 native 修复搭同一步。

## 为什么类型按位宽命名

下面的 63 位缺陷与裸的 `Int` 拼写同根：一个不说出自己位宽的名字
会引来 C 的那个问题——"`int` 在**这里**到底多宽？"——而这正是本
决定要消除的歧义。位宽后缀的名字：

- 说它是什么——everything is visibly what it is；
- 不给 FFI 代码留下可误投的"自然宽度类型"（主流 ABI 上 C 的
  `int` 是 32 位；它的 `float` 与 `double` 位宽也不同，旁边放一个
  无位宽的 `Float` 是常设陷阱）；
- 跟随系统语言的谱系（Rust、Zig 写作 `i32`/`i64` 与 `f32`/`f64`）
  ——由实现自定义宽度的 `int` 是 C 的异类，也是反面教材。

## Int64：三个目标，三种整数

此前每个目标各自回答"整数是什么"：

| 目标 | 当前表示 | 当前语义 |
| --- | --- | --- |
| Wasm | `i64` | 64 位回绕 —— 符合 |
| BEAM | 掩码后的 Erlang 整数（step 17） | 64 位回绕 —— 符合 |
| native | OCaml `int`（去箱） | 63 位回绕 —— 偏差 |

native 后端发射 OCaml 源码，把整数映射到 OCaml 的 `int`——64 位
平台上它是 63 位：机器字里有一个 bit 是运行时的立即数/指针标记。
（BEAM 的 small integer 为同样的目的付出四个 bit——这正是 BEAM
后端要做掩码的原因；不掩码的话 Erlang 整数会升级为大数而非回绕。）
因此 `(2^62) * 2` 今天在 native 和在 Wasm/BEAM 上落在不同的值。

这个映射把宿主语言的实现细节写进了语言语义。那个标记位是 OCaml
运行时为它的值模型付出的代价——整数去箱、无标记的多态比较、GC
栈扫描——Emo 没有理由替用户付这笔税。宿主 `int` 从此只是实现
候选之一，不是定义。

## native 侧的修复（待决）

在 native 后端落实这套语义，意味着用 63 位的宿主 `int` 造出
64 位算术。两条路线——真实的权衡，动工前定案（登记于
`CHECK.md`）：

- **发射 OCaml 的装箱 `Int64`。** 语义精确，但宿主的 `Int64` 是
  装箱的——特化通道失去当初选择这个映射所依赖的去箱算术。
- **在 OCaml `int` 上做双字（hi/lo）模拟。** 保持去箱；add/sub
  变成带进位的指令对，mul/div 拆 hi/lo——算术膨胀约 2–4 倍。
  与将来 RV32 代码生成需要的技术相同（见下），工作量可以共享。

## Float64：本来就一致

与整数不同，浮点不需要修复：今天它在每个目标上都是 IEEE 754
binary64——OCaml `float`、Wasm `f64`、Erlang float、TypeScript
后端的 JS `number`。所有目标早已符合，这里的决定只是名字；显示
与解析规则天然与目标无关。

## RISC-V 32 位是代码生成问题，不是语义问题

裸金属目标按 ISA 命名（`riscv64`，step 14）。将来的 `riscv32`
用寄存器对实现同一个 `Int64`：add/sub 走进位链，mul/div 拆
hi/lo——教科书式的 `long long` 技术，与上面 native 的 hi/lo
路线共享。在 RV32 上角色反转：`Int32` 是寄存器宽度的快路径，
`Int64` 是被模拟的那个——语义不变，性能特征随目标不同。代价
（每值两个寄存器、8 字节，算术 2–4 倍）由目标承担，不由语言
承担；把 RV32 上的 `Int64` 缩成 32 位等于另一门语言，不予考虑。
`riscv32` 暂不排期——只有真实硬件提出需求时才跟随 `riscv64`
之后立项。

## Int32（方向已认可；排期时单独立 step）

`Int32` 将作为第二个显式命名的整数类型加入：32 位二进制补码，
按 2³² 回绕。它的存在不是为了修默认整数——上面那条决定已经修了。
它的动机：

- **FFI。** C 的 `int32_t` 参数需要落点类型（`foreign def` 目前
  只放行 `Float`/`String`/`Bool`）。
- **裸金属。** RV32 的 MMIO 与设备寄存器是 32 位的；`peek`/
  `poke` 需要精确位宽。
- **RV32 性能。** 寄存器宽度的逃生通道：热循环里本机宽度的算术
  胜过模拟的 64 位。

约束，依 strictness-first：

- 默认整数是 `Int64`；无注解的字面量是 `Int64`；不做类型引导的
  字面量推断。
- 任何方向都不做隐式转换；混合算术（`Int64 + Int32`）直接拒绝；
  转换必须显式调用。
- `Int32` 按 32 位回绕，同一条模规则。

## Float32（方向已认可；排期时单独立 step）

`Float32` 将作为第二个显式命名的浮点类型加入：IEEE 754 binary32。
它的动机：

- **FFI。** C 的 `float` 参数需要与 `double` 区分的落点类型。
- **裸金属。** 设备寄存器与固件结构使用 binary32。
- **内存带宽。** 精度本已受限的数值数组，字节数减半。

约束，依 strictness-first（与 `Int32` 同形）：

- 默认浮点是 `Float64`；无注解的浮点字面量是 `Float64`；不做
  类型引导的字面量推断。
- 任何方向都不做隐式转换；混合算术（`Float64 + Float32`）直接
  拒绝；转换必须显式调用。
- `Float32` 逐运算舍入到 binary32（经 binary64 ALU 可精确舍入
  ——53 位覆盖 2×24+2）；显示用 binary32 最短往返表示。
