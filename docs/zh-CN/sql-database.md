# Emo 与 SQL 数据库 —— 一份评估

写于 2026-10-06。这是一份技术可行性评估,不是已定的设计决策;文中
关于项目状态的描述以写作日期的仓库为准。

问题:用 Emo 造一款声称 SQL 标准兼容的原创数据库产品,到底有多难?

## 结论

**可行,但要分档——而且难度的大头与语言无关。** 十分里七八分的工程量
是语言无关的:SQL 标准的广度、存储引擎的正确性、一致性验证的证据。
Emo 的 actor 模型与直接风格 IO 在架构上是真适配——比多数系统类目都
近——但产品要踩的头两层,持久化 IO 与精确数值,恰恰是 Emo 今天做不到
的:`file` 包只有两个函数,FFI 只放行三种类型。分档给结论:

| 档位 | 产品 | 工作量量级 |
|---|---|---|
| A | 声明式 SQL 子集上的嵌入式内存引擎 | 一人 6–12 个月;Emo 今天就够用,数据结构由引擎自带 |
| B | 单机持久化 OLTP——WAL、B 树、MVCC、wire 协议、SQLLogicTest 规模的子集 | 3–6 人年;须先补齐 Emo 的四项缺口,比成熟语言多三分之一到一半 |
| C | 可以站得住地称为"标准兼容"的产品——声明的一致性档位、有竞争力的性能、备份、安全、HA | 任何语言都要数百人年;Emo 额外叠加 pre-1.0 依赖与未测量的性能上限 |

## "SQL 标准兼容"实际上钉死了什么

ISO/IEC 9075 在 SQL:2023 版有十几个部分;光 Foundation(第 2 部分)
就超过一千页,Core SQL:1999 按通常的统计约有 170 项强制特性。
PostgreSQL——在役系统里对标准追踪最紧的一个——不声称完全符合,也没有
任何其他系统这么声称。

官方的一致性认证体系随 NIST 的 SQL 验证计划(FIPS 127-2)一起死在了
上世纪 90 年代。今天"兼容"在实践中的含义是一组东西:明确声明的方言
档位、对着 SQLite 的 SQLLogicTest 语料(数百万条查询)做 diff 测试、
以 PostgreSQL wire 协议为事实互操作标准、SQLSTATE 错误码、
`information_schema`。第一个产品决策就是把"兼容"降维成其中可验收的
一个档位——否则这个项目没有终点。

## 工作量的锚点

- **SQLite**——二十多年、约 15 万行 C 量级,而测试语料比源码庞大得多。
- **DuckDB**——站在 CWI 二十五年以上的研究积累上(MonetDB 谱系);
  约十人的核心团队用五年左右做到 1.0,语言是 C++。
- **TiDB、CockroachDB**——各自数百人年,而且都把存储层外包给
  RocksDB;谁都没自己写 B 树。
- **H2**——证明带 GC 的语言也能用小团队承载一个像样的 SQL 引擎。
- **Mnesia**——证明 actor 模型形态(进程私有状态、消息传递)能跑
  生产数据库;只是它始终没长出 SQL 层。

全自研这条路——自己的解析器、计划器、执行器、B 树、WAL、MVCC、
服务器协议——到*可用*的量级是 5 万至 15 万行、个位数人年;到*可声明
合规*还要再加一个数量级。

## Emo 的设计真正对得上的地方

- **actor 模型正好映射数据库的控制面。** 进程持有连接、锁管理器、
  MVCC 快照表——Erlang/Mnesia 验证过的形态;这也是少数几个 Emo 的
  并发是优势而非中性的系统类目之一。
- **wire 协议服务器是现成脚手架。** io_uring/kqueue/IOCP 上的直接
  风格异步网络,正是 `http.serve` 和 tcp/http 基准已经在跑的东西。
- **编码的原材料已经存在。** `Bytes`(可变、定长)、绕回语义在所有
  目标上一致的 `Int64`、处处 IEEE 754 的 `Float64`——页与记录编码
  今天就写得出来。
- **不可变优先天然是 MVCC 形态。** 不可变页在构造上就能跨进程安全
  共享,`Box` 的可变性不跨进程边界,快照是一个值而不是一种纪律。

SQL 前端本身也是有先例的地盘:已经用 Emo 写成的 wasm 解码器与验证器
(目前约 3900 行)就是同一工种——文法、二进制格式、索引空间校验——
只是规模差一到五十倍。

## 缺口,按阻塞程度排序

1. **持久化 IO 是硬门槛。** `file` 包就是 `read(path) String` 和
   `write(path, contents String)`——没有 `fsync`、没有 append、没有
   seek 或定位写、没有 `Bytes` 级 IO。没有 fsync 就没有 WAL;没有
   WAL 就没有数据库。FFI 只放行 `Float64`、`String`、`Bool` 且仅限
   native——mmap、`O_DIRECT`、sendfile 全部不可达。与工业软件评估
   发现的是同一扇门。
2. **精确数值。** SQL 的 NUMERIC(38) 需要 128 位运算;Emo 既没有
   `Int128` 也没有 bignum。在 `Int64` 上手写 128 位乘、除、取模是
   可行的——几千行代码,外加那个出了名的边界长尾。
3. **集合与性能地板。** 标准库里没有通用 Map、Set,也没有 sort;
   没有泛型;每个值带运行期类型标签;不可变数组靠分配来做变换。
   第一版 join/sort 的热循环会落后 C++ 与 Rust 同行,落后的倍数
   没有人测量过——specialization 叙事("types feed performance")
   是已声明的设计,不是一个数字。
4. **GC 尾延迟。** native 后端共享一个堆,major GC 的工作可能落在
   p99 上;BEAM 的进程私有堆没有这个问题,但吞吐有上限。延迟与
   吞吐的取舍要趁早、想清楚再选后端。
5. **迁移税。** 全局改名仍在落地——实现里还写着 `Int`、`Float`,而
   已定的表层是 `Int64`、`Float64`——group 语法也未决。在 pre-1.0
   语言上写十万行,意味着语言搬家你也搬家。

## 需要先在 Emo 落地什么

- `file`:fsync、append、seek 与定位写、`Bytes` IO。
- FFI 放行 `Bytes`(最终是指针),native 目标优先。
- `Int32`/`Int128`——NUMERIC 进入视野的那天,numeric-width 文档里的
   未来宽度就成了前置条件。
- collections 包(Map、Set、sort)——虽然数据库终究会自带一部分。

这是几个 step 量级的路线图切块——以月计,不是以天计——而且每一块
都是通用能力,不是数据库专用。

## 定位表述

数据库的难,难在正确性的广度与存储工程,不在语言;换任何语言都买不
来这一层。Emo 能做的是在并发与网络这两个面上减摩擦——多数数据库还在
手搓线程与回调——而 actor 模型与 MVCC 引擎控制面的结构性契合是真实的。
如果档位 A 的引擎存在、持久化的门关上了,档位 B 是一个诚实的多年工程,
不是研究赌博;而一个站得住的数据库会是 Emo 自己最有说服力的生态证明。
在那之前,站得住的范围是声明子集的嵌入式引擎,"SQL 标准兼容"是一个
挂着测试套件的目标档位——不是宣传语里的一个词。
