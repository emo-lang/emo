# 原子操作 —— `Atomic`，Box 的同步兄弟，只有顺序一致性

## 决定

`Atomic` 进入 `core`，作为 **Box 的同步兄弟**：一个可变的单值 cell，其每个
操作各自原子（2026-10-25 定案）。顺序一致性是唯一的 memory order——每个操作
连同 `fence()` 都进入同一条全序，所有上下文对这条全序看法一致；表面上任何
地方都不存在 memory order 参数。第一刀只覆盖两种负载，`Int64` 与 `Bool`，
此外没有第三种：任何其他负载的原子操作在检查期按名拒绝。

最直接的需求来自 EmoOS：在裸机上，中断体与被它打断的线程代码共享同一
地址空间，而用 `peek` 和 `poke` 搭出的读-改-写撑不住落在中间的中断。这个
构造本身是通用构造——落在 `core`，每个目标都有——但裸机是共享最锋利的
地方，也是这项工作现在排期的原因。

## 为什么这个构造挣得它的位置

- **普通字段访问保持原样。** 没有隐藏的锁，不共享任何东西的代码不缴
  同步税；`Atomic` 是唯一为同步付费的类型，且只在程序员开口要的地方付。
- **消息传递仍是核心共享通道。** `Atomic` 不是第二套并发模型——它是一个
  在抢占之下读写依然诚实的 cell，在进程模型旁边，而不是替代它。
- **它关掉的那类错误没有别的写法。** 一个被抢占上下文在普通代码运行的
  同时递增的计数器、一个恰好只清一次的标志位：`peek` + `poke` 做不到
  （中断会落在两者之间），普通 `Box` 也做不到（未同步的跨上下文共享是
  未定义的——见下文「数据竞争」）。一个构造，整类丢更新就此关死。

## 表面

类型词汇跟容器家族走：能过检查的拼写只有 `Atomic[Int64]` 与
`Atomic[Bool]`，裸 `Atomic` 意为「两种负载皆可」，正如裸 `Box` 意为
「任意元素」。一个类型、负载作参数——没有按位宽铺开的一族原子类型名。
`Atomic.new(0)` 构造；cell 的负载就是实参的类型。

```emo
const served = Atomic.new(0)     // an Atomic[Int64]
served.fetch_add(1)              // the value the cell held before the add
served.compare_exchange(1, 0)    // (true, 1) when it swapped
```

`Atomic[Int64]`：

| 操作 | 返回 | 行为 |
| --- | --- | --- |
| `load()` | `Int64` | 读出 cell 当前持有的值 |
| `store(v)` | — | 替换该值 |
| `exchange(v)` | `Int64` | 替换该值，返回旧值 |
| `compare_exchange(expected, new)` | `(Bool, Int64)` | cell 持有 `expected` 时才交换；返回是否交换，以及调用前 cell 持有的值，交换与否都返回 |
| `fetch_add(v)` | `Int64` | 加上 `v`，返回旧值 |
| `fetch_sub(v)` | `Int64` | 减去 `v`，返回旧值 |
| `fetch_and(v)` / `fetch_or(v)` / `fetch_xor(v)` | `Int64` | 按位读-改-写，返回旧值 |

`Atomic[Bool]`：

| 操作 | 返回 | 行为 |
| --- | --- | --- |
| `load()` / `store(v)` / `exchange(v)` | `Bool` / — / `Bool` | 与 `Int64` cell 同形 |
| `compare_exchange(expected, new)` | `(Bool, Bool)` | 同一对子契约 |
| `fetch_and(v)` / `fetch_or(v)` / `fetch_xor(v)` | `Bool` | 逻辑读-改-写，返回旧值 |

表格之下的规则：

- **每个读-改-写都返回操作之前 cell 持有的值**——名字里的 `fetch_` 说的
  就是这件事。
- **`compare_exchange` 不匹配不是错误。** `(false, actual)` 就是答案，
  调用者自行决定怎么办；什么都不抛。
- **回绕依 `Int64` 规则**：`fetch_add`/`fetch_sub` 按 64 位二进制补码
  回绕，每个目标一致。
- **`fence()` 是 `core` 里的自由函数，不是方法**——它栅栏的是程序，不是
  某个 cell：对一切内存访问——普通访问与 volatile（`peek`/`poke`）——
  的完整顺序一致性屏障。
- **拒绝，依 strictness-first。** `fetch_add`/`fetch_sub` 在
  `Atomic[Bool]` 上拒绝——算术不是 Bool 的词汇表，按位运算才是。两种负载
  之外的都按名拒绝：`Atomic[Float64]` 在各目标上都拿不出诚实的无锁
  读-改-写，而非标量——字符串、容器、box、嵌套的 `Atomic`——根本不是
  cell。
- **`==` 比较两个 cell 现在持有的值**，每个操作数各作一次原子读——与
  可变家族同一条结构化规则。

## 只有顺序一致性

- 一条全序，一种要学的行为。操作强到可以局部推理：读-改-写永不丢更新，
  `load` 永远看不到撕裂的值，程序在 `store` 或 `fence()` 之前做过的一切，
  对每个观察到其后继的上下文可见。
- 这门语言要写的内核是正确性工程，不是从无锁结构里抠最后百分之几的吞吐。
  弱序买来那百分之几，代价是多出一套看不见的程序——这个代价被拒绝。
- 原生带着弱序的目标把它们留在 FFI 身后；只要目标容纳原子操作，Emo 表面
  一律降到顺序一致性。

## 复制语义——cell 如何变成共享

- Emo 进程不共享内存：跨进程边界的值一律复制，可变值复制为快照——可变性
  永不跨过进程边界。
- **`Atomic` 是声明在案的例外，而且在每个目标上都是同一条例外：复制一个
  `Atomic` 值复制的是句柄，两侧持有同一个 cell。** 先例是 `Pid`——复制
  pid 不会复制进程。共享句柄是安全的，因为对 cell 的每个操作都原子；共享
  正是这个类型的用途。
- 为什么不做复制即快照：在 BEAM 上，共享的 cell 无法再变成不共享——
  运行时的原子数组经由引用到达，引用被复制，共享就已发生。给 `Atomic`
  定快照规则，等于定一条必被某个目标悄悄破坏的规则。每个目标都守得住的
  规则只有一条：句柄被复制，cell 被共享，每次访问都同步。
- 这也是这个构造在**每个**目标上都挣得位置的原因，不止裸机：一个服务与
  它的客户端递增同一个 cell、一个父进程设置而子进程们读取的标志——写一次，
  处处一致地跑，同一份逻辑在双跑基架的解释器一端与 QEMU 一端原样运行
  （EmoOS T3.8）。

## 每目标支持矩阵

| 目标 | cell 机制 | 操作覆盖 | `fence()` |
| --- | --- | --- | --- |
| 解释器 | 精确空操作 | 全集 | 空操作 |
| `ts` | 精确空操作 | 全集 | 空操作 |
| `wasm` | 精确空操作 | 全集 | 空操作 |
| `c` | `__atomic` 内建，顺序一致性序 | 全集 | `__atomic_thread_fence` |
| `ocaml` | `Atomic` 模块，单调度域 | 全集；按位 `fetch_*` 以比较并交换环补足 | 空操作 |
| `beam` | 运行时的 `atomics` 数组 | 全集；按位 `fetch_*` 以比较并交换环补足 | 空操作 |
| `riscv64` | AMO、LR/SC、`fence`——生成镜像中的运行时助手 | 全集 | `fence` 指令 |

各行背后的诚实注记：

- **托管端的空操作是精确的，不是近似。** 这些目标上每个 Emo 进程都在
  同一条 OS 线程上协作、只在定义好的点切换，顺序一致性平凡成立，空操作
  就是正确的 lowering。操作仍然存在、仍然受查——负载范围与拒绝在所有
  目标上都是检查期的事。
- **`ocaml`。** `Atomic.fetch_add`/`fetch_sub` 是原生的且返回旧值；按位
  家族没有原生读-改-写，降到比较并交换环。环可能重试，但契约——返回旧值、
  不丢更新——是精确的。
- **`beam` 一行取代本笔记之前记录的一行式选择**（EmoOS README 的
  「每目标诚实」，2026-10-25，当时写的是 `counters`，CAS 与按位运算拒绝）。
  `counters` 无法诚实地撑起这套表面：它的读-改-写（`add`/`sub`）只报
  `ok`，不给旧值。运行时的 `atomics` 数组可以：顺序一致性是它的成文行为，
  cell 是按 2⁶⁴ 回绕的有符号 64 位（正是 `Int64` 规则），`exchange` 与
  `compare_exchange` 恰好给出对子契约所需的东西，`add_get`/`sub_get` 在
  回绕规则下能精确还原旧值——`previous = new − v` 回绕回去就是真值。只有
  按位家族降到比较并交换环，与 `ocaml` 行已有的兜底同款。`Atomic[Bool]`
  在 cell 里映射为 0/1。
- **`riscv64` 是真主场。** `store` 与 `exchange` 走 `amoswap.d.aqrl`，
  `load` 走栅栏夹持的加载（`fence rw,rw; ld; fence r,rw`），
  `compare_exchange` 走 LR/SC（`lr.d.aqrl`/`sc.d.rl`）——在动态模型里 cell
  的字还是装箱值的期间，`fetch_*` 家族也走 LR/SC：环内解码该字、按回绕规则
  计算、装箱，再对着读到的那个字原样交换，cell 中途被挪动就重读。`fence()`
  就是 `fence rw, rw` 指令。这些以运行时助手落在生成的镜像里（随 T1.6 到位）；
  Stage B（S2）让 cell 持有裸 `Int64` 字的那一刻，AMO 算术（`amoadd` 一族）
  就是直接形式。

## 数据竞争——什么是定义的，什么不是

定义的：

- **消息传递**——值跨进程边界走复制。
- **对 `Atomic` cell 的操作**——它们把 cell 的历史放进顺序一致性全序，
  在容纳该操作的每个目标上如此。
- **`peek`/`poke`**——定义上就是 volatile：永不消除、互不重排。
  `fence()` 把这条成对规则扩成完整屏障；它不能让 `peek` 再 `poke` 的
  组合变原子——什么都不能，裸内存读-改-写不是一个构造。
- **上下文永不同时运行之处的未同步共享**——交错就是调度器的既定切换点，
  永远不存在「同时」被错过。

未定义的——**未同步的跨上下文共享 `Box` 字段**：当两个可能同时执行的
上下文在没有原子操作或栅栏定序的情况下到达同一块普通内存，行为未定义。
让这件事成真的上下文：

- **裸机上，中断体与被它打断的线程代码**——ISR 纪律用预分配环形缓冲与
  裸内存作答的那个案例；
- **SMP hart**——路线图上挂起；解挂之后仍由同一条款覆盖；
- **运行时将来同时运行的任何上下文。**

语言的方式是把它说出来，而不是把它藏起来：普通字段访问永不缴隐藏的同步税，
也没有运行时替竞争打圆场。修复就是本笔记给出的这几件——共享状态是值，用
`Atomic` cell；共享状态是裸内存，用 `peek`/`poke` 加 `fence()` 与单写者
环形缓冲纪律。在这些之外共享的程序是错的，而在竞争真实存在的目标上，
没有任何目标让它碰巧变对。

检查器的界线，依 strictness-first：负载范围与操作集响亮且早查；跨上下文
可达性在检查期不可判定，所以上述语义是契约，不是诊断。
