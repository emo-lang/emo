# Emo 与实时操作系统 —— 一份评估

写于 2026-10-06。这是一份技术可行性评估,不是已定的设计决策;文中关于
项目状态的描述以写作日期的仓库为准。

问题:用 Emo 实现一个实时操作系统——FreeRTOS 级的内核——有多难?

## 两件不同的事

- **把 FreeRTOS(C)移植进 Emo 镜像,由 Emo 调用。** 借 freestanding
  `riscv64` 目标的 C 互操作(freestanding C 源码编入镜像、以 psABI 为
  契约),这是低到中等的工作量。摩擦在于:Emo 的进程是**协作式**的,
  而 FreeRTOS 任务是**抢占式**的,两套调度器必须就"谁占有 CPU、谁占有
  中断向量"达成一致。
- **用 Emo 重写一个 RTOS。** 这才是真正的问题,而且很难——但难点在
  **语言、运行时与工具**,不在调度算法。

下面只谈第二件。

## RTOS 需要什么

- **抢占式优先级调度**与有界的上下文切换延迟——这是它的定义特征,也是
  Emo 目前没有的;
- **定时器与中断基础设施**:trap handler、tick、时间片、ISR;
- **ISR 安全的同步**:mutex(含优先级继承)、信号量、队列、事件组、
  软定时器;
- **确定性内存**:静态或 arena 分配,无 GC 停顿,临界路径上没有隐藏
  分配;
- **`volatile`/MMIO 语义**与**带内存屏障的原子操作**(ISR 与任务的
  竞争);
- 每任务独立栈、优先级、idle task、tick 频率配置;
- **WCET 可分析**;
- (可选)内存保护(MPU/MMU);
- 安全关键场景还需要**可认证的工具链**。

## Emo 现有设计:哪些帮忙

- **freestanding 目标 + 可替换的运行时。** `plan/step-22` 给的是无 OS、
  无 libc、无默认运行时,分配器、GC、调度器都是可替换组件——正是内核
  自持运行时所需的形态。
- **无 GC 对抢占友好。** 抢占于是只是"存寄存器、换栈";若有追踪式 GC,
  它反而必须做成抢占安全或增量的。当前的无 GC 方向消掉了 RTOS 与抢占
  之间最难的一处耦合(将来再加 GC 只会让这件事**更难**,不会更容易)。
- **协作式优先 + 消息复制**让单 hart 无锁、无原子,因为进程之间不共享
  可变状态。
- **上下文切换是教科书式的**:约三十条汇编交换 `sp`、`ra` 与被调用者
  保存的寄存器,而 `emo_sched_det` 提供了可做差分验证的参照模型。
- **显式 MMIO**(`peek`/`poke`);值语义减少数据竞争;结构接口配编译期
  vtable,内核没有运行时方法查找。
- **位宽显式**的数值:RV64 上 `Int64` 占一个寄存器。
- **单语言闭环**(EmoOS 的抱负):内核与 shell 用同一门语言。

## Emo 现有设计:哪些帮倒忙

- **不承诺抢占。** `plan/step-22` 把 timer preemption 放在 M3,并标注
  "optional; semantics do not require it"。RTOS 需要它,所以必须补。
- **语言层没有 `volatile`、原子或屏障语义。** `peek`/`poke` 是调用,
  优化器可能重排或消除;ISR 与任务的竞争没有原语。这是**语言 + 代码
  生成**的缺口。
- **渐进类型会给动态区域装箱**,而 step-22 在 freestanding 动态世界里
  把 `Int64`/`Float64` 装箱;带标签的路径代价不恒定,与 WCET 冲突。
- **值语义会产生分配**(字符串、数组、实例、消息)——配 arena 或静态
  分配没问题,无界就是灾难。
- **尚无循环语句**(已决定,未实现);今天紧密循环与 ISR 体都是递归。
- **异常**(catch 语法在 `CHECK.md` 仍未定)必须在有界时间内展开。
- **没有调试器、profiler、WCET 工具、MISRA 类检查器。**
- **未冻结**(无 1.0/LTS),生态(BSP、驱动、中间件)为零——这使功能
  安全认证暂时无从谈起。

## 按目标的难度

| 目标 | 难度 | 说明 |
| --- | --- | --- |
| 协作式内核(green threads、消息、MMIO console) | 中 | step-22 M2 的范围;不是 RTOS |
| 软实时工控/监督面 | 中 | 协作式 + 有界分配或许够用 |
| 抢占式 RTOS 核心(FreeRTOS 级) | 难(数月~数年) | 需 M3 抢占 + `volatile`/原子 + 确定性内存 + ISR 基础设施 |
| 移植 FreeRTOS(C)并由 Emo 驱动 | 低到中 | C 互操作;两套调度器共存的摩擦 |
| 硬实时 + 功能安全认证 | 极难,暂不可及 | 需冻结的语言与可认证的工具链 |

## 真正的拦路者

调度算法是教科书内容;拦路的是**语言与运行时级的保证**——抢占安全、
确定性内存、`volatile`/原子、WCET 分析、认证工具。还有一层**模型错配**:
Emo 的进程与 mailbox 是为**隔离**而生的(Erlang 血统),而 RTOS 的优先级
与优先级继承是为了**界定最坏延迟**。有界延迟语义今天不在 Emo 的模型里。

这与 `docs/industrial-software.md` 的结论一致——"硬实时够不着"——而且
这段距离在**语言与工具**,不在调度。

## 若要推进的路线

1. **协作式内核 bring-up**(M1/M2):freestanding 后端与调度策略。
2. **抢占(M3)**:`stvec` trap handler、定时器(CLINT 或 SBI
   `set_timer`)、时间片。无 GC 让这一步只是寄存器/栈切换——Emo 的
   优势。
3. **语言原语**:`volatile` 语义与原子/屏障;在 `CHECK.md` 单独立项。
4. **确定性内存**:静态或 arena 分配器;内核路径上不做无界分配。
5. **优先级调度与优先级继承**:策略用 Emo 写,架在汇编机制之上
   (step 14 已定下这个分工)。
6. **工具**:调试器、栈深分析、WCET、静态检查。
7. **认证**:等 1.0/LTS 冻结之后。

## 结论

在 Emo 里做一个协作式、无 GC、可调度的内核,是**中等**工作量,骨架已
经规划好。做 FreeRTOS 级硬实时 RTOS 则**很难**,预算花在语言、运行时
与工具上,而非内核逻辑。**可认证**的 RTOS 在 Emo 冻结、工具齐备之前
不可及。最现实的第一目标是**软实时监督面**,而非硬实时。
