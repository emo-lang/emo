# 裸内存 —— `peek`/`poke`,定义上就是 volatile

## 定案

`peek8` / `poke8` / `peek64` / `poke64` 以自由函数加入 `core` —— 沿
`fence()` 的先例:裸名字、免导入、无包装类型。它们定义上就是
volatile(随原子内存模型一并定案,2026-10-25):永不被消除、互相之间
永不被重排。语言面同日定案:两个访问宽度——字节线与字线——以及一条
把它们限定在 freestanding 目标的准入规则。

需求来自 EmoOS:16550A UART 靠 `0x10000000` 处的寄存器驱动,物理帧与
页表是裸内存里的字,内核拥有机器上的每一个地址。这个构造就是裸内存
本身——内核设计早已命名的无类型内存纪律——如今给它一个受检查的语言
面,而不是一个逃生口。

## 语言面

| 内建 | 签名 | 作用 |
| --- | --- | --- |
| `peek8(addr)` | `Int64 → Byte` | 一次 volatile 字节读,按无符号(0–255)读回 |
| `poke8(addr, b)` | `Int64 → Byte → Void` | 一次 volatile 字节写 |
| `peek64(addr)` | `Int64 → Int64` | 一次 volatile 字读 |
| `poke64(addr, v)` | `Int64 → Int64 → Void` | 一次 volatile 字写 |

表格所依据的规则:

- **宽度由载荷类型承载。** `Byte` *就是*八位,`Int64` *就是*六十四位:
  不存在扩展问题,也没有截断要执行——传递的值就是放得下的值。
  字节线按无符号读,是 MMIO 的自然读法;寄存器的高位以 128–255 存活,
  而不是一个负数。转换用的是既有的显式转换:`Byte.from_int64`(检查
  0–255,越界是响亮错误)、`Int64.to_byte`(取低八位)、
  `Byte.to_int64`(加宽,恒安全)。
- **`poke` 回答 `Void`。** 裸内存的读-改-写不是构造——`peek` 接
  `poke` 挨不过两者之间打来的中断,任何 fence 都改变不了这一点
  (atomics 设计笔记正是这么写的)。回答旧值会诱使这个模式;什么都不
  答才让拒绝保持诚实。读-改-写的同步形态是 `Atomic` cell。
- **地址就是硬件看到的东西。** `Int64`,不校验、不问出处——一个裸的
  物理(以后是虚拟)地址。坏地址**陷入 trap**:内核装上陷阱向量之前,
  trap 就是固件的重启;之后(EmoOS M2)是内核的 trap 路径。这是机器
  的确定行为,点名说出,而不是笼统地归为未定义。
- **对齐与端序是调用者的纪律。** MMIO 寄存器按总线协议天然对齐;内存
  在机器上是小端。不做检查,也没有 byteswap 构造——位掩码是程序员的
  事,内核设计早已声明这条纪律。
- **Byte 算术保持家族规则。** `Byte` 操作数按模 256 无符号回绕,在每
  个目标上完全一致——托管目标已经在跑的规则。位运算留在型内
  (`peek8(lsr) & 32B`);混合宽度拒绝,与其他地方一致,想让算术变宽
  就用 `.to_int64()` 过去。

宽度集刻意取 `{8, 64}`。32 位线等 `Int32`——它的语言面已经定案
(`docs/numeric-width.md`),落地之时 `peek32 : Int32` /
`poke32(addr, v : Int32)` 就是第一个消费者(virtio MMIO,EmoOS
T7.1)的诚实形态。16 位线在 roadmap 上没有消费者,不做投机构建。

## volatile —— 这条规则意味着什么

- 四个内建永不被消除、互相之间永不被重排;`fence()` 把这条两两规则
  加宽为覆盖普通访问与 volatile 访问的全屏障(atomics 笔记的契约)。
  任何东西都不能让 `peek` 接 `poke` 变成原子。
- 在 `riscv64` 上,每个内建是一条 load/store 指令(`lbu`、`ld`、
  `sb`、`sd`)——动态体走运行时 helper,类型化体自 EmoOS T2.3 起在裸
  地址上内联——按程序序发射。这个没有优化器的后端天然守住规则。

## 按目标矩阵

| 目标 | `peek8`/`poke8`/`peek64`/`poke64` |
| --- | --- |
| `riscv64` | 准入 —— 生成镜像里的 volatile 访问 helper |
| 解释器、`c`、`ocaml`、`ts`、`wasm`、`beam` | 检查期按名拒绝(E4028) |

各行背后的原则:**一个目标准入 `peek`/`poke`,当且仅当程序拥有地址
空间。** 托管目标上,运行时的堆属于宿主——tag 位、回收器、是否移动
都由宿主说了算——程序能叫出名字的任何地址,穿过它去读都不诚实,何况
程序根本没有 in-language 的途径拿到一个合法地址。atomics 的 no-op
先例搬不过来:原子的 no-op 是精确的,因为没有并发在跑;peek 的 no-op
必须发明一个返回值——那是静默回退。拒绝才是诚实的行,而托管侧真需要
裸 C 的罕见场合早有 `foreign def`。

双运行奇偶 harness(EmoOS T3.8)在构造上不受影响:设备躲在结构接口
后面,假设备在托管解释器下实现这些接口,解释器里跑的代码永远拼不出
一个 `peek`——按名拒绝把这条缝强制出来,而不是指望纪律。

## riscv64 上的 Byte 线(随本笔记落地的东西)

riscv64 值模型获得 `Byte` 立即数——立即数 kind 3 占 bits 3:1,字节
占 bits 11:4——补齐每个托管目标早已携带的东西:字节字面量(`32B`)、
型内算术模 256 回绕、比较、`to_string`、转换。缺口点名说出而不是藏
起来:

- 静态类型被 IR 丢掉的 `Byte`——类型级方法调用的结果、模块级 `const`
  读取——会落到动态分派,而动态分派对 Byte 立即数只答 `to_string`,
  其余响亮失败。参数、局部量与普通表达式都携带类型;先绑定再调用。
- `Bytes` 缓冲区在 riscv64 上继续拒绝:暂无消费者,另列工作。

排期中的代价已经付清:动态值模型下每次 `peek` 分配一个装箱 cell——
正是 Stage B 存在要消除的代价,EmoOS T2.3 已把它消掉。全类型化的体
(内核的形状)把每次访问降为一条内联 volatile 指令:一次 MMIO 读不
分配任何东西,轮询循环烧的是寄存器,不是堆。动态体保留 helper 与其
每次读取的 cell。金测:`examples/peek_poke` 的 `burn` def 把一个字节
读四百万次——若每次读取仍装箱就是 128 MiB,越过 96 MiB 堆——并打印
校验和。

## 这份笔记关掉什么

`xv6.md` 把 volatile 访问与屏障列为用 Emo 写操作系统的理论阻塞项;
atomics 笔记回答了屏障那一半,本笔记回答 volatile 这一
半。2026-10-26 随 EmoOS T1.8 落地。金测:QEMU 语料
`examples/peek_poke`(两个宽度的 RAM 往返、小端字节图景、Byte 算术
家族、按字节宽度读 16550 的线路状态寄存器——0x60,复位值),以及每
个托管目标一条的拒绝金测,各自点名 E4028。
