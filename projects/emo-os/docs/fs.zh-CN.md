# 文件系统服务——权威态与可重建态

EmoOS 如何保存文件：拥有磁盘布局的那个服务，它在「磁盘持有的状态」与「内存中保存的状态」之间划下的那条线，服务崩溃的代价与内核如何把它拉回来，以及用户程序看到的动词。定案于 T7.2（2026-10-30）。下方的块设备驱动是 T7.1 的；上方的 shell 是 T7.3 的。

英文原文：[`fs.md`](fs.md)。

## 分裂

立项时定下：内核服务死亡即重启；而一个服务只有把两类状态分开才可能被重启——**权威态**，只存在于唯一一处，丢了就是事物本身丢了；**可重建态**，从权威态推导而来，可以扔掉再推导一遍。文件系统是第一个拥有权威态的服务，所以这条线在这里第一次真正划下。

- **权威态——磁盘。** 第 0 扇区的超级块（挂载表在其中）、名字表、数据扇区。此外没有任何东西是权威的。磁盘不持有的关于文件的事实，就不存在。
- **可重建态——服务的内存。** 超级块的副本、名字表的副本、空闲图、请求簿记。服务的新实例在它最初的几毫秒里从磁盘推导出全部这些，对内存里找到的一切概不信任。

让这道分裂保持诚实的规则是**写穿（write-through）**：每一次改动都在发起它的那个请求之内落盘，然后才应答。已应答的写就在盘上；服务的内存从不持有磁盘尚未持有的改动。没有写回缓存，也没有 flush 动词，因为没有什么需要 flush。

空闲图是唯一只存内存、从不写盘的状态，而这是有意的：空闲图是名字表的函数（文件 extent 覆盖的每个扇区都已占用，其余数据扇区都空闲），盘上若再存一份就是第二个权威，可能与第一个不一致。空闲图在每次挂载时从名字表重建。

## 磁盘

磁盘就是驱动找到的那个块设备（T7.1）：512 字节扇区，`run.sh` 建的 1 MiB 镜像有 2048 个。布局按扇区号固定：

| 扇区 | 内容 |
| --- | --- |
| 0 | 超级块 |
| 1–8 | 名字表：64 条 64 字节的条目，每扇区 8 条 |
| 9–2047 | 数据区 |

**超级块**（第 0 扇区），按 64 位小端字：

| 偏移 | 内容 |
| --- | --- |
| 0 | 魔数，按序读出为八个字节 `EmoFS-01` |
| 8 | 代数（generation）：每次挂载递增并写回 |
| 16 | 磁盘扇区数，格式化时按驱动报告的值记下 |
| 24 | 挂载条目数 |
| 32 | 挂载表：每条 64 字节 |

**挂载表**是服务所服务的卷的列表——每个卷的名字表与数据区在哪里。今天一条：磁盘自身这一个卷，名为 `root`，名字表在扇区 1–8，数据区从 9 到末尾。这张表在盘上且只在盘上，这正是它持久的含义：服务的新实例——无论崩溃之后还是断电之后——读第 0 扇区就知道自己服务什么，无须任何人告知。条目不带设备字段，因为只有一个设备；第二块盘到来时，正是它会补上这个字段的条目。

| 条目偏移 | 内容 |
| --- | --- |
| 0 | 卷名，16 字节，NUL 填充 |
| 16 | 名字表首扇区 |
| 24 | 名字表扇区数 |
| 32 | 数据区首扇区 |
| 40 | 数据区扇区数 |

**名字表条目**（64 字节）：

| 偏移 | 内容 |
| --- | --- |
| 0 | 文件名，至多 24 字节，NUL 填充；首字节为 NUL 即空条目 |
| 24 | 字节大小 |
| 32 | extent 首扇区 |
| 40 | extent 扇区数 |
| 48 | 写入它的那次挂载的代数 |
| 56 | 保留，为零 |

一个文件就是一段连续的扇区 extent。命名空间是平坦的：没有目录，因为服务之上还没有谁需要它——shell（T7.3）列出并点名文件，一个平坦的卷正是它所需。

**格式化。** 第 0 扇区没有魔数的磁盘是空盘，服务的首次挂载会格式化它：八个名字表扇区写零，然后写入代数为 1、带那一条挂载条目的超级块。格式化是挂载自身的动作而非单独工具，于是空镜像一启动就是可用的文件系统；带魔数的磁盘绝不会被格式化，不论其上还有什么。

## 操作与提交点

每个操作就是一个请求，一个请求就是一个事务：服务在请求之间不替客户端持有任何句柄，所以重启之后客户端没有什么需要重新打开。四个操作：

- **写**整个文件：名字与字节；已有的名字被替换。
- **读**整个文件：名字；字节落到调用者的缓冲区。
- **列出**名字，一行一个。
- **删除**一个文件。

写是磁盘发生变化之处，它的顺序就是崩溃语义：

1. 从内存空闲图分配 extent——首次适配一段恰够这些字节的连续扇区。没有这样的段：拒绝（原因 5），磁盘未动。
2. 字节写入新扇区，向驱动一次一扇区；末扇区的尾部写零。
3. 名字表条目——名字、大小、extent、代数——先写内存，再把它所在的扇区写盘。**这一次单扇区写就是提交点。**
4. 若该名字已存在，其旧 extent 在内存图中释放。

第 3 步之前崩溃，旧条目完好：文件仍是原样，新扇区无人引用——下一次挂载重建空闲图时它们又空闲了。第 3 步之后崩溃，留下的是新文件：第 4 步只碰内存，重建会正确推导出来。不存在磁盘引用了未写入字节的状态，因为字节先于点名它们的条目写入。

删除的提交点是同一次条目写，只是条目被清空；读与列出不改变任何东西。

这一顺序所假设的是**512 字节扇区写是原子的**：设备要么写整个扇区，要么一个字节都不写。这是驱动所说的块设备契约，也是崩溃语义所依赖的唯一假设；撕裂的扇区不在设计之内。

## 重启

### 死亡是什么

内核服务以 S-mode 跑在内核自己的页表上，所以进程边界为它买到的隔离比用户 pass 窄：**内核服务的故障就是内核的故障**。文件系统代码里的一次非法访问是内核 bug，整机随之响亮终结，如同任何监管者 trap（T4.6）。内核服务能独自死去的死法有两种：

- **arena 击杀。** 内核没有垃圾回收器，服务收发的每条消息都在它 64 KiB 的 arena 里分配，于是长寿的服务终会耗尽它——T5.1 圈禁的那种击杀（`heap gone in process N`）。重启正是把它从寿命上限变成维护事件的东西：实例死去，带着新鲜 arena 的新实例从磁盘重建，文件分毫不差，因为磁盘才是权威。
- **停止。** 从循环返回的服务像任何进程一样结束。文件系统在内核侧客户端要求时返回（下文的操作），这就是有意驾驭重启的方式。

两种死法汇入同一套机制。

### 通知

运行时新增了一个**死亡钩子**，console/block 钩子的同款模式：一个字（`emo_death_hook`），在 stub 不碰它的每个镜像里为零，内核的 boot stub 把它停靠到 trap shim 的一个例程上。运行时在绿进程结束的两处——entry thunk 的返回与 arena 击杀——以死进程的 pid 调用它，时机在槽标为 done 之后、回收之前。该例程以门投递请求的方式（`emo_gate_post`，零分配，在掩码区内）向 supervisor 的邮箱投一个裸字：`256 << 32 | pid`，一个任何门动词都到不了的 op。supervisor cell 为零的内核收不到通知；用户 pass 的死亡一如既往走 shim 自己的路由与进程服务的退出表。

### supervisor

**supervisor** 是 root 只生一次的内核进程，是文件系统服务的拥有者：

- 它从帧分配器取一次服务的**缓存块**——服务内存所在的那一个 64 KiB 块（超级块副本、名字表副本、空闲图、扇区暂存区）——并把同一块交给每个实例。块比实例活得长；每个实例都从磁盘覆写它，对它原先持有的一切概不信任。
- 它生出服务，接收宣告（实例的 pid），把裸号停进门用来路由的文件系统 pid cell，并把 Pid 转发给 root。
- 收到点名当前实例的死亡通知时，它先应答死实例留下的每个停靠客户端：文件系统页上的请求槽（下文）记着谁在等，每一个都以原因 5 拒绝——内核耗尽了资源，这正是发生的事——然后清空槽与暂存环。接着生出下一个实例，照旧停靠其 pid。崩溃时请求在飞的客户端得到的是拒绝而非挂起，它的下一个请求会找到新实例；而在一个实例死亡与下一个实例启动之间的窗口里抵达的请求根本不被拒绝——门把它放进同一个暂存环、shim 只停靠不投递，下一个实例会最先服务它（跨窗口重试的客户端只会在拒绝上空转，而协作式内核没有任何收回处理器的手段）。

supervisor 自身每次通知几乎零分配，且不受监管；它的死亡会是内核的 bug。

### 挂载

每个实例都以同样的方式开始，不论它是上电后的第一个还是崩溃后的第五个：经驱动读第 0 扇区；魔数缺失即格式化；代数递增并写回超级块——于是超级块写路径在每次挂载都跑一遍，线上的代数计着这块盘见过的实例数；八个名字表扇区读进块里；空闲图由此重建；打印挂载行（`fs gen <代数> files <数目>`，若本次挂载格式化了则先有 `fs formatted`）；向 supervisor 宣告；进入循环。实例的内存是磁盘的函数（启动时算出）加上此后请求的函数——前一个实例的任何东西都不会活进来。

## 门

动词，接续 `docs/syscalls.md` 的表——每个指针参数都在门的检查之下，名字与字节在门处拷入（写动词的纪律，T6.2）：

| 动词 | 拼写 | 应答 |
| --- | --- | --- |
| 6 | `file_write(name, name_len, buf, len)` | `name` 处 `name_len` 字节点名的文件变为 `buf` 处的 `len` 字节；应答 `len` |
| 7 | `file_read(name, name_len, buf, cap)` | 文件的字节落到 `buf`，至多 `cap` 个；应答文件大小 |
| 8 | `file_list(buf, cap)` | 名字（各带一个换行）落到 `buf`；应答写入的字节数——装不下的名字连同其后的全部被略去 |
| 9 | `file_remove(name, name_len)` | 文件消失；应答 0 |

名字为 1 到 24 字节，不含 NUL 与换行（否则原因 4）；一次写至多 2048 字节（原因 4）；没有条目持有的名字是**原因 6，no such file**——原先的表里没有的原因，由 `syscall` 包命名（`"no such file"`）；名字表满或数据区没有足够长的连续段是原因 5。

**请求槽。** 文件系统是第一个事务要等待另一进程（驱动的回复）的服务，等待期间到达的请求绝不能被误认为那个回复。门把每个请求的参数拷进文件系统固定页上**四个请求槽**之一（名字、长度、调用者缓冲区地址、字节），把槽标为 busy，并把槽号编进路由（`-(1000 + op + 16 × slot)`，于是服务解码的请求字是 `(slot << 36 | op << 32 | pid)`）；服务应答了该请求，槽才重新空闲。四个调用者可以同时停靠在文件系统上；第五个在拷贝任何东西之前以原因 5 被拒绝。服务等待驱动期间收到的若是请求，则进入同一页上的裸字**暂存环**，事务结束后按序服务——邮箱与暂存环合起来是一个 FIFO。

服务自己的应答遵循门的惯例：写从门的拷贝应答；读与列出经监管者低位窗（内核自表把 RAM 恒等映射，门往停靠帧写应答走的就是这个别名）写进调用者的缓冲区——范围已在门处检查，字节落地时调用者正停靠着。

**内核侧。** 内核进程不经门也能到达服务：一条六元组消息 `(op, from, name, name_len, buf, len)`，地址是内核地址，以发给 `from` 的消息应答。同样的 op，再加一个：**op 0 是停止**——服务返回，这是一次 supervisor 会重启的死亡。root 在启动时用它一次，驾驭链条所钉住的那次重启。内核客户端一次只发一个请求并等其应答；跨崩溃停靠的内核客户端会永远等下去（root 从不如此）。

## 块驱动的部分

驱动的协议为一个不是 root 的客户端而生长。请求是元组 `(op << 32 | sector, from, word)`：op 为 1 或 2 时是 T7.1 的一个字进出一个扇区，为 **3 或 4** 时是整扇区从一个缓冲区写出或读入该缓冲区，其内核地址为 `word`——设备看到的是它的物理地址，缓冲区必须是一整片连续 RAM，服务的缓存块正是（T6.5 的纪律）。回复发给 `from`：op 1 与 2 回那个字，3 与 4 回显扇区号——回显正是服务要核对的，于是一条不是回复的消息会响亮终结而不是被当成回复。完成等待仍是轮询，上限如 T7.1 所留；本任务没有任何东西要求中断驱动的等待。

## 边界

- 一块盘、一个卷、平坦命名空间、整文件操作；64 个文件，名字至多 24 字节；一次写至多 2048 字节；一个文件是一段连续 extent。
- 持久性即设备的完成：没有 flush 动词，驱动也不发 flush，于是缓存镜像的宿主机是宿主机自己的事。
- 扇区写假设为原子（见上）。
- 驱动不受监管：它的 arena 是它的边界（每次启动数百个请求），而重启它需要一样今天被重启服务的客户端所缺的东西——按号而非按 Pid 值到达服务的办法。这是会话寿命超过驱动 arena 时的下一块。
- 崩溃时在飞的客户端请求被拒绝，绝不重放：服务无法知道一次写进行到哪，而磁盘无论如何都是一致的。
- supervisor 应答停靠的门客户端，不应答停靠的内核客户端。

## 钉子

`run.sh` 在首次启动前把镜像清零，于是两腿是一个故事：legacy 启动格式化磁盘，sstc 启动找到它。每次启动，链条带着挂载行，然后是 root 的内核侧证明——经第一个实例写入一个文件、停止、supervisor 重启出的实例的挂载行（代数高一、文件计入）、经它读回那个文件、`fs restart ok`——然后在 U-mode 是 hello 经门的证明：600 字节的文件写入并逐字节读回（`fs rw ok`），第二个文件写入并删除，列表点名两个（`fs ls 2`）。第二腿的首个挂载行计着第一腿留下的两个文件，其中没有 `fs formatted`。

## 固定地址

文件系统的页（`.emo_fs`，自 `0x87005000` 起三页），由内核的常量寻址：

| 地址 | 内容 |
| --- | --- |
| `0x87005000` | 文件系统服务的 pid（门按它路由） |
| `0x87005008` | supervisor 的 pid（死亡钩子向它投递） |
| `0x87005010` | 暂存环的计数 |
| `0x87005018` | 暂存环：四个请求字 |
| `0x87005100` | 请求槽 0；槽间距 2304 字节 |

一个请求槽：

| 偏移 | 内容 |
| --- | --- |
| 0 | busy |
| 8 | 调用者的 pid |
| 16 | 名字长度 |
| 24 | 写的长度，或读与列出的容量 |
| 32 | 调用者的缓冲区，供读与列出 |
| 64 | 名字，32 字节 |
| 256 | 写的字节，2048 字节 |
