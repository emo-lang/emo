# 内核的高半区布局

内核在 Sv39 下如何安身:地址空间的两个半区、内核为自己建的那张表、每个字节都有的两个别名、从 OpenSBI 的物理入口走到一个分页运行的内核的那段启动、每个用户 pass 跑在其上的每进程页表,以及——自 T6.3 起——每个 trap 都要穿过的 trampoline。T6.1(2026-10-29)、T6.2(2026-10-29)与 T6.3(2026-10-30)定案;缺页击杀(T6.4)与隔离金测(T6.5)在本文档上延伸,而不是取代它。

英文版:[`sv39.md`](sv39.md)。

## 两个半区

Sv39 翻译 39 位虚拟地址——512 GiB——并要求 64 位地址的高 25 位复制第 38 位,所以地址空间是中间隔着一个洞的两个半区:低半区 `0` 到 `0x3fffffffff`,高半区 `0xffffffc000000000` 到顶。低半区是用户的;高半区是内核的。

每个内核地址都是它的物理地址加上 `koff`——高半区的基址 `0xffffffc000000000`,作为 `Int64` 即 −2³⁸——因此内核镜像、空闲 RAM、固定页与设备全都坐落在距它们物理位置一个固定偏移的地方,而指针的符号说出它属于谁:内核地址为负,用户地址为正。内核镜像链接在 OpenSBI 进入的加载地址的高别名上(`0xffffffc080200000`);`link.ld` 让每个 section 的加载地址保持物理,所以 QEMU 与固件看到的镜像位置一如既往。

为什么是高半区而不是窗口期跑的恒等映射:用户得到整个低半区——每个用户 ELF 一个固定加载地址,没有要避开的内核区段(T6.2);内核的映射可以共享进任何地址空间而不与用户的相撞;符号位是任何查表比较都比不过的一次测试。

## 内核的表

由 `sv39.emo` 在启动时建一次,建在分配器交出的帧上,此后不再变动。它映射了什么,按 QEMU 监视器读回的样子(`info mem`):

| 虚拟 | 物理 | 大小 | 位 | 内容 |
| --- | --- | --- | --- | --- |
| `0xffffffc080200000` | `0x80200000` | text | `r-x` | 内核的代码 |
| text 末尾 | | rodata | `r--` | 只读数据,含内嵌的用户镜像 |
| rodata 末尾 – `0xffffffc088000000` | | 到 RAM 顶 | `rw-` | data、bss(96 MiB 堆、进程槽、绿色进程栈)、帧区域、固定页 |
| `0xffffffc010000000` | `0x10000000` | 4 KiB | `rw-` | 16550A |
| `0xffffffc00c000000` | `0x0c000000` | 4 MiB | `rw-` | PLIC |
| `0x80200000` | `0x80200000` | 到 RAM 顶 | `rw-` | 监管者的低位 RAM 窗——大页,**无 U**(T6.2) |

这张表遵守的规则:

- **权限按链接器边界划分。** `link.ld` 把 `.text` 与 `.rodata` 的末尾对齐到页并导出;stub 把两者传给建表者,建表者把它们记录在 Sv39 页上——此后每张表(每个进程的,T6.2)画同一幅图——text 为 RX,rodata 为 R,从 data 起全部为 RW。
- **粒度按对齐决定。** 一段范围在两个地址都落在 2 MiB 边界且还剩至少 2 MiB 的地方用 2 MiB 大页映射,其余用 4 KiB 页——于是镜像开头的两兆字节(权限边界落在这里)花费一张小表,其后的一百兆字节花费六十二条表项。整张内核表五个帧:根、RAM 的一级表、镜像头部的零级表、MMIO 的一级表、UART 那页的零级表——拆了一个块。
- **每个叶子都置了 accessed 与 dirty。** 内核不记使用计数,而一个遇到清零位就陷入的实现不该有机会这么做。无 global 位,ASID 0。
- **没有一条表项带 U。** T6.1 的窗口两条 U 巨页已经消失(T6.2):内核的表映射内核的半区与监管者的低位窗,而没有任何东西在这张表上跑 U-mode——boot pass 在进入 shim 处领它自己的表,每个用户进程跑在其中一张自己的表上。
- **监管者的低位窗是唯一的低位映射。** 装载器往窗口里拷贝、用户 stub 的 cell(`0x87fff000`)、进程服务读被停放的程序 cell、以及门往一个停放的 pass 的 trap 帧里写答案,全是低位地址,而内核进程跑在这张表上:低位窗是内核自己的簿记够及它们的路。它是 RW、无 U、永不被执行,并且始于加载地址——固件的 PMP 锁定区不在任何映射里,T6.1 的决定保持。
- **固件不在任何映射里。** `0x80000000`–`0x80200000` 是 OpenSBI 的;内核从不碰它,内核仍会发出的 SBI 调用(关机)是 M-mode ecall,不经翻译地运行。

## 表项格式与遍历

一张表是一个 4 KiB 帧,装 512 条八字节表项。表项是 `PPN << 10 | flags`:下一级表或页的物理页号,以及 V(有效)、R、W、X、U(用户可及)、G、A(accessed)、D(dirty)各位。R、W、X 任一置位的表项是叶子,不论它在哪一级——零级是 4 KiB 页,一级是 2 MiB 大页,二级是 1 GiB 巨页;一个都不置的表项是指向下一级表的指针。遍历每级取虚拟地址的九位——根表取 38–30 位,中间取 29–21,末级取 20–12——从 `satp` 里的根表往下三级。

`sv39.emo` 就是 README 定案的无类型内存纪律——`Int64` 地址、`peek`/`poke`、位掩码,没有任何语言值指进表里——每个 def 都是完全类型化的 native 体。它的规则是严格的:往下走遇到叶子是内核 bug(一个更大的页已经覆盖了该地址),一个地址映射两次是内核 bug,叶子或范围偏离页边界是内核 bug——每一种都是响亮的终结(控制台上 `sv39: …` 一行,然后 SBI 关机),绝不悄悄覆盖。`lookup` 是软件遍历,硬件在 TLB 未命中时做的事;建表者在答出根表之前先用它遍历自己的表,核对接下来的指令所依赖的地址——一张错表死于一行字,而不是死于 `satp` 写入处的一次故障。

## 两个别名,各归谁用

机器上的每个字节都有两个地址:内核的,在高半区;以及物理的。

- **内核地址是通货。** 内核自己的 load、store、取指所及的一切——镜像、分配器的块与帧(`frames.emo` 的区域界址、链接与答案全是内核地址)、两个环与固定页、设备——都以内核地址命名,在 Emo 里是 `koff` 加物理常量,在 shim 的汇编里是 `EMO_KOFF` 加物理常量。
- **物理地址恰好出现在三处**:叶子表项里(`sv39.emo` 写入 `pa_of(内核地址)`)、`satp` 里(shim 接收根表的物理地址)、以及作为用户对自己内存的地址——用户镜像照旧跑在 `0x87100000`,用户 pass 的栈块与 arena 块由该 pass 以物理地址访问(每个 pass 的表按恒等映射它们),`0x87fff000` 处的用户 cell 是用户的。T6.2 没有挪动用户的世界;它关掉的是用户原本能多碰的一切。
- **内核以用户的地址、借 SUM 够及用户内存。** 门读缓冲区、装载器往窗口里拷贝、shim 在用户栈上铺 trap 帧、spawn 搭合成帧——全是 S-mode 对带 U 位的页的访问,`sstatus.SUM` 准许它们。stub 在内核的表生效后置一次 SUM,resume stub 在每一次返回任何模式时再置一次:SUM 是内核的属性,不是帧的——spawn 的合成帧带的是一个裸 `sstatus`,一次信了它的返回会丢掉 SUM,在下一次 trap 的第一条 store 处故障。
- **两个翻译点,都是显式的。** 用户 cell 处的 arena 交接(`trap.S`):槽里的游标与末端字是内核地址,cell 收的是用户的,所以进 U-mode 的路上减去偏移,trap 出来时加回去。以及 reaper 的栈归还(`frames.give`):运行时以 pass 跑在其上的地址——物理地址——称呼一个死去 pass 的栈,分配器先把物理基址译成内核的,再用与其他任何归还相同的严格检查去判断它。pass 跑在其上的地址就是它自己的表所映射的那些;这里没有东西终结——用户世界的恒等映射是有意从 T6.2 存活下来的。

## 每进程页表(T6.2)

每个用户进程——boot pass 与每个 spawn 出来的 pass——跑在自己的 Sv39 表上,表由 `space.emo` 以 Emo 建,帧来自分配器。一个 pass 的表映射:

| 范围 | 位 | 内容 |
| --- | --- | --- |
| 内核的半区(`map_kernel`,无低位窗) | `r-x` / `r--` / `rw-`,**无 U** | 内核的镜像、固定页、设备——trap 进内核需要的一切 |
| 镜像的各段,按页并集权限 | `r-x` / `rw-` / ELF 的段共享一页处 `rwx`,**带 U** | 该 pass 的代码与数据 |
| 该 pass 的栈块,恒等 | `rw-u` | 它自己的 64 KiB |
| 该 pass 的 arena 块,恒等 | `rw-u` | 它自己的 64 KiB |
| `0x87fff000`,恒等 | `rw-u` | 用户 cell 页——stub 写它,trap shim 经它交接 arena |

规则:

- **U-mode 的世界恰是这些页。** 代码 RX、数据 RW、它自己的栈与 arena、cell 页——加上不带 U 映射的整个内核高半区,因为内核跑在 `satp` 所指的任何一张表上,一次 pass 的 trap 必须找到它自己的世界。机器的其余每个字节要么不在这张表里(野访问缺页),要么在而无 U(U-mode 碰不到)。弱隔离窗口关闭。
- **用户表里的内核半区不带低位窗。** 监管者的窗是大页,用户的页是同一半区同一棵树里的 4 KiB 页——一张同时携带两者的表会撞上"遍历被叶子挡住"。trap 内内核跑在其上的表不需要 pass 自己的映射之外的任何东西:shim 碰的一切要么在高半区,要么在调用者自己已映射的页里。
- **一个镜像的各 pass 共享它的页。** spawn 出来的 pass 重入顶层,找到父进程 poke 的 token——T4.4 以来的 spawn 语义,不变。每进程的部分是那张表:它自己的栈、它自己的 arena,以及一个它够不到的内核半区。
- **spawn 时建,严格性照搬。** `space.build` 在 `emo_user_spawn` 的屏蔽区内运行(运行时的 build 钩子,在没有每进程地址空间的镜像里为零):`frame_take`、清零、内核半区(`sv39.map_kernel`)、装载器停放的段表里的各段——ELF 权限翻译后加 U——text 与 data 共享一个 4 KiB 页的边界页取并集,两个段以不同物理地址认领同一页是响亮的终结——然后 cell 页、栈块、arena 块,根表的物理地址进槽的 space 字(872;槽 stride 是 880)。

**切换就在 pick 里。** `emo_sched_pick`——协作与被抢占的每次切换都流经的唯一一处——把来槽的 space 字送进运行时的 resolve 钩子,拿到根表就再过写钩子(`emo_os_satp_switch`:fence、写、fence)。字 0 表示内核自己的表,每个绿色进程的答案;resolve 维护一个缓存(Sv39 页的第三个字)记着 `satp` 现在指向谁,来字解到它时答 −1,于是内核的进程之间互相切换时一次 fence 也不做。切换发生在装入来进程任何寄存器之前——出去的上下文在切换点的易变寄存器都是死的——并在调度器的屏蔽区内,所以任何中断都无法落在 resolve 与乘着新表的那次 `sret` 之间。槽指针跨钩子调用骑在 s1 上(a1 是调用者可以丢的,而 resolve 是普通的类型化 Emo,它自己的调用会随便花掉它)。trampoline(T6.3)精化这段跨越;这里没有任何东西依赖 trap 跨的是它的哪一半。

**boot pass 的表在 stage 时建。** 装载器(`user.emo`)在停放段表之后、停放入口之前建它——建表失败让入口字保持零,机器根本不进 U-mode——并把它的物理根停放在交接页的 space cell(`0x870021c8`)。进入 shim(`emo_os_user_boot`)把它送进根槽的 space 字(运行时的 `emo_space_set`),收进切换的缓存(`space.adopt`),并在 `sret` 之前完成 satp 切换——于是 boot pass 的字在它第一次可能被抢占的 trap 之前就在它的槽里,而第一次切回它时装的就是同一张表。

## trampoline(T6.3)

U-mode 的一次 trap 曾要服从这个 pass 两次:帧落在 pass 的 `sp` 所指之处,内核的分派跑在 pass 的表上。trampoline 把两者都拿掉。它住在自己的一页上——`link.ld` 给 `.emo_tramp` 段在 text 末尾一页对齐的、独占的一页——而 `map_kernel` 的 text RX 把这页带进每张表,不带 U:每个地址空间里同一个虚拟地址,为监管者的取指而映射,U-mode 够不着。`stvec` 对一切 trap——内核的与用户的——都落在这里。

**路径由一次交换选择。** 用户代码运行期间,`sscratch` 持有运行中 pass 的 **trap 锚**——它那张固定 trap 帧的恒等地址;内核代码运行期间,它持哨兵值 0。入口在最开始只有两条指令:`csrrw sp, sscratch, sp`,再按 sp 分支。用户的 trap 在 sp 里找到锚(非零),被打断的用户 sp 停进 `sscratch`;内核的 trap 找到 0,用第二条 `csrrw` 撤销交换,跳给 shim——shim 逐字节照旧推进,把帧铺在被 interrupts 的内核栈上。在被打断的状态安全之前一个寄存器都不花:用户路径先把全部 32 个寄存器以 sp 相对存进锚帧,再从 `sscratch` 恢复被打断的 sp、停进帧下方的那个字(sp 槽),然后清掉哨兵,此后才花寄存器。

**锚是没有任何执行拿去放活数据的内存。** spawn 出来的 pass 锚在自己栈块的底部:544 字节的帧在块+552 处,sp 槽在其下一个字——低于栈顶能长出的任何调用链,因为深到那种程度的下探本来就是块的边缘以前吞下的溢出。boot pass 锚在自己的 trap 页 `0x87ffe000`——cell 页下面那张固定页,由 `space.base` 以 rw 无 U 映进每张表:镜像的栈属于 stub,堆是活数据,这张页是 boot pass 独有的那份 scratch。帧区域在 pass 运行时是 scratch,在它停住时是帧——一个 pass 不可能既运行又停住,所以用户侧没有任何东西够得着停放的帧,而下一次 trap 会在读任何字之前重写帧的每一个字。野的 sp 被保存、被原样交还,绝不被服从。

**transition 的中段换 `satp`,走 pick 自己的那对钩子。** trampoline 解析字 0(`emo_space_hook`)并按答案调用写钩子(`emo_os_satp_switch`)——与 pick 相同的 resolve/write 纪律,于是 Sv39 页的缓存对 `satp` 现在指向谁保持诚实;这里一次裸的 `csrw` 会让缓存撒谎——说内核的表活着而实际是用户的——pick 的下一次 resolve 就会跳过一次必要的写。交换之后,分派跑在内核的表**和内核的 trap 栈**上——trampoline 把 8 KiB 的 `.bss` 放进 `sp`——所以内核的任何一行都不会顺着 pass 的帧下探进 pass 的内存。帧本身经 `emo_os_trap_frame` 到达——两个序言都停放的那个基址(trampoline 停锚,shim 停被打断的内核 sp 减 544)——绝不经 sp,因为 sp 的值现在因路径而异;帧下方被碰的只有那一个字。

**sret 回家是 resume 的事。** answer 与 home 路径不经 pick、直接 resume——而 trampoline 留下的是内核的表,所以 resume 的用户路径在 `sret` 之前经同一对 resolve/write 把 pass 自己的表带回(停放的与被抢占的上下文从 pick 那里免费得到这一步)。它重新武装锚(`emo_os_anchor_arm`),趁 sp 还是帧顶恢复所有寄存器,然后**最后**移动 sp——用那条自相对加载、从帧下方的槽里读回被打断的 sp——pass 选的 sp 无论是什么都原样奉还。内核路径清掉哨兵、不动自己的 sp:内核帧本就铺在被 interrupts 的内核栈上。spawn 合成的帧随锚搬家:落在块的底部,把初始 sp 停进槽里——pass 在自己栈的顶上进 U-mode,它的第一次 trap 落在自己的帧上。

## 启动

1. OpenSBI 在 `0x80200000` 物理地址进入,`satp` 关着。stub 跑在物理别名上——`la` 是 PC 相对的,所以每个符号答出的都是物理地址——清 `.bss`,把启动表写进一个清零过的页:`root[2]`,RAM 的恒等映射(`rwx`),让 `satp` 写入之后的指令继续取得到;`root[258]`,RAM 的高别名;`root[256]`,MMIO 首个千兆字节的高别名。然后写 `satp`(模式 8,根表的 PPN),`sfence.vma`,跳到下一条指令的高别名。
2. 从此一切都在高半区、在启动表上:以内核地址设栈,挂钩子(console、block、resume),trap 初始化,运行时初始化,帧分配器启动。
3. `sv39.boot` 建内核的表——`frame_take` 把一个块拆成十六个帧,上面的各段范围依次映射,建表者遍历自己的表核对镜像、data、根表、自己的页、UART、窗口——答出根表的物理地址。shim `emo_os_satp_switch` fence、写 `satp`、再 fence,答出写入的值;stub 把它放在 Sv39 页上建表者记录的根表旁边,并置 SUM。
4. 程序的第二行是它自己的检查:`sv39_report` 读回活着的 `satp`,要求模式为 8、根表是建表者记录的那一个,打印 `sv39 8 0x<root>`——否则以 `sv39: the live table is not the kernel's` 终结机器。`run.sh` 把这一行钉在它的链条首位。
5. 程序返回之后,装载器 stage 用户镜像并建 boot pass 的表(T6.2);进入 shim 在第一次 `sret` 进 U-mode 之前把 `satp` 切到它。从那时起,每次切换随进程换表。

为什么要有一张启动表:建真表的那段 Emo 本身就链接在高半区,通过内核地址读分配器的页——它没有一条指令能不经翻译地运行——于是 stub 里的三条 store 让高半区在第一条 Emo 指令之前就存在,随后 Emo 建的表以内核真正想要的权限取代这幅巨页草图。

## shim

`sv39.S` 装着任何 Emo 拼写都够不到的两条特权指令:`emo_os_satp_switch`(`a0` 里是根表的物理地址;`sfence.vma`、写 `satp`、`sfence.vma`;答出写入的值)与 `emo_os_sfence`(整个 TLB)。分工是门的分工:Emo 建表、读表,shim 写 CSR。自 T6.2 起,写钩子就是 pick 的切换(运行时的 `emo_space_write_hook`,由内核的 stub 停放在 resolve 钩子旁边),进入 shim 的 boot pass 切换是另一个调用者;trampoline(T6.3)是下一个。

## 缺页(T6.4)

缺页是一次击杀,不是一个提问。三种 cause——取指(12)、load(13)、store(15)——像任何门不认领的异常一样到达,fault 路线(T4.6 对 SPP 的分裂)终结肇事的 pass:报告、槽 done、弃帧、块回家、机器继续。T6.4 加上的是名字:两个 trap 序言——shim 的与 trampoline 的——都把 `stval` 存在 `scause`、`sepc` 旁边(rest section 唯一空闲的那个字,偏移 328),报告把它读回来:`user fault <pid> cause <c> at 0x<epc> addr 0x<stval>`——对缺页,是遍历从未到达的地址;对其他异常,是硬件记下的任何东西(非法指令的位,或零)。地址在链条里被断言而 epc 不被:它是程序自己的常量,跨构建稳定。

没有任何东西检查这个地址去填一个映射——demand paging 按决定出局,copy-on-write 与 swap 随它一起:还没有被填页的消费者,而一个能发明映射的 handler 会成为表的严格性够不到的唯一部件。S-mode 里的缺页——内核自己的表未命中——维持它一直是的整机响亮失败;内核跑在它自建的表上,所以监管者缺页是内核 bug,永远不是某个进程的。

## 这还没做到什么

窗口的够及范围已经关闭,跨越有了自己的一页,缺页成了有名有姓的击杀:一个 pass 的世界是它自己的页,内核的分派跑在内核自己的表和栈上,trap 入口不服从 pass 选定的任何东西,一次缺页指名它的地址、终结它的进程,机器继续。Step 6 剩下的是隔离金测(T6.5):用户态向内核地址的 store 独死——smash pass 已经为未映射地址证明了同一形状——以及经分配器的 DMA 缓冲物理连续性。

## 钉子

- `run.sh`:`sv39 8 0x8…` 在两种定时器传输下都是链条的第一行;链条其余部分与 T6.2 之前逐字节相同,只除了两行——击杀报告的 cause 是 13(load page fault;pass 自己的表在 `0x80000000` 处什么都不映射,而前的表窗口在那里的 RAM 巨页让同一访问由 PMP 答 cause 5),以及最后一行——每进程表的帧拆出的块在十三个之外。问候行(`U-MODE 500500`)如今走门——线上字节相同,经 console service,因为 pass 自己的表不映射 UART。自 T6.3 起,链条**再次不变,两种传输下逐字节相同**,连续三轮——变的是跨越,不是行为;击杀报告的 epc 随构建而移、不作断言。T6.4 加长了链条:store 缺页的 pass(`smash`,cause 15,它的 store 落在 `0x40000000`、它自己的表在那里什么都不映射)插在 runaway 与好孩子之间,两份击杀报告都指名地址(`addr 0x80000000`、`addr 0x40000000`——被断言,跨构建稳定),最后一行是 `frames 19 12`——store 缺页 pass 的栈与 arena 在 T6.2 的十七之外,它表的帧取自拆分的剩余。
- 没有翻译,内核根本跑不起来——它的每个地址都是高半区地址——所以链条的存在本身就是 `satp` 已开的证明;`sv39` 那一行证明正在运行的表是 Emo 建的那张,而不是 stub 的。链条也是每进程表工作的证明:问候行、门行、spawn/wait 往返全都在 pick 处跨过 `satp` 切换,而击杀报告证明一个 pass 的野访问迎头撞上它自己表的"不在",而不是机器的 RAM。自 T6.3 起,链条里的每一次用户 trap 都穿过 trampoline——问候、各条门行、read 的阻塞、击杀、heap 报告、退出全都在各自 pass 的锚上铺帧——所以链条就是这段跨越端到端工作的证明。
- QEMU 监视器,内核的表活着时 `info mem`:上表中内核表的七条映射——监管者的低位窗恒等 `rw-`、PLIC 与 UART 高位 `rw-`、text `r-x`(自 T6.3 起多出一页:trampoline 页)、rodata `r--`、镜像的 RW 头部与高位 RAM 大页 `rw-`——并且**没有一条表项带 U**。同一会话读 CSR:`stvec` 指着 trampoline 页的地址,**页对齐**(该段独占一页),`sscratch` 在内核进程运行时为 0——哨兵,被进入任何一个世界的每次返回保持为真。
- 锚上的硬件观察点抓得到跨越的那次保存:trampoline 的 store 把帧写进锚,`sscratch` 持有被打断的用户 sp,而交换已把锚放进 `sp`——入口没有服从 pass 选定的任何东西。
