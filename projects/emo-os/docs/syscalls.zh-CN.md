# ecall 门——用户态/内核态 ABI

用户镜像与 EmoOS 内核之间的契约:什么跨过特权边界、寄存器里怎么拼写、
supervisor 在行动之前检查什么。T4.2(2026-10-27)定案;动词集合随服务
扩充,但编号、寄存器拼装与应答约定从此不动。

英文版:[`syscalls.md`](syscalls.md)。

## 跨越

用户程序执行机器的 `ecall`。在 Emo 侧,这是裸内建
`ecall(verb, r0, r1, r2, r3, r4, r5)`——只有 `riscv64` 准入,与裸机器
族的准入规则一致(其余目标按名拒绝,E4028)——它下降为这条指令:
动词在 `a7`,六个字在 `a0`..`a5`。

trap 落进内核的 shim,它把动词与六个字拼装给门的分派器
(`gate.dispatch`,普通的类型化 Emo,在 trap 内、调用者自己的栈上运行,
零分配),然后带着 `a0` 里的应答 `sret` 回家。调用者的其余寄存器原样
往返,一个不动。

## 应答

一个寄存器,`a0`:

- **`a0 >= 0`——已应答。** 载荷:对 `write`,是接收的字节数。
- **`a0 < 0`——已拒绝。** 原因是 `-a0`:

| 原因 | 含义 |
| --- | --- |
| 1 | 动词不在门的集合里 |
| 2 | 指针参数落在调用者的内存之外 |
| 3 | 指针参数的内存不带这次访问所需的权限 |
| 4 | 非指针参数超出定义域 |
| 5 | 内核耗尽一项资源(`spawn` 没有空闲块可给新进程的栈与 arena;文件系统动词没有空闲请求槽,或没有名字表条目或数据段可用) |
| 6 | 没有这个文件(文件系统动词,T7.2) |

拒绝是一种应答,不是故障:调用者的寄存器原样,执行从 `ecall` 之后
继续。程序拿拒绝做什么是程序的事;门的事是:任何未写入契约的动作
永不发生。

## 动词

| 动词 | 拼写 | 应答 |
| --- | --- | --- |
| 0 | `exit(code)` | 永不返回——root 的退出结束整台机器(SBI poweroff);被 spawn 的进程退出则应答其父进程的 `wait` |
| 1 | `write(buf, len)` | `buf` 处的 `len` 个字节走上内核的控制台;应答 `len`——超过门暂存页容量(2048 字节)的 `len` 按原因 4 拒绝 |
| 2 | `read()` | 下一个输入字节,阻塞到有一个存在;应答它(0–255)——归输入服务(T8.3),串口控制台的字节 |
| 3 | `spawn()` | 新进程在本镜像的顶层、一个新栈上进入;应答子进程的 pid 号 |
| 4 | `wait(pid)` | 该 pid 号子进程的退出码,阻塞到它退出 |
| 5 | *(分配器的)* | 对调用者永不返回——arena 耗尽的报告 |
| 6 | `file_write(name, name_len, buf, len)` | `name` 处 `name_len` 字节点名的文件变为 `buf` 处的 `len` 字节(至多 2048);应答 `len` |
| 7 | `file_read(name, name_len, buf, cap)` | 文件的字节落到 `buf`,至多 `cap` 个;应答文件大小 |
| 8 | `file_list(buf, cap)` | 名字(各带一个换行)落到 `buf`;应答写入的字节数 |
| 9 | `file_remove(name, name_len)` | 文件消失;应答 0 |
| 10 | `present(grant, x, y, w, h)` | grant 点名的缓冲整帧落地——damage rect 是设备取走的、也是扫描输出显示的;提交完成应答 0(T8.4,见下) |
| 11 | `output_info(index)` | 第 index 个输出的矩形,打包应答;没有输出应答的索引按原因 4 拒绝(T8.4,见下) |
| 12 | `input_read()` | 机器合并输入流的下一个事件,阻塞到有一个存在;应答打包好的事件(T8.3,见下) |
| 13 | `win_new(w, h)` | 给定大小的窗口缓冲:分配器连续块的运行,映射进调用者自己的表;应答打包的帧号与 grant id(T8.5,见下) |
| 14 | `win_close(grant)` | 缓冲的释放:运行归还分配器,grant 消失;应答 0(T8.5,见下) |
| 15 | `win_focus(grant)` | 合成器的栈记录该窗口为焦点;应答 0(T8.6,见下) |
| 16 | `win_move(grant, x, y)` | 合成器的 blit 把窗口帧放到该位置;应答 0(T8.6,见下) |
| 17 | `win_role(grant, role)` | 缓冲成为合成器栈上该角色的表面——0 toplevel、1 popup、2 subsurface、3 panel;合成器实现的是 toplevel,其余按原因 4 拒绝,第二次声明与没有表面在背后的 grant 同罪;栈满为原因 5(T8.13,见下) |
| 18 | `input_info(index)` | 第 index 个指针的轴,打包的设备自报量程(X 在上、Y 在下);没有设备应答的索引为原因 4(T8.13,见下) |

动词 10 到 16 **为桌面段预留**(门的编号规矩不变:预留号在它的动词落地前不携带含义,落地之日起冻结)——`present`、`output_info`、`input_read`、`win_new`、`win_close`、`win_focus`、`win_move`,见 [`docs/desktop-abi.zh-CN.md`](desktop-abi.zh-CN.md)。动词 10 到 16 已全部落地(T8.3、T8.4、T8.5、T8.6)——桌面段前七个动词,冻结。动词 17 和 18(T8.13,emo-desktop A9.1)按同一条规矩生长段——只在新的号下添加,绝不改写——而它们骑的路由号是邮箱的,不是动词的:窗口 present 投递的合成请求占 op 17(动词 10 的派生,T8.6),指针的通知占 op 18(T8.11),所以 win_role 的请求骑 −1019,input_info 的 op 18 落进输入服务的邮箱——那里原本只有 2 和 12 两个住客。

动词 6 到 9(T7.2)归文件系统服务;格式、名字规则(1 到 24 字节,不含 NUL 与换行——否则原因 4)与服务自身的状态纪律见 [`docs/fs.md`](fs.zh-CN.md)。其中每个指针参数都像 `write` 的缓冲区一样被检查并在门处拷贝:名字与写入的字节在检查它们的那个 trap 内落进文件系统页上四个请求槽之一(四个都有停靠者时第五个调用者是原因 5),槽号编进路由,于是服务的请求字点名它(`slot << 36 | op << 32 | pid`)。读与列出的字节在调用者停靠期间经监管者低位窗落进调用者的缓冲区。

动词 5(T5.1)不是服务请求,而是用户镜像的分配器在说话:当运行中
pass 自己的 arena——内核 spawn 时从帧分配器取来的 64 KiB 块(T5.3)
——装满时,
用户镜像的 `emo_alloc` 说动词 5,而不是拖垮整台机器。门的应答就是
调用者的死亡:supervisor 在肇事者自己的栈上印出响亮的报告
(`user heap <pid> gone`),槽以 done 收尾,机器在失去这个进程之后
继续跑——fault 路线的那套回收,只是经由门抵达而非经由 trap。没有
什么阻止程序替自己说动词 5,应答也一样:程序想要退出。root 骑着
动词 5 则结束整台机器,一如它自己的 exit。

动词 0 永不返回,所以它没有可返回的 handler 可拼装:trap 入口在
分派器之前直接接手。服务拥有的动词(1 归 console 服务,2 和 12 归
input 服务,10、11、13 和 14 归 display 服务,15、16 与窗口 present 归 compositor,0、3 和 4 归 process 服务,6 到 9 归文件系统服务)走门的路由——请求抵达它的服务,调用者
停靠,服务的应答落回停靠帧,仿佛 `ecall` 直接应答了一样。exit 是
路由唯一的例外:它的事务就是调用者自己的死亡,所以调用者的槽以
done 收尾而不是停靠——发给该已退出 pid 的 send 会丢弃,退出表的
条目是进程留下的唯一东西。(语言的
`halt` 内建是 kernel profile 自己的 shutdown ecall——在用户镜像上
它以动词 8 抵达门——自 T7.2 起是文件系统的列出,它带着零缓冲区与零容量到达,作为调用者内存覆盖不到的范围被拒绝。)

动词 10 和 11(T8.4)归显示器所有,授权表的首个条目随它们落地。**动词 10,`present(grant, x, y, w, h)`**,提交 grant 点名的缓冲:damage rect 是设备 transfer 的、也是扫描输出 flush 的,两个命令都在应答之前完成——帧要么整帧落地、要么机器响亮收场,扫描输出在 flush 自己完成之前显示的还是旧帧。grant 号 0 是屏幕 carve 的——授权表的首个条目,持有者的 pid 是 process 服务交出 carve 那一刻停进去的;不是持有者的调用者按原因 3 拒绝(槽永不复用,死去的持有者 pid 永远匹配不上新调用者)。表里没有的 grant 号按原因 4 拒绝——窗口 grant 是 T8.5 的。空 rect、或超出显示器的 rect,按原因 4:合理性检查在门,边界由显示服务对着模式判断。**动词 11,`output_info(index)`**,是输出列表的动词——协议第二接缝:列表不是常量,索引就是枚举的形状。应答打包该输出的矩形(宽在 32..63 位,高在 0..31 位);没有输出应答的索引按原因 4 拒绝。一个显示器是第一个应答,不是唯一的形状。

动词 13 和 14(T8.5)是窗口缓冲的生命周期。**动词 13,`win_new(w, h)`**,把属于自己的显示内存交给调用者:分配器的连续块运行(`frames.take_run`——运行基址块对齐、诸块连续,是设备与合成器都能点名的一段),按运行物理地址的 identity 映进**调用者自己的表**,RW 带 U——映射进一张 `satp` 已点着的表是活表自己的动作:新条目是整字,其后跟 `sfence`(raw 家族的地址翻译围栏,`docs/raw-memory.zh-CN.md`)。grant——内核授权表长出的那行(id、owner、base、范围)——是这块缓冲此后被点名的方式:`present` 与 `win_close` 拿的是 id,绝不是地址。应答把缓冲的帧号(本程序绘制的字节地址,在客户端左移 12 位——帧号保住字的符号位为真)装在 grant id 之上。超过窗口上界(四百万像素)的大小按原因 4 拒绝;机器垫不起的运行或表行按原因 5。**动词 14,`win_close(grant)`**,是释放:运行逐块归还分配器,行归还表。门在任何东西移动之前检查调用者与行的 owner(原因 3)、id 与表(原因 4)。owner 死了没 close 的窗口把运行泄漏到合成器的回收(T8.6)为止——言明的边界,M9 的杀死重启验收正是死亡侧回收挣得席位之处。窗口的 `present`(动词 10,grant 号非零)按行检查——owner 与缓冲范围内的 damage rect——并路由到**合成器**(T8.6):栈的条目持有位置,合成**blit**把窗口帧按其放进行进屏幕 carve(字存储),显示服务的 flush 把它送上显示器,应答在 flush 之后——帧整帧落地(协议第六接缝)。行的 ready 旗与记录的 rect 是合成器的状态;flush 进行期间到达的请求暂存其后服务。**动词 15 和 16(T8.6)**是合成器栈的动词:`win_focus(grant)`记录焦点窗口,且自 T8.13 起把它抬到栈顶——下一次合成把它画在其余之上;`win_move(grant, x, y)`设置 blit 的位置——x 为偶数(blit 的字粒度,原因 4),对显示模式的边界由合成器判定(界外原因 4)。owner 与 id 是门在两者上的检查,且自 T8.13 起,每个栈动词对声明过角色的 grant 以外的一律回答原因 4:角色造出的表面才是栈行动的对象。**动词 17(T8.13,emo-desktop A9.1)**是表面之所由:`win_role(grant, role)`让缓冲成为栈上该角色的表面,落在原点,直到一次 move 把它放好。词表是门的边界(0 toplevel、1 popup、2 subsurface、3 panel——越界原因 4),owner 与 id 是门的检查;合成器实现哪些角色是合成器的回答——toplevel 是,popup、subsurface、panel 按**它们的号**拒绝——协议不携带文本(第七接缝),选了角色的调用者才是把它说出来的人(`role popup r4`,机器的窗口 pass 明知答案仍一一去问)。同一表面的第二次声明按原因 4 拒绝(表面的角色不变);栈上已有八个表面为原因 5。窗口 present 投递的合成把整条栈自底向上走一遍,走之前把 carve 清成合成器自己的背景——最后一个条目压住其余,挪走的窗口旧位重新成为背景——搬走每个 ready 行所在的表面,客户端呈现的帧与其余栈一起整帧落地(第六接缝)。线上每次合成为 `comp <x> <y> <sum>`——正在呈现的表面位置与这次走栈搬过去的字。死亡侧回收:owner 死了没 close 的窗口,其运行由合成器的 supervisor 回收、其行清空、其表面离栈(T8.6 的死亡通知流,T8.13 的剪除)。**动词 18(T8.13,emo-desktop A9.1)**是第二接缝的输入侧:`input_info(index)`回答第 index 个指针的轴——其驱动从设备 config 读来的最大值,按显示模式的打包方式打包(X 在 32..63 位,Y 在 0..31 位)——程序把流里的绝对报告缩放到显示所用、正如合成器缩放自己光标的那个量程。一个指针是第一个回答,不是唯一的形状;越过它的索引为原因 4,输入服务的。

动词 12(T8.3,`input_read`)是串口之外的机器输入:合并输入流的下一个事件,阻塞到有一个存在。应答把事件打进一个字——类型在 48..63 位,代号在 32..47 位,值在 0..31 位——virtio-input 设备自己的事件类型原样照搬(0 分隔、1 按键、2 相对移动、3 绝对移动),旁边加一个机器自己的类型:0x454D("EM")是串口控制台的字节,字节在值里,代号为 0。流把三个来源合成一个没有时钟也能命名的唯一顺序——串口的字节在前,然后是键盘的事件,然后是指针的(T8.11:平板的绝对报告——ABS_X 与 ABS_Y,代号 0 与 1,值在设备自己的量程里——和它的按钮,经指针驱动的 ring 汇入合并,正如串口的字节经它们的 ring 到达);机器的常设纪律不变:一次一个读者(服务的邮箱就是等待队列,一次读让调用者与服务一起停靠,直到流里有了东西)。设备这两半都已接线:每个 eventq 的完成走 PLIC(每个输入驱动把自己传输的 IRQ 号作为一位置进 shim 的掩码单元),设备的事件和串口的字节一样能唤醒机器;某设备的十六个预投递缓冲那一刻装不下的事件,是该设备唯一会丢的事件。指针的报告同时驱动合成器的光标平面,但这不属于本动词:平面读驱动的位置单元,流原样运事件——要指针的读者在这里读,显示器上的精灵是合成器的(T8.11,桌面 ABI 的精灵内存)。

## 用户表面

用户代码不直接拼写裸 ecall。`syscall` 包——它自己的包，区别于 hosted
的 `os`——是门的用户侧：类型化 Emo 表面，也是用户代码看见的边界的
全部。它只准入 `riscv64` 目标；裸 `ecall` 只活在这十八个函数体里，
用户程序写不到的地方再多都没有。

- `syscall.exit(code)`——退出动词；永不返回。root 的退出结束整台
  机器；被 spawn 的进程退出则应答其父进程的 `wait`。
- `syscall.write(buf, len)`——写入动词，按错误约定应答
  `(R.ok, 字节数)` 或 `(R.error, why)`——门的拒绝原因化作指名它的
  消息（`"outside the caller's memory"`、`"not writable"`、
  `"bad argument"`、`"the kernel is out of a resource"`、
  `"unknown verb"`）。
- `syscall.read()`——下一个输入字节,阻塞到有一个存在。
- `syscall.input_read()`——合并输入流的下一个事件(T8.3,动词
  12),阻塞到有一个存在;即上一节描述的打包字。
- `syscall.present(grant, x, y, w, h)`——桌面段的提交(T8.4,动词
  10),应答 `(R.ok, 0)` 或 `(R.error, why)`。
- `syscall.output_info(index)`——桌面段的枚举(T8.4,动词 11),应答
  `(R.ok, 打包的矩形)` 或 `(R.error, why)`。
- `syscall.win_new(w, h)`——窗口缓冲的创建(T8.5,动词 13),应答
  `(R.ok, 打包的帧号与 grant id)` 或 `(R.error, why)`。
- `syscall.win_close(grant)`——窗口缓冲的释放(T8.5,动词 14),应答
  `(R.ok, 0)` 或 `(R.error, why)`。
- `syscall.win_focus(grant)`——合成器的焦点(T8.6,动词 15),应答
  `(R.ok, 0)` 或 `(R.error, why)`。
- `syscall.win_role(grant, role)`——表面的角色声明(T8.13,动词
  17):缓冲成为合成器栈上的 toplevel(0)表面;合成器拒绝的角色——
  popup(1)、subsurface(2)、panel(3)——按各自号码得到 `(R.error,
  "bad argument")`,第二次声明、越出词表的 角色、任何栈动词或
  present 遇到的没声明过表面的 grant 同样;第九个表面得到 `"the
  kernel is out of a resource"`。
- `syscall.input_info(index)`——指针设备的枚举(T8.13,动词 18):
  `(R.ok, 打包的轴)`——X 的最大值在 32..63 位、Y 的在 0..31 位,程序
  缩放流的绝对报告所用、设备自己的回答;没有设备应答的索引得到
  `(R.error, "bad argument")`。
- `syscall.win_move(grant, x, y)`——合成器的移动(T8.6,动词 16),应答
  `(R.ok, 0)` 或 `(R.error, why)`。
- `syscall.spawn()`——新进程在本镜像的顶层、一个新栈上进入,应答
  `(R.ok, 子进程的 pid 号)`;子进程凭镜像自己的内存里有什么认出自己
  是子(被 spawn 的一趟重入程序、共享镜像),两方靠原始单元或控制台
  协调。
- `syscall.wait(pid)`——该 pid 号子进程的退出,阻塞到它发生,应答
  `(R.ok, 退出码)`。
- `syscall.file_write(name, name_len, buf, len)`、
  `syscall.file_read(name, name_len, buf, cap)`、
  `syscall.file_list(buf, cap)`、`syscall.file_remove(name, name_len)`
  ——文件系统动词(T7.2),各应答 `(R.ok, 应答)` 或 `(R.error, why)`;
  原因沿用前面动词所命名的,外加原因 6 的 `"no such file"`。名字与
  字节是程序自己内存里的裸地址,如同 `write` 的缓冲区。

程序像任何包一样钉住它（`deps { "syscall" = "0.1.0" }`），从内置
registry 解析。kernel profile 把它连同标准库其余部分一起拒绝——
内核只建在 `core` 之上，永不 require 自己的用户态；user profile 是
普通程序，能 require 什么由各包自己的 target 声明决定。

## supervisor 检查

每个指针参数都在门行动之前检查,依据是 loader 装载本镜像时停下的
段表(每个 `PT_LOAD` 的范围与 ELF `p_flags`):整个范围
`[buf, buf + len)` 必须落在**单个**段内——跨段的调用被拒绝,不会被
拆开——且该段必须带这次访问所需的权限(`write` 需要 `W`)。范围检查
以防溢出的形式书写(`len > end - buf`,绝不写 `buf + len > end`);
可写段内的零长度应答 0;范围与权限的区分是诚实的:有段覆盖但无可写
段覆盖的范围是原因 3,任何段都不覆盖的范围是原因 2。超过门暂存页
容量的写入(2048 字节)在任何拷贝发生之前按原因 4 拒绝。

自 SV39 的每进程表(T6.2)起,检查与使用是同一个 trap:write 的
字节由检查范围的那个 trap 拷进内核的暂存页——门恰好读一次调用者的
内存,走的是调用者自己的表、带着 SUM——console service 在内核自己
的表上从这份拷贝打印,而那张表不映射调用者的任何内存。每进程表
之前,service 借窗口的别名直接读调用者的缓冲;门处拷入是表使这成为
必要的诚实形式(也顺手关掉了先查后读自带的竞态)。

这些检查仍是映射之上的 supervisor 之言——拒绝是答案,不是故障——
而映射是硬件的:自 T6.2 起,一个 pass 自己的表只带 U 地映射它镜像
的各段,一条溜过所有检查的野指针等在路上的仍是硬件的缺页,而不是
一次落地。

## 固定地址

loader 与门共享的内核侧布局(内核的 `link.ld` 给 `.emo_user` 段
这一页):

| 地址 | 内容 |
| --- | --- |
| `0x87002000` | 内嵌用户镜像的起点(boot stub 停入) |
| `0x87002008` | 终点 |
| `0x87002010` | 已装载的入口(0 = 什么都没装载) |
| `0x87002018` | 段数 |
| `0x87002020` | 段表:八个槽,每槽 24 字节(start, end, flags) |

帧分配器的页(T5.3,`.emo_frames`,再上一页)是内核自己的——freelist
头、空闲块数与总块数、区域界址、take 与 give 的累计、已认领位图——
只由 `frames.emo` 写入;机器作为最后一行印出的账目
(`frames <taken> <given>`)读的就是那两个累计。

| 地址 | 内容 |
| --- | --- |
| `0x87003000` | freelist 头(一个空闲块的基址;0 = 区域已用尽) |
| `0x87003008` | 空闲块数 |
| `0x87003010` | 区域持有的块数 |
| `0x87003018` | 区域基址(镜像末尾,向上取整到块) |
| `0x87003020` | 区域终点(`0x87000000`,tick 环的页) |
| `0x87003028` | 累计取走的块数 |
| `0x87003030` | 累计归还的块数 |
| `0x87003040` | 已认领位图:每块一位,八个字 |

这一页的用户侧(T5.1)在用户 profile 自己的单元页里,位于 RAM 顶部
——三个字,由用户 stub 停入,内核的 trap shim 在每一次 U-mode 边界
穿越上读写它们,让用户镜像自己的分配器向正在运行的 pass 收账:

| 地址 | 内容 |
| --- | --- |
| `0x87fff000` | 用户镜像的 `emo_program` 入口(process 服务从这里启动被 spawn 的 pass) |
| `0x87fff008` | 用户镜像 arena 光标的地址(其 root 槽的字) |
| `0x87fff010` | 其 arena 终点的地址 |

文件系统的页(T7.2,`.emo_fs`,自 `0x87005000` 起三页)放着门用来路由的服务 pid cell、运行时死亡通知投递去的 supervisor pid cell、暂存环与门填写的四个请求槽;布局见 [`docs/fs.md`](fs.zh-CN.md)。

用户窗口是 `[0x87100000, 0x88000000)`;用户 profile 链接在其基址。
