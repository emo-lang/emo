# ecall 门——用户态/内核态 ABI

用户镜像与 EmoOS 内核之间的契约:什么跨过特权边界、寄存器里怎么拼写、
supervisor 在行动之前检查什么。T4.2(2026-10-27)定案;动词集合随服务
扩充,但编号、寄存器拼装与应答约定从此不动。

英文版:[`syscalls.md`](syscalls.md)。

## 跨越

用户程序执行机器的 `ecall`。在 Emo 侧,这是裸内建
`ecall(verb, r0, r1, r2, r3, r4, r5)`——只有 `riscv64` 准入,与裸机器
族的准入规则一致(其余目标按名拒绝,E4028)——它下降为这条指令:
动词在 `a7`,六个字在 `a0`..`a5`。

trap 落进内核的 shim,它把动词与六个字拼装给门的分派器
(`gate.dispatch`,普通的类型化 Emo,在 trap 内、调用者自己的栈上运行,
零分配),然后带着 `a0` 里的应答 `sret` 回家。调用者的其余寄存器原样
往返,一个不动。

## 应答

一个寄存器,`a0`:

- **`a0 >= 0`——已应答。** 载荷:对 `write`,是接收的字节数。
- **`a0 < 0`——已拒绝。** 原因是 `-a0`:

| 原因 | 含义 |
| --- | --- |
| 1 | 动词不在门的集合里 |
| 2 | 指针参数落在调用者的内存之外 |
| 3 | 指针参数的内存不带这次访问所需的权限 |
| 4 | 非指针参数超出定义域 |
| 5 | 内核耗尽一项资源(`spawn` 没有空闲块可给新进程的栈与 arena) |

拒绝是一种应答,不是故障:调用者的寄存器原样,执行从 `ecall` 之后
继续。程序拿拒绝做什么是程序的事;门的事是:任何未写入契约的动作
永不发生。

## 动词

| 动词 | 拼写 | 应答 |
| --- | --- | --- |
| 0 | `exit(code)` | 永不返回——root 的退出结束整台机器(SBI poweroff);被 spawn 的进程退出则应答其父进程的 `wait` |
| 1 | `write(buf, len)` | `buf` 处的 `len` 个字节走上内核的控制台;应答 `len`——超过门暂存页容量(2048 字节)的 `len` 按原因 4 拒绝 |
| 2 | `read()` | 下一个控制台字节,阻塞到有一个存在;应答它(0–255) |
| 3 | `spawn()` | 新进程在本镜像的顶层、一个新栈上进入;应答子进程的 pid 号 |
| 4 | `wait(pid)` | 该 pid 号子进程的退出码,阻塞到它退出 |
| 5 | *(分配器的)* | 对调用者永不返回——arena 耗尽的报告 |

动词 5(T5.1)不是服务请求,而是用户镜像的分配器在说话:当运行中
pass 自己的 arena——内核 spawn 时从帧分配器取来的 64 KiB 块(T5.3)
——装满时,
用户镜像的 `emo_alloc` 说动词 5,而不是拖垮整台机器。门的应答就是
调用者的死亡:supervisor 在肇事者自己的栈上印出响亮的报告
(`user heap <pid> gone`),槽以 done 收尾,机器在失去这个进程之后
继续跑——fault 路线的那套回收,只是经由门抵达而非经由 trap。没有
什么阻止程序替自己说动词 5,应答也一样:程序想要退出。root 骑着
动词 5 则结束整台机器,一如它自己的 exit。

动词 0 永不返回,所以它没有可返回的 handler 可拼装:trap 入口在
分派器之前直接接手。服务拥有的动词(1 和 2 归 console 服务,
0、3 和 4 归 process 服务)走门的路由——请求抵达它的服务,调用者
停靠,服务的应答落回停靠帧,仿佛 `ecall` 直接应答了一样。exit 是
路由唯一的例外:它的事务就是调用者自己的死亡,所以调用者的槽以
done 收尾而不是停靠——发给该已退出 pid 的 send 会丢弃,退出表的
条目是进程留下的唯一东西。(语言的
`halt` 内建是 kernel profile 自己的 shutdown ecall——在用户镜像上
它以动词 8 抵达门,像集合外的任何动词一样被拒绝。)

## 用户表面

用户代码不直接拼写裸 ecall。`syscall` 包——它自己的包，区别于 hosted
的 `os`——是门的用户侧：类型化 Emo 表面，也是用户代码看见的边界的
全部。它只准入 `riscv64` 目标；裸 `ecall` 只活在这五个函数体里，
用户程序写不到的地方再多都没有。

- `syscall.exit(code)`——退出动词；永不返回。root 的退出结束整台
  机器；被 spawn 的进程退出则应答其父进程的 `wait`。
- `syscall.write(buf, len)`——写入动词，按错误约定应答
  `(R.ok, 字节数)` 或 `(R.error, why)`——门的拒绝原因化作指名它的
  消息（`"outside the caller's memory"`、`"not writable"`、
  `"bad argument"`、`"the kernel is out of a resource"`、
  `"unknown verb"`）。
- `syscall.read()`——下一个控制台字节,阻塞到有一个存在。
- `syscall.spawn()`——新进程在本镜像的顶层、一个新栈上进入,应答
  `(R.ok, 子进程的 pid 号)`;子进程凭镜像自己的内存里有什么认出自己
  是子(被 spawn 的一趟重入程序、共享镜像),两方靠原始单元或控制台
  协调。
- `syscall.wait(pid)`——该 pid 号子进程的退出,阻塞到它发生,应答
  `(R.ok, 退出码)`。

程序像任何包一样钉住它（`deps { "syscall" = "0.1.0" }`），从内置
registry 解析。kernel profile 把它连同标准库其余部分一起拒绝——
内核只建在 `core` 之上，永不 require 自己的用户态；user profile 是
普通程序，能 require 什么由各包自己的 target 声明决定。

## supervisor 检查

每个指针参数都在门行动之前检查,依据是 loader 装载本镜像时停下的
段表(每个 `PT_LOAD` 的范围与 ELF `p_flags`):整个范围
`[buf, buf + len)` 必须落在**单个**段内——跨段的调用被拒绝,不会被
拆开——且该段必须带这次访问所需的权限(`write` 需要 `W`)。范围检查
以防溢出的形式书写(`len > end - buf`,绝不写 `buf + len > end`);
可写段内的零长度应答 0;范围与权限的区分是诚实的:有段覆盖但无可写
段覆盖的范围是原因 3,任何段都不覆盖的范围是原因 2。超过门暂存页
容量的写入(2048 字节)在任何拷贝发生之前按原因 4 拒绝。

自 SV39 的每进程表(T6.2)起,检查与使用是同一个 trap:write 的
字节由检查范围的那个 trap 拷进内核的暂存页——门恰好读一次调用者的
内存,走的是调用者自己的表、带着 SUM——console service 在内核自己
的表上从这份拷贝打印,而那张表不映射调用者的任何内存。每进程表
之前,service 借窗口的别名直接读调用者的缓冲;门处拷入是表使这成为
必要的诚实形式(也顺手关掉了先查后读自带的竞态)。

这些检查仍是映射之上的 supervisor 之言——拒绝是答案,不是故障——
而映射是硬件的:自 T6.2 起,一个 pass 自己的表只带 U 地映射它镜像
的各段,一条溜过所有检查的野指针等在路上的仍是硬件的缺页,而不是
一次落地。

## 固定地址

loader 与门共享的内核侧布局(内核的 `link.ld` 给 `.emo_user` 段
这一页):

| 地址 | 内容 |
| --- | --- |
| `0x87002000` | 内嵌用户镜像的起点(boot stub 停入) |
| `0x87002008` | 终点 |
| `0x87002010` | 已装载的入口(0 = 什么都没装载) |
| `0x87002018` | 段数 |
| `0x87002020` | 段表:八个槽,每槽 24 字节(start, end, flags) |

帧分配器的页(T5.3,`.emo_frames`,再上一页)是内核自己的——freelist
头、空闲块数与总块数、区域界址、take 与 give 的累计、已认领位图——
只由 `frames.emo` 写入;机器作为最后一行印出的账目
(`frames <taken> <given>`)读的就是那两个累计。

| 地址 | 内容 |
| --- | --- |
| `0x87003000` | freelist 头(一个空闲块的基址;0 = 区域已用尽) |
| `0x87003008` | 空闲块数 |
| `0x87003010` | 区域持有的块数 |
| `0x87003018` | 区域基址(镜像末尾,向上取整到块) |
| `0x87003020` | 区域终点(`0x87000000`,tick 环的页) |
| `0x87003028` | 累计取走的块数 |
| `0x87003030` | 累计归还的块数 |
| `0x87003040` | 已认领位图:每块一位,八个字 |

这一页的用户侧(T5.1)在用户 profile 自己的单元页里,位于 RAM 顶部
——三个字,由用户 stub 停入,内核的 trap shim 在每一次 U-mode 边界
穿越上读写它们,让用户镜像自己的分配器向正在运行的 pass 收账:

| 地址 | 内容 |
| --- | --- |
| `0x87fff000` | 用户镜像的 `emo_program` 入口(process 服务从这里启动被 spawn 的 pass) |
| `0x87fff008` | 用户镜像 arena 光标的地址(其 root 槽的字) |
| `0x87fff010` | 其 arena 终点的地址 |

用户窗口是 `[0x87100000, 0x88000000)`;用户 profile 链接在其基址。
