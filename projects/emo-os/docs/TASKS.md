# EmoOS — Development Tasks

The standalone tracker for the EmoOS project (the kernel package `emo_os`
under `projects/emo-os/`). EmoOS is its own project: it does **not** write
into the Emo compiler's `docs/TASKS.md`. Compiler-side work (atomics,
Stage B, image packaging) is executed in the Emo tree on feature branches
with its own ground rules, but every task is tracked here.

## How to use this file

- **Numbering:** `T<step>.<n>` — the step numbers are EmoOS steps
  (this file), unrelated to the compiler's `plan/step-NN` numbering.
- **Working in spare time:** tasks within a step are ordered; any prefix of
  completed tasks leaves the tree in a consistent state. A step boundary is
  the checkpoint: the kernel boots, the goldens are green, and — for the
  compiler-side steps — `dune test` is green.
- **Ground rules:**
  - Never start the next step on a red build.
  - Strictness first: reject early with a clear diagnostic. No auto-fixing,
    no implicit additions, no silent fallbacks.
  - Milestone aliases (`M1`, `S1`, `S2`, `M2`…`M6`) match the README's
    milestone table; the mapping is listed below.
  - Check items off here as you go, and refresh the README's milestone
    table when a step completes.

## Step 1 — Memory primitives (S1)

Pure compiler work; no OS code. Design settles before any emitter moves.

- [x] **T1.2** — `CHECK.md` decisions recorded: the atomic semantics; `peek`/`poke` defined as volatile (never elided, never reordered against each other); `fence()`.

- [x] **T1.4** — Hosted targets: the interpreter (exact no-op), `c` (`__atomic` builtins), `ocaml` (the `Atomic` module; CAS-loop fallbacks for `fetch_and`/`fetch_or`/`fetch_xor`).
- [x] **T1.5** — Managed targets: `ts` and `wasm` as exact no-ops under the cooperative scheduler; `beam` via the runtime's `atomics` array (the full set; the bitwise `fetch_*` as compare-exchange loops — `docs/atomics.md` supersedes the earlier `counters` line).

- [x] **T1.7** — Goldens: one cross-target corpus answered byte-for-byte on every target that admits the ops (`examples/atomic_cell`, all seven); refusal goldens for every non-scalar payload, through the type position and the constructor (BEAM's CAS needs none — the `atomics` array serves it, per T1.5); a riscv64 golden under QEMU.
- [x] **T1.8** — `peek`/`poke`: the volatile raw-memory builtins `CHECK.md` defines (T1.2), with the surface settled in [`docs/raw-memory.md`](../../../../docs/raw-memory.md) — `peek8`/`poke8` over `Byte` (the byte lane, unsigned 0–255), `peek64`/`poke64` over `Int64`, addresses `Int64`, `poke` answering `Void`, the width set `{8, 64}` (the 32-bit lane waits for `Int32`). `riscv64` lowers them as volatile `lbu`/`ld`/`sb`/`sd` runtime helpers — landing the `Byte` immediate in the value model beside them — the six hosted targets refuse by name at check time (E4028; a target admits them iff the program owns the address space), and goldens pin both: RAM roundtrips on both widths plus the 16550's line-status register under QEMU, and a refusal golden per hosted target.

## Step 2 — riscv64 Stage B (S2)

Why this is its own step: in the dynamic value model one MMIO read
allocates a boxed `Int64` that nothing ever reclaims — a polling loop
exhausts the heap. Unboxing is a prerequisite of the kernel primitives.

- [x] **T2.1** — The typed calling convention: a fully typed signature gets raw-register params and results (`Int64` in a register, `Float64` in an f-register); boxing adapters at typed↔dynamic call boundaries. Landed 2026-10-26: top-level `def`s only — methods, constructors, and closures keep the dynamic convention (the runtime's by-name dispatch passes tagged words and cannot know a signature; extending needs trampolines, a later task) — with the psABI's two independent banks (`Int64` raw in `a0..a7`, `Float64` raw in `fa0..fa7`, every other known type the tagged word both sides share); the adapters are the callee's entry boxes and exit unbox, the call site's arg unboxes and result box (bodies still emit dynamic — T2.2 melts them away); a tail call requires matching result representations, else the plain call plus this function's own return-label adapter; a const thunk's memo slot holds the raw result. The value heap grew 64 → 96 MiB for the T2.1→T2.2 window: the boundary adapters allocate, and `examples/fib`'s `count_down(1000000)` rides ~61 MiB of them on top of fib's own cells — past the old end, still far inside QEMU virt's 128 MiB (the `peek_poke` playground at `0x87000000` stays above the new end). Goldens: `examples/typed_calls` (bank-interleaved int/float params, the 100k tail chain, Int64 wrap at the bounds, Bool/Byte/String tagged params, a Void result, the const memo hit, method and closure calls beside the convention) byte-identical on the interpreter, `c`, `wasm`, `beam`, and `riscv64` under QEMU; all nine prior riscv64 goldens byte-identical.
- [x] **T2.2** — Escape-point boxing: locals and arithmetic stay unboxed; a value boxes only where it escapes (container element, field, closure capture, message, dynamic-call boundary). Landed 2026-10-26: a fully typed def emits a **native body** — representation is per-expression (`Int64` raw in `a0`, `Float64` raw in `fa0`, everything else the tagged word both conventions share), so locals, arithmetic, comparisons, conversions, and loop variables run unboxed and the result answers raw with no exit adapter. The escape points, and only these, box: container elements, field writes, closure captures, interpolation parts and `println`, every dynamic callee's arguments (method calls, dynamic-signature defs, first-class blocks), `Box`/`Atomic` payloads, and a `case` scrutinee — whose pattern bindings hold tagged words and drop out of the raw set, unboxing again on read so the rule stays universal. A dynamic producer's result crosses back through an unbox keyed on the expression's static type; `peek64` unboxes its helper's cell until T2.3 inlines the load. Dynamic-signature functions emit exactly as before. `examples/fib`'s `count_down(1000000)` now recurses allocation-free (`add`'s body: 24 → 15 instructions, 3 heap calls → 0; the formal hot-loop corpus count lands with T2.4). The value heap stays at 96 MiB — the T2.1→T2.2 window closed, the headroom stays for dynamic bodies' per-operation boxing. Goldens: all riscv64 QEMU goldens byte-identical; a native-body stress corpus (while/for loops, array indexing, string building, case with bindings, float loops) verified interpreter-identical under QEMU — it caught the case-binding double-box on the way (fixed: unbox-on-read for tagged numeric locals). Found, not fixed, on the way: the IR's `decl_type` maps `Byte` and every applied annotation (`Array[Int64]`, `Box[Int64]`, class/interface names) to `Unknown`, so defs with such signatures stay on the dynamic convention — correct, just not native; enriching it touches every backend's `fparams` assumptions and is its own task.
- [x] **T2.3** — `peek`/`poke` lowered to unboxed raw `Byte`/`Int64` — an MMIO read allocates nothing — with the volatile ordering preserved through emission. Landed 2026-10-26: in a native body each builtin is its one inline volatile instruction (`lbu`/`ld`/`sb`/`sd`) at the raw address, in program order — a `peek64` answers the raw payload, a `peek8` re-encodes the byte as the immediate, a `poke` decodes or moves its raw operand — no helper call, nothing allocated. Dynamic bodies keep the runtime helpers (their tagged world must box the answer regardless), so the interpreter-parity corpus is untouched. The zero-allocation pin is load-bearing in `examples/peek_poke`: a typed `burn` def reads one byte four million times — at 32 bytes a read that would be 128 MiB, past the 96 MiB heap, a loud failure — and prints the checksum (`peek64` gets a native roundtrip beside it).
- [x] **T2.4** — Re-verification: every existing riscv64 golden byte-identical; a before/after instruction count for a hot-loop corpus (`count_down`-style) recorded in the step trail. Done 2026-10-26: the full `dune runtest` suite is green with all ten riscv64 QEMU goldens byte-identical through T2.1–T2.3 (verified after each task; the peek_poke corpus itself grew the T2.3 pin). The count, taken from real images — the same `count_down` program built by the T1.8 compiler (pre-Stage B) and by this one:

  | per call, `count_down(n Int64) Int64` | T1.8 (dynamic) | post-S2 (native) |
  | --- | --- | --- |
  | instructions in the function | 43 | 33 |
  | heap calls per level | 1 (`emo_box_i64`) | 0 |
  | heap allocation per level | one 32-byte cell | 0 |

  and both images boot to the same `0`. The bigger multiplier is `add`'s (24 → 15 instructions, 3 heap calls → 0, recorded with T2.2); a tail-call-heavy function's dynamic form was already lean, so its honest ratio is smaller — the allocation elimination is the point, and it is total.

## Step 3 — The cooperative kernel (M2)

- [x] **T3.1** — Package-carried native sources for `riscv64`: per-package `.S` sources compiled into the image; the freestanding runtime (boot stub + linker script) becomes a package-provided component — a kernel package owns its image — while the default runtime stays for ordinary programs. Landed 2026-10-26: the c target's package-carried-native shape, carried over — the tree is the package, sources auto-collected, the manifest stays data. Every `.S` in a package's tree assembles into the image beside the program; a `runtime.S` is the package's boot stub and a `link.ld` its linker script (fixed base names, either optional, at most one provider each — two refuse with E5013); the root package's own tree rides in, so the kernel package owns its image as the root. Each shape is honored by its one target — the C shapes by `c`, the riscv64 shapes by `riscv64` — and every other target refuses outright (E5007) in both directions. The compiler's runtime splits into the boot stub (replaceable) and the runtime body (always the compiler's; `emo_program` is global so a stub in its own object reaches it), and the package's object links first — OpenSBI enters at the load address, so the stub must open `.text`. Goldens: `examples/native_image` (stub magic, plain-source data through a stub-parked pointer, a script-only symbol — all three in the output, under QEMU); the unit suite pins collection (root and dependency), the two-directional refusals, and the conflict; all prior riscv64 goldens byte-identical on the default path. The decision record: CHECK.md, 2026-10-26.
- [x] **T3.2** — The `emo_os` package: `package.emo` renamed from `emo/os` to `emo_os` (deps syntax verified); the kernel-only `core` layering enforced — stdlib requires refuse on the kernel target. Landed 2026-10-26: the manifest now carries the flat name the READMEs already wrote — a manifest name is plain data (the registry's owner/name rule lives in the publish path alone, and the kernel never publishes), verified by `emo build` and `emo emoji build` and the QEMU boot. The layering gate sits at the front of the build's resolution: on `riscv64`, a require of a name the bundled standard library publishes refuses with E5014 at the require's site — whether or not the manifest pins it, preempting E5006 and the resolution target gate — while a typo'd unscoped require keeps its E5009 and a scoped require stays legal (a kernel service is an ordinary package declaring the target). Unit tests pin the pinned and unpinned refusals and the unknown-require answer; the decision record: CHECK.md, 2026-10-26.
- [x] **T3.3** — Processes on metal: `spawn`/`send`/`receive` unblocked on `riscv64` — green threads on the boot hart, the context switch as the callee-saved swap plus `sp` in the `.S` shim, per-process stacks, copy-on-send mailbox semantics matching the hosted `emo_sched` reference. Landed 2026-10-26: the riscv64 runtime gains the process world — 64 non-reused slots (context, pid, state, bounded 32-word mailbox) plus 64 64-KiB stacks in `.bss`; `emo_schedule` saves the callee-saved set plus `sp` into the outgoing slot, picks the next runnable FIFO, and switches; spawn does not yield, send snapshots the message (the copy-on-send `emo_copy_deep` — Atomic shares the cell), wakes a parked receiver and yields the sender; receive scans oldest-first and parks on no match; the root exiting ends the program; an empty run queue is the loud deadlock. Pid = pointer kind 9; `self_pid` answers a boxed Pid; `==` is identity; `to_string` renders `<pid N>`. The golden `examples/processes` pins int messages, a Box message, a tuple message with both elements bound, a guarded fan-in with a non-matching message left queued, a send to a dead pid dropped, `self_pid`, and pid printing — byte-identical under QEMU. Decision record: CHECK.md, 2026-10-26. Found and fixed on the way: the deep copy's element loop stopped one block word short (the header counts payload words, the elements end at word `header`), which broke a tuple message across the wake-and-rescan path — `copy_deep` now bounds at `header + 1`.
- [x] **T3.4** — The scheduler: round-robin first, with the priority and quota fields present; send-time priority donation wired behind the fields (dormant until priorities are settable); the wait graph held by the scheduler. Landed 2026-10-26: dispatch stays round-robin — the run queue is the FIFO ring and `emo_schedule` pops its head. Every slot now carries the scheduler's policy words beside its context, pid, state, and mailbox: the process's **own priority**, its **effective priority**, and its **CPU quota** (the slice budget in ticks the tick of T3.6 will consume; 0 is the unassigned value until then); a child inherits its spawner's own priority and quota at spawn, its effective starting at its own. The wait graph the scheduler holds is the slot table itself — who is parked (the state word) and what work each process is holding for whom: the mailbox became two rings, the message and **the priority it carries** (the sender's effective priority at the send), and a process's effective priority is **the maximum of its own and the priorities its queued messages carry** — the asynchronous form of the README's "the priorities of the processes waiting on it" — raised at enqueue (the send-time donation, in `emo_send`) and re-formed from the remaining messages at dequeue (`emo_mb_remove`), so it is always a function of the graph and never a stale residue; the synchronous edge — a process blocked on one specific process — arrives with the synchronous kernel call (T4.2) and extends the same graph. Dormant by construction: no surface sets a priority, so every one is 0 and the dispatch reads none of them — every riscv64 golden stays byte-identical. Verified: the full `dune runtest` suite green (all twelve QEMU goldens); `examples/processes` grew the T3.4 pin (six carriers into one mailbox, pulled out in a scrambled order so every dequeue lands on a different ring position and shifts both rings behind it); a 60-process scratch corpus (30 scrambled ints, 15 tuples, 15 boxes — 61 of the 64 slots) ran interpreter-identical under QEMU; and the dormant chain was driven live under gdb against the golden's own image, priorities injected into the slots — the first child inherited own 3 and quota 11, a child's effective 7 rode into the root's ring and raised the root 3 → 7, and the dequeue dropped it back to 3 — with the serial output unchanged. Decision record: CHECK.md, 2026-10-26.
- [x] **T3.5** — The UART driver, polling: the 16550A at `0x10000000` on `virt` through `peek`/`poke`; `println` leaves the SBI console; SBI stays for poweroff. Landed 2026-10-26: the driver is ordinary Emo in the kernel's `main.emo` — `uart_init` (no interrupts until T3.6, divisor, 8N1, FIFOs enabled and cleared), `console_put_byte` (poll the line-status register's transmitter-empty bit, then one byte-wide `poke8` to the transmit holding register), `console_read_byte` (poll the data-ready bit, one `peek8` of the receive buffer) — both fully typed, so their bodies are native: one inline volatile load or store per poll step, zero allocation on the console path. The runtime's print path gained one indirection point: a `emo_console_hook` word in `.bss`, checked by `emo_console_emit` — zero means the legacy SBI putchar ecall (the default boot stub leaves it, so every hosted-path image and all twelve riscv64 goldens are untouched), non-zero is a tail call with the raw byte in `a0`, the psABI discipline. The kernel's boot stub (T3.1's package-owned component) parks the raw entry of `console_put_byte` in the hook after the `.bss` clear — the stub references the def by its module-prefixed label, which is now `.globl` (top-level defs are global; T3.6's trap shim will reach its handler the same way). SBI keeps exactly one duty: the shutdown ecall in the stub and in `emo_fail`. Goldens: `projects/emo-os/run.sh` grew three assertions — the kernel echoes a line fed after boot (the read lane's proof; OpenSBI's boot takes the UART first, so input written before the payload polls never arrives), the `-d int` trace counts exactly **one** `supervisor_ecall` for the whole boot (the poweroff — `println` made zero), and QEMU exits on its own (the SBI poweroff still ends the machine). Decision record: CHECK.md, 2026-10-26.
- [x] **T3.6** — Traps and the tick: the `stvec` entry shim, `sstatus`/`sepc` save-restore, `sstc` `stimecmp` (SBI `set_timer` fallback) driving the tick; the ISR discipline enforced — no allocation in an ISR body, preallocated ring, ack + enqueue + wake. Landed 2026-10-27: the kernel package owns `trap.S` (the shim, the timer init, the resume stub, the ring) beside its `runtime.S` stub, and its own `link.ld` places the ring at a fixed address in the free RAM above the heap — the kernel's Emo reads it with `peek`/`poke` like any device. The shim lays a 544-byte frame on the interrupted process's own stack, two sections: the top 208 shaped exactly like the scheduler's context frame — which is what makes preemption a context switch (`emo_sched_preempt` points the victim's slot at it, swaps the ra slot for the resume stub, re-queues the victim, and jumps into the scheduler's pick) — and the rest below it, restored through negative offsets once the scheduler's pop has brought sp back to the interrupted value; every general and floating register, `sstatus`, `sepc`, and `scause` round-trips. The timer transport is probed by attempting the capability itself — Sstc is an ISA delegation, not an SBI extension, so nothing can be asked: the first `stimecmp` write either works or traps as an illegal instruction, and the shim answers the probe (state word, `sepc` + 4, sret) — with the legacy SBI `set_timer` ecall (a7 = 0) as the fallback transport, chosen per boot. The dispatch is `scause`'s: the supervisor timer interrupt runs the discipline — ack (re-arm at the 10 ms interval), enqueue (a sequence number into the ring's free slot, store fence, then the producer cursor; drop-counted when full), wake (the quota step: the dispatch loaded the incoming slot's quota into the runtime's slice countdown, the tick consumes it, and a spent slice preempts — unassigned quotas of 0 stay dormant, so every cooperative golden is untouched) — and any other trap is the loud failure. The ISR discipline holds by construction: the shim and everything it calls are assembly over fixed words, no `emo_alloc` is reachable from a trap. The race it all hangs on is closed in the runtime: every scheduler-state mutation (schedule, yield, park, send, spawn, done) opens a masked region — `csrci sstatus, 2` — and unmask on every exit the resumed process flows through, the switch recording the mask in its context frame's spare word so a process preempted or parked mid-region resumes still masked; a timer interrupt therefore never lands inside a scheduler region. Goldens: the kernel's `run.sh` boots twice — `sstc=false` (the fallback visibly driving the tick: one `set_timer` ecall per re-arm) and `sstc=true` (the stimecmp transport: exactly one ecall for the whole boot, the poweroff) — both pinning the tick proof: a 100M-iteration typed sweep whose exact checksum is the register-file pin under dozens of interleaved traps, the tick-count verdicts, the echo, and the self-exit. The dormant quota chain was driven live under gdb against a scratch image: quota 2 injected, the preempt path hit within two ticks, the victim's frame verified in the slot (ra slot = the resume stub, `scause` = 0x8000…005, the spare word carrying the pre-trap SIE, the resume landing at `X + 208` = the interrupted sp), and the preempted sweep finishing with the exact checksum. Decision record: CHECK.md, 2026-10-27.
- [x] **T3.7** — The interrupt-driven console: the input ring drained by a console process; reader processes block on the ring. Landed 2026-10-27: the receive line rides the PLIC — the trap shim's init wires the UART's IRQ 10 into S-mode context 1 (priority 1, enable bit, threshold zero — OpenSBI leaves the context's threshold at 7, masked, and the kernel owns the context now) — and the shim's external-interrupt branch runs the ISR discipline on the console's line: claim through the PLIC, drain the UART's FIFO into the input ring (a preallocated 128-byte channel in its own section at a fixed address the kernel's `link.ld` gives it, single-producer single-consumer with a store fence before the cursor, a full ring leaving the bytes in the FIFO for the line to re-raise), wake the device-waiter, complete the claim. The wake is a new scheduler state: `device_wait` — a raw builtin beside the peek/poke lanes (checker-registered on `riscv64` alone, refused by name everywhere else like the rest of raw memory; the interpreter refuses it by name) — parks the caller in state 4, a state only the device world wakes (`emo_sched_wake_console` flips the first state-4 slot to alive and re-queues it; a send does not wake it — requests queue in its mailbox for the next pass), the resume being exactly the call's return. The console process is ordinary Emo: it sleeps in `device_wait` while the ring is empty, then hands each byte to the oldest unread request; readers block on an ordinary `receive` — the mailbox is the wait queue, no bare-memory rendezvous. The race this hangs on is closed in the runtime: the deadlock detector learned the idle loop — a switch with nobody runnable waits in `wfi` when a state-4 waiter exists (the timer and the devices can land), and is still the loud deadlock otherwise; and the timer dispatch loads each slot's quota into the slice countdown, so a preemption cannot steal an in-flight slice. Two latent bugs surfaced and were fixed on the way: the trap shim had no `.align 2`, so compression could leave `stvec` pointing at a 2-byte-aligned address — the vector mode bits made every trap land in the weeds; and a spawned process's initial context frame never wrote the spare word recording the mask state, so every child was born with interrupts masked and never knew — invisible until a spawned process needed to observe ticks (T3.6's goldens were all root-process). Found, not fixed: `do builtin()` lowers as a spawn whose "closure" is the builtin's return value — the honest form for a statement park is the plain call `device_wait()`, which is what the kernel writes. Goldens: `projects/emo-os/run.sh` boots twice (`sstc=false`, the SBI `set_timer` fallback visibly re-arming; `sstc=true`, the stimecmp transport with exactly one ecall for the boot) — both pinning the tick proof (the exact 100M-sweep checksum, the tick verdict), then five console deliveries in request order (`0:97` … `4:101`), the echo of a line fed only after the reader's request was already pending (the console demonstrably slept in `device_wait` first), and the machine's own exit. All twelve riscv64 QEMU goldens stay byte-identical. Decision record: CHECK.md, 2026-10-27.
- [x] **T3.8** — The dual-run parity harness: kernel-service logic runs under the hosted interpreter against fake devices and under QEMU against real ones; outputs asserted byte-identical; the QEMU smoke wired into `dune test`/CI. Landed 2026-10-27: the corpus is the console service in `examples/parity_fake` and `examples/parity_metal` — one service block (an interface over ready/read/send, the line-assembly and echo logic) held byte-identical between the two files by cut markers, with the harness asserting the prefix; the fake device is arrays and boxes on the interpreter, the metal device is the 16550A's LSR/RBR polled through raw reads and a raw output ring — the hot receive loop lives in fully typed top-level defs so the poll allocates nothing. The hosted leg rides the interpreter examples' auto-discovery (its expected.txt is the contract); the metal leg is a feed-driven boot in the new `test/emo_os` suite — the harness waits for the greeting on the serial log, feeds the same twelve bytes through a named pipe, transforms the payload after OpenSBI's banner, and asserts byte-identity with the same expected file. The suite also wires the kernel's `run.sh` smoke into `dune test`: it builds the kernel into a scratch copy of the project tree and runs `./run.sh`, whose own assertions (both timer transports, the tick proof, the five console deliveries, the echo, the self-exit) decide the test. Found and fixed on the way: **the interface dispatch table on `riscv64` carried one entry per class — the interface's first method only — so every method call through an interface jumped to the first method's address** (single-method interfaces, which every golden used, worked by accident; a two-method interface sent `send` to `read`, which spun on the emptied FIFO and burned the heap through the caller's per-iteration boxing). The table now carries one slot per interface method in the interface's own order, and the dispatch multiplies the class id by the row width and reads the method's slot; single-method interfaces emit the same jump shape they always did. Found, not fixed: `do builtin()` lowers as a spawn (T3.7's note), and the riscv64 target refuses array-element assignment (E2015) — the corpus writes its shared service without either. Verified: `dune runtest` green with the new suite in it, all twelve riscv64 QEMU goldens byte-identical through the dispatch fix, and the parity legs byte-identical to each other. Decision record: CHECK.md, 2026-10-27.

## Step 4 — User mode (M3)

- [x] **T4.1** — The user ELF profile: a second riscv64 image shape (U-mode entry, own stack, no runtime CSRs); the kernel loads it and enters via `sret`. Landed 2026-10-27: the shape is the compiler's, selected by `emo build --profile user` beside the default `kernel` profile — `--profile user` on any other target refuses, an unknown name refuses by name, and a package's own `runtime.S`/`link.ld` still ride in above either profile (T3.1 unchanged). The user image boots with the compiler's U-mode stub (no hart check — a0 is the kernel's; .bss clear, own stack, `emo_runtime_init`, `emo_program`, then the shutdown ecall, which lands in the kernel), links at 0x87100000 — the pre-SV39 user window's base, a page above the kernel's fixed rings, under the top of the board's 128 MiB (SV39 replaces the fixed window with address spaces) — and sizes .bss as a guest: one 64 KiB stack (the per-process stack size) over an 8 MiB heap, the process world unchanged; the kernel profile emits byte-for-byte what it did. The kernel carries the user image (`user.S` embeds the built ELF via `.incbin`, the assembler's include search resolving the path, so the build runs from anywhere) and loads it in Emo (`user.emo`): the boot stub parks the blob's bounds in a new handoff page (`.emo_user` at 0x87002000, the link.ld's third fixed section) and zeroes the entry word; the loader — fully typed defs, so the copy loop is one volatile byte load and store per step, zero allocation — parses the ELF64 header (magic, class, machine, sane program-header table), copies each `PT_LOAD` into the window and zeroes its tail (the user image's .bss — stack and heap included), bounds every segment to the window, and parks the entry; every refusal is loud and stages nothing. Entry is `emo_os_user_boot` (trap.S, beside the resume stub it joins): the entry word zero returns to the stub's poweroff, otherwise `sepc` = the entry and `sstatus` keeps what the kernel left but three bits — SPP cleared (sret enters U-mode), SPIE set (S-mode interrupts return on), FS set Dirty (the floats run). The gate's door exists: the shim answers exactly one U-mode ecall — a7 8, the shutdown request the user stub exits with — by taking the SBI poweroff, and any other verb is the loud failure (`a user ecall the gate does not answer`); the syscall dispatch (T4.2) replaces the single answer with the table. Ticks land during U-mode and round-trip through the same shim (the frame on the user's own stack; the root slot's quota is 0, dormant), and the illegal-instruction probe state is settled to 3 after init so a user program's stray illegal instruction is the loud failure it looks like, never the probe's answer. Found and fixed on the way: **`collect_files` walked through nested packages** — the module walk has always left a directory holding its own `package.emo` out entirely, but the shape walk did not, so the kernel tree's user programs would have leaked their `.S` into the kernel's image (two `runtime.S` candidates, E5013); the walk now applies the same rule. The pins: `run.sh` grew the serial chain — the five console deliveries, then `user: staged <entry>` (0x87100000, the window's base), then the user program's own greeting `U-MODE 500500` (explicit bytes plus a computed sum — U-mode has no console service yet, and riscv64 refuses array-element assignment, so the digits ride a recursion), then the self-exit — under both timer transports; `dune runtest` grew the profile suite (the two refusals, the two load addresses, the user stub and sizing in the emitted text) and the nested-package shape pin; the emo_os harness builds hello (profile user) into the scratch tree before the kernel, exactly as the README recipe does. All twelve riscv64 QEMU goldens byte-identical; `emo_cli` 325 green. Decision record: CHECK.md, 2026-10-27.
- [x] **T4.2** — The syscall gate: ecall dispatch in the kernel; the ABI (numbers, register marshaling, error convention) fixed and documented; supervisor checks on every pointer argument (range and permission). Landed 2026-10-27: the gate is real — [`docs/syscalls.md`](syscalls.md) (with the zh-CN mirror) is the contract, and the kernel side is ordinary typed Emo. **The user side exists first**: `ecall(verb, r0..r5)` joins the raw-machine family (`peek`/`poke`/`device_wait`) — checker-registered on `riscv64` alone, refused by name everywhere else (E4028; the message names the machine's gate rather than raw memory) — lowering in a native body to the inline instruction with no boxing (the seven words evaluate, spill, and load raw; the first cut reused the dynamic-callee argument helper and boxed the args, which the very first boot caught: the gate received cell pointers as its verb and refused everything), and in a dynamic body to a runtime helper that decodes the seven cells, runs the instruction, and boxes the answer. **The ABI is one register**: `a0 >= 0` is the payload (`write` answers the byte count), `a0 < 0` is a refusal whose reason is `-a0` — 1 unknown verb, 2 out of range, 3 no permission, 4 bad argument; a refusal is an answer, not a fault, and the caller's registers round-trip untouched. The verb set: 0 `exit` (never returns — a handler that cannot return has no return path to marshal, so the trap entry takes it before the dispatcher; the T4.1 shutdown verb 8 is retired) and 1 `write(buf, len)`. **The dispatch is the shim's two instructions plus Emo**: verb 0 branches to the SBI poweroff, everything else loads the verb and the six words from the trap frame, calls `gate.dispatch` (module `gate`, fully typed — it runs inside the trap on the caller's own stack and allocates nothing), stores the answer into the frame's `a0` slot, advances the frame's `sepc` past the `ecall` (a synchronous exception — without the +4 the same ecall re-executes forever, the second thing the first boot caught), and srets home. **The checks are the loader's record**: staging now parks a segment table in the handoff page (eight slots of start/end/`p_flags`, one per loaded `PT_LOAD`), and every pointer argument must lie inside one segment — overflow-safe (`len > end - buf`, never `buf + len > end`), all-or-nothing across segments — carrying the permission the access needs; a range some segment covers but no writable one covers is reason 3, a range nothing covers is reason 2. The gate's `write` rides the kernel's own polled console byte by byte — syscall dispatch is core kernel code, called directly (the architecture's own rule); the console service process arrives with T4.4. Goldens: the hello program's serial line grew `gate 500500 r3 r2` — one `write` that answered (this line's own bytes, sent from a buffer the program poked into its own data segment) and two refusals, the text segment (reason 3) and the kernel's memory (reason 2), each printed by the same gate that refused it — under both timer transports, with the stub exiting through verb 0; the `ecall` refusals are pinned at check time beside the rest of the raw family. All twelve riscv64 QEMU goldens byte-identical. Decision record: CHECK.md, 2026-10-27.
- [x] **T4.3** — The syscall stub package: user-side stubs over the raw ecall — its own package, distinct from the hosted `os` package; the typed Emo surface is the only thing user code sees. Landed 2026-10-27 (the package named `emoos` at first, renamed `syscall` the same day — two letters from `os` was a misread waiting to happen): the package is **`syscall`**, in the bundled registry (`stdlib/registry/syscall`), admitting the `riscv64` target alone — its own package in name, admission, and surface. Two stubs: `syscall.exit()` (the exit verb; never returns) and `syscall.write(buf, len)` (the write verb, answering `(R.ok, the byte count)` or `(R.error, why)` — the gate's numeric reasons translated into the error convention's messages: a refusal is a String that names itself, because `(R.error, why)` binds `why` as the String it is, whatever the ok slot carries). The raw `ecall` lives in those two bodies and nowhere else a user program writes; the ABI stays `docs/syscalls.md`, which gained the user-surface section (EN + zh). **The layering gate learned the profile** (EmoOS T3.2's premise moved: with a user profile, riscv64 is no longer the kernel's alone): `compile_inputs` carries the profile, and on riscv64 the kernel profile keeps the strict rule — a bundled require refuses E5014, `syscall` included, because the kernel builds on `core` alone and never requires its own userland — while the user profile is an ordinary program whose packages declare their own targets; a hosted-only require gets past the layering gate and refuses at the solve, by the solve's own answer (`syscall: no build for target`), never E5014's. The demo reaches the gate only through the stubs now: hello requires `syscall` (pinned, lockfile committed), and the `gate 500500 r3 r2` line is the same proof riding `syscall.write` — with the refusal reasons mapped back to the ABI's numbers for the line. Found on the way, working as designed: the lockfile's checksum caught the stub changing under a pinned version — `checksum mismatch for syscall@0.1.0` — and the refresh is the explicit regeneration path (a fresh resolve at first build; `emo deps resolve` itself resolves under the `c` target alone, a limitation for riscv64-only projects noted, not fixed — the first build resolves correctly). All twelve riscv64 QEMU goldens byte-identical; `dune runtest` green with the two new layering pins (the user profile standing the gate down, the kernel profile refusing `syscall`) and the emo_os smoke building hello through the dependency. Decision record: CHECK.md, 2026-10-27.
- [x] **T4.4** — Kernel services as processes: the console service (read/write) and the process service (spawn/exit/wait) answering the gate. Landed 2026-10-27; the close-out — the exit's slot reclamation and this record — 2026-10-28: two ordinary Emo service processes behind the gate — `console_service` (the write verb prints its buffer through the polled driver and answers the count, the read verb answers the next console byte through the device-wait, the boot demo's older bare-pid readers ride the same loop, the kinds separated by the request word's height) and `process_service` (spawn carves a 64 KiB stack above the user image and starts the child at the image's program, refusing −5 when the stacks run out; exit records `(pid, code)` in the exit table and answers a waiting parent; wait answers from the table or parks holding the pending-wait pair — one wait transaction at a time, the stated bound) — each announcing its pid to the root, which parks the raw numbers in the handoff cells the shim posts by. **The routing**: the gate's dispatch answers what needs no service and returns a route (`-(1000 + op)`) for the rest; the shim packs the request word `op << 32 | caller-pid` (the reply's addressee rides the request), posts it (`emo_gate_post` — the service wakes), and the caller parks state 5 (gate-wait, its trap frame IS its context); the service's `gate_reply(target, answer)` lands the word in that exact parked frame's a0 slot and switches it back alive. **The exit is the one route that never answers, and the close-out's reclamation is the death made honest**: the shim's exit route marks the caller's slot done (state 3, the same state a returning entry thunk writes) instead of parking it as a gate-wait no reply would ever relieve — the slot stops claiming a transaction at the ecall itself, a send to the exited pid drops instead of queueing into a mailbox nobody drains, a stray reply to it is the loud service bug instead of a resurrection (the zombie at 5 was resurrectable — a reply flipped it alive past its own exit), and the frame stays on the dead process's own stack for T5's arena reclamation. The exit table holds eight unreaped exits; a ninth is dropped and its eventual waiter walks into the loud blocked deadlock — the stated bound, the full-table rework its own piece if it ever earns one. **Three faults the spawn/wait round trip caught and fixed on the way** (the failure record lived in `docs/temp-spawn-wait-problem.md`, retired at landing, its substance in CHECK.md): the child's jump-to-0 was its slot holding the trap frame's base where the switch-in protocol reads the switch-section base (`emo_user_spawn` stores frame + 336, and the user-exit stub — moved into the compiler's runtime body, the user profile assembles without the kernel package — rides the frame's ra slot so a top-level fall-off exits); the reply path rebuilt targeted (`gate_reply` takes the target beside the answer and refuses loudly on a pid not parked in a 5, the argument cells split per service, the process service holds `pending_waiter` beside `pending_target`); and the shim's answer test `>= -1000` swallowed `route_process_exit`, which *is* −1000 (strict `>` now, the exit a route like its siblings). **The pins**: `run.sh`'s ordered chain grew `born` (the child re-enters the image's top level, finds the token the parent poked, prints through the gate) and `wait 7` (the parent's wait answered by the child's exit) — under both timer transports, with the machine's self-exit; the reclamation itself is scheduler-internal, so it verifies under gdb against the golden's own image — at the exit's recording (a hardware watchpoint on the exit count), the child's slot (pid 8, slot 7) reads state 3 with the root still gate-waiting beside it (state 5, the answer in flight) and the services in their own states: a finished process holding no transaction. Found and fixed on the way: `Pid == Pid` on metal was hardcoded false — `emo_eq_deep`'s kind-18 arm now compares payloads, the language-level bug the demo's pid work surfaced. Decision record: CHECK.md, 2026-10-28.
- [x] **T4.5** — The weak-isolation window, documented: what U-mode can and cannot reach pre-SV39, in the README and the kernel's docs. Landed 2026-10-27: [`docs/isolation.md`](isolation.md) (with the zh-CN mirror) is the window's standing record — the route and why it is priced this way, the flat map (the firmware behind its PMP lock, the kernel image with the 96 MiB heap and the process world, the three fixed rings, the user window, the MMIO), what U-mode can reach (every load and store untranslated; the raw family admitted by target, not profile — the process service's own words included, the greeting's direct UART poke the golden's own proof; the gate the one sanctioned door, a U-mode ecall never reaching OpenSBI), what it cannot (privileged instructions — today the loud failure ends the machine, T4.6 confines the kill; the firmware's PMP-locked region; the gate's refusals are answers, not faults), the defense inventory meanwhile (instruction privilege, the gate's supervisor checks, the copy semantics, Step 5's per-process accounting; what does not defend — the MMU, PMP for S-mode memory, trap containment until T4.6), and why the window is accepted (bounded in time and in kind; SV39 turns the software checks into hardware ones without changing the contract). The README's isolation-route bullet states the same and links the note (EN + zh); syscalls.md's supervisor-checks paragraph links it where the checks' pre-SV39 form is stated. No code moves — the goldens and `run.sh` already pin the reach the document describes. Decision record: CHECK.md, 2026-10-27.
- [x] **T4.6** — Goldens: a user program prints through the gate; a misbehaving program's loud failure kills only itself. Landed 2026-10-28: both proofs ride `run.sh`'s ordered serial chain under both timer transports. **The print**: the `gate 500500 r3 r2`, `echo 88`, `born`, and `wait 7` lines are all the gate's — `syscall.write` through the console service (T4.2–T4.4), already pinned; the task's new half is the kill. **The kill**: the shim's exception dispatch now splits on the saved `sstatus.SPP` — a trap from the kernel's own code stays the loud machine-wide failure (that is the kernel's bug), a fault from U-mode is the offender's alone: the shim calls the kernel's typed `fault_report(pid, scause, sepc)` on the offender's own stack (the gate's precedent — typed Emo inside the trap, zero allocation, the polled console) and prints `user fault <pid> cause <scause> at <epc>`, marks the slot done (state 3, the exit route's reclamation), abandons the frame, and picks the next process; the root's death ends the machine as its exit does. The misbehaving program is hello's second spawned pass: a `doomed` token claimed on entry (the good child re-enters the same top level and must not follow), its line through the gate, then one load at `0x80000000` — the firmware's PMP-locked region, the one range the hardware refuses to a lower privilege, probed first (a misaligned `peek64` does not trap under QEMU; the firmware region does, cause 5) — and the parent does not wait on it (a killed process never exited; its wait would block forever, the stated bound). The chain pins the survival: `doomed`, `user fault 8 cause 5` (the epc moves per build and is not asserted), then `born` and `wait 7` — the good child's spawn/wait round trip completing after the kill. **Two latent faults the kill surfaced, both fixed**: ① `emo_gate_reply` opened a 16-byte frame and stored its second argument at `16(sp)` — eight bytes past the frame, into the caller's own spill slot (the reply's answer silently overwrote a live local of the service that replied; the frame is 24 bytes now); ② **the switch-in unmask window**: a trap frame's switch section carried the pre-trap SIE in its spare word, so `emo_sched_pick` re-enabled interrupts two instructions before the resume stub read the frame's rest section — an interrupt landing there laid its own 544-byte frame over the rest section (`sstatus`, `sepc`, `ra`) of the process being switched in, and the resume then `sret`ted into garbage. The kill made the window hit deterministically often: `fault_report` prints for ~4 ms with SIE masked, so a timer is pending at the kill's pick, and the very next unmask takes it. The trap frame's spare word is now 0 — a trap frame switches in masked and its `sret` restores SIE from the saved SPIE, the one place that restore belongs — in both the shim and `emo_user_spawn`'s synthetic frame; the baseline (T4.4's demo, one spawn, no fault) never widened the window enough to show it. The flake was 1-in-3 before the fix, 12-for-12 after, with a 10-round no-fault control (two spawns, the doomed pass exiting normally) at 10-for-10 isolating the kill as the trigger. **Also fixed on the way**: `run.sh`'s `-d int` trace shared the serial's stream and split lines non-atomically — the trace is on its own stream now (`$log.trace`), the serial assertions read the pure serial, and the ecall count reads the trace. `dune runtest` green with all twelve riscv64 QEMU goldens byte-identical through the runtime fixes; `@fmt` green. **Step 4 complete — M3.** Decision record: CHECK.md, 2026-10-28.

## Step 5 — Process memory (M4)

- [x] **T5.1** — Per-process arenas: a bump heap per process with the quota enforced at `emo_alloc`; exhaustion is loud and confined. Landed 2026-10-28: the slot table grew the arena pair — the cursor at 576, the end at 584, the stride 592 — and `emo_alloc` charges the current slot's pair instead of the one global cursor; the root's arena is the whole image heap (set by `emo_runtime_init`), and every spawned process's arena is a 64 KiB carve from the root's top, its end closing above the carve, so the root can never reach into a child's arena and a child's exhaustion is its own (the first cut carved at the cursor's edge and dropped the root's end onto its own cursor — the root could never allocate again; the top-carve is the fix). Spawn-time arena exhaustion is the machine's loud end (`no arena left for a new process`), the process table's ceiling in memory; no pool section, no link.ld change. **Exhaustion is the profile's**: a kernel image's spawned process dies alone — `heap gone in process N` on the console (a decimal printer the runtime grew), the slot done, `emo_sched_pick` carrying on, the fault route's reclamation reached from the allocator (masked, the dead frame abandoned, the arena unclaimed until T5.2) — the root's exhaustion stays the machine-wide failure; the user image's allocator instead says the gate's **verb 5**, and the shim's −104 route reports `user heap <pid> gone` through the kernel's typed `heap_report` and ends the caller done — the root riding verb 5 ends the machine, as its exit does. **The cross-image handoff** makes the user side honest: the user image's runtime is its own instance, so its stub parks the addresses of its root slot's arena words in its cell page (0x87fff008/0x87fff010, beside `emo_program`), and the kernel's trap shim saves the cells' cursor into the leaver's slot at every trap with SPP = 0 and restores the passer's cursor and end at every resume into U-mode — the user image's `emo_alloc` (reading its own slot table, like any image) always charges the pass the kernel is running. The boot pass is the kernel's own root still, and its progress rides a dedicated boot pair in the kernel's `.bss` instead of the root slot — whose words the spawn carve reads as the kernel heap's (the first cut poisoned the root slot with a user-heap cursor and the second user spawn refused loudly; the boot pair is the fix). The kill's registers follow the ABI: the slot pointer on `s0`, the pid on the stack across the print calls. Stated out of scope: a user program mixing its own green threads with gate spawn; reclamation, message charging, and the frame pool are T5.2/T5.3. Goldens: `examples/arena_gone` (a runaway green child burns its own 64 KiB and dies inside it — the report between the root's lines, the root and `<pid 2>` surviving; riscv64 golden, beyond the interpreter), and hello's third spawned pass — the greedy one — whose `run.sh` chain grew `greedy` and `user heap 9 gone` between the fault report and `born`/`wait 7` under both timer transports (five consecutive smoke rounds green on top of the suite's two); the profile suite pins the arena words, both exhaustion tails, and the user-only cells; all twelve prior riscv64 QEMU goldens byte-identical. Decision record: CHECK.md, 2026-10-28.
- [x] **T5.2** — Reclaim on death: exit returns the arena to the frame pool; message copies charged — copy-in to the sender's quota, copy-out to the receiver's heap. Landed 2026-10-28: **the pool** is a freelist of 64 KiB blocks (`emo_arena_pool`, the link in a waiting block's first word) — every spawn, green and user alike, pops a block first and carves from the root's top only when the pool is empty, so a dead process's arena is the next process's; T5.3's frame allocator generalizes it to stacks and page tables. **Reclaim is `emo_arena_reap` at every death** — the entry thunk's return, the kernel profile's arena kill, and the shim's exit route, fault kill, and heap kill — and it reclaims only when the slot is done, its arena still claimed (the new flag at 600; the root's never is), and nothing it sent is still queued (the new count at 592); otherwise the death leaves the arena where it is. **The pin is the count of queued messages**: `emo_send` raises the sender's count at every enqueue and writes the sender's slot into a third mailbox ring (608..; the stride 592 → 864), `emo_mb_remove` shifts all three rings, lowers that sender's count, and reaps it — a sender already done whose last queued message this was gets its arena back at the receive that cleared it, never earlier; a gate request posts a 0 sender (nothing pinned). **Copy-in is the send's snapshot** (the sender's arena, the sender's quota, as T5.1 left it); **copy-out is the receive's `emo_copy_out`**, placed between the pattern test and the bindings (the bindings destructure — a copy at the remove would leave element words pointing into a reclaimable arena), cloning what the snapshot shared — cells, Pids, Strings verbatim, closures with their captures recursed, containers, Boxes by unbox/recurse/rebox — with the Atomic alone staying shared, and a shared Atomic pinning the sender's arena for good (the copy sets a flag the remove reads) rather than dangling under it. **The sender ring, not the word, decides what is a value**: the first cut told gate requests by their height and the kernel trapped at the good child's exit — op 0's request word is the bare pid, and pid 10 reads as a Box pointer; `emo_copy_out_at` reads the ring instead. Found on the way: the clone loop ported from `emo_copy_deep` dropped its second bound store and came one element short (the processes golden's tuple lost its second half — the deadlock after `4` named it). Stated bounds: a receiver dying with messages queued pins its senders' arenas for good (a leak, never a dangle); a receive nested in a guard clobbers the shared-Atomic flag (unsupported). Goldens: `examples/outlives` (a boxed message correct through the copy-out, the sender's arena home at its death; riscv64, beyond the bare interpreter like every process example); all thirteen prior riscv64 QEMU goldens byte-identical; the kernel chain unchanged under both transports, five consecutive smoke rounds green; and the gdb forensics — on `arena_gone` the kill's reap turns `pool nil` into `pool = 0x86300000`, the dead child's block base; on `outlives` the remove's reap returns on a live sender and the pool stays nil; on the kernel the four readers' deaths fill the pool LIFO, doomed and greedy pop readers' blocks, and born pops doomed's own reclaimed block — a killed pass's arena reused by the next spawn. Full `dune runtest` green; `@fmt` green. Decision record: CHECK.md, 2026-10-28.
