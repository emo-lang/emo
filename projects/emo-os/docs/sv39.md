# The kernel's high-half layout

How the kernel lives under Sv39: the two halves of the address space,
the table the kernel builds for itself, the two aliases every byte has,
and the boot that gets from OpenSBI's physical entry to a kernel
running paged. Fixed as of T6.1 (2026-10-29); the per-process tables
(T6.2), the trampoline (T6.3), and the page-fault kill (T6.4) extend
this document rather than replace it.

Chinese translation: [`sv39.zh-CN.md`](sv39.zh-CN.md).

## The two halves

Sv39 translates 39-bit virtual addresses — 512 GiB — and requires the
upper 25 bits of a 64-bit address to copy bit 38, so the space is two
halves with a hole between them: the lower half, `0` to
`0x3fffffffff`, and the upper half, `0xffffffc000000000` to the top.
The lower half is the user's; the upper half is the kernel's.

Every kernel address is its physical address plus `koff`, the base of
the upper half — `0xffffffc000000000`, which as an `Int64` is −2³⁸ —
so the kernel image, the free RAM, the fixed pages, and the devices
all sit at one fixed offset from where they physically are, and a
pointer's sign says whose it is: a kernel address is negative, a user
address positive. The kernel image links at the high alias of the
load address OpenSBI enters (`0xffffffc080200000`); `link.ld` keeps
every section's load address physical, so QEMU and the firmware see
the image where they always did.

Why the high half rather than the identity map the window ran on: the
user gets the whole lower half — one fixed load address for every
user ELF, no kernel range to avoid (T6.2); the kernel's mappings can
be shared into any address space without colliding with a user's; and
the sign bit is a test no comparison against a table can beat.

## The kernel's table

Built once at boot by `sv39.emo`, over frames the allocator hands out,
and never changed afterwards in T6.1. What it maps, as QEMU's monitor
reads it back (`info mem`):

| Virtual | Physical | Size | Bits | Contents |
| --- | --- | --- | --- | --- |
| `0xffffffc080200000` | `0x80200000` | text | `r-x` | the kernel's code |
| text end | | rodata | `r--` | the read-only data, the embedded user image included |
| rodata end – `0xffffffc088000000` | | to the RAM's top | `rw-` | data, bss (the 96 MiB heap, the slots, the green stacks), the frame region, the fixed pages, the user window as the kernel sees it |
| `0xffffffc010000000` | `0x10000000` | 4 KiB | `rw-` | the 16550A |
| `0xffffffc00c000000` | `0x0c000000` | 4 MiB | `rw-` | the PLIC |
| `0x0` | `0x0` | 1 GiB | `rw-u` | the window's MMIO (T4.5) — until T6.2 |
| `0x80000000` | `0x80000000` | 1 GiB | `rwxu` | the window's RAM — until T6.2 |

The rules the table follows:

- **Permissions by linker boundary.** `link.ld` aligns the ends of
  `.text` and `.rodata` to a page and exports them; the stub passes
  both to the builder, and text is RX, rodata R, and everything from
  the data onward RW. The kernel executes only in the high half: the
  RAM's low alias has X for the user image's sake, but S-mode never
  fetches from a U page.
- **Granularity by alignment.** A range maps in 2 MiB megapages
  wherever both addresses sit on a megapage boundary with a megapage
  to go, 4 KiB pages elsewhere — so the image's first two megabytes,
  where the permission boundaries fall, cost one small table, and the
  hundred megabytes behind them cost sixty-two entries. The window's
  two entries are gigapages, leaves in the root. The whole table is
  five frames: the root, the level-1 table for the RAM, the level-0
  table for the image's head, the level-1 table for the MMIO, the
  level-0 table for the UART's page — one block split.
- **Every leaf is accessed and dirty.** The kernel keeps no use
  counts, and an implementation that traps on a clear bit must not
  get the chance. No global bit, ASID 0.
- **The firmware is in no kernel mapping.** `0x80000000`–`0x80200000`
  is OpenSBI's; the kernel never touches it, and the SBI calls the
  kernel still makes (the poweroff) are M-mode ecalls, which run
  untranslated. The window's RAM gigapage covers the range for the
  user, and a user load there still meets PMP's refusal — the kill
  golden's cause 5.

## The entry format and the walk

A table is one 4 KiB frame of 512 eight-byte entries. An entry is
`PPN << 10 | flags`: the physical page number of the next table or of
the page, and the bits V (valid), R, W, X, U (the user may reach it),
G, A (accessed), D (dirty). An entry with any of R, W, X set is a
leaf, at whichever level it sits — a 4 KiB page at level 0, a 2 MiB
megapage at level 1, a 1 GiB gigapage at level 2; an entry with none
is a pointer to the next table. The walk takes nine bits of the
virtual address per level, bits 38–30 for the root, 29–21 for the
middle, 20–12 for the last, three levels down from the root in
`satp`.

`sv39.emo` is the untyped-memory discipline the README decides —
`Int64` addresses, `peek`/`poke`, bit masks, no value of the language
pointing into a table — and every def is a fully typed native body.
Its rules are strict: a leaf met on the way down is a kernel bug (a
larger page already covers the address), an address mapped twice is a
kernel bug, a leaf or a range off its page boundary is a kernel bug —
each the loud end (`sv39: …` on the console, then the SBI poweroff),
never a silent overwrite. `lookup` is the software walk, what the
hardware does on a TLB miss, and the builder walks its own table for
the addresses the next instructions depend on before it answers the
root — a wrong table dies with a line, not with a fault at the `satp`
write.

## The two aliases, and who uses which

Every byte of the machine has two addresses: the kernel's, in the high
half, and the physical one.

- **The kernel's address is the currency.** Everything the kernel's
  own loads, stores, and fetches reach — the image, the allocator's
  blocks and frames (`frames.emo`'s region bounds, links, and answers
  are all kernel addresses), the rings and the fixed pages, the
  devices — is named by its kernel address, in the Emo (`koff` plus
  the physical constant) and in the shim's assembly (`EMO_KOFF` plus
  the physical constant).
- **The physical address appears in exactly three places**: in a leaf
  entry (`sv39.emo` writes `pa_of(kernel address)`), in `satp` (the
  shim takes the root's physical address), and — until T6.2 — as the
  user's address of its own memory, since the window is now the
  identity alias: the user image runs at `0x87100000` as before, a
  user pass's stack and arena blocks are reached by the pass at their
  physical addresses, and the user's cells at `0x87fff000` are the
  user's.
- **The kernel reaches user memory by the user's addresses, with
  SUM.** The gate's buffer reads, the loader's copies into the window,
  the trap frames the shim lays on a user stack, the synthetic frame a
  spawn builds — all S-mode accesses to pages carrying the U bit,
  which `sstatus.SUM` permits. The stub sets SUM once the kernel's
  table is live, and the resume stub sets it again on every return
  into any mode: SUM is the kernel's property, not the frame's — a
  spawn's synthetic frame carries a bare `sstatus`, and a return that
  trusted it would drop SUM and fault at the next trap's first store.
- **Two translation points, both explicit.** The arena handoff at the
  user's cells (`trap.S`): the slot's cursor and end words are kernel
  addresses, the cells take the user's, so the offset comes off on the
  way into U-mode and goes back on at the trap out. And the reaper's
  stack give (`frames.give`): the runtime names a dead pass's stack by
  the address the pass ran on — physical — and the allocator
  translates a physical base to the kernel's before judging it with
  the same strict checks as any other. T6.2 ends the alias and both
  points with it.

## Boot

1. OpenSBI enters at `0x80200000`, physical, `satp` off. The stub runs
   at the physical alias — `la` is PC-relative, so every symbol
   answers its physical address — clears `.bss`, and writes the boot
   table into one zeroed page: `root[2]`, RAM at identity (`rwx`), so
   the instructions after the `satp` write keep fetching; `root[258]`,
   RAM at the high alias; `root[256]`, the first gigabyte of MMIO at
   the high alias. Then `satp` (mode 8, the root's PPN), `sfence.vma`,
   and a jump to the high alias of the next instruction.
2. From there everything is the high half, on the boot table: the
   stack by its kernel address, the hooks (console, blocks, resume),
   the trap init, the runtime init, the frame allocator's boot.
3. `sv39.boot` builds the kernel's table — `frame_take` splits a block
   into sixteen frames, the ranges above map, the builder walks its
   own table for the image, the data, the root, its page, the UART,
   the window — and answers the root's physical address. The shim
   `emo_os_satp_switch` fences, writes `satp`, fences, and answers the
   value written; the stub keeps it on the Sv39 page beside the root
   the builder recorded, and sets SUM.
4. The program's second line is its own check: `sv39_report` reads the
   live `satp` back, requires mode 8 and the root the builder
   recorded, and prints `sv39 8 0x<root>` — or ends the machine with
   `sv39: the live table is not the kernel's`. `run.sh` pins the line
   first in its chain.

Why a boot table at all: the Emo that builds the real table is itself
linked high and reads the allocator's page through a kernel address —
not one instruction of it could run untranslated — so three stores in
the stub make the high half exist before the first Emo instruction,
and the Emo-built table then replaces the gigapage sketch with the
permissions the kernel means.

## The shims

`sv39.S` holds the two privileged instructions no Emo spelling
reaches: `emo_os_satp_switch` (a root's physical address in `a0`;
`sfence.vma`, the `satp` write, `sfence.vma`; the written value
answered) and `emo_os_sfence` (the whole TLB). The division of labor
is the gate's: Emo builds and reads the tables, the shim writes the
CSR. The stub is the only caller in T6.1; the context switch (T6.2)
and the trampoline (T6.3) are the next.

## What this does not yet do

The window's reach is unchanged. The two gigapages give U-mode exactly
what it had — every physical address of the RAM and the first gigabyte
of the MMIO — so the account in [`isolation.md`](isolation.md) stands:
a wild user store into kernel memory still lands, through the low
alias, even though the kernel's own mappings carry no U bit. What T6.1
changes is where the kernel stands, not what the user can touch: the
kernel runs paged, in the high half, on a table of its own making, and
every later step is a change to that table. The per-process tables
(T6.2) replace the two gigapages with each process's own lower half;
the trampoline (T6.3) carries the trap across the `satp` swap; the
page fault (T6.4) becomes the kill; the isolation goldens (T6.5) pin
what the window no longer allows.

## The pins

- `run.sh`: `sv39 8 0x8…` is the chain's first line under both timer
  transports; the rest of the chain is byte-identical to the pre-T6.1
  chain except its last line, `frames 13 10` — the page tables' block
  taken beside the twelve, kept for the whole run like the services'
  arenas.
- The kernel could not run at all without translation — its every
  address is a high-half one — so the chain's existence is the proof
  that `satp` is on; the `sv39` line is the proof that the table
  running is the Emo-built one and not the stub's.
- QEMU's monitor, `info mem` after the boot: the eight mappings in the
  table above, with those attribute bits; `info registers`: `satp
  0x800000000008676f` on the recorded image (mode 8, the root the
  serial line printed), `stvec` in the high half, SUM set in
  `sstatus`.
- Three consecutive smoke rounds, the serial payload byte-identical.
