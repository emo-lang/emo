# 弱隔离窗口

SV39 关上窗口之前,U-mode 能与不能够及什么。窗口随 user profile(T4.1)开启,随 SV39(M5)关闭;在它存在期间,用户程序与内核共享一张平坦的物理地址空间,指令特权是硬件在两者之间画的唯一一条线。T4.5(2026-10-27)定案:本文档是窗口的常设记录,够及范围是有账可查的事实,不是口口相传的传说。

英文版:[`isolation.md`](isolation.md)。

## 路线

特权先行,地址空间后置——既定的隔离路线。用户程序在分页存在之前一个里程碑就以 U-mode 站到 ecall 门后面,因为门与门背后的东西——supervisor 的参数检查、拷贝语义、每进程记账——才是永久契约,SV39 随后把它们的强制执行搬进硬件,契约本身一字不动。窗口就是代价:M3 到 M5 之间,隔离是有效的,却不是被强制的,两者的差别写在本文档里,绝不遮掩。

## 内存图

一张平坦的图,每个地址都是物理地址。QEMU `virt` 的 128 MiB RAM 里有什么,以及旁边的 MMIO:

| 范围 | 内容 |
| --- | --- |
| `0x80000000`–`0x80200000` | OpenSBI(M-mode)——唯一被 PMP 锁住的区域 |
| `0x80200000` | 内核镜像——text、rodata、data,以及装着 96 MiB 值堆、64 个进程槽、64 × 64 KiB 进程栈的 `.bss` |
| `0x87000000` | tick 环(`.emo_tick`) |
| `0x87001000` | 输入环(`.emo_in`) |
| `0x87002000` | 用户交接页(`.emo_user`)——内嵌镜像的界址、staged 入口、段表 |
| `0x87100000`–`0x88000000` | 用户窗口——每个用户镜像都链接在其基址 |
| `0x10000000`、`0x0c000000`、… | MMIO——16550A UART、PLIC、`virt` 的其余设备 |

## U-mode 能够及什么

- **每一次访存都不经翻译。** 用户地址与上面这张图之间什么都没有:内核 text 与 data、堆、调度器的槽表、每个进程的栈、两个环、交接页、其他进程的内存、设备,全部在一条野地址的够及范围内。野跳转进内核 text 甚至能执行——而且停在 U-mode,因为特权跟着模式走,不跟着代码走。
- **裸机器族按 target 准入,不分 profile。** `peek`/`poke`、`ecall`、`device_wait` 在用户镜像里是合法拼写,依据正是准入自己的原则——target 准入裸机器族当且仅当程序拥有地址空间,而 SV39 之前,硬件给用户程序的就是这些内建所能够及的一切。拒绝拼写只会遮住够及,不会移除它;进程世界自己的词(`user_spawn`、`gate_reply`、`pid_num`,T4.4 的服务词汇)也在这个族里,出于同样的原因在用户镜像里拼得出来。第一个用户程序的问候就是有意骑在准入上的——它直接 poke 16550A,完全不经过门,`run.sh` 钉住了这一行。
- **门是受认可的门。** U-mode 发出的 `ecall` 永远陷入内核的 shim——永远不会到 OpenSBI——五个动词都骑在它上面。门拒绝的东西以应答的形式拒绝:调用者的寄存器原样往返,执行继续。

## U-mode 不能够及什么

- **特权指令,以及其他一切故障。** 所有 S-mode CSR(`satp`、`sstatus`、`stvec`、`stimecmp`)、`sfence.vma`、`sret`——在 U-mode 里都是非法指令;硬件拒绝的访存(固件的 PMP 锁定区)——访问故障。任何此类来自 U-mode 的 trap 只杀出事者自己:supervisor 在控制台响亮报告(`user fault <pid> cause <scause> at <epc>`),该进程的槽以 done 收尾,机器带着其余进程继续运行。来自内核自身代码的故障仍是终结整台机器的响亮失败——那是内核的 bug,不是用户的。这条 SV39 之前的边界对自己的宽度是诚实的:击杀包容的是 *trap*,不是 trap 之前一条野写已造成的损害——一个先腐蚀了内核内存再故障的用户程序会被干净地杀掉,内核则带着那份腐蚀继续运行,直到 SV39 让那条写入本身成为故障。
- **固件。** U-mode 发出的 `ecall` 是内核的门,不是 OpenSBI 的;固件自己的区域是 PMP 从低特权手里扣下的唯一一段(OpenSBI 启动时锁住它——击杀金测骑的恰是这一点:失控程序对 `0x80000000` 的那次 load 就是 supervisor 报告的那条访问故障),别的任何东西都无法站到 PMP 后面:该 CSR 只有 M-mode 可写,OpenSBI 也没有定义扩充它的标准调用。
- **门拒绝的一切。** 集合之外的动词、调用者段之外的指针、不带这次访问所需权限的段——每一个都是越过门答回来的编号拒绝,不是故障,也不是崩溃。

## 这期间什么在防守什么

- **指令特权**——硬件的唯一一条线,而且它绝对成立:U-mode 无法自我提权。
- **门的 supervisor 检查。** 每个指针参数都被限定在调用者自己的某个段内,带这次访问所需的权限,防溢出,跨段全有或全无(契约见 [`syscalls.md`](syscalls.md))。门从不在调用者内存之外解引用;SV39 之前这是 supervisor 的口头承诺,SV39 让它变成 MMU 的。
- **拷贝语义。** 消息在 send 时快照,记账记发送方:被腐蚀的进程无法通过邮箱给别人的对象起别名。它仍然能按地址够及它们——那就是窗口,拷贝纪律对此毫不装糊涂。
- **Trap 包容。** 用户故障只杀自己的进程;内核自身的故障保持整机级——它就该如此。
- **每进程记账随 Step 5 到来**——arena 与配额;失控进程耗尽的是自己的 arena。
- **不在防守的:** MMU(SV39 之前不存在)、S-mode 内存的 PMP(见上)、以及——击杀诚实的限度——野写在进程 trap 之前已造成的任何损害。

## 为什么接受这个窗口

时间与性质上都有限。时间上:SV39 关闭它,在固定路线图上只隔一个里程碑。性质上:长期要紧的防线已经是软件契约,窗口并不侵蚀它们——一个待在自己段内、经门办事的用户程序,今天实际上就是被隔离的,因为门检查每一样跨过的东西,拷贝让进程无法互相起别名。窗口留下不强制的东西恰恰是野地址够及这一类,而 SV39 正是消除这一类错误的构造。够及范围已有记录在案;没有任何东西假装不是这样。
